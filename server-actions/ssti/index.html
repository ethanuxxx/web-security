本節模型：shop.example.com 的帳號設定頁，暱稱會顯示在歡迎訊息裡

你在 shop.example.com 的帳號設定頁把暱稱改成 Demo，按下儲存。瀏覽器送出一個 POST 請求，本體是 nickname=Demo。網站的應用程式拿著一份寫好的歡迎訊息模板，把暱稱填進去，回傳的頁面頂端寫著「歡迎回來，Demo」。

上一節的 XXE 讓 XML parser 讀到宣告就照做。網站把資料填進頁面用的模板引擎也有自己的語法，使用者的輸入若進了它讀的那份文字，同樣會被照做。

7.3.1 模板引擎在做什麼

網站的頁面大部分內容固定，只有幾處隨使用者或資料而變：歡迎訊息裡的暱稱、購物車的商品清單、訂單通知信裡的金額。逐頁用字串拼接 HTML 很容易出錯，所以多數 Web 框架把固定的部分寫成模板（template），變動的部分留成空格，由模板引擎（template engine）在每次請求時把資料填進去。

輸入是兩樣東西：模板原始碼（template source，一段含空格標記的文字）和資料（一組名稱與值）。輸出是填好的頁面。下面是 Jinja（Python 生態常用的模板引擎）的語法：

<h1>歡迎回來，{{ nickname }}</h1>
{% for item in cart %}
  <li>{{ item.name }}</li>
{% endfor %}

{{ … }} 叫運算式（expression）：引擎算出裡面的值，放到這個位置。{% … %} 是敘述（statement），負責迴圈和條件判斷。大括號以外的文字原樣輸出。每套引擎的標記不同：Jinja、Twig、Tornado、ERB、Freemarker 各有各的寫法，但分工一致，標記內都能取值、做運算、呼叫函式。有的引擎自己設計了一套小型語言（如 Jinja、Freemarker），有的直接嵌入宿主語言（如 ERB 嵌入 Ruby、Tornado 嵌入 Python）。

所以模板引擎是一種直譯器（interpreter）：它讀文字，照其中的語法做事。這與第 2 章的 SQL 和 shell 是同一類元件，每一類都有一段「該當成語法」和「該當成資料」的界線。

7.3.2 暱稱放在資料，還是放進模板

下面的程式用 Flask（Python 的一套 Web 框架）寫成，render_template_string 的作用是把一段模板字串和資料交給引擎，回傳填好的頁面。歡迎訊息功能有兩種寫法。第一種，模板是程式裡寫死的字串，暱稱以資料傳入：

# 較安全的做法：模板固定，暱稱當資料傳入
from flask import render_template_string

def greeting(nickname):
    return render_template_string(
        "<h1>歡迎回來，{{ nickname }}</h1>", nickname=nickname)

第二種，開發者覺得「把暱稱接進句子裡」最直接，於是在呼叫引擎之前，先把暱稱拼進模板原始碼：

# 不安全的做法：把暱稱接進模板原始碼
def greeting(nickname):
    return render_template_string("<h1>歡迎回來，" + nickname + "</h1>")

兩種寫法在暱稱是 Demo 時產生一模一樣的頁面，測試不會發現差別。差別在引擎讀到的東西：第一種的原始碼從頭到尾由開發者決定，暱稱只出現在「資料」那一側，引擎把它當成要輸出的文字，裡面長什麼樣子都一樣。第二種的原始碼有一段來自使用者，引擎讀它的方式和讀開發者寫的部分完全相同。

這就是 Server-Side Template Injection（SSTI，伺服器端模板注入）：使用者的輸入成了模板原始碼的一部分，由伺服器上的模板引擎解讀。SQL Injection 的輸入進入查詢文字，Command Injection 的輸入進入 shell 命令列，SSTI 的輸入進入模板原始碼，三者的結構相同。

7.3.3 從暱稱到伺服器端求值

假設 shop.example.com 的歡迎訊息用上面第二種寫法，引擎是 Jinja。先記下正常請求與回應：

Request
POST /account/nickname HTTP/1.1Host: shop.example.comContent-Type: application/x-www-form-urlencodednickname=Demo
Response
HTTP/1.1 200 OKContent-Type: text/html<h1>歡迎回來，Demo</h1>

接著把 nickname 換成 [模板運算式]。方括號代表被換掉的那段輸入：它是用該引擎的運算式標記包起來的一個簡單運算，結果可以預先算出來；其餘欄位與正常請求相同。

Request
POST /account/nickname HTTP/1.1Host: shop.example.comContent-Type: application/x-www-form-urlencodednickname=[模板運算式]
Response
HTTP/1.1 200 OKContent-Type: text/html<h1>歡迎回來，[運算結果]</h1>
  1. 你的瀏覽器送出請求。
  2. 暱稱欄位的值含有模板語法。
  3. 應用程式把暱稱接進原始碼，交給引擎的字串變成「<h1>歡迎回來，、模板運算式、</h1>」三段相連。
  4. 引擎從頭解讀這段文字：<h1> 原樣輸出，運算式交給運算，算出一個數值。
  5. 回應是已經填好的頁面，原本的運算式不在裡面，出現的是它的結果，也就是上方第二組框的 Response 窗格。

瀏覽器收到的只是一般的 HTML 文字，沒有任何語法等著它去執行，運算早在伺服器上完成。把 nickname 換成別的簡單運算，結果跟著變，就能確認這個值確實被算出來，而不是原樣照抄。若把 nickname 換成 [不完整的模板語法]，會看到 500 或帶引擎名稱的錯誤頁，表示引擎在解讀時遇到語法錯誤，錯誤訊息常透露引擎種類與出錯位置。

輸入落在文字裡，或落在運算式裡

輸入進入模板的位置有兩種。上面的例子是文字脈絡（plaintext context）：輸入落在大括號以外的普通文字裡，直接寫上運算式標記就會被解讀。

另一種是程式碼脈絡（code context）：輸入被放進一個本來就存在的運算式裡。假設設定頁提供「顯示名稱格式」，讓使用者選要顯示的欄位，程式把選項接成 {{ user.[使用者選的欄位] }}。輸入已經在運算式裡面，多數引擎的運算式裡不能再開一層標記，常得到語法錯誤；要先結束原本的運算式，才能接上自己的內容。判讀的難度在這裡：同一個功能在文字脈絡下直接有反應，在程式碼脈絡下卻只看到錯誤，容易誤判成沒有問題。

7.3.4 和 XSS 的差別

XSS 也是輸入被當成語法。兩者的差別是誰來解讀：

表 7.3.4-1
項目XSSSSTI
解讀發生的時間回應送達之後回應產生之前
程式以誰的身分執行目標網站的 origin，受瀏覽器同源政策限制網站程序，擁有伺服器上的檔案與網路權限
誰受影響載入那個頁面的使用者伺服器本身

輸出跳脫（output escaping）把 < 之類的符號換成實體，處理的是引擎已經產生的輸出，用來防輸出面的 XSS。SSTI 的語法在輸出之前就被求值，所以不能用它防 SSTI。

辨認時要靠原始回應。前端框架也有模板語法，伺服器若把使用者輸入原樣放進頁面，瀏覽器端的模板引擎可能在 DOM 裡把它算出來（Client-Side Template Injection，CSTI，是瀏覽器端解讀輸入的一種）。畫面上看到運算結果，不足以分辨是哪一邊算的；原始回應裡該位置已是結果，才是伺服器端求值的證據。

7.3.5 影響可以到哪裡

模板引擎執行時，手上有兩樣東西：它自己的語法，以及應用程式交給它的資料物件。能做到什麼，取決於這兩者。

  • 只有運算：多數引擎的運算式至少能做算術與字串處理，這已足以證明輸入被求值。
  • 讀取資料：模板能讀到的變數都是目標。以 Flask 為例，它預設把應用程式的 config、request、session 放進模板的變數；config 裡常放資料庫密碼和簽章金鑰。
  • 走到語言的執行環境：許多引擎執行在通用程式語言之上，模板語法能從手上的物件出發，取到比開發者原本打算開放的更多東西，嚴重時連語言的內建函式與模組都在內。這條路若沒有被封住，檔案讀寫與系統命令就在範圍內，也就是伺服器端的程式碼執行（remote code execution，RCE）。通用的語法與可用物件隨引擎而異，要查該引擎的官方文件才知道。
  • 沙箱或「無邏輯」引擎：引擎限制了可呼叫的東西時，路徑可能被截斷，只剩讀資料或什麼都做不了。

RCE 出現時，程式以網站程序的身分在伺服器上執行；SSRF 的內部請求與 XXE 的讀檔，這時用程式碼就能做到。

7.3.6 什麼情況下成立

  • 輸入被併進模板原始碼：字串拼接、格式化字串，或把使用者提供的整份模板交給引擎。輸入以資料傳進去時，沒有這個問題。
  • 使用者決定的是文字脈絡或程式碼脈絡中的某一段，兩者進入的方式不同，判讀也不同（見前面「輸入落在文字裡，或落在運算式裡」）。
  • 輸入進模板和求值可能在不同請求。暱稱在設定頁存下，之後每次渲染歡迎訊息才被求值；觸發的請求與送出的請求要分開記錄。
  • 結果是否出現在回應，取決於應用程式把渲染結果放到哪裡。結果沒有回傳時，求值仍然發生，只是看不到，稱為盲目（blind）SSTI；判斷方式和盲目 XXE 相同：看回應差異與耗時，或用帶外連線觀察。
  • 有些功能本來就開放使用者編輯模板，例如電子報、通知信或自訂頁面。這類功能的輸入就是模板，沒有被「誤拼」的過程；風險取決於誰能編輯，以及引擎有沒有限制。

7.3.7 辨認與判斷引擎

先找哪些功能會把使用者的值放進頁面或通知：暱稱、留言署名、訂單通知信的收件人名稱、自訂主題、匯出報表的標題。這些位置若是由模板產生，就是候選。

  1. 記下正常的請求與回應，包括值出現在哪些頁面、哪個時間點才出現。
  2. 把值換成 [模板運算式]：一個語法合法、結果可預先算出的簡單運算，用候選引擎的運算式標記包起來。值若被當資料，輸出會原樣顯示；被求值，輸出是結果。
  3. 換一個運算再試一次。結果跟著輸入變，才是求值；結果固定不變，可能是頁面其他部分的數字。
  4. 改看原始 HTTP 回應，排除瀏覽器端的求值（見「和 XSS 的差別」）。
  5. 把值換成 [不完整的模板語法]，引擎常回傳帶有引擎名稱、版本與出錯模板片段的錯誤。這份資訊本身就可以鎖定引擎。

第二步看到字面文字，不代表安全：標記是否對得上引擎、輸入是否落在程式碼脈絡，都會讓同一個漏洞對這一次嘗試沒有反應。鎖定引擎的做法是比較：不同引擎對同一個構造的處理不同，有的算出結果，有的報錯，有的原樣輸出，把幾個構造的反應湊在一起就能縮小範圍。確定引擎之後，讀它的官方文件，查它預設提供哪些物件與函式、官方對安全的說明。

7.3.8 防禦手法

有效的防禦

不要用使用者輸入組模板原始碼

模板寫在檔案或固定字串裡，使用者的值用引擎提供的參數機制傳入。前面 A 排的寫法就是這個做法。模板檔放在伺服器上，只有部署流程能改。

程式碼審查時搜尋直接吃字串的入口：Flask 的 render_template_string、Jinja 的 Environment.from_string（直接建立 Template 物件時，autoescape 預設是關的），其他引擎也有等價的函式；看傳進去的字串是否含有請求裡來的值：用 + 拼接，或用 f-string（Python 把變數直接寫進字串的語法）、格式化字串，都算。

必須讓使用者寫模板時，縮小它能做的事

  • 限制誰能編輯。能改模板的帳號等於能在伺服器上寫程式，編輯權限比照管理員權限看待，帳號保護與稽核跟著提高。
  • 用沙箱環境渲染。Jinja 提供 SandboxedEnvironment，遇到不安全的存取就丟 SecurityError；官方文件也說明，沙箱本身不是完美安全的解答，還要處理渲染中的其他例外，並限制 CPU 與記憶體，因為模板可以產生極大的輸出。
  • 只傳最少的資料，而且是簡單型別（字串、數字、字典），避免傳入帶有副作用方法的物件。Jinja 文件同樣建議避免傳全域資料。
  • 改用「無邏輯」（logic-less）引擎，例如 Mustache：沒有運算式、迴圈與條件，模板只能取值與重複區塊，語言執行環境更難被取到。資料裡的可呼叫值在有些實作會被區塊呼叫，所以仍要只傳簡單型別；資料物件上的內容仍然讀得到，函式庫的實作與版本也要持續追蹤。
  • 渲染使用者模板的程式放在低權限的程序或容器裡，檔案系統唯讀、網路出站受限，萬一被突破，範圍停在那個容器。

縮小萬一失守的損害

  • 網站程序以最小權限執行，設定檔裡的密鑰按環境分開、能輪替。
  • 一般使用者看到的錯誤頁不含引擎名稱、版本與模板片段，細節只寫進伺服器端日誌。這降低被辨認的速度，屬於縱深防禦，修補仍在模板的組法。
  • 更新模板引擎與框架。

無效的防禦

表 7.3.8-1
做法為什麼不夠
把輸出的 HTML 跳脫（autoescape）跳脫處理的是引擎產生的輸出。求值發生在輸出之前，原始碼裡的語法已經被算過；Flask 的 render_template_string 預設對輸出啟用 autoescape，拼接寫法仍然成立。
黑名單：過濾大括號、關鍵字或特定函式名稱標記與語法依引擎而異，也可以在引擎設定中改掉；同一件事有多種寫法，過濾名單總有漏掉的。
拼接前自己把引擎的標記字元替換掉要掌握每套引擎、每個版本與每種設定的標記，漏掉任何一種寫法就被求值；直接用資料傳入沒有這些問題。
隱藏錯誤訊息，不讓使用者看到引擎資訊求值仍然發生，只是難以辨認；回應差異、耗時與帶外連線仍可觀察。
只在瀏覽器端驗證暱稱格式使用者可以自己組請求，伺服器收到的才是實際的值。
相信沙箱已經安全而不做其他限制沙箱封住部分語法與屬性，仍可能因引擎版本、傳入的物件或設定而留下路徑；官方文件本身就明說不是完整保證。

7.3.9 小結

  • 模板引擎是直譯器，使用者的輸入進入模板原始碼（而不是以資料傳入）時，就會被當成語法求值；兩種寫法對正常輸入的結果相同，差別只在引擎讀到什麼。
  • 輸入在文字脈絡或程式碼脈絡中被求值，判讀方式不同；原始回應裡出現運算結果才是伺服器端求值的證據，畫面上的結果也可能來自瀏覽器端的模板。
  • XSS 在瀏覽器解讀輸入，SSTI 在伺服器的模板引擎解讀輸入；輸出跳脫處理的是已產生的輸出，不能用來防 SSTI。
  • 影響取決於引擎、交給它的物件、沙箱與程序權限：從只能運算，到讀取設定與密鑰，到伺服器端程式碼執行。
  • 修補是不用輸入組模板，改以資料傳入；必須開放模板編輯時，限制編輯者並使用沙箱。字元黑名單與輸出跳脫不是修補。

PortSwigger Academy 的對應練習（主題頁 Server-side template injection，另有 Exploiting SSTI 說明如何查文件）：

  • Basic server-side template injection：輸入落在文字脈絡時，怎樣確認它被求值。
  • Basic server-side template injection (code context)：輸入落在已有的運算式裡，與文字脈絡的判讀有什麼不同，設定與觸發是兩個請求。
  • Server-side template injection using documentation：引擎未知時，從錯誤訊息鎖定引擎，再查它的官方文件。
  • Server-side template injection in an unknown language with a documented exploit：沒見過的語言與引擎，如何靠辨認加文件往下走。
