本節模型：shop.example.com 的商品庫存查詢功能，請求本體是 XML 文件

你在 shop.example.com 的商品頁按下「查詢庫存」，瀏覽器送出一個 POST 請求，本體是一份 XML 文件，記著商品編號和門市編號。網站的應用程式把這份文件交給 XML parser，取出兩個編號，向庫存服務查詢，再把件數寫進頁面。

上一節的伺服器依網址發出請求，網址放在一個看得見的欄位裡。這一節的請求本體是整份 XML 文件，沒有哪個欄位叫網址。負責載入資源的是 parser：XML 這種格式有一套語法，能讓文件指向別處的內容，parser 若照做，就會去載入使用者文件裡指定的資源。

7.2.1 XML、DTD 與 entity

XML 是用成對標籤描述資料的文字格式。<productId>7</productId> 由開始標籤、內容和結束標籤組成，合稱元素（element）；元素可以巢狀，整份文件只有一個最外層的根元素。XML parser 是讀這段文字、還原成元素結構、再交給應用程式使用的程式庫。

內容裡的 < 和 & 對 parser 有特殊意義，要表達字面的符號，得寫成 &lt; 和 &amp;。這種以 & 開頭、以 ; 結尾的寫法叫 entity 引用（entity reference）：parser 讀到它，就換成它代表的文字。&lt;、&gt;、&amp;、&quot;、&apos; 是 XML 內建的五個。

DTD（Document Type Definition，文件類型定義）寫在文件開頭的 <!DOCTYPE …> 裡，原本用來規定文件可以有哪些元素。DTD 也能宣告新的 entity，也就是讓文件自己決定 &名稱; 代表什麼。下面的文件宣告了一個叫 label 的 entity，值是一段固定文字，再在內容裡引用它：

<!DOCTYPE note [
  <!ENTITY label "demo-text">
]>
<note>&label;</note>

parser 讀到 &label; 時換成 demo-text，應用程式拿到的內容是 demo-text，看不到引用本身。展開在 parser 內部完成，早於應用程式用到任何資料。值寫在宣告裡的 entity 叫內部 entity（internal entity）。

7.2.2 外部 entity 的值來自別處

entity 的值也可以不寫在宣告裡：在名稱後面寫關鍵字 SYSTEM，再接一個 URI（Uniform Resource Identifier，資源的位置；上一節看到的網址是它的一種），指向另一份資源。這種叫外部 entity（external entity）。宣告的形狀如下，URI 的位置以占位符表示：

<!ENTITY 名稱 SYSTEM "[資源的 URI]">

與前面的內部 entity 相比，值的位置從一段固定文字換成 SYSTEM 加 URI。URI 的前綴決定資源的種類：file: 指本機檔案，http: 指網路上的資源，上一節的網址屬於後一類。XML 規格允許 parser 載入外部資源，但不強制：驗證型處理器必須讀取，非驗證型可以選擇。parser 若載入，展開引用時就先取得那個資源，再把內容放到引用的位置。

載入資源的是 parser，而 parser 跑在網站的伺服器上，所以兩件事都以伺服器的身分發生：file: 讀的是伺服器的檔案系統，用網站程序的權限；http: 發出的請求，來源是網站的伺服器，與上一節的第二段連線是同一個位置。

XML External Entity injection（XXE）指使用者送來的 XML 文件，讓伺服器上的 parser 展開了外部 entity，載入開發者沒打算讓使用者指定的資源。出問題的不是 XML 文件本身，而是 parser 照文件的指示行動。文件由使用者決定。

Path Traversal 也是讀到不該讀的檔案，路徑由使用者的輸入決定，開檔的是應用程式自己的程式碼。XXE 的路徑寫在使用者的 XML 文件裡，開檔的是 parser，應用程式的程式碼可以完全沒有檔案操作。兩者共通的是：能讀到什麼，取決於網站程序的檔案權限。

7.2.3 從庫存查詢到錯誤訊息

沿用庫存查詢的例子。假設應用程式使用的 parser 允許外部 entity，並且在商品編號不合法時，把收到的值放進錯誤訊息。

正常的請求

Request
POST /product/stock HTTP/1.1Host: shop.example.comContent-Type: application/xml<?xml version="1.0" encoding="UTF-8"?><stockCheck>  <productId>7</productId>  <storeId>1</storeId></stockCheck>
Response
HTTP/1.1 200 OKContent-Type: text/plain18
  • parser 解析本體：根元素是 stockCheck，底下有 productId 和 storeId 兩個元素。
  • 應用程式取出 productId 是 7、storeId 是 1，向庫存服務查詢。
  • 庫存服務回傳 18，應用程式把它放進回應，頁面顯示「庫存：18 件」。

把 productId 的內容換成沒有對應商品的普通文字，例如 abc，應用程式找不到商品，回 400，並把收到的值寫進錯誤訊息：

Request
POST /product/stock HTTP/1.1Host: shop.example.comContent-Type: application/xml<?xml version="1.0" encoding="UTF-8"?><stockCheck>  <productId>abc</productId>  <storeId>1</storeId></stockCheck>
Response
HTTP/1.1 400 Bad RequestContent-Type: text/plainInvalid product ID: abc

這個錯誤訊息是 productId 的值回到瀏覽器的出口。

哪一步出了問題

在 <?xml …?> 那一行之後加上 [外部 entity 宣告]，並把 productId 的內容換成 [entity 引用]。方括號代表被換掉的那段輸入：宣告就是上面那種 <!ENTITY … SYSTEM …>，名稱與 URI 都由使用者決定，引用把資源的內容放進 productId 的位置；其餘欄位與正常請求相同。

Request
POST /product/stock HTTP/1.1Host: shop.example.comContent-Type: application/xml<?xml version="1.0" encoding="UTF-8"?>[外部 entity 宣告]<stockCheck>  <productId>[entity 引用]</productId>  <storeId>1</storeId></stockCheck>
Response
HTTP/1.1 400 Bad RequestContent-Type: text/plainInvalid product ID: [被引用資源的內容]
  1. 你的瀏覽器送出請求。
  2. 請求本體是 XML 文件，外部 entity 宣告與引用都在裡面。
  3. parser 讀到宣告，記下這個 entity 的值要到指定的資源去取；解析 productId 時遇到引用，就向資源要內容，放進 productId 的位置。這一步在應用程式拿到任何資料之前完成。
  4. 應用程式拿到的 productId 是一段資源內容，不是商品編號，查不到商品，走到錯誤分支，把收到的值放進訊息。
  5. 錯誤訊息隨回應回到瀏覽器，資源的內容就在上方第二組框的 Response 窗格裡。

你的瀏覽器從沒碰過那個資源，卻在回應裡看到它的內容。

7.2.4 parser、資源與回應各自的結果

一次嘗試要依序通過三個檢查，每個檢查失敗時看到的現象不同，現象之間也會重疊。

  • parser 接受嗎：DOCTYPE 是 XML 語法的一部分，parser 可以拒絕它。語法有錯，或設定禁止 DTD 與外部 entity，可能得到解析錯誤；有些設定改成靜默略過，什麼錯誤都沒有。
  • 資源載入了嗎：parser 接受宣告，外部資源解析仍可以單獨關閉。開啟時，檔案不存在、沒有讀取權限、網路不通，載入就失敗。資源內容會當成 XML 文字放進文件，含有 < 或 & 這類符號的檔案，可能讓整份文件解析失敗，此時資源已經讀入，看到的卻也是 parser 錯誤。
  • 結果看得到嗎：載入成功之後，展開的值往哪裡去，由應用程式決定。上面的例子是錯誤訊息把值帶了出來；應用程式若只拿它查庫存、不放進回應，載入已經發生，回應裡卻沒有任何痕跡。

所以單看一則 parser 錯誤或沒有錯誤，都不能判斷資源有沒有被載入。

看不到結果時

資源載入了，回應卻不含內容，稱為盲目 XXE（blind XXE）。觀察方式與盲目 SSRF 相同：回應的狀態、錯誤文字或耗時是否隨資源而變；或帶外觀察：把資源換成 [觀察端]，也就是一台由你控制、會記錄收到的連線的主機，看紀錄中是否出現來自應用程式伺服器的連線。連線的來源位址與時間要與測試請求對得上，因為同一環境的 proxy 或安全閘道也可能發出連線。紀錄只說明 parser 向那個位置發出了請求，看不出檔案或內部服務有什麼內容。

7.2.5 同一個 parser 能讀檔，也能發請求

外部 entity 的 URI 可以是檔案，也可以是網址，所以 XXE 同時接上前面兩節。

  • 讀檔：URI 指向伺服器上的檔案，結果與 Path Traversal 同類，例如系統帳號清單、應用程式的設定檔。parser 讀得到的只限網站程序有權限讀的檔案；一般的 file:、http: 載入只做讀取，其他 scheme 依 parser 的實作而定。
  • 發請求：URI 指向 HTTP 網址時，parser 替伺服器發出請求。請求的來源是伺服器，所以依來源放行的內部服務也可能回應它。請求方法通常是 GET，標頭由 parser 或底層函式庫決定；使用者決定的是位置，包括 scheme、主機、路徑與查詢字串。雲端主機的中繼資料服務若要求 token 或自訂標頭，parser 發出的請求通常補不上，不一定取得。

上一節的庫存例子有一個叫 stockApi 的欄位，一眼看得出那是網址。XXE 沒有這種欄位：整份請求看起來只有商品編號和門市編號，伺服器仍可能因為文件裡的一段宣告而發出請求。能不能看到回應內容，取決於上面的第三個問題。

7.2.6 什麼情況下成立

  • 應用程式用 XML parser 處理使用者送來的內容。請求若是 JSON 或表單，沒有經過 XML parser，就沒有這個問題。
  • 使用者決定的是整份文件，或至少文件開頭。DOCTYPE 只能出現在根元素之前；使用者若只決定嵌進大文件中間的一個值，就不能自己加宣告。
  • parser 允許 DTD 與外部 entity。預設值依函式庫與版本而異：新版常預設關閉或限制，舊版本與舊寫法的程式常是開著的。
  • 讀檔受限於網站程序的權限，內容還要能作為 XML 文字放進文件。
  • 網路請求受限於防火牆與出站規則，與 SSRF 相同。
  • 看得到什麼，取決於應用程式怎麼使用展開後的值：放進錯誤訊息、完整放進頁面、只用於內部運算或完全不回傳。
  • 讀到檔案或連到內部服務，只代表 parser 做了這兩件事；後續能做什麼，看讀到什麼、那個服務提供什麼功能。

7.2.7 辨認 XML 入口

  • 直接收 XML 的請求：Content-Type 是 application/xml 或 text/xml，本體以 <?xml 或標籤開頭。SOAP 服務（用 XML 交換訊息的 Web 服務）、老舊的 API 與匯入功能常見這種格式。
  • 平常收 JSON 或表單的端點：有些框架依 Content-Type 選 parser。把同樣的資料改寫成 XML，再改 Content-Type，伺服器可能照收，於是多出一個你原本沒看到的 XML 入口。HTTP 請求的 Content-Type 就是在告訴伺服器該怎麼解讀本體。
  • XML 包在檔案裡：SVG（向量圖格式）圖片是 XML 文字；Word、Excel 的 docx、xlsx 是壓縮檔，裡面放的是 XML 檔。伺服器若在上傳之後解析檔案內容，例如縮圖、轉檔或擷取文字，解析用的就是 XML parser。
  • 使用者只決定其中一個值：伺服器把它放進自己組的 XML 文件，使用者寫不出 DOCTYPE。XInclude 是另一套機制：文件裡用 xi:include 元素，要求 parser 把別的資源併進來，不靠 DTD 宣告。parser 啟用 XInclude 處理時才會照做，這是和 DTD 分開的開關，只關 DTD 擋不住它。

確認時先記下正常的請求與回應，一次只改一處，再依前面的三個問題判讀。

7.2.8 防禦手法

有效的防禦

關掉 parser 用不到的能力

庫存查詢的 XML 只有兩個元素，沒有任何需要 DTD 的地方。最直接的做法是整個禁止 DOCTYPE：

# 較安全的做法：用 defusedxml 解析，並禁止 DOCTYPE
from defusedxml import ElementTree

def parse_stock_request(body):
    root = ElementTree.fromstring(body, forbid_dtd=True)
    return root.findtext("productId"), root.findtext("storeId")

文件含 DOCTYPE 時，這段程式在解析階段就丟出例外，第一個問題的答案固定是「不接受」。各語言的做法不同，下表列出幾個常見函式庫關閉相關功能的設定名稱與預設值，當查詢用的對照，不必記住：

表 7.2.8-1
平台做法預設與備註

各函式庫的預設值隨版本改變，所以設定要明確寫在程式裡，並用測試固定下來：拿一份含 DOCTYPE 的文件餵給解析函式，確認它被拒絕。XInclude 要單獨確認已關閉。

縮小萬一失守的損害

  • 限制 entity 展開的次數與總大小，避免層層巢狀的 entity 耗盡記憶體。
  • 網站程序以最小權限執行：只讀得到它需要的檔案，容器只掛載必要的目錄。
  • 出站請求與內部服務比照上一節的防禦：限制出站目的地，內部服務不單靠來源放行。
  • 錯誤訊息不回傳收到的整段值。這降低結果的可見度，屬於縱深防禦，修補仍在 parser 的設定。
  • 更新 XML 函式庫。同時評估資料格式本身：不需要 XML 的介面可以改用 JSON，那裡沒有 entity 機制。

只擋 file: 這類前綴URI 還能指向 HTTP 網址，變成 SSRF。
只檢查文件有沒有 DOCTYPE，卻不管 XIncludeXInclude 不需要 DTD 宣告，另有開關；多數 parser 預設關閉，被某些設定或框架打開後才會生效。
在瀏覽器端限制輸入使用者可以自己組請求，伺服器必須處理實際收到的文件。

7.2.9 小結

  • XML 有自己的語法：DTD 能宣告 entity，引用時由 parser 換成宣告的值；外部 entity 的值來自 URI 指向的資源，parser 會去載入。
  • XXE 發生在使用者能決定 XML 文件，而 parser 又允許 DTD 與外部 entity 時。載入資源的是伺服器上的 parser，權限與網路位置都是伺服器的。
  • parser 是否接受、資源是否載入、結果是否出現在回應，是三個分開的問題；看不到結果不能排除 XXE。
  • 同一個機制能讀檔（連回 Path Traversal），也能發請求（連回 SSRF），而且不需要任何網址欄位。
  • 修補在 parser 的設定：關閉 DTD、外部 entity 與外部資源解析，XInclude 另外確認，並更新函式庫。隱藏錯誤訊息與過濾字串不是修補。

PortSwigger Academy 的對應練習（主題頁 XML external entity (XXE) injection）：

  • Exploiting XXE using external entities to retrieve files：庫存功能的 XML 請求，觀察 parser 展開與錯誤訊息帶出值是兩個階段。
  • Exploiting XXE to perform SSRF attacks：外部 entity 指向網址時，請求的來源與回應內容，對照上一節的 SSRF。
  • Blind XXE with out-of-band interaction：回應沒有內容時，用外部觀察端確認 parser 有沒有發出請求。
  • Exploiting XInclude to retrieve files：使用者只決定一個值、寫不出 DOCTYPE 時，哪個機制仍然可用。
  • Exploiting XXE via image file upload：XML 包在上傳的圖片格式裡，解析發生在處理檔案的時候。

XXE 的 parser 讀到一段特殊語法就照做。下一節 Server-Side Template Injection 談頁面模板：網站用模板（template）把資料填進 HTML，模板引擎有自己的語法，能做變數取值與運算。使用者的輸入若被併進模板本身，而不是填進模板的空格，引擎就會把其中的語法當成指令執行。
