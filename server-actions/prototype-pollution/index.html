本節模型：shop.example.com 的帳號偏好設定頁，請求本體是 JSON，應用程式把它合併進使用者的設定

你在 shop.example.com 的帳號設定頁把主題改成深色、語言選繁體中文，按下「儲存」。瀏覽器送出一個 PATCH 請求，本體是一小份 JSON，裡面只有你改的那幾項。網站的應用程式把它併進你目前的設定，存回去，頁面顯示「已儲存」。

前面幾節裡，使用者送來的資料交給 parser、模板引擎或還原器，由它們依各自的語法解讀。上一節談的是資料被還原成物件的時候會不會連帶觸發行為。這一節的元件是 merge（合併）工具，它把使用者送來的每個鍵（key，物件裡每個屬性的名稱）都當成物件裡的一個位置，逐一處理。使用者決定的不只是值，還有鍵的名字；鍵的名字若碰巧指到一個所有物件共用的地方，寫入的對象就換了。

7.5.1 物件、屬性與 prototype

JavaScript 的物件（object）是一組屬性（property），每個屬性有名稱（也稱為鍵）和值。程式用 物件.名稱 讀取屬性，沒有這個屬性就得到 undefined：

const user = { name: "demo", theme: "dark" };

user.theme   // "dark"
user.lang    // undefined：user 沒有叫 lang 的屬性

請求本體裡的 JSON 是文字。伺服器用 JSON.parse 把文字轉成這樣的物件，後面的程式才能用屬性的方式讀它。

每個物件另有一條隱藏的連結，指向另一個物件，稱為它的 prototype（原型）。讀取屬性時，JavaScript 先找物件自己的屬性；找不到，就沿著連結到 prototype 去找；prototype 也沒有，再往它的 prototype 找，直到鏈的盡頭回傳 undefined。下面的程式用 Object.create 明確建立這種關係：

const defaults = { lang: "zh-TW" };
const user = Object.create(defaults);   // user 的 prototype 是 defaults
user.theme = "dark";

user.theme   // "dark"：user 自己的屬性
user.lang    // "zh-TW"：user 自己沒有，從 prototype 讀到

圖中 defaults 自己也有 prototype，就是最右邊的 Object.prototype。用 { } 或 JSON.parse 建立的一般物件，prototype 都是這同一個內建物件。所以空物件 {} 沒有任何屬性，({}).toString 卻是一個函式，來自它共用的 prototype。

寫入和讀取不對稱。user.lang = "en" 在 user 自己身上建立屬性，prototype 不動。但若程式拿到的就是 prototype 這個物件，直接改它，所有繼承它的物件（沿 prototype 連結找得到它的物件）讀到的值都跟著變：

const proto = Object.getPrototypeOf(user);   // 就是 defaults
proto.lang = "en";

user.lang    // "en"：user 自己沒有 lang，讀到 prototype 上改過的值

這是 prototype 的正常用法。出問題的情況是：改 prototype 的不是程式自己的決定，而是使用者的輸入透過鍵的名字，把寫入引到那裡。一般物件都能讀到一個名為 __proto__ 的特殊屬性（定義在 Object.prototype 上，用 Object.create(null) 建立的物件沒有），讀它會得到該物件的 prototype。另一條路徑是先讀物件的 constructor 屬性，再讀它的 prototype 屬性，在許多物件上也到同一個地方；某個函式會不會被這條路徑影響，取決於它的實作。這些名稱在字面上和 theme、lang 一樣是普通的字串鍵。

使用者的輸入藉這類鍵改動共用的 prototype，稱為 prototype pollution（原型污染）：被改的是所有物件共同依賴的那一個物件，它被「污染」，之後每個繼承它的物件讀到的都是被改過的內容。

7.5.2 合併函式把鍵當成路徑

回到偏好設定。使用者每次只送改動的幾項，應用程式用 merge 把它們併進完整的設定。設定可以有巢狀結構，例如 notify 底下還有 email，所以 merge 對每個鍵分兩種情況：值是字串或數字，就直接寫進目標；值本身又是一個物件，就拿目標裡同名的物件，把這個物件再合併一次。函式在處理中呼叫自己，這種寫法叫遞迴（recursion）。下面是常見的寫法：

function merge(target, source) {
  for (const key in source) {
    if (typeof source[key] === "object" && source[key] !== null) {
      if (typeof target[key] !== "object") target[key] = {};
      merge(target[key], source[key]);
    } else {
      target[key] = source[key];
    }
  }
  return target;
}

逐行讀法：for (const key in source) 逐一取出來源的每個鍵；typeof source[key] === "object" 判斷值是不是物件（null 另外排除）；if (typeof target[key] !== "object") 在目標還沒有這個物件時，先放一個空的；merge(target[key], source[key]) 是函式呼叫自己；else 底下是普通值，直接寫進目標。

用一份正常的更新跑一遍。目前的設定與請求本體如下：

// 目前的設定
{ theme: "light", lang: "zh-TW", notify: { email: true } }
{
  "theme": "dark",
  "notify": { "email": false }
}
  1. 鍵 theme 的值是字串，直接寫進 target.theme。
  2. 鍵 notify 的值是物件，target.notify 也是物件，於是遞迴：對 target.notify 與來源的 notify 再合併一次，email 變成 false。
  3. 結果是 { theme: "dark", lang: "zh-TW", notify: { email: false } }，lang 沒被動到。

函式從頭到尾沒有檢查鍵是什麼，因為它預設鍵就是設定項目的名稱。現在把其中一個鍵換成 7.5.1 說過、會指到 prototype 的名稱。方括號代表被換掉的那段輸入：

{
  "theme": "dark",
  "[指向原型的鍵]": { "[新增的屬性]": "[值]" }
}
  1. 鍵 theme 的值是字串，直接寫進 target.theme。
  2. 鍵 [指向原型的鍵] 的值是物件，函式進入第一個分支，檢查 target[key]。這個名稱在一般物件上讀出來的是它的 prototype，也就是共用的 Object.prototype，型別是 object。
  3. 條件 typeof target[key] !== "object" 不成立，所以不建立新的空物件，接著執行 merge(target[key], source[key])：這一次的 target 就是 Object.prototype。
  4. 下一層的鍵 [新增的屬性] 值是普通值，走 else，寫進這次的 target，也就是 Object.prototype。
  5. 結果：theme 照常更新，目前的設定裡沒有任何新項目，共用的 Object.prototype 卻多了一個屬性，所有一般物件都讀得到。

函式沒有出錯，也沒有任何步驟分得出「叫 notify 的鍵」與「指到 prototype 的鍵」。JSON.parse 不改動 prototype，它讀到這個鍵，只是在解析出的物件上建立一個名稱相同的普通屬性；寫進 prototype 的是 merge，因為它拿這個鍵去 target[key] 查詢，再往查到的物件裡寫。

鍵變成結構的地方不只 merge。查詢字串剖析器把 preferences[notify][email]=false 還原成巢狀物件；set(obj, "a.b.c", 值) 這類依路徑字串設值的函式，以及深層複製（deep clone，把物件連同每一層複製一份）與 extend（把一個物件的屬性擴充進另一個）工具，也都逐層用鍵處理物件。只要鍵來自使用者，又沒有限制可以走到哪裡，就有相同的問題。

7.5.3 從偏好更新到後台權限

假設 shop.example.com 的後端是 Node.js（在伺服器上執行 JavaScript 的環境）程式，用常見的 Express 框架，並用上面的 merge 處理偏好更新。app.patch 處理 PATCH 請求，app.get 處理 GET 請求；express.json() 讓 req.body 成為解析好的 JSON 物件。/admin 的處理程式用 req.user.isAdmin 決定要不要顯示後台。req.user 是每次請求從資料庫載入的一般物件，一般使用者的物件上沒有 isAdmin 這個屬性：

app.use(express.json());

app.patch("/preferences", (req, res) => {
  merge(req.user.settings, req.body);
  saveSettings(req.user);   // 存回資料庫，細節省略
  res.send("saved");
});

app.get("/admin", (req, res) => {
  if (req.user.isAdmin) {
    res.send(renderAdminPage());
  } else {
    res.status(403).send("Forbidden");
  }
});

把本體換成前面那份帶占位符的 JSON，其餘不變。假設 [新增的屬性] 的名稱，正好是後台檢查讀取的 isAdmin，值是 [通過檢查的值]（程式會當成「是」的值）：

Request
PATCH /preferences HTTP/1.1Host: shop.example.comContent-Type: application/jsonCookie: session=[你的 Session]{ "theme": "dark", "[指向原型的鍵]": { "[新增的屬性]": "[通過檢查的值]" } }
  1. 使用者 A 送出請求，本體裡有一個鍵指向 prototype，底下是要新增的屬性。
  2. merge 逐層檢視輸入的鍵，遇到值是物件的鍵就遞迴。
  3. 指向 prototype 的那個鍵，在 target[key] 查出來的是共用的 Object.prototype。函式對它遞迴，新屬性寫進共用物件，不屬於 A 的任何設定。伺服器照常回 200 saved。
  4. 之後使用者 B 請求 GET /admin，程式讀 req.user.isAdmin。B 的物件自己沒有這個屬性，JavaScript 向它的 prototype 查找。
  5. 查到上一步寫入的值，檢查通過，B 看到後台頁面。B 的帳號、Session 與資料庫裡的紀錄都沒有改變。

污染的範圍是那個 Node.js 行程（process，伺服器上一個正在運行的程式；重啟後它的記憶體清空）。同一個行程處理的每個請求都共用一份 Object.prototype；網站若跑多個行程，只有處理到那次更新的行程受影響，這也是後續請求結果時有時無的原因之一。

7.5.4 讀到沒設定屬性的 gadget

污染只是把一個屬性放到共用的位置，本身不會讓網站做出新的事。屬性要發揮作用，需要另一段程式讀取它：這段程式讀的屬性在物件自己身上沒有設定，所以落到 prototype，讀出污染者放進去的值，再拿這個值去做事。這樣的程式碼稱為 gadget（原意是小零件：借用程式裡現成的一段碼，替污染者做事）。前面的例子裡，req.user.isAdmin 那一行就是 gadget，它拿讀到的值做權限判斷。

前端的 gadget 常長得像這樣。頁面腳本有一個設定物件，banner 是選用項目，平常沒有人設定，這段程式就不會執行：

const config = { theme: "light" };

if (config.banner) {
  document.getElementById("notice").innerHTML = config.banner;
}

config 自己沒有 banner，讀取會落到 Object.prototype。prototype 上若已被放進同名屬性，條件成立，值被交給 innerHTML（把字串當 HTML 放進頁面的屬性）。

3.2 的 source 與 sink 說過，source 是使用者的值進入頁面程式的地方，sink 是值被寫進頁面或交給危險功能的地方，值從 source 直接走到 sink。prototype pollution 在中間多了一段：source 的值先寫進共用物件，離開原來的程式路徑，等另一處的 gadget 讀到，才走到 sink。追查時只看 sink 前面的變數從哪來，會找不到 source，要連同這段合併一起看。

伺服器端的 gadget 不限於權限旗標。程式把選項物件交給函式庫，函式庫讀取呼叫端沒寫的選項時，也會落到 prototype；選項若決定要執行的命令或模板內容，後果就接到命令注入、模板注入那類問題。

與上一節的還原相比，prototype pollution 不重建任何物件，它改的是所有物件共同依賴的一個物件，影響其他物件事後的讀取。

7.5.5 前端與伺服器端

前端的污染常以網址為來源。頁面腳本把查詢字串或片段剖析成物件（含巢狀鍵），再合併進設定物件；污染發生在受害者開啟那條連結的瀏覽器裡，gadget 可能在頁面自己的程式，也可能在載入的第三方腳本。伺服器端的來源是請求本體或查詢字串，污染發生在伺服器的行程裡。

表 7.5.5-1
項目前端（瀏覽器）伺服器端（Node.js）

伺服器端看不到內部物件，加上污染的範圍是整個行程，測完要重新啟動。

即使沒有 gadget，寫入與既有方法同名的屬性也可能讓其他程式出錯，伺服器端表現為服務異常。

7.5.6 什麼情況下成立

  • 有一段程式用使用者提供的鍵走訪物件並寫入：遞迴 merge、依路徑設值、深層複製、把 a[b]=c 剖析成巢狀物件的函式庫。
  • 走訪邏輯沒有擋掉會到達 prototype 的鍵。函式庫通常在某個版本之後修補，所以舊版本才有問題。
  • 目標是一般物件。用 Object.create(null) 建立的物件沒有 prototype，Map 也不依屬性查找，兩者都不受影響。
  • 有 gadget。prototype 上多一個屬性，沒有任何程式讀它，就看不出效果。屬性名稱必須和 gadget 讀的名稱一致。
  • gadget 讀取時不檢查「是不是物件自己的屬性」。用 Object.hasOwn(obj, "banner") 這類檢查的程式，讀不到繼承來的值。

7.5.7 辨認合併點與污染

  • 輸入端：端點接受有巢狀結構的 JSON，或查詢字串寫成 a[b]=c，後端把它併進一個儲存的設定或個人資料；匯入設定、更新個人檔案、複製物件的功能都是候選。
  • 程式碼端：搜尋遞迴合併、extend、deep clone、依路徑設值的函式，以及處理這類工作的第三方套件，對照套件版本與安全公告；npm audit 這類工具會列出已知問題。
  • 污染的證據是不相干的物件上出現你沒有設定過的屬性。送一個無害的新屬性名稱，再檢查另一個全新的物件有沒有它：前端用開發者工具檢視頁面裡的物件，伺服器端則看別的請求的回應有沒有跟著改變。
  • 伺服器端常沒有任何回饋。更新請求的回應與正常時相同，需要比較其他請求的行為：狀態碼、回應中 JSON 的格式、錯誤訊息有沒有差異。差異能說明有東西被改，不能直接說明改在哪裡。
  • 確認過的污染要記下屬性名稱與影響的範圍，通報時說明需要重啟才能清除。

7.5.8 防禦手法

有效的防禦

合併時只更新已知的項目

合併邏輯不必接受任意的鍵。下面的版本只更新目標物件上「自己已經有」的屬性：

const isObject = (v) => typeof v === "object" && v !== null;

// 較安全的做法：只更新 target 自己已有的屬性
function safeMerge(target, source) {
  for (const key of Object.keys(source)) {
    if (!Object.hasOwn(target, key)) continue;
    if (isObject(source[key]) && isObject(target[key])) {
      safeMerge(target[key], source[key]);
    } else {
      target[key] = source[key];
    }
  }
  return target;
}

擋住它的是 Object.hasOwn(target, key)。指向 prototype 的鍵不是 target 自己的屬性，它回傳 false，整項被略過，遞迴不會走進共用物件。來源物件自己就帶著這個鍵，所以 Object.keys(source) 照樣會列出它，與 for…in 在這裡沒有差別。代價是使用者不能新增項目，只能改既有項目；需要新增時，改用下面的白名單。Object.hasOwn 在 2021 年後的環境（Node.js 16.9 起、近年的瀏覽器）才有；要支援更舊的環境，改用 Object.prototype.hasOwnProperty.call(obj, key)。

用白名單驗證請求本體

更新偏好只有兩個欄位，可以在合併之前依結構描述（schema）驗證，不認得的鍵直接拒絕：

{
  "type": "object",
  "properties": {
    "theme": { "enum": ["light", "dark"] },
    "lang": { "type": "string" }
  },
  "additionalProperties": false
}

additionalProperties: false 讓清單以外的鍵一律不通過，指向 prototype 的鍵也在其中。這同時限制了值的型別與範圍，比事後挑出幾個危險的鍵可靠。

使用者決定鍵名的資料，用不會查 prototype 的容器

鍵由使用者決定的資料，例如自訂標籤、欄位對照表，改放在 Map，或用 Object.create(null) 建立的物件：

const labels = new Map();
labels.set(key, value);   // key 只是資料，不會被當成物件的結構

const plain = Object.create(null);   // 沒有 prototype，查找到自己為止

沒有 prototype 的物件也沒有 toString、hasOwnProperty 這些繼承來的方法，程式若呼叫它們會出錯；要檢查屬性時用 Object.hasOwn(plain, key)。查詢字串剖析套件通常有避開這個問題的選項，升級並查文件。

讓 gadget 不依賴繼承

  • 選用設定在程式裡明確給預設值，並用 Object.hasOwn 判斷物件自己有沒有，讀取就不會落到 prototype。
  • 前端把來自網址的值放進頁面時，寫入點用 textContent 一類不解析 HTML 的方式，即使 gadget 被觸發，值也只是文字（見 3.2 的防禦）。

縮小萬一失守的損害

  • 在程式啟動、載入其他程式碼之前呼叫 Object.freeze(Object.prototype)，凍結後對它新增或改屬性不再生效：一般模式靜默忽略，嚴格模式（strict mode）丟出例外。凍結必須早於任何污染發生。
  • 凍結有副作用：有些套件在載入時會修改內建 prototype（例如 polyfill，用來補上舊環境缺少的功能），凍結後可能壞掉；用賦值覆寫 toString 這類繼承來的屬性也會被擋。上線前要完整測試。
  • 凍結只保護被凍結的那個物件，Array.prototype、自己的類別與前面 defaults 這類物件要分別處理。
  • Node.js 的 --disable-proto=delete 選項把 7.5.1 說的第一個特殊屬性整個移除，--disable-proto=throw 則讓存取它時丟出例外（ERR_PROTO_ACCESS）。7.5.1 的第二條路徑仍在，所以它不能單獨當作修補。
  • 更新用到的合併、複製與剖析套件，並讓依賴掃描定期跑；這類套件過去多半被回報過這個問題並修補。

無效的防禦

表 7.5.8-1
做法為什麼不夠
只過濾一個鍵名到達 prototype 的路徑不只一條（7.5.1 說了兩條），各個函式庫的實作會被哪一條影響也不同，本節的 merge 就只受第一條影響。用名稱列舉無法涵蓋所有實作，擋掉一個名稱，另一條路徑在別的實作上仍然通。
只檢查請求最外層的鍵merge 會遞迴，指向 prototype 的鍵可以出現在任何一層巢狀物件裡。
清理值（例如跳脫 HTML），不檢查鍵污染靠的是鍵的名稱，寫進去的值清理得再乾淨，結構仍被改了；gadget 讀到的屬性名稱也是來自鍵。
改用 JSON.parse 就當作安全解析本來就不是寫入 prototype 的地方，合併照舊。
只在前端表單限制欄位使用者可以直接組請求，或構造含巢狀鍵的網址；伺服器與頁面腳本必須處理實際收到的輸入。
回應不再反映新屬性，不讓人看出污染屬性仍在 prototype 裡，gadget 照樣讀它；回應看不到，只表示症狀被藏起來。

7.5.9 小結

  • JavaScript 物件讀取屬性時，自己沒有就沿 prototype 往上找；一般物件共用同一個 Object.prototype，改它，所有繼承它的物件讀到的值都變。
  • 遞迴 merge、依路徑設值、查詢字串剖析這類程式，把使用者的鍵當成物件裡的位置；鍵若指向 prototype，寫入的對象就是共用物件。
  • 污染需要 gadget 才有後果：有一段程式讀物件自己沒設定的屬性，並把值交給 sink 或用來決策。前端常接到 DOM-based XSS，伺服器端常是權限旗標與選項，污染的範圍是整個行程。
  • 辨認的證據是不相干的物件出現沒設定過的屬性；伺服器端要靠其他請求的行為差異。
  • 修補在合併處：只更新已知的自己的屬性、用白名單驗證請求本體、使用者決定鍵名的資料放 Map、更新套件；凍結 prototype 是縱深防禦，過濾單一鍵名與清理值都不是修補。

PortSwigger Academy 的對應練習（主題頁 Prototype pollution）：

  • DOM XSS via client-side prototype pollution：對照 3.2 的 source 與 sink，找出中間多出來的那段合併，以及讀取沒設定屬性的 gadget。
  • Privilege escalation via server-side prototype pollution：伺服器端的偏好更新與權限旗標，分開確認「污染發生」與「gadget 讀到」兩件事。
  • Detecting server-side prototype pollution without polluted property reflection：回應看不到新屬性時，靠哪些行為差異判斷。
