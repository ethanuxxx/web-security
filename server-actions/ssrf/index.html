本節模型：shop.example.com 的商品庫存查詢功能

你在 shop.example.com 的商品頁按下「查詢庫存」，瀏覽器送出一個 POST 請求，本體裡的 stockApi 欄位是庫存服務的網址。網站的應用程式讀到這個網址，自己向它發出另一個 HTTP 請求；庫存服務回傳件數，應用程式再把件數寫進頁面。庫存服務放在內部網路（簡稱內網），網際網路上的人連不到它，所以由網站的應用程式代為查詢。

第 5 章談過瀏覽器被誘導去送出請求。這一節換成伺服器：請求裡有一個網址，決定了網站接下來要連到哪裡；這個網址由使用者的請求帶來。

7.1.1 網站同時是 server 與 client

一次 HTTP 對話有兩個角色：發出請求的一方是用戶端（client），回應的一方是伺服器（server）。角色是針對每一條連線而言的。你的瀏覽器連到 shop.example.com 時，瀏覽器是 client；網站的應用程式去問庫存服務時，應用程式是 client，庫存服務是 server。一次庫存查詢因此包含兩段連線，兩段的發起者不同。同一台伺服器上除了網站，通常還有只給本機使用的管理介面。

連線的另一端怎麼知道「從哪裡來」，要先認識幾個名詞。

  • IP 位址是機器在網路上的編號，例如 203.0.113.5。伺服器收到連線時，看得到對方的 IP 位址，這就是這條連線的來源。
  • DNS（Domain Name System）把名稱換成 IP 位址：瀏覽器連 shop.example.com 之前，先問 DNS 這個名稱對應哪個 IP 位址。名稱指向哪裡，由管理該網域的人設定。
  • 連接埠（port）是主機上區分服務的編號。同一台機器可以在不同的 port 同時提供網站、管理介面與資料庫。網址沒寫 port 時，http 預設用 80，https 預設用 443。
  • loopback 是指向「發出連線的這台機器自己」的 IP 位址，名稱 localhost 通常解析到它（IPv4 是 127 開頭，IPv6 是 ::1）。連到 loopback 的流量不會離開這台機器。本節的例子中，應用程式與管理介面在同一個網路環境，所以應用程式連 localhost 就連得到管理介面。
  • 內部網路（內網）常使用私有 IP 位址，這類位址通常不在網際網路上直接路由，伺服器、資料庫與管理工具常放在這裡。

同一個名稱，在不同機器上指向不同的地方：你的瀏覽器連 localhost 連到你的電腦，網站的應用程式連 localhost 連到運行網站的那台伺服器。

7.1.2 內部服務依來源放行

管理介面、內部 API 和資料服務常常只開放給特定來源：本機的其他程式，或內部網路中的機器。設計者的想法是，能從那些位置連進來的，就是自家元件，所以這些服務不一定再要求登入，或只做較寬鬆的檢查。網路位置在這裡當成了身分。

這個假設在「只有可信的元件能決定連線目標」時才成立。Server-Side Request Forgery（SSRF，伺服器端請求偽造）指使用者能影響伺服器所發出的請求，讓伺服器連到開發者沒打算讓使用者指定的地方。請求由伺服器發出，目標卻由使用者決定，所以叫伺服器端的請求偽造。內部服務看到的連線來自伺服器，依來源放行，使用者就借道取得了自己直接連不到的東西。

表 7.1.2-1
項目使用者直接連透過 SSRF 連
發出連線的是使用者的瀏覽器網站的應用程式
內部服務看到的來源外部網路伺服器本機或內部網路
內部服務的回應被拒絕或連不到可能照常回應，應用程式再轉給使用者

伺服器能做的事，通常比使用者自己的連線多。除了管理頁和內部 API，常見的目標還有雲端主機上的中繼資料服務（instance metadata service）。以 AWS EC2 為例，主機上的程式可以向它取得實例的設定；實例若配置了 IAM 角色，也能取得該角色的臨時憑證。這個端點對實例上的程式開放，同一台主機上的其他程序，以及其他能連到它的工作負載，一樣取得到。應用程式如果被指揮去連它，可能取回本來只屬於這台主機的資訊。

各家供應商對請求的要求不同。AWS 的 IMDSv2 要求先取得短期的 session token，之後的請求都帶著它；Azure 的 IMDS 要求每個請求帶特定的 metadata 標頭。只能影響網址的 SSRF 通常不容易滿足這類要求，但是否被擋下，還要看實例是否仍接受舊版的簡單請求，以及應用程式的 HTTP 用戶端能否被使用者影響請求的方法與標頭。

7.1.3 從庫存查詢到管理頁

沿用庫存查詢的例子，假設應用程式沒有檢查 stockApi 的網址，並把庫存服務回傳的內容放進回應。

正常的請求

Request
POST /product/stock HTTP/1.1Host: shop.example.comContent-Type: application/x-www-form-urlencodedstockApi=http%3A%2F%2Fstock.internal%2F7
  1. 瀏覽器送出：依表單編碼規則，欄位值裡的特殊字元改寫成 % 加兩位十六進位，例如 : 變成 %3A、/ 變成 %2F，整個網址放進一個欄位值。
  2. 應用程式解碼：還原成 http://stock.internal/7。
  3. 第二段連線：應用程式向這個網址發出 GET 請求。請求的方法由應用程式的程式碼決定，使用者能改的只有網址。stock.internal 在內部網路，看到連線的來源 IP 位址屬於網站的伺服器，放行。
  4. 內部服務回應：回傳 18，表示庫存 18 件。
  5. 回到頁面：應用程式把結果整理成「庫存：18 件」，放進回應。

哪一步出了問題

把 stockApi 的值換成 [內部管理介面的網址]。方括號代表被換掉的那段輸入，指向同一台伺服器或內部網路上的管理介面；外部使用者直接連它會被拒絕。

Request
POST /product/stock HTTP/1.1Host: shop.example.comContent-Type: application/x-www-form-urlencodedstockApi=[內部管理介面的網址]
  1. 應用程式解碼後，得到的不再是庫存服務的網址。因為沒有檢查，它照常向這個網址發出請求。
  2. 管理介面看到的連線來自同一台伺服器或內部網路，符合「只接受本機或內網」的條件，回傳管理頁。
  3. 應用程式把取回的內容放進回應。你的瀏覽器從沒連過管理介面，卻看到了它的內容。
表 7.1.3-1
條件你看到的判讀
瀏覽器直接開管理介面被拒絕或連不到外部來源被擋，作為基準。
原本的 stockApi庫存件數建立正常功能的基準。
只換 stockApi 的值管理頁內容回應出現只有管理介面才有的內容，表示應用程式取回了它；要確認來源，可對照管理介面或觀察端的紀錄。
改回原本的值庫存件數差異隨這個欄位出現與消失。

要分清楚是誰發出連線。若應用程式自己沒有連線，只把網址放進 3xx 回應的 Location 標頭，指向 [同一個網址]，連線的就是你的瀏覽器：它按照指示再發一個請求，localhost 指向你自己的電腦，沒有第二段連線，這條路徑也就不是 SSRF。應用程式也可能先自己連線，再把上游的 3xx 轉給瀏覽器，兩種行為可以同時存在。因此判斷證據是回應本體裡有沒有出現只有伺服器端連線才取得的內容；本體出現管理頁文字時，還要排除它來自反射的輸入、快取或應用程式自己產生。

管理頁若有刪除使用者之類的功能，並且單靠一個 GET 請求就能觸發，那些操作同樣以伺服器的身分發出。

7.1.4 什麼情況下成立

  • 連線必須由伺服器發出。參數名稱叫 url 或內容長得像網址，都只是線索；網址若只是顯示在頁面上，或由瀏覽器自己去載入，就沒有第二段連線。
  • 目標至少有一部分由使用者決定：整個網址，或只有主機名稱、路徑、查詢字串之一。只能決定路徑時，影響範圍比較小，但同一個服務上的其他端點仍可能被連到。
  • 網路必須走得通。伺服器所在的網段能連到哪裡，取決於防火牆、容器網路和出站規則；IP 位址存在還不夠，還要看這些規則是否讓應用程式連得到。
  • 協定受限於應用程式使用的函式庫。多數網站功能只發 HTTP 或 HTTPS 請求，有些函式庫還支援其他協定（例如讀本機檔案的 file），是否可用視函式庫與設定而定。
  • 看得到什麼取決於應用程式怎麼處理回應：完整放進頁面、只擷取一部分、只顯示成功或失敗，或完全不回傳。
  • 能連到內部服務，不等於能在伺服器上執行命令。能做到什麼，要看那個服務提供什麼功能，以及它讓這個來源做什麼。讀取管理頁和取得整台主機的控制權是兩個不同的結論。

看不到回應時

應用程式發出請求之後，若只在內部使用結果，或回傳的內容與取回的資料無關，這類情況稱為盲目 SSRF（blind SSRF）。和 OS command injection 的盲目情況類似，看不到直接結果，仍可能看到處理造成的其他效果：

  • 回應差異：目標網址有服務與沒有服務、port 開放與關閉，應用程式回傳的狀態、錯誤文字或耗時可能不同，可據此判斷哪些目標有回應。
  • 帶外通道（out-of-band）：把網址換成 [觀察端]，即一台由你控制、會記錄收到的連線的主機。紀錄裡出現來自應用程式伺服器的連線，表示伺服器很可能依你給的網址發出了請求；內部服務有什麼內容，這個方法看不出來。

單次變慢可能只是負載，錯誤頁可能是應用程式自己產生的，帶外連線也可能來自別的元件。這些訊號要和正常功能的基準對照，並且重複確認。

7.1.5 辨認會替使用者連線的功能

先問網站為什麼需要替使用者連線。有下列需求的功能，背後可能就有第二段連線：

表 7.1.5-1
功能伺服器為什麼要連線
查庫存、查運費、查匯率向內部或合作的服務取資料
用網址匯入頭像、圖片或文件伺服器自己去下載
連結預覽、網址縮圖抓取網頁標題與圖片
Webhook（讓使用者填一個網址，事件發生時網站送通知到那裡）事件發生時，伺服器向使用者給的網址送資料
把網頁轉成 PDF 或截圖伺服器上的瀏覽器（沒有畫面，只負責載入與繪製）去載入該網址
流量分析顯示「這個訪客從哪個頁面來」讀取請求的 Referer 標頭（記錄上一頁是哪個網址），再去訪問那個頁面

網址可能出現在 URL 的查詢字串、表單或 JSON 的欄位、HTTP 標頭，甚至只是路徑的一段；資料格式（例如下一節的 XML）也可能間接引發請求。看到欄位值長得像網址或主機名稱，就是值得檢查的位置。

確認時先記下正常功能的請求與回應，一次只改一個欄位，再比較回應。回應的差異可能出現在內容、狀態碼、錯誤文字或耗時。一個錯誤頁只說明應用程式遇到了問題，不足以說明背後有什麼服務。

7.1.6 只檢查網址字串為什麼不夠

發現這類問題後，常見的第一反應是在送出請求前檢查網址，拒絕看起來指向內部的網址。這種檢查會在這幾處失效：

  • 同一個 IP 位址有多種寫法。IPv4 位址是 203.0.113.5 這種四段數字，除了常見的四段十進位，還有其他等價的表示法；IPv6 是較新、更長的寫法，也能表示 IPv4 位址。逐一列出禁止的寫法，總可能漏掉一種。
  • 主機名稱由 DNS 解析成 IP 位址，網域的擁有者決定它解析到哪裡，包括內部的 IP 位址。檢查了名稱，還沒檢查它最後連到哪裡。
  • 轉址（redirect）。允許的主機回應 3xx 並指向別的網址時，若 HTTP 用戶端啟用自動跟隨（例如 Python 的 Requests 對一般 GET 預設會跟隨），連線就換了目標。只檢查最初的網址，擋不住這一步。
  • 檢查與連線之間的空檔。檢查時解析一次、連線時再解析一次，兩次結果可以不同，這稱為 DNS rebinding：例如 DNS 記錄的存活時間（TTL，記錄被快取多久）很短，兩次查詢之間被改掉。
  • 網址解析器不一致。檢查用的程式與實際連線的函式庫，對網址裡的特殊部分（帳號資訊、片段、不尋常的分隔符號）切出的主機可能不同。

下排只畫出「解析到內部 IP 位址就拒絕」這一種結果。解析後再檢查一次，兩次解析之間仍有空檔，所以還要用檢查過的 IP 位址連線，並對每一次轉址重做檢查，做法見下一節的表。

7.1.7 防禦手法

有效的防禦

不讓使用者提供網址

庫存查詢只需要知道查哪個商品。瀏覽器送商品編號，網址由伺服器端的設定決定：

# 較安全的做法：只收商品編號，網址由伺服器端決定
STOCK_SERVICE = "http://stock.internal"

def check_stock(product_id):
    if not product_id.isdigit():
        abort(400)
    return http_get(STOCK_SERVICE + "/" + product_id)

使用者能影響的只剩一個整數，第二段連線的目標固定；功能允許時優先這樣做。

必須接受網址時

匯入圖片、Webhook 這類功能本來就要使用者給網址。能做的是多層限制：

表 7.1.7-1
檢查項目做法
協定與 port只允許需要的協定（通常是 https）與 port，其他一律拒絕。
網址解析驗證與建立請求使用同一份解析結果。主機的允許清單比對解析後的完整主機值，不用原始字串的包含或前綴；拒絕用不到的帳號資訊（userinfo）等容易造成歧義的部分。
主機能列出可連線的主機時，用允許清單比對，不用禁止清單。
解析後的 IP 位址自己解析名稱，取得所有可能被選用、重試或 fallback 的 IPv4（A 記錄）與 IPv6（AAAA 記錄）位址，每一個都要驗證。拒絕 loopback（含 IPv6 的 ::1）、私有範圍、IPv6 的 unique-local 與 link-local（自動配置的位址範圍，雲端中繼資料服務常在其中），以及 IPv4-mapped 位址內嵌的 IPv4。只供公開網址的功能，宜改成只放行明確可公開連線的位址，並依部署排除特殊用途的範圍與內部路由；「不屬於私有位址」不代表可以安全連線。
連線方式用驗證過的那個 IP 位址連線，不再交給用戶端重新解析。HTTPS 仍以原本的主機名稱做 SNI 與憑證驗證，Host 標頭也維持原主機；不要只把網址的主機換成 IP 位址，也不要關閉憑證驗證。請求若經過 proxy，由實際解析與連線的那一端落實同一套政策。
轉址關掉自動跟隨；必須跟隨時，每一次轉址都重做全部檢查，並限制次數。
回應處理設定逾時、大小上限與預期的內容型別；不把上游的原始回應或詳細錯誤整段交給使用者。

網路層與內部服務

應用層的檢查可能有漏洞，所以還要在其他層限制損害：

  • 出站限制：發出請求的元件放在受限網段，防火牆只放行必要的目的地；或讓所有出站請求經過專用的代理（proxy），由代理負責檢查。
  • 內部服務不單靠來源放行。管理介面要登入與授權；有副作用的操作不要只靠 GET 請求就能觸發；「從 loopback 或內網來」不是授權依據。
  • 雲端主機的中繼資料服務要依供應商的做法收緊。以 AWS EC2 為例，把實例設定為強制使用 IMDSv2：請求必須先取得短期的 session token，並帶著指定的標頭；只是支援 IMDSv2、同時仍接受 IMDSv1，無 token 的路徑並沒有關閉。這是縱深防禦的一層，仍需限制應用程式能連到的目標，並依最小權限設定主機角色，降低憑證被取走的代價。
  • 中繼資料服務的 IP 位址因供應商與 IPv4／IPv6 設定而異，出站限制要依實際使用的供應商與設定涵蓋它們。

拒絕含 localhost 或幾個特定 IP 位址字串的網址同一個 IP 位址有多種寫法，主機名稱也可以解析到內部 IP 位址。
只檢查最初網址的主機名稱允許的主機可以轉址；名稱解析的結果也可能在檢查後改變。
檢查後交給 HTTP 用戶端重新解析兩次解析不一定一致；檢查程式與用戶端切網址的規則也可能不同。

相信「內部網路外面連不到」SSRF 的連線就是從內部發出的，網路位置擋不住它。

7.1.8 小結

  • SSRF 指使用者能影響伺服器所發出的請求：第二段連線由網站的應用程式發起，位置與權限和使用者的瀏覽器不同。
  • 內部服務依來源放行時，伺服器等於替使用者開了一條路；localhost 指向發出連線的機器，在 SSRF 裡就是網站伺服器。
  • 要確認是伺服器取回內容，還是瀏覽器被轉址；看不到回應時，仍可能從回應差異與帶外連線觀察到請求發出了。
  • 字串黑名單和只檢查一次的做法，擋不住 IP 位址的多種寫法、DNS 和轉址。
  • 優先不讓使用者提供網址；必須接受時，用允許清單，檢查解析後的所有 IP 位址並用同一個位址連線，每次轉址重新檢查。出站限制與內部服務自己的驗證，是網址檢查失效時的第二層。

PortSwigger Academy 的對應練習（主題頁 Server-side request forgery (SSRF)）：

  • Basic SSRF against the local server：比較從外部直接存取管理頁，與透過庫存功能由伺服器代為存取的差別。
  • Basic SSRF against another back-end system：目標在內部網路的另一台系統：觀察怎麼確認哪些內部位置有回應。
  • Blind SSRF with out-of-band detection：回應沒有內容時，用外部觀察端確認請求有沒有發出。
  • SSRF with blacklist-based input filter：觀察黑名單檢查比對的是什麼，與連線實際去的地方差在哪裡。
  • SSRF with filter bypass via open redirection vulnerability：允許清單內的網站若有轉址功能，檢查和連線的目標怎麼分開。

本節庫存例子的網址放在一個明顯的欄位裡，但網址也可能藏在資料格式中。XML External Entity Injection 談的就是這種情況：若 XML parser 啟用外部實體解析，並允許存取外部資源，文件就能引用本機檔案或網路資源；引用網路資源時，你看不到任何網址欄位，伺服器仍然替你發出了請求。
