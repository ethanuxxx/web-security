本節模型：shop.example.com 的「我的帳號」頁，登入狀態放在 session Cookie 裡，值是一個序列化的物件

你登入 shop.example.com，點選「我的帳號」。瀏覽器送出的請求帶著一個 session Cookie，值是一長串看不出意思的字元。應用程式收到它，還原成一個 Session 物件：使用者是 demo，購物車編號 1042，不是管理員。帳號頁就依這些欄位畫出來。

前一節 Server-Side Template Injection 談的是模板引擎，讀到文字裡的語法就照做。這一節的元件是反序列化器（deserializer）：它讀一段描述物件的資料，重建出物件，而資料的內容決定建出哪種物件、每個欄位填什麼。Cookie 存在使用者的瀏覽器裡，下一次請求送回來時，伺服器收到的是一份使用者碰得到的資料。

7.4.1 序列化與反序列化

程式運行時，資料以物件（object）的形式存在記憶體裡。物件由類別（class）造出來：類別定義這種物件有哪些欄位（property，也稱屬性），以及能執行哪些方法（method，附在物件上的函式）。購物網站的程式可能有個 Session 類別，欄位是 username、role、admin、cart_id；一位登入者對應一個 Session 物件。

記憶體裡的物件無法直接存進檔案、放進 Cookie 或傳給另一台機器。序列化（serialization）把物件寫成一段文字或二進位資料，反序列化（deserialization，也稱還原）讀這段資料，在記憶體裡重建出物件。Cookie 這類位置只收文字，所以序列化的結果常再經過 Base64 編碼：一種把任意資料轉成英數字元的編碼，不需要金鑰，任何人都能解回來。

序列化的格式分兩類。原生格式（native format）是各語言自己的物件格式：PHP 的 serialize()、Java 的 ObjectOutputStream、Python 的 pickle、.NET 的 BinaryFormatter。資料裡記著類別名稱、每個欄位的型別與值，反序列化器照著建出物件。純資料格式（data-only format）如 JSON、XML，只描述數字、字串、布林、陣列與鍵值對，解析結果是一般的資料結構，沒有「這是哪個類別」這種資訊。

7.4.2 序列化的資料放在哪裡

只要資料會離開伺服器再回來，就可能被序列化：

  • Cookie：把登入狀態放在 Cookie，伺服器不必替每位使用者保存狀態。session Cookie 的值常是序列化物件，編碼後放進去。
  • 隱藏表單欄位（hidden field）：多步驟的流程把中間狀態寫在頁面的隱藏欄位，下一步提交表單時帶回。
  • API 的請求或回應本體：前端與後端交換整個物件，用原生格式時，類別名稱也在裡面。

這些位置都經過使用者的瀏覽器或工具，使用者可以讀、也可以改。HTTP 與 session 那一節看過 Cookie 的運作：伺服器設定，瀏覽器保存並在之後的請求帶回，帶回來的內容由瀏覽器端決定，伺服器沒有辦法保證它沒被改過。

7.4.3 從 session Cookie 到管理頁

沿用「我的帳號」的例子。假設 shop.example.com 的應用程式用 PHP 的 serialize() 把 Session 物件寫進 Cookie，並以 Base64 編碼。管理頁 /admin 的檢查是：從 Cookie 還原 Session，admin 欄位為 true 才放行。

哪一步出了問題

Cookie 在使用者手上，解碼、修改、重新編碼都不需要金鑰。把 admin 欄位的值換成 [改過的布林值]，其他欄位不動，再編碼回 Base64。方括號代表被換掉的那段輸入。

Request
GET /admin HTTP/1.1Host: shop.example.comCookie: session=[改過 admin 欄位後重新編碼的值]
  1. 瀏覽器送出請求，Cookie 裡 admin 欄位已被改過。
  2. Base64 解碼成一段文字。
  3. 反序列化器建出 Session 物件，admin 是 true。
  4. 授權檢查讀 admin，條件成立，放行。
  5. 回應是管理頁。

這個例子裡沒有漏掉任何一道檢查：反序列化成功，檢查也照規則做了。問題在於 admin 是否為 true 這個資訊從頭到尾由使用者送來，Cookie 裡沒有任何東西能讓伺服器確認它還是當初寫下的值。這和 Access Control 那一節由使用者送來的角色是同一類錯誤，只是這次放在 Cookie 裡一段序列化的文字，而不是表單欄位。

7.4.4 欄位的型別也由資料決定

序列化文字裡的每個值都帶著型別標記：s 是字串、i 是整數、b 是布林。反序列化器照標記還原，不會檢查「這個欄位原本應該是字串」。使用者把標記連同值一起換掉，應用程式拿到的就是另一種型別的值，這稱為型別混淆（type confusion）。

例子：假設 Session 多了一個字串欄位 token，登入時存的是一組隨機字串，之後每次請求，程式用 == 把它和資料庫裡的 token 比較。PHP 8.0 之前，整數與字串用 == 比較時，字串會先被轉成數字，開頭不是數字的字串轉成 0，所以把 token 欄位的型別標記換成整數、值換成 [整數型別的值]，就可能與 "k3f9…" 相等；PHP 8.0 起這個比較為 false。

這個例子要成立，反序列化器得接受被換掉的型別，比較得用會轉型別的 ==，執行環境還得是 PHP 8.0 之前。第二項由程式自己控制：改用嚴格比較 ===，同時比較型別與值。JSON 也有同類問題：欄位 "admin":"false" 是字串，在 JavaScript 的 if 判斷裡，非空字串一律當 true；PHP 只有 "" 與 "0" 是 false，所以 "false" 也當 true。嚴格比較 === true 則不做這種轉換。

原生格式還多一層：類別本身也寫在資料裡。應用程式以為還原出來的是 Session，資料卻可以指定別的類別，只要那個類別在程式碼裡存在。

7.4.5 還原時自動執行的程式

很多語言允許類別定義「還原時自動被呼叫」的方法，稱為 magic method 或 hook。PHP 的 __unserialize()（舊程式為 __wakeup()，兩者都有時只呼叫前者）在 unserialize() 執行期間被呼叫；__destruct() 在物件不再被任何地方引用時被呼叫，包括請求結束、腳本收尾時。Cookie 還原出的物件通常到請求結束前就會被丟棄，所以 __destruct() 幾乎一定會執行。這些方法是為了正常用途設計的：還原後重新連上資料庫、物件結束時釋放資源。

問題出在 hook 讀取的欄位值由資料決定。假設應用程式有個 TempExport 類別，用來產生匯出報表的暫存檔，欄位 path 記著檔案位置，它的 __destruct() 在物件結束時刪掉 path 指向的檔案。應用程式正常使用時，path 永遠是自己建立的暫存檔，這個設計沒有問題。但如果資料可以指定「建出 TempExport」並給 path 一個值，反序列化器照做，物件結束時 hook 就刪掉使用者選定的檔案。應用程式從沒打算讓這個類別出現在 Cookie 裡。

單一類別未必有這麼直接的危險動作。實務上的利用常把幾個類別接起來：某個類別的 hook 會呼叫另一個物件的方法，那個方法又呼叫第三個，最後落在刪檔、對外發出請求或執行程式碼這類動作上。每一段都是程式裡原本就有的，使用者不必上傳任何新程式，只要在資料裡決定物件怎麼彼此指向、欄位填什麼。這樣串起來的現成片段稱為 gadget，整條路徑是 gadget chain。能不能串出來，取決於應用程式與它依賴的函式庫裡有哪些類別，所以同一類弱點在不同網站的影響差很多。

有些 hook 在還原時執行，有些（例如 __destruct()）在物件被丟棄時執行。物件一建出來，之後檢查通不通過，兩種 hook 都照樣執行，所以還原之後才做的檢查來不及攔住。管理頁那個例子只靠一個被信任的欄位，hook 靠的是程式裡有可串的類別；改動 admin 欄位成功，不能推論 hook 也能被利用，反過來也一樣。

7.4.6 什麼情況下成立

資料要經過使用者再回到伺服器：放在 Cookie、隱藏欄位或 API 本體，或伺服器收下使用者上傳的序列化資料。在這之上，改欄位值（管理頁的例子）要求伺服器用資料裡的欄位決定權限、價格或使用者編號，而不是查自己保存的資料；改型別要求反序列化器不檢查欄位型別，程式又在比較時做型別轉換；hook 要求資料格式是原生格式、能指定類別，程式碼或依賴裡有 hook，且 hook 的行為受欄位值左右。改用 JSON 能去掉 hook 的問題，因為 JSON 沒有類別；改欄位值與格式無關，程式若照單全收 "admin": true，換成什麼格式都一樣。

7.4.7 辨認序列化資料

Cookie、隱藏欄位或請求本體裡一段看不懂的長字串，先判斷是否是 Base64（字元只有字母、數字、+、/，結尾常有 =），解碼後看開頭：

  • PHP：解碼後是可讀文字，開頭常是 O:（物件）或 a:（陣列），後面接數字與引號，像上面的例子。
  • Java：二進位資料，開頭的四個位元組（bytes）是 AC ED 00 05；未壓縮、整段用標準 Base64 編碼時，字串常以 rO0 開頭，先壓縮或改用 Base64URL 就不同。
  • .NET 的 BinaryFormatter 等其他格式也有固定的開頭，要查各自的格式文件。

7.4.8 防禦手法

有效的防禦

狀態留在伺服器，Cookie 只放隨機識別碼

Session 的內容放在伺服器的資料庫或快取，Cookie 只放一組不可猜的隨機 ID（session ID，見 HTTP 與 session）。使用者能改的只剩這個 ID，改過就查不到對應的 session。admin、role 這類欄位完全不離開伺服器，不需要反序列化任何使用者送來的物件。

不用原生格式，必須用時限制類別

資料必須經過使用者時，改用純資料格式（JSON），解析後檢查欄位清單、每個欄位的型別與值的範圍，不認識的欄位或型別不對的值直接拒絕。權限等決策欄位仍從伺服器的資料取得。PHP 與 Python 的官方文件都建議這樣做：改用 JSON，要保存或傳遞序列化資料時再加簽章。

必須用原生格式時，限制可還原的類別。PHP 的 unserialize() 有 allowed_classes 選項：false 不接受任何類別，或列出允許的類別；不在清單內的類別會改建成 __PHP_Incomplete_Class，原類別不會被實例化。官方文件仍警告：不論怎麼設定，都不要把使用者輸入交給 unserialize()。Java 用序列化過濾器（ObjectInputFilter）只允許確定需要的類別；清單的最後要有「其餘一律拒絕」的規則，沒寫的話，沒匹配到的類別會被放行，allow-list 就不成立。.NET 的 BinaryFormatter 與 Python 的 pickle 不對不可信資料使用。

簽章先驗，再解析

資料必須經過使用者、又要防止被改時，把資料（payload）和它的簽章（signature）一起放進 Cookie。簽章是用 HMAC（Hash-based Message Authentication Code，用金鑰與雜湊函式算出的驗證碼）對資料算出來的。伺服器收到後先用自己的金鑰重算一次，與附帶的簽章比對，相符才解析資料。沒有金鑰的人改了資料，簽章就對不上。

下面的程式假設 Cookie 的格式是「Base64URL 編碼的 JSON、一個點、十六進位的簽章」，簽章通過後還要檢查欄位：

import base64, hashlib, hmac, json

def load_session(cookie: str, key: bytes) -> dict:
    payload, _, signature = cookie.partition(".")
    # 先驗簽章（比對耗時不隨相符長度變化）
    expected = hmac.new(key, payload.encode(), hashlib.sha256).hexdigest()
    if not hmac.compare_digest(expected.encode(), signature.encode()):
        raise ValueError("簽章不符")
    # 簽章相符才解析，並檢查欄位與型別
    data = json.loads(base64.urlsafe_b64decode(payload + "=" * (-len(payload) % 4)))
    if (not isinstance(data, dict) or set(data) != {"username", "cart_id"}
            or not isinstance(data["username"], str)
            or not isinstance(data["cart_id"], int)
            or isinstance(data["cart_id"], bool)):
        raise ValueError("欄位不符")
    return data

簽章有兩項限制。它只證明資料出自持有金鑰的一方，金鑰一旦外洩，攻擊者能替任何內容簽章，所以金鑰放在環境變數或金鑰管理服務，不寫進原始碼與版本庫，定期輪替。它也不防重放：舊的 Cookie 連同簽章一起送回去仍然有效，需要時把過期時間放進被簽章的資料。

縮小萬一失守的損害

應用程式以最小權限執行，能刪的檔案、能連的內部服務盡量少，伺服器對外發出的請求比照 SSRF 那一節的防禦。定期更新依賴的函式庫：gadget 來自依賴裡的類別，更新後可串接的路徑會變少，但任何版本都不保證完全沒有。

只加密、不做完整性驗證加密藏起內容，但沒有驗證碼就不知道密文有沒有被改，某些加密模式還允許對密文做有意義的位元修改。要的是帶驗證的加密或 HMAC
反序列化之後才檢查類別，例如檢查它是不是 Session物件已被建出來：還原時的 hook 已經跑過，丟棄時的 __destruct() 之後也會跑，不論檢查通不通過
用黑名單列出要擋的危險類別可串接的類別來自應用程式與所有依賴，數量多、隨更新改變，清單永遠追不上；要改成只列允許的類別

7.4.9 小結

  • 序列化把物件寫成文字或二進位資料，反序列化再還原；Cookie、隱藏欄位與 API 本體常帶著這種資料，經過使用者之手。
  • Base64 只是編碼，不防竄改。伺服器若讀使用者送回的物件欄位來決定權限，就是 Access Control 那一節由使用者決定角色的同一類錯誤。
  • 原生格式讓資料決定型別與類別：型別混淆能繞過比較，hook 在還原或丟棄物件時自動執行，多個類別可串成 gadget chain。
  • 修補的順序：狀態留伺服器；必須經過使用者時改用 JSON 加欄位與型別檢查，再加 HMAC 簽章，簽章在解析之前驗；必須用原生格式時限制可還原的類別。

PortSwigger Academy 的對應練習（主題頁 Insecure deserialization）：

  • Modifying serialized objects：session Cookie 裡有序列化的使用者物件，觀察哪個欄位被用來決定權限。
  • Modifying serialized data types：欄位型別被換掉之後，比較運算的結果怎麼變。
  • Arbitrary object injection in PHP：資料能指定類別時，哪個類別的 hook 讀到了欄位值。

改用 JSON 之後不再有類別與 hook 可利用，問題轉到解析之後，也就是程式怎麼使用這份資料。下一節 Prototype Pollution 談 JavaScript：伺服器把使用者送來的 JSON 逐欄位合併進現有物件時，欄位名稱若能指到所有物件共用的 prototype，改動就會波及其他物件。
