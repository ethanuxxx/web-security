點地圖：到首頁地圖看這一章

還是那個購物網站，這回看它的訪客商品頁。頁面上有一排分類連結：Tea、Teaware、Snacks……點下 Tea，瀏覽器請求 /products?category=Tea，頁面就只列出茶葉類的商品。商品資料存在資料庫（database）裡，沒有寫死在網頁上；網站收到分類名稱後，要向資料庫問一次：請給我分類是 Tea 的商品。

前兩節的輸入都和檔案有關：doc 由檔案系統解讀，上傳的檔案由取回時的處理器決定用途。這裡的 category 是一段文字，交給資料庫解讀。使用者送來的文字若被資料庫當成問題的一部分，而不只當成要查的值，查詢的意思就會跟著改變。

2.3.1 表、列、欄

最常見的資料庫是關聯式資料庫（relational database）。你可以把它想成一本有很多張試算表的檔案，每張試算表叫一個表（table），有固定的欄（column，每欄有名稱，也有固定種類的內容），裡面每一筆資料占一列（row）。下面的商品表 products 有三列。

idnamecategorymembers_only
1烏龍茶包Tea0
2會員試飲組Tea1
3茶壺Teaware0
  • name、category 是文字值（字串）；id、members_only 是數字值。文字值在查詢裡要用單引號圍起來，數字值不用。
  • members_only 是網站自己的約定：0 表示任何訪客都能看，1 表示只留給登入的會員。第二列「會員試飲組」雖然分類是 Tea，卻不應該出現在訪客看的頁面上。

網站和資料庫之間講的語言叫 SQL（Structured Query Language，結構化查詢語言）。網站把一句 SQL 文字交給資料庫，資料庫解析（parse）這串文字：先判斷它是什麼意思，再照意思執行，把結果列送回來。資料庫和 Path Traversal 裡把 .. 解讀成往上一層的檔案系統一樣，都是應用程式下游的解讀者（interpreter）；應用程式與下游元件之間的縫隙，見 Path Traversal。

2.3.2 讀懂一句 SELECT

要取得分類是 Tea 而且開放給訪客的商品，網站會送出這句 SQL：

-- 正常的查詢
SELECT * FROM products WHERE category = 'Tea' AND members_only = 0
  • SELECT *：要取回什麼。* 表示「每一欄都要」。
  • FROM products：從哪張表查。
  • WHERE …：篩選條件。資料庫會逐列檢查，只留下條件為真的列。
  • category = 'Tea'：category 欄的值等於文字 Tea。單引號是文字值的邊界：兩個單引號之間的部分是資料，資料庫不把它當 SQL 語法讀。
  • AND：兩邊都要為真；OR：任一邊為真就行。

拿三列資料逐列驗算：

列category = 'Tea'members_only = 0兩者皆真（AND）
1　烏龍茶包真真入選
2　會員試飲組真假不入選
3　茶壺假真不入選

正常情況下，訪客只看得到烏龍茶包。擋住會員專屬商品的，是 WHERE 裡的 AND members_only = 0。

2.3.3 拼接出來的查詢

網站的程式不會為每個分類各寫一句 SQL，通常用一個樣板，把使用者送來的分類名稱填進去。最直覺的寫法是把字串接起來（字串拼接，string concatenation），例如下面這段程式：

# 不安全的做法
category = request.args["category"]   # 使用者送來的文字
query = ("SELECT * FROM products WHERE category = '"
         + category
         + "' AND members_only = 0")
rows = db.execute(query).fetchall()   # 整串文字交給資料庫

這段程式可以讀成三個動作：request.args["category"] 取出使用者送來的輸入；db.execute(…) 把查詢交給資料庫執行；fetchall() 取回所有結果列。

其中 + 把三段文字接成一長串。拼好之後，資料庫收到的只是一整串文字，分辨不出哪些字是程式設計者寫的、哪些是使用者填的，只會從頭到尾解析。使用者填的文字若含有 SQL 的語法字元（尤其是單引號），資料庫就把它讀成語法。

應用程式把使用者可控制的文字拼進交給資料庫解析的查詢，資料庫把其中一部分讀成語法，這類問題稱為 SQL Injection（SQL 注入）。Path Traversal 越界的是路徑中的 ..，這裡是單引號、OR、註解符號這些語法字元。

2.3.4 從網址追到結果

拿同樣三列資料，跟著一個請求一路走到結果。

正常情況

  1. 瀏覽器請求：GET /products?category=Tea。
  2. 伺服器取出參數 category 的值：Tea。
  3. 拼接：固定前半 + Tea + 固定後半，得到 SELECT * FROM products WHERE category = 'Tea' AND members_only = 0。
  4. 資料庫逐列驗算（見前面的真假表），結果：只有「烏龍茶包」入選。

被操縱的情況

其他都不變，只把 category 的值換成一段含有攻擊者語法片段的文字。方括號代表被換掉的那段輸入。同一個值在四個階段長得不一樣：

階段內容
1　網址裡的傳輸表示/products?category=[百分比編碼後的內容]
2　伺服器解碼後的值[攻擊者加入的語法片段]
3　拼接後的 SQLSELECT * FROM products WHERE category = '[攻擊者加入的語法片段]' AND members_only = 0
4　資料庫實際讀到的條件由片段決定：條件的結構已被改寫，後半的 members_only = 0 可能不再限制結果

階段 1 是網址的百分比編碼（percent-encoding）：參數的值依所用的格式序列化，空白與有特殊作用的字元寫成 % 加兩位十六進位，例如空白是 %20。網址語法本身允許哪些字元，和表單序列化規則是不同層的約定；瀏覽器或工具也常自動處理。編碼只是搬運用的包裝，伺服器收到後先依該格式還原成階段 2 的文字。讓資料庫改變行為的是階段 3、4 裡的語法，%20 這類編碼本身沒有 SQL 的作用。編輯參數時，別把已編碼的字串再編碼一次。

從階段 3 到階段 4，片段可以扮演三種語法角色：

  1. 字串邊界：單引號是文字值的邊界。如果值裡有引號字元，字串就可能比設計者預期的更早結束，後面的字被當成語法。
  2. 條件組合：AND 要求兩邊皆真，OR 只要一邊為真。多加一段用 OR 連接的條件，可以讓篩選對更多列成立。
  3. 註解：SQL 有註解符號，資料庫會忽略它之後同一行的內容。如果註解出現在樣板的固定後半之前，後半（包含 members_only = 0）就不再參與判斷。

假設片段的效果是「條件對每一列都成立，且會員限定的限制失效」，資料庫對三列各驗算一次，結果如下圖：

三列都入選，包含原本只留給會員的「會員試飲組」。第二列的 members_only 為 1，所以多回傳的那一列就是會員專屬商品；若只看頁面上商品變多，並不能確定多出來的是什麼。

2.3.5 什麼情況下成立

  • 上面的情況只在輸入被拼進查詢文字時發生。同一個 category 參數若改用參數化查詢（見後面），就不會成立。
  • 註解寫法、字串引號規則、跳脫字元都因資料庫（MySQL、PostgreSQL、SQL Server、Oracle、SQLite 等）而異，沒有一套寫法適用所有環境。
  • 注入點的位置決定需要什麼語法。這個例子裡的 category 放在單引號之間（字串情境）。如果參數是數字、沒有引號圍住，例如 WHERE id = 後面直接接使用者的值，片段不必處理字串邊界，直接就是語法。注入點也可能在 ORDER BY、登入表單或 HTTP 標頭等地方。
  • 能做到的事受查詢本身與資料庫帳號限制。前面的例子只改變了 WHERE 的篩選結果；能不能進一步讀其他表、更動資料，要看查詢的位置、回應怎麼呈現，以及資料庫帳號的權限，下一節與縱深防禦那一段會談。
  • SQL 錯誤只是線索，不代表漏洞已被利用。

2.3.6 從現象辨認

你看不到伺服器的程式碼，只能從 request 與 response 的差異推測。做法和 HTTP Requests and Sessions 一樣：先記下正常的 request 與 response 當基準，每次只改一個地方，比較差異，最後恢復原樣。這類觀察只在 Lab 或自己擁有、獲授權的系統上做。

  • 哪些參數可能進資料庫：篩選、搜尋、排序、登入帳號、分類、商品 id 等用某個條件查資料的功能都有可能。光看參數名稱無法確定，只能先列為候選。
  • 引號的對照：在已知正常的值裡加入一個在 SQL 中有特殊作用的字元（如引號），若回應變成錯誤頁、空白頁或內容明顯不同，改成 SQL 中表示普通字元的寫法後又恢復正常，就暗示該字元在查詢裡有語法作用。這只是線索：出錯也可能來自輸入檢查、另一層過濾，或應用程式處理不了這個字元。
  • 錯誤訊息：有些網站會把資料庫的錯誤訊息原樣顯示在頁面上，裡面可能出現 SQL 文字片段，或資料庫的名稱與版本；這既是辨認線索，也是資訊揭露的一種。沒看到錯誤訊息也不能放心：錯誤可能被隱藏，查詢照樣被改變。
  • 條件的對照：拿兩種意義相反的輸入比較，一個讓條件保持成立、一個讓條件不成立。若兩者的回應穩定地不同（例如列數、內容），就支持「輸入影響了查詢邏輯」這個假說。比較時排除頁面上本來就會變動的內容（時間、廣告、推薦商品），以固定的欄位（例如商品列數）判斷。面對未知的網站，你看不到內部資料流，還要排除應用程式的其他分支、輸入驗證、快取等解釋，所以要重複對照。
  • 空結果與錯誤要分開：合法的查詢可以回傳零列，找不到商品是成功查詢的一種結果。資料庫報錯也不只語法錯誤一類，還有權限不足、資料轉換或執行時的錯誤，看到錯誤時要讀內容。

2.3.7 防禦手法

有效的防禦

參數化查詢

參數化查詢（parameterized query，也稱 prepared statement）的做法，是把「SQL 的結構」與「要填入的值」分成兩個通道送給資料庫。

# 較安全的做法
category = request.args["category"]
rows = db.execute(
    # 通道一：固定的 SQL，? 是佔位符
    "SELECT * FROM products WHERE category = ? AND members_only = 0",
    # 通道二：要填進 ? 的值
    (category,)
).fetchall()
  • ? 叫佔位符（placeholder），意思是「這裡之後會有一個值」。
  • (category,) 是一組值（Python 稱為 tuple），依序對應各個 ?；結尾那個逗號是 Python 的語法，用來表示「只有一個元素」。
  • 佔位符的寫法依程式語言與資料庫驅動程式（driver）而異，可能是 ?、%s、:name 或 $1；不論哪種，SQL 與值都分開傳入。

為什麼有效

資料庫收到帶佔位符的 SQL，會先解析這句固定的文字，這時查詢的結構（WHERE category = ? AND members_only = 0：兩個條件，用 AND 相連）就決定了。之後送來的值只放進 ? 的位置，當作一個值來比較，不再被解析成語法。所以值裡有沒有引號、關鍵字或註解符號，結構都不會變。

拿前面的例子驗算：把那段攻擊者加入的語法片段當作值，用參數化查詢送出，資料庫要找的是「category 欄的值剛好等於這整串文字」的商品。三列都沒有這個分類，所以回傳 0 列，就是三列結果圖最右欄的空結果。空結果正是預期的：查詢合法地執行了，只是沒有符合的列，而且 members_only = 0 這個條件還在。

判斷是不是參數化，看的是 SQL 與值有沒有分開傳入。先用字串格式化（例如 f-string、% 或 +）把值組進字串，再把整串交給 execute，仍然是拼接。

參數化的限制

  • 佔位符只能代表值。表名、欄位名、排序方向（ASC／DESC）這類結構不能用佔位符。如果功能需要使用者選擇排序欄位，應在程式裡建一份允許清單：使用者送來 price 或 name 這樣的代號，程式用固定的對照把它換成事先寫好的欄位名，不在對照表裡的一律拒絕。
  • 預存程序（stored procedure，事先存在資料庫裡、可以被呼叫的一段程式）裡再拼接字串，一樣有風險。要檢查的是最後有沒有一段由使用者文字拼出的 SQL，與用了什麼技術名詞無關。
  • 程式框架或資料庫工具通常內建參數化；用到它們「直接寫原始 SQL」的出口時，原則相同。

縱深防禦

這些做法不能代替參數化，用途是在仍有漏洞時縮小損害：

  • 最小權限（least privilege）：網站連資料庫的帳號只給它需要的權限。例如只讀的功能使用只能 SELECT、且只能碰必要資料表的帳號；不要用資料庫管理員帳號連線。這樣即使某個查詢被改變，可讀寫的範圍也有上限。
  • 對使用者顯示一般性的錯誤訊息，詳細的 SQL 錯誤只寫入受保護的內部紀錄。
  • 輸入驗證（型別、長度、允許的格式）也要保留。

無效的防禦

把危險字元擋掉是很直覺的反應。這些做法處理的是輸入長什麼樣子，輸入和語法仍然放在同一串文字裡：

做法為什麼不夠
自己跳脫（escape）單引號，例如把 ' 換成 ''只在值被單引號圍住的情境有用。數字情境（WHERE id = 後面直接接值）根本沒有引號，沒有東西可跳脫。不同資料庫與設定對跳脫的規則不同：例如 MySQL 8.4 在沒有啟用 NO_BACKSLASH_ESCAPES 時，反斜線在字串裡有跳脫意義（實際規則取決於連線的 SQL mode，詳見 MySQL 的字串常值說明），單引號替換的邏輯若沒考慮這點就會被繞過；字元編碼的處理也出過問題。要完全正確，得逐個資料庫、逐種情境維護。
黑名單：擋 SQL 關鍵字、註解符號、引號等字樣「壞樣子」列不完：SQL 對大小寫、空白與寫法有很大彈性，同樣的語意有許多種變形。黑名單還會誤傷正常輸入，例如人名 O'Brien 含有單引號，或一件商品名叫 Select 或 Order。
只在瀏覽器端用 JavaScript 檢查輸入瀏覽器端的檢查只約束一般使用者的畫面。request 可以用工具直接改，完全不經過那段檢查，伺服器端必須自己負責。
隱藏 SQL 錯誤訊息能少給攻擊者一些線索，但查詢結構照樣被改動。看不到錯誤時，還有其他方式從回應差異推測，留到 下一節。
依賴網站防火牆（WAF）擋可疑輸入WAF 是額外的一層，能降低風險，但它同樣靠辨識「壞樣子」，限制和黑名單相同，不能取代把程式改對。

2.3.8 小結

  • SELECT … FROM … WHERE … 取出條件為真的列；單引號是文字值的邊界。
  • SQL Injection：程式把使用者文字拼進查詢，資料庫整串解析，把其中一部分讀成語法。
  • Tea 的例子裡條件被改寫，members_only = 0 這類限制失效；改動的位置不同，後果也不同。
  • 手動跳脫與黑名單靠不住。修補用參數化查詢，動態結構用允許清單，最小權限與一般性錯誤訊息當縱深防禦。
  • 空結果是合法的查詢結果；SQL 錯誤只是線索。

PortSwigger Academy 的對應練習（主題頁 SQL injection），只在 Lab 或其他獲明確授權的系統上測試：

  • SQL injection vulnerability in WHERE clause allowing retrieval of hidden data：只改分類參數，用回應的商品清單驗算被改寫的 WHERE 條件。
  • SQL injection vulnerability allowing login bypass（選讀）：同一個機制換到登入檢查的 WHERE 條件。

Tea 分類的例子裡，被改過的查詢結果直接顯示在頁面上，許多網站卻不會把查詢結果印出來。下一節 UNION and Blind SQL Injection 談兩種情況：把另一張表的資料併進同一份結果，以及結果不顯示在頁面上時，從回應的內容、長度或時間差異推測資料庫的判斷。
