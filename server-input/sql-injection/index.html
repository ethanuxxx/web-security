本節模型：shop.example.com 的訪客商品頁

頁面上有一排分類連結，Tea、Teaware、Snacks……你點下 Tea，瀏覽器請求 /products?category=Tea，頁面就只列出茶葉類、開放給訪客的商品。換一個分類，列表跟著換：網站每次收到分類名稱，就向資料庫查一次這個分類的商品，再把結果畫成列表。用 HTTP 看，請求與回應是這樣：

Request
GET /products?category=Tea HTTP/1.1Host: shop.example.com
Response
HTTP/1.1 200 OKContent-Type: text/html烏龍茶包

前兩節的輸入交給檔案系統與上傳處理，這裡的 category 是一段文字，交給資料庫讀。若資料庫把這段文字當成 SQL 語法，而不只是要比對的值，查詢的意思就會改變。

2.3.1 網站如何查詢商品

商品存在資料庫的 products 表裡，下表有三列。

表 2.3.1-1
idnamecategorymembers_only
1烏龍茶包Tea0
2會員試飲組Tea1
3茶壺Teaware0
  • name、category 是文字值，在查詢裡要用單引號圍起來；id、members_only 是數字值，不用引號。
  • members_only 是網站自訂是否會員才可讀的設定值：0 表示任何訪客都能看，1 表示只留給登入的會員。第二列「會員試飲組」雖然分類是 Tea，卻不應該出現在訪客看的頁面上。

要取得分類是 Tea 而且開放給訪客的商品，網站會送出這句 SQL：

-- 正常的查詢
SELECT * FROM products WHERE category = 'Tea' AND members_only = 0

這句查詢從 products 表取出符合 WHERE 後面條件的列，SELECT * 表示取出所有欄。

資料庫逐列檢查兩個條件，AND 要求兩者都為真，三列的結果如下：

表 2.3.1-2
列category = 'Tea'members_only = 0兩者皆真（AND）
1　烏龍茶包真真回傳
2　會員試飲組真假不回傳
3　茶壺假真不回傳

正常情況下，訪客只看得到烏龍茶包。擋住會員專屬商品的，是 WHERE 裡的 AND members_only = 0。

2.3.2 拼接出來的查詢

網站的程式不會為每個分類各寫一句 SQL，通常用一個樣板，把使用者送來的分類名稱填進去。最直覺的寫法是把字串接起來（字串拼接，string concatenation），例如下面這段程式：

# 不安全的做法
category = request.args["category"]   # 使用者送來的文字
query = ("SELECT * FROM products WHERE category = '"
         + category
         + "' AND members_only = 0")
rows = db.execute(query).fetchall()   # 整串文字交給資料庫

這段程式做了三件事：request.args["category"] 取出使用者送來的輸入；+ 把三段文字接成一長串；db.execute(…) 把查詢交給資料庫執行，fetchall() 取回所有結果列。程式裡的雙引號只是 Python 標示文字的範圍。雙引號裡面的單引號是查詢本身的一部分，拼好後就是 SQL 圍住 Tea 的那對引號。拼好之後，資料庫收到的只是一整串文字，分辨不出哪些字是程式設計者寫的、哪些是使用者填的。category 是 Tea 時，這串文字拆開來，是兩個以 AND 相連的條件：

固定前半由五個部分組成：SELECT * 取出所有欄，FROM products 指定資料來源，WHERE 開始篩選條件，category = 比對分類，最後的單引號是字串的開始，使用者的值就接在它後面。

使用者填的文字若帶著 SQL 語法，資料庫照樣從頭讀到尾。把 category 換成 Tea 加上 [結束字串的引號][恆真條件][註解符號]，拼出的查詢讀起來是這樣：

只有 Tea 還是字串值。[結束字串的引號] 是字串邊界：值裡出現引號，字串就在這裡結束，後面的字被讀成語法。[恆真條件] 用 OR 接在 category = 'Tea' 後面，只要一邊為真，整個條件就為真；恆真條件永遠成立，所以每一列都符合。

資料庫讀到 [註解符號]，就忽略它之後同一行的所有內容，固定後半的 ' AND members_only = 0 不再參與判斷，會員限制隨之消失。

應用程式把使用者可控制的文字拼進交給資料庫解析的查詢，資料庫把其中一部分讀成語法，這類問題稱為 SQL Injection（SQL 注入）。

三列都回傳。茶壺的分類是 Teaware，本來不該出現在 Tea 的頁面，它被回傳，是因為恆真條件讓分類條件失效；會員試飲組被回傳，是因為註解掉固定後半，讓會員限制失效。兩列被多回傳，都表示查詢條件已被使用者改寫。

2.3.3 成立條件

Tea 的例子能成立，是因為 category 的值被拼進 SELECT * FROM products WHERE category = '…' 這個查詢文字。值在查詢裡的位置，決定要帶哪些語法：

  • 字串情境：值在單引號之間，像這個例子裡的 category。通常用單引號結束字串，後面的字才被讀成語法。
  • 數字情境：值直接接在 WHERE id = 後面，沒有引號圍住，值裡的語法直接生效。

引號與註解的寫法依資料庫產品（MySQL、PostgreSQL、SQL Server、Oracle、SQLite 等）而異。分類參數只是其中一個來源。只要後端把值拼進查詢，不論值來自登入表單的帳號欄還是 HTTP 標頭，都會被讀成語法；值所在的子句也不限於 WHERE，放在 ORDER BY（決定結果列的排序）後面同樣成立。

影響範圍：Tea 的例子只改變 WHERE 的篩選結果。能不能進一步讀其他表、更動資料，取決於查詢的位置、回應怎麼呈現和資料庫帳號的權限。

2.3.4 判斷查詢是否被改寫

你看不到伺服器的程式碼，只能從回應推斷查詢有沒有被改寫。值得試的參數，是篩選、搜尋、排序、登入帳號、商品 id 這類用來查資料的參數。做法是把同一個請求送兩次，只改 category 的值，先用正常的分類值留下基準。

再把 category 換成 Tea[結束字串的引號][恆真條件][註解符號]，回應從一件商品變成三件：

商品變多，先別下結論。核對三件事：

  • 第一，把 category 換回 Tea 再送一次。回應回到一件，表示多出來的商品由這個值觸發。
  • 第二，看多出來的商品是什麼。其中有「會員試飲組」，它的 members_only 為 1，用任何一般的分類值都查不到。
  • 第三，把 [恆真條件] 換成 [恆假條件] 再送。恆真時回應是三件；恆假時剩兩件 Tea 商品（烏龍茶包、會員試飲組），因為固定後半仍被註解掉。恆真與恆假的件數不同，表示這個條件有作用；「會員試飲組」兩次都出現，表示會員限制已不在查詢裡。
表 2.3.4-1

三項核對都成立，表示 category 的值裡帶的 SQL 語法進了查詢。

另一條線索：只在 Tea 後面加一個引號，頁面若變成錯誤頁或空白頁，甚至印出資料庫的錯誤訊息（見資訊揭露），是引號進了查詢的線索。

2.3.5 小結

  • 判斷輸入有沒有進查詢，先看後端程式碼裡組查詢的那一行：使用者的值是接在查詢文字裡，還是另外傳入。
  • 被拼進查詢的使用者輸入若帶 SQL 語法，能結束字串、接上用 OR 連接的條件、註解掉固定後半，使 members_only = 0 失效。確認靠對照：同一個請求只改 category 的值，換回原值就恢復，多出來的是會員專屬商品，條件成立與不成立的件數穩定不同。
  • 資料庫收到的是一整串文字，無從分辨哪一段來自使用者，哪些字是語法由它自己決定。

PortSwigger Academy 的對應練習（主題頁 SQL injection）：

  • SQL injection vulnerability in WHERE clause allowing retrieval of hidden data：分類頁的回應多出本來看不到的商品。
  • SQL injection vulnerability allowing login bypass：同樣的改寫用在登入檢查的 WHERE 條件，驗證不再擋人。

各資料庫的字串串接、註解、版本查詢等語法對照，可自行參閱 PortSwigger 的 SQL injection cheat sheet。

Tea 分類的例子裡，被改過的查詢結果直接顯示在頁面上，但有些網站的頁面不顯示查詢結果。下一節 UNION, Blind, and NoSQL Injection 先看怎麼用 UNION 把另一張表的資料併進同一份結果，再看結果不顯示時，如何從回應的內容、錯誤或時間差異推測資料庫的判斷。最後換成以 JSON 文件存資料的資料庫，看同樣的資料與查詢混淆如何發生在資料結構裡。
