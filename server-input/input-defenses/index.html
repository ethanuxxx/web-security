這兩類注入的共同問題是：值交到下游元件手上時，元件把其中一段讀成語法。

2.6.1 值要保持資料的身分

查詢和命令都有兩部分。結構是程式事先寫好的骨架：SQL 的 SELECT ... WHERE、命令的程式名稱與參數位置。值是使用者給的字串。防禦的做法是把兩者分開交給下游元件，元件知道哪個是結構、哪個是值，值裡的內容再像語法，也只是值。

反過來，結構和值被接成同一串文字再交出，元件拿到的只有文字，沒有哪一段來自使用者的標記，它只能自己判斷哪些字是語法。檢查若只做在瀏覽器畫面端，你用 Burp Suite 改掉請求就繞過了；檢查若在框架還原 URL 編碼之前做，檢查看到的和元件最後收到的也會不同。這兩種都沒有改變值與語法混在一起的事實。

2.6.2 資料庫查詢

參數化查詢

參數化查詢（parameterized query，也稱 prepared statement）把「SQL 的結構」與「要填入的值」分成兩個通道交出：結構是一句固定的 SQL，值要出現的位置留一個佔位符（placeholder，意思是「這裡之後會有一個值」）。

沿用 2.3 的 products 表：欄位是 id、name、category、members_only，三列分別是烏龍茶包（Tea，0）、會員試飲組（Tea，1）、茶壺（Teaware，0），members_only 為 0 表示訪客看得到，1 表示只留給會員。固定的查詢是 category = ? AND members_only = 0，兩個條件用 AND 相連。值裡有沒有引號、OR 或註解符號，結構都不會變。

把 Tea[結束字串的引號][恆真條件][註解符號] 整串當作 category 的值送出，資料庫要找的是 category 欄剛好等於這整串文字的商品。三列都沒有這個分類，所以回傳 0 列，而且 members_only = 0 這個條件還在：

2.4 的 UNION 也是同樣的結果。沿用 2.4 的例子：正常是查 products 中 Gifts 分類的商品，[UNION 查詢] 要另外讀 users 的 username、login_count。拼接時，同一個 category 值改變了查詢的結構；參數化時，整串只拿來和 category 比對，users 的資料不會出現：

你看不到後端程式碼，但有時能拿到原始碼或在程式碼審查時看到。判斷是不是參數化，看值是在交給 execute 之前就被組進字串，還是作為另一個參數交出：

# f-string 把值塞進字串：拼接
db.execute(f"SELECT * FROM products WHERE category = '{category}' "
           "AND members_only = 0")
# % 格式化把值塞進字串：拼接
db.execute("SELECT * FROM products WHERE category = '%s' "
           "AND members_only = 0" % category)
# 值放在第二個參數：參數化
db.execute("SELECT * FROM products WHERE category = ? "
           "AND members_only = 0", (category,))

網站沒有參數化時，常見的替代做法是自己跳脫引號，或只擋 UNION 這類關鍵字。前者只在值被單引號圍住時有意義，數字情境沒有引號可跳脫；後者擋不到 blind 的是非條件。OWASP 把跳脫列為不建議採用，主要防禦是參數化。

網站防火牆（WAF）也不能取代參數化。接收 XML 的端點若先由 WAF 檢查文字，再由 XML parser 還原實體，兩者讀到的內容不同，請求就可能繞過檢查，後端拼接查詢的程式並沒有改。請求被 WAF 擋下時，換個編碼再送一次，看回應是擋下的頁面還是後端的回應，記錄下來再下結論。

表名、欄名與排序用允許清單

佔位符只能代表值，表名、欄位名、排序方向（ASC／DESC）這類結構不能用佔位符。功能讓使用者選排序欄位時，網站會用固定的對照把你送來的代號換成事先寫好的欄位名。你送出對照表之外的代號，會被拒絕。

允許清單（allow-list）列出明確接受的值，其餘拒絕。它比黑名單可靠，因為黑名單要列出所有壞寫法，而 SQL 對大小寫與空白很有彈性，同一個意思有許多種寫法，列不完。黑名單還會誤傷正常輸入，例如人名 O'Brien 含有單引號，或一件商品名叫 Select 或 Order。

NoSQL 要檢查值的型別

NoSQL 的問題是值變成了結構：應該是字串的欄位，收到帶運算子的物件。網站若做了 schema 驗證：只收預期的鍵，值必須是預期的型別。你把應該是字串的欄位換成物件，請求會直接被拒絕，運算子物件進不了查詢。只封鎖某一個運算子則不夠，運算子有很多個，換一個照樣改變條件。

2.6.3 shell 命令

沿用 2.5 的例子：Linux 上的 /bin/sh 執行 demo-shipping 出貨報表，兩個參數是日期與倉庫。shell 的情況和資料庫相同，只是沒有佔位符：最可靠的做法是讓值根本不進入命令字串。報表若能在應用程式內，用函式庫（library）的 API 直接算出來，值就只是函式的參數，不會再交給 shell。必須啟動外部程式時，網站不組字串，而是把程式名稱、日期與倉庫分成三個獨立的元素，直接交給作業系統（例如 Python 的 subprocess.run 收到 list 而不設 shell=True）。這和參數化查詢是同一個原則：結構與值分開交出。

經過 shell 時，應用程式交出一整段字串，由 shell 依語法切，值的內容能改變切法。分開傳入時，應用程式自己交出切好的三個獨立元素。中間沒有元件再切，值裡的內容加不出第四個：

此處的報表程式把整段值當成一個倉庫名稱。沒有倉庫叫這整串名稱，報表程式查不到這個倉庫，附加的命令也不會被執行。

網站若只刪除少數看似危險的字元，漏掉任何一個 shell 語法符號，那個符號就能把字串切開。自己替值加引號也不夠：只在值外面包一對引號、沒有處理值裡本身的引號時，值裡的引號會提早結束這對引號。

引號只圍住 warehouse-a，後面的 [命令分隔符號][附加的命令] 已經在引號外面，shell 照常切開；[註解符號] 把程式自己加的結尾引號一起註解掉，整條命令仍然合法。

允許清單在這裡也要用。不經過 shell 時，demo-shipping 自己仍會讀參數，例如把開頭是 - 的值當成選項。所以日期要符合格式，倉庫要在清單內，才交給 demo-shipping。

2.6.4 縮小損害

最小權限（least privilege）不能阻止值被讀成語法，只縮小出事後的範圍。網站連資料庫的帳號只給需要的權限，例如只讀的功能用只能 SELECT、且只能碰必要資料表的帳號；執行外部命令的服務帳號只給報表需要的權限。注入成功時，你能讀寫、能動到的範圍因此有上限。

錯誤頁只說「發生錯誤」，不帶資料庫的錯誤內文或堆疊，你就不會從錯誤頁讀到表名與查詢結構。但這只改變你看到什麼：頁面內容或回應時間的差異仍會洩漏條件的真假，blind 的判斷照樣能做。shell 也一樣，隱藏命令的輸出，附加的命令照樣執行。

2.6.5 小結

  • 防禦的目標是讓值一路保持資料的身分：結構由程式固定，值另外交出，元件收到時就知道哪個是哪個。
  • 資料庫要用參數化查詢；表名、欄名與排序這類結構用允許清單；NoSQL 檢查值的型別與預期的鍵。shell 要不啟動 shell，或把值分開傳入，並搭配允許清單。
  • 跳脫、黑名單、加引號、WAF、隱藏錯誤這類做法都沒有把值和語法分開，只改變輸入的長相或你看到的東西。
  • 最小權限與一般性錯誤訊息只縮小損害，前者限制能動的範圍，後者只讓錯誤內文不帶細節。

PortSwigger Academy 的對應練習（主題頁 SQL injection）：

  • Blind SQL injection with time delays：隱藏錯誤與頁面內容之後，回應時間的差異仍透露條件的真假。
  • SQL injection with filter bypass via XML encoding：WAF 擋下明顯的請求，換一種編碼形式就可能通過。
