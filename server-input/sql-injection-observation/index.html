本節模型：shop.example.com 的商品分類頁

你點選「Gifts」，瀏覽器把分類值放在請求的網址裡，網站把這個值接進 WHERE 條件交給資料庫，再把查回來的商品畫成列表。換成別的分類，列表跟著換。上一節 SQL Injection Basics 說過，使用者的輸入若被當成查詢語法而不是單純的資料，查詢的意思就會改變。

實際能觀察到什麼，取決於頁面怎麼處理查詢結果。頁面把結果印出來時，一個被改變的查詢可以讓不屬於列表的資料混進頁面；頁面完全不印結果時，查詢成功與沒成功的差別本身也會透露資料庫裡的事。

2.4.1 查詢、資料與語法

這裡沿用上一節的詞彙。關聯式資料庫把資料放在表（table）裡，每一列（row）是一筆記錄，每一欄（column）是一種屬性，例如商品的名稱、價格、分類。SELECT 指定要取哪些欄，FROM 指定從哪張表，WHERE 指定哪些列符合條件。查詢裡有語法（告訴資料庫要做什麼）與資料（被拿來比較的值）兩種東西：安全的程式把兩者分開；有問題的程式把使用者輸入直接接在查詢文字裡，資料庫便可能把輸入的一部分當成語法。修補方法是參數化查詢（parameterized query，也稱 prepared statement）：查詢的結構先固定，使用者的值另外傳入，只被當成資料。

例子都來自同一家商店，但這一節的清單是商店的另一個頁面，不是上一節 Tea 的那三列：商品表另有 Gifts 分類，還有一張 clearance_items 特價表。商品表 products 有 name、price 與分類欄 category，網站用使用者選的分類組出查詢：

-- 使用者選了 Gifts，網站組出的正常查詢
SELECT name, price FROM products WHERE category = 'Gifts'

2.4.2 用 UNION 合併結果

UNION 在正常 SQL 裡做什麼

UNION 是 SQL 的一個正當功能：把兩個 SELECT 的結果上下接在一起，變成一張結果表。例如商店想在同一份清單上同時列出一般商品與特價商品，可以寫成：

-- 兩個正常查詢合併，各自回傳 (name, price) 兩欄
SELECT name, price FROM products WHERE category = 'Gifts'
UNION
SELECT name, price FROM clearance_items

下圖是合併的結果：第一個查詢回傳 2 列，第二個回傳 1 列，合併後得到 3 列。列數可以不同，但每一列的格子數（欄數）必須一樣。

兩個查詢必須相容

欄數必須一致，因為結果是一張表，每一列都要有相同數量的格子，才排得成整齊的欄。除了欄數，對應位置的欄位型別也要相容：名稱欄對名稱欄，價格欄對價格欄。第一個查詢的第一欄是文字，第二個查詢的第一欄就必須是能當文字看待的東西。「相容」的標準因資料庫產品而異，有的會自動轉型，有的會直接報錯。

UNION 會把完全重複的列合併成一列，UNION ALL 則全部保留。資料庫裡另有一個特殊值 NULL，意思是「沒有值」，不是空字串，也不是 0；它可以放在多數型別的格子裡，所以常用來表示「這格先不填」。用 NULL 填格子可以讓欄數對上，但那一欄未必能放文字值，應用程式也未必會把它畫出來；有的應用程式遇到 NULL 就會出錯。

額外的列怎麼出現在頁面上

商品頁的程式不在乎一列資料從哪裡來，它拿到一張結果表，就把每一列的名稱欄和價格欄畫成頁面上的一個商品。加上上一節的弱點，過程是這樣：

  1. 使用者輸入被放進 WHERE 條件，而且沒有被當成純資料處理。
  2. 被當成語法的那一段輸入，可以讓原本的查詢後面再多接一個 SELECT。
  3. 資料庫忠實地把兩個結果表合併。只要欄數和型別相容，合併就成功。
  4. 商品頁拿到的是合併後的表，於是額外那個查詢取回的列，被畫在商品列表裡，看起來就像普通商品。

被操縱的查詢長這樣，方括號代表被換掉的那段輸入：

-- 只表達形狀
SELECT name, price FROM products
WHERE category = '[使用者輸入的值，其中含
                  攻擊者附加的查詢片段]'

這個片段先讓原本的條件在「該結束的地方」結束，再接上另一個 SELECT，於是原本的查詢和附加的查詢被同一個 UNION 串起來，結果合成一張。附加的查詢可以指向這個資料庫帳號讀得到的任何表，不必是商品表，所以這類問題的影響取決於資料庫帳號的權限（見後面的「修補」）。

先弄清欄數與型別

附加的查詢要成功合併，就必須與原查詢欄數相同、型別相容。不知道原查詢有幾欄、各欄是什麼型別的人，一開始只能從回應的變化推測：

表 2.4.2-1
情形頁面可能的樣子代表什麼

欄數、型別與應用程式的處理方式都相容頁面可能回到基準的樣子，或多出額外的列欄數相容的證據之一，但不是唯一的解釋

整個過程看不到資料，原查詢的結構是從回應的差異一步步推出來的，所以每一步都要記下當時的前提。

欄數相容之後，能讀哪些表還要看資料庫帳號的權限。附加的查詢即使成功，頁面也可能只畫出其中某幾欄（例如只畫文字欄），其餘欄看不到。

2.4.3 看不到資料時的訊號

什麼叫 blind

前面的情況，被改變的查詢結果會畫在頁面上。很多網站卻根本不顯示查詢結果，例如登入檢查只回「成功／失敗」，或網站在背景記錄瀏覽紀錄，用了查詢卻從不印出結果。此時即使查詢被改變，頁面上也不會出現多餘的列。這種情況稱為盲注（blind SQL injection）。

不過查詢仍在資料庫裡執行，結果仍會影響網站之後的行為。觀察者只要看得到行為上的任何差異，那個差異就帶著一個「是或否」的答案。常見的差異有三種：

  • 內容差異：條件成立時頁面多一行提示文字，不成立時沒有。
  • 錯誤差異：條件成立時正常回應，不成立時（或相反）資料庫報錯，網站回一個錯誤頁。
  • 時間差異：條件成立時多花幾秒才回應，不成立時立刻回應。

另外還有一類：讓資料庫自己對外發出一個網路請求（稱為 out-of-band，帶外通道），結果不經過原本的回應，而是從別的管道觀察。這需要資料庫具備發出網路請求的功能，網路環境也允許它對外連線。

一次只問一個是非題

先不看 SQL。想像一位朋友心裡想了一個 1 到 100 的整數，只肯回答「是」或「不是」。你問不出數字本身，但可以問它是否大於 50。答案是「是」，就知道在 51 到 100；再問是否大於 75，答案是「不是」，範圍縮成 51 到 75。每問一題，候選範圍減半，最多約 7 題就能鎖定任何一個 1 到 100 的數字。

blind 用的是同一個想法：資料庫裡有一個你看不到的值，無法直接要它，但可以反覆問關於它的是非題，從網站行為的差異讀出答案。代價是慢：每次請求只得到一位元（是或否）的資訊，需要很多次請求。因此這類活動會在網站的紀錄裡留下明顯的規律：同一個功能被大量重複請求，每次只差一點點。

是非答案怎麼洩漏

下圖是資料流：條件在資料庫裡成立或不成立，應用程式據此走不同分支，分支的差異變成觀察者看到的訊號。資料本身不會出現在回應裡。

用控制組排除其他解釋

以結帳頁的優惠碼欄位為例。網址帶著 coupon 參數，網站在資料庫查這個優惠碼是否存在；存在就在訂單摘要上方多顯示一行「已套用優惠」，不存在則什麼都不顯示。查詢結果本身從不印出，只決定這一行。

假設把 coupon 的值改成別的內容後，這一行消失了。消失可以有好幾種原因，每一種都要有對應的對照才能排除：

  • 解釋一：改動的內容讓查詢的條件變成不成立。
  • 解釋二：改動的內容讓查詢壞掉，網站遇到錯誤就當作沒有優惠碼，條件的真假根本沒有被評估。
  • 解釋三：優惠碼剛好過期、被其他人用完，或回應來自不同的快取，與這次改動無關。

因此對照分成五列：兩個基準、真條件、假條件，最後回到基準。[已知為真的條件] 是事先知道會成立的條件，[已知為假的條件] 是事先知道不會成立的條件：

表 2.4.3-1
組別送出的優惠碼欄位摘要上方用來檢驗
基準：有效資料庫裡存在的優惠碼已套用優惠確認這個功能在正常時顯示什麼
基準：無效不存在的優惠碼（沒有這一行）確認「查不到」時顯示什麼
真條件有效優惠碼加上 [已知為真的條件]已套用優惠與基準有效相同，表示改動後的查詢仍然執行，沒有因語法出錯而中斷（降低解釋二的可能性）。後端若有紀錄，可以確認有沒有錯誤、查詢有沒有執行
假條件有效優惠碼加上 [已知為假的條件]（沒有這一行）其他輸入都沒變，只有條件的真假不同，結果卻不同，支持差異來自條件的真假（解釋一）
恢復原本的有效優惠碼已套用優惠回到基準，表示優惠碼本身沒有過期，降低偶發變化的可能性。單次恢復排除不了快取或其他分支，要交錯重複基準與對照

真條件與假條件這兩列最能說明問題：兩者只差條件的真假，回應穩定地不同，這個差異才算可信的訊號。輸入驗證、另一層過濾或快取也會造成同樣的現象，所以每次對照都讓其他輸入與初始狀態保持一致，並交錯重複基準與對照。有了這個基礎，換成想問的條件，得到的差異才有意義。

時間訊號要重複量測

假設條件成立時，資料庫刻意多等幾秒再回應。時間差異比內容或錯誤差異更容易受干擾：

  • 網路本來就忽快忽慢，單次請求慢了幾秒，可能只是網路或伺服器忙碌。
  • 較可靠的做法是交錯重複量測：對照組與實驗組輪流各送多次，比較兩組的分布是否穩定地分開。
  • 差異要足夠大。如果延遲只有幾十毫秒，很容易被雜訊淹沒。

資料庫產品的差異

不同的資料庫產品（例如 MySQL、PostgreSQL、Oracle、Microsoft SQL Server、SQLite）在字串寫法、註解寫法、型別轉換、讓查詢延遲的函式，以及出錯的行為上都有差異。推論的思路通用，細節要依實際的資料庫決定。

2.4.4 NoSQL injection

到目前為止談的都是關聯式資料庫。但很多網站使用另一類資料庫，統稱 NoSQL（意思是「不只是 SQL」）。它們不一定用表和列，也不一定用 SQL 語言。其中常見的一種把資料存成 JSON 文件，要理解這類資料庫上的問題，得先看懂 JSON。

JSON 的最小模型

JSON（JavaScript Object Notation）是一種用純文字表示結構化資料的格式，網站之間傳資料時很常用。這裡會用到四個詞：

  • 鍵（key）：資料的名稱，一定是用雙引號包起來的字串，例如 "username"。
  • 值（value）：鍵對應的內容，寫在冒號後面，例如 "alice"。
  • 字串（string）：雙引號包起來的文字。值也可以是數字（25）、真或假（true）。
  • 物件（object）：用大括號 { } 包起來的一組「鍵：值」。物件的值可以又是一個物件，這叫巢狀（nested）。

一份正常的登入請求，網站收到的 JSON 內容如下：

{
  "username": "alice",
  "password": "demo-password"
}

這份資料有兩個鍵，兩個值都是字串。資料庫裡可能存了這樣的使用者文件（省略了密碼欄；真實網站存的是密碼雜湊，不存明文）：

{ "username": "alice", "role": "user" }
{ "username": "bob",   "role": "user" }
{ "username": "carol", "role": "admin" }

應用程式拿到 "alice" 這個字串，要在這些文件裡找人時，查詢用白話說是：「找出 username 等於 alice 的文件」。三份文件中只有第一份符合。

字串變成了結構

在這類資料庫中，查詢本身通常也是用 JSON 物件寫成的，一個「鍵：值」代表「欄位等於這個值」。許多這類資料庫還允許把「值」的位置換成一個帶有運算子的物件：鍵是運算子的名稱（通常以特殊符號開頭），表達「不等於」「大於」「符合某個模式」這類比較，不再只是「等於」。

風險就出現在應用程式和資料庫之間的交接點：

  1. 應用程式預期 username 欄位是個字串，例如 "alice"。
  2. 但 JSON 的語法允許欄位的值是任何東西，包括巢狀物件。若請求裡送來的 username 是一個帶有查詢運算子的物件，而應用程式不檢查型別，就會把整個值原封不動交給資料庫。
  3. 資料庫把這個物件解讀成查詢條件的一部分，而非要比對的文字。條件的意思從「username 等於 alice」，變成像「username 不等於某個指定的值」這樣的另一種條件。
  4. 「不等於某個值」會符合所有不是那個值的文件，通常就是使用者本來碰不到的許多人。

用上面三份文件算一次。假設條件用白話寫成「username 不等於 demo-absent」，而三份文件的名稱都不是 demo-absent：

表 2.4.4-1
文件username是否符合「不等於 demo-absent」
第一份alice符合
第二份bob符合
第三份carol符合

三份全都符合。如果比較的值剛好是 alice，第一份就不符合，只剩第二、三份。符合的文件有哪些，取決於被比較的值。

和 SQL 對照：SQL 的混淆發生在文字裡（引號和關鍵字），這類 NoSQL 的混淆發生在資料的結構裡（字串變成物件）。兩者的共同點是使用者控制的內容跨過了「資料」和「查詢語法」的邊界。

成立的條件

  • 應用程式得把請求中的 JSON 值不經型別檢查就放進查詢。先確認 username 是字串，這條路就走不通。
  • 「運算子」的意義由資料庫（和它的驅動程式）決定，不同的 NoSQL 系統語法不同，一個系統的結論不能套到另一個上。這裡的模型以 MongoDB 風格的查詢為例，其他產品需查各自的文件。
  • 光有這種結構上的差異，不能證明漏洞存在，也不能證明登入被繞過。登入流程通常還要比對密碼等其他條件，是否有影響，要看實際的程式怎麼寫。
  • NoSQL 也有其他類型的問題（例如在伺服器端執行 JavaScript 條件的查詢），屬於進階主題。

2.4.6 防禦手法

SQL 改用參數化查詢

UNION 與 blind 是同一個根本問題的不同表現：使用者的輸入被當成語法。兩者的修補也相同：不要用字串相接組查詢，改用參數化查詢。

# 不安全的做法（把輸入接進查詢文字）
query = "SELECT name, price FROM products WHERE category = '" + category + "'"

# 參數化的做法（結構固定，值另外傳入）
cursor.execute(
    "SELECT name, price FROM products WHERE category = ?",
    (category,)
)

資料庫先把查詢結構（語法）固定下來，值之後才以「資料」的身分傳入，無論值裡寫了什麼，都不會被重新解讀為語法。UNION 無從附加，blind 的條件也改不了。

參數化只保護「值」的位置。表名、欄名、排序方向這類結構性的片段不能用參數傳入；功能若需要讓使用者選擇，就用允許清單（只接受事先列好的幾個選項）對應到固定的查詢片段。

NoSQL 的修補

  • 強制型別：username 必須是字串。收到物件、陣列或其他型別就直接拒絕。
  • 用 schema 驗證輸入：schema（綱要）是事先寫好的規格，說明允許哪些欄位、每個欄位是什麼型別、長度或格式有什麼限制。不符合規格的請求在進入查詢之前就被擋掉。
  • 不要把整個請求物件直接當查詢：由伺服器自己寫出固定的查詢結構，只把驗證過的單一值填進去，而不是把使用者送來的物件整份交給資料庫。
  • 不要只封鎖某一個運算子名稱：運算子不只一個，也會隨資料庫版本增加。允許清單加上型別檢查才穩定。

寫成程式是這樣：

# 先檢查型別，再放進固定結構的查詢
username = request.json.get("username")
if not isinstance(username, str):
    return error("invalid request")       # 一般性的錯誤，不洩漏細節
user = users.find_one({"username": username})   # 結構由伺服器決定

這段程式分三步：取出請求中的 username；用 isinstance 確認它是字串，不是就拒絕；最後才放進由伺服器寫死的查詢結構。

其他防線（縱深防禦）

  • 最小權限（least privilege）：網站使用的資料庫帳號只給必要的權限。商品頁只需要讀商品表，就不該能讀使用者表。這樣即使輸入被當成語法，能影響的範圍也小。
  • 一般性的錯誤訊息：對外只回「發生錯誤」，詳細內容寫進有存取控制的內部紀錄。這會讓依賴錯誤差異的觀察更困難，但只是第二道防線，不能取代參數化，因為 blind 的訊號也可以來自內容或時間。
  • 監控與限制請求頻率：blind 需要大量重複請求，異常的頻率是可偵測的特徵。

2.4.7 小結

  • UNION 把兩個查詢的結果合成一張表；欄數必須相同、對應欄型別必須相容。商品頁不在意列從哪裡來，所以被合併進來的額外列會被畫在頁面上。
  • 頁面不顯示結果時，仍可能有內容、錯誤或時間上的差異；每次差異帶來一個是非答案，反覆詢問就能推論出看不到的事實，代價是需要大量請求。
  • NoSQL 的問題是同一個想法的結構版：應該是字串的值，變成了帶運算子的物件，使條件的意義改變。
  • 同一個現象可以有多種解釋；錯誤、500、變慢單獨都不構成證明，要有對照組才能判斷。
  • 修補在源頭：SQL 用參數化查詢；NoSQL 強制型別、用 schema 驗證、不直傳請求物件；再加上最小權限與一般性的錯誤訊息。

PortSwigger Academy 的對應練習（主題頁 SQL injection），只在 Lab 或其他獲明確授權的系統上測試：

  • SQL injection UNION attacks，判斷欄數的 Lab：從回應的差異判斷哪一種能支持「欄數相容」。
  • Blind SQL injection，條件回應 Lab（選讀）：先建立明知為真與明知為假兩種基準，找出穩定的回應差異。
  • NoSQL injection，NoSQL 運算子 Lab（選讀）：值的型別變成結構之後，看回應的哪一部分顯示條件的意義已經不同。

SQL injection 裡解讀輸入的是資料庫。下一節 OS Command Injection 把解讀者換成作業系統上的 shell：網站有時為了完成功能，把使用者的輸入放進一條交給 shell 執行的命令；輸入一旦被 shell 當成命令的一部分，改變的就是主機上要執行的程式。
