本節模型：shop.example.com 的商品分類頁

你點選「Gifts」，瀏覽器把分類值放在請求的網址裡，網站把這個值接進 WHERE 條件交給資料庫，再把查回來的商品畫成列表。換成別的分類，列表跟著換。

上一節 SQL Injection Basics 的輸入進了查詢字串，資料庫把其中一段讀成 SQL 語法。這一節看同一個問題的三個變化。頁面把結果印出來時，被改寫的查詢可以用 UNION 把別張表的資料併進同一份結果。頁面不印結果時，查詢成功與否的差別本身會透露資料庫裡的事，這種 blind 的情況，要從回應的差異推斷。資料庫換成存 JSON 文件的 NoSQL 時，改的是值的型別：應該是字串的值，變成了帶運算子的物件。

2.4.2 結果不顯示時如何得到答案

UNION 的情況，被改變的查詢結果會畫在頁面上。很多網站卻不顯示查詢結果，例如登入檢查只回「成功／失敗」，或網站在背景記錄瀏覽紀錄，用了查詢卻從不印出結果。查詢被改了、結果卻不顯示在頁面上的 SQL injection，稱為盲注（blind SQL injection）。

查詢仍在資料庫裡執行，結果仍會影響網站之後的行為。只要看得到行為上的任何差異，那個差異就帶著一個「是或否」的答案。這一段改用結帳頁的優惠碼欄位當模型：網址帶著 coupon 參數，網站在資料庫查這個優惠碼是否存在；存在就在訂單摘要上方多顯示一行「已套用優惠」，不存在則什麼都不顯示。查詢結果本身從不印出，只決定這一行。優惠碼表 coupons 只有一列：

表 2.4.2-1
codediscount
SAVE1010

先送 SAVE10，摘要上方有「已套用優惠」。再在 SAVE10 後面接 [已知為真的條件]（事先知道會成立的條件），這一行還在；接 [已知為假的條件]（事先知道不會成立的條件），這一行消失。優惠碼沒變，只有條件的真假不同，回應就不同。

條件接在 SAVE10 後面，是因為你不知道其他優惠碼，只能拿已知存在的當基準。

blind 的推論方式，可以用猜數字來類比：一位朋友心裡想了一個 1 到 100 的整數，只肯回答「是」或「不是」。你問不出數字本身，但可以問它是否大於 50。答案是「是」，就知道在 51 到 100；再問是否大於 75，答案是「不是」，範圍縮成 51 到 75。每問一題，候選範圍減半，最多約 7 題就能鎖定任何一個 1 到 100 的數字。

blind 用的是同一個想法：資料庫裡有一個你看不到的值，不能直接要，但可以反覆問關於它的是非題。一次請求只能問一題，因為回應只有「出現」和「沒出現」兩種。代價是慢，要很多次請求。

條件在資料庫裡成立或不成立，應用程式據此走不同分支，分支的差異就是你看到的訊號。優惠碼的例子裡有三種，見下圖。

另外還有一類：讓資料庫自己對外發出一個網路請求（稱為 out-of-band，帶外通道），結果不經過原本的回應，而是從別的管道觀察。這需要資料庫具備發出網路請求的功能，網路環境也允許它對外連線。

2.4.3 NoSQL 的值如何變成查詢結構

到目前為止談的都是關聯式資料庫。但很多網站使用另一類資料庫，統稱 NoSQL（意思是「不只是 SQL」）。它們不一定用表和列，也不一定用 SQL 語言。其中常見的一種把資料存成 JSON 文件，查詢本身也寫成 JSON 物件。

網站的帳號查詢功能收到的請求內容是：

{ "username": "alice" }

資料庫裡可能存了這樣的使用者文件：

{ "username": "alice", "role": "user" }
{ "username": "bob",   "role": "user" }
{ "username": "carol", "role": "admin" }

應用程式拿到 "alice" 這個字串，查詢用白話說是：「找出 username 等於 alice 的文件」。三份文件中只有第一份符合。

JSON 對值沒有限制，字串的位置放物件也合法。把 username 換成帶運算子的物件再送一次，筆數從一變成三：

正常的 username 值
Request
POST /api/users/lookup HTTP/1.1Host: shop.example.comContent-Type: application/json{"username": "alice"}
Response
HTTP/1.1 200 OKContent-Type: application/json{"found": 1}
帶運算子物件的 username 值
Request
POST /api/users/lookup HTTP/1.1Host: shop.example.comContent-Type: application/json{"username": [帶運算子的物件]}
Response
HTTP/1.1 200 OKContent-Type: application/json{"found": 3}

筆數為什麼變了，要看查詢怎麼寫。

查詢裡一個「鍵：值」代表「欄位等於這個值」。例如商品頁要列出已封存的商品，查詢寫成：

{ "status": "archived" }

要列出還沒封存的商品，條件是「不等於」，值的位置要換成一個物件：

{ "status": { "$ne": "archived" } }
  • 外層的鍵 status 是欄位。
  • 值不再是字串 "archived"，而是一個物件。
  • 物件的鍵 $ne 是運算子，以 $ 開頭（MongoDB 的寫法），ne 是 not equal，表示「不等於」。
  • 物件的值 "archived" 是比較的對象。

同一個欄位，值是字串時表示「等於」，值是這種物件時表示別的比較。

帳號查詢把請求裡的 username 放進查詢，原本就是上面那種「等於」。如果 username 的位置收到同樣形狀的物件，運算子是 $ne，物件的值是某個字串，條件就從「username 等於 alice」變成「username 不等於物件裡的那個值」。過程是這樣：應用程式預期 username 是字串，沒有檢查型別，就把整個值原封不動交給資料庫，資料庫把物件讀成條件的一部分。這會符合所有不是那個值的文件，包含你本來碰不到的帳號。

用這三份文件算一次。假設物件裡的值是 demo-absent，條件就是「username 不等於 demo-absent」，而三份文件的名稱都不是 demo-absent：

表 2.4.3-1
文件username是否符合「不等於 demo-absent」
第一份alice符合
第二份bob符合
第三份carol符合

三份全都符合。比較的值若是 alice，第一份不符合，只剩兩份。符合哪些文件，取決於被比較的值。

SQL injection 改的是字串裡的語法，這類 NoSQL injection 改的是值的型別。兩者的共同點，是你控制的內容跨過了「資料」和「查詢語法」的邊界。

2.4.4 成立條件

UNION、blind 與 NoSQL 的共同前提，是你的輸入跨過了資料與查詢的邊界。各自還要多幾個條件：

  • UNION：附加的 SELECT 必須與原 SELECT 欄數相同、對應欄型別相容；要從頁面讀到資料，網站還得顯示含有該資料的結果欄。只畫其他欄，或處理不了 NULL、轉型後的值時，合併成功也可能看不到。
  • blind：回應要有可觀察的差異。
  • NoSQL：伺服器要把請求解析成物件（JSON 本體，或表單參數被巢狀語法解析成物件），而且應用程式把這些值不經型別檢查就放進查詢。username 若是字串，這條路就走不通。

寫法依資料庫產品而異：字串、註解、型別轉換與讓資料庫延遲回應的寫法不同，NoSQL 運算子的意義也由資料庫與它的驅動程式決定。這裡的 NoSQL 模型以 MongoDB 風格的查詢為例，其他產品需查各自的文件。

影響範圍：SQL 的附加查詢能讀哪些表、哪些欄，由網站連資料庫所用的帳號決定。

2.4.5 判斷查詢是否被改寫

你看不到後端組出的查詢，只能從回應推斷查詢有沒有被改寫。做法是把同一個請求只改一個值送兩次，先用正常的值留下基準。三種情況各有不同的線索：頁面有畫出結果時看列，NoSQL 看回應裡的筆數，沒有畫出結果時看對照與時間。回應變了，要排除驗證、快取等其他原因，才算查詢條件的訊號。

UNION 先在 Gifts 後面加一個引號。頁面若變成錯誤頁或空白頁，甚至印出資料庫的錯誤訊息（見資訊揭露），就是引號進了查詢的線索。看到 500，先換回原值再送一次，確認是這個值造成的。

再推測欄數與型別。你一開始不知道原查詢有幾欄、各欄是什麼型別，所以送出欄數不同的 UNION 查詢試探，回應可能是：

表 2.4.5-1
情形頁面可能的樣子代表什麼
欄數不合資料庫報錯，頁面出現錯誤或空白附加的查詢與原查詢的欄數不一致
欄數、型別與應用程式的處理方式都相容頁面回到基準的樣子，或多出額外的列欄數相容
欄數相容，但型別不合，或應用程式處理不了 NULL，或結果沒有被畫出來仍然出現錯誤，或看起來與基準相同單靠這個差異判斷不了欄數，要換個角度再對照

欄數與型別都推出來以後，把 category 換成 UNION 完整例子的值，頁面多出別的列。核對兩件事：

  • 第一，把 category 換回 Gifts 再送一次。頁面回到 Mug 與 Pen 兩列，表示多出來的列由這個值觸發。
  • 第二，把多出來的列逐列對上 users 表：alice／12、bob／4、carol／7 分別對上 username 與 login_count，而這些資料沒有寫在送出的值裡。

兩項核對都成立，表示附加的查詢被合併進結果了。

回頭看 NoSQL 那組 username 請求，核對兩件事：

  • 第一，把 username 換回 "alice" 再送一次。筆數回到一，表示多出來的筆數由這個值觸發。
  • 第二，只改物件裡被比較的帳號名稱，再送一次。筆數隨比較值改變（例如比較值是 alice 時只剩兩份），表示條件由物件決定，而不是回應固定多算了幾筆。

兩項核對都成立，表示 username 的值被當成查詢條件讀，而不是要比對的文字。筆數變化只說明條件變了，不說明登入被繞過；繞過與否要看實際的程式怎麼寫。

blind 要用對照排除其他解釋

優惠碼的查詢結果不印出，你只能從摘要那一行有沒有出現，推斷條件的真假。這一行消失，可能是條件不成立，也可能是改動讓查詢壞掉、優惠碼剛好失效，或回應來自不同的快取。用五組對照分開這些解釋：

表 2.4.5-2
組別送出的 coupon摘要上方檢驗什麼
基準：有效SAVE10已套用優惠功能正常時顯示什麼

blind 的時間差異要重複量測

資料庫可以被要求在條件成立時多等幾秒再回應，回應時間因此帶著條件的真假。不帶延遲條件的請求稱為「對照」，帶延遲條件的請求稱為「實驗」。時間差異比內容或錯誤差異更容易受干擾，量測時要注意三件事：

  • 網路本來就忽快忽慢，單次請求慢了幾秒，常只是網路或伺服器忙碌。
  • 較可靠的做法是交錯重複量測：對照與實驗輪流各送多次，比較兩組的分布是否穩定地分開。
  • 差異要足夠大。如果延遲只有幾十毫秒，很容易被雜訊淹沒。

2.4.6 小結

  • 判斷輸入能不能改變查詢，先看結果出現在哪裡。畫在頁面上，就看有沒有別張表的列被 UNION 併進來；不畫出來，就看內容、錯誤或時間的差異。
  • 確認靠對照：同一個請求只改一個值，真條件與假條件的差異穩定出現，換回原值就消失。時間訊號要重複量測，代價是需要大量請求。
  • NoSQL 的問題是同一個想法的結構版：應該是字串的值變成帶運算子的物件，條件的意義改變。

PortSwigger Academy 的對應練習（主題頁 SQL injection、NoSQL injection）：

  • SQL injection UNION attack, determining the number of columns returned by the query：從回應的差異推出原查詢的欄數，用 UNION 附加的查詢才合併得起來。
  • Blind SQL injection with conditional responses：先建立明知為真與明知為假兩種基準，找出穩定的回應差異。
  • Exploiting NoSQL operator injection to bypass authentication：值的型別變成結構之後，看回應的哪一部分顯示條件的意義已經不同。

SQL injection 裡解讀輸入的是資料庫。下一節 OS Command Injection 把解讀者換成作業系統上的 shell：網站有時為了完成功能，把使用者的輸入放進一條交給 shell 執行的命令；輸入一旦被 shell 當成命令的一部分，改變的就是主機上要執行的程式。
