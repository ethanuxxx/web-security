一個活動網站讓使用者選擇日期與會場，再下載人數摘要。網站可能自己計算，也可能呼叫伺服器上既有的報表程式。後者看起來只是重用功能，卻多了一次交接：使用者在表單填的資料，可能被放進一段作業系統命令。

上一節的解讀者是資料庫，這裡換成作業系統的命令語言。看懂一條正常命令怎麼運作，就能追出資料在哪一步取得了改變命令結構的能力。讀這一節不需要會寫程式，也不必在自己的電腦執行任何命令。

2.5.1 程式在哪裡執行

作業系統（operating system，OS）負責管理電腦的資源與程式執行。儲存在磁碟上的程式，執行時會形成行程（process），即正在運作的程式實例。網站的應用程式同樣在伺服器上運作，也能要求作業系統啟動另一支程式。

程式常需要接收參數（argument），說明要處理哪一天、哪個會場。例如這條命令：

demo-attendance 2026-10-01 hall-a

demo-attendance 是報表程式，後面的日期和 hall-a 是兩個資料參數。整句的意思是「請報表程式查詢這一天、這個會場」。字串（string）是一串文字；應用程式若先把這三段文字接成一個字串，就需要有人解讀哪段是程式、哪段是參數。

命令解讀器（shell）就是理解命令語言的程式。它能辨認程式與參數，也有串接其他命令、連接輸入輸出等語法。透過 shell 執行一段字串，和直接把資料參數交給固定程式，是不同的呼叫方式。不是每個網站都需要 shell。

網站帳號回答「這筆請求代表哪位使用者」；作業系統帳號則限制「伺服器上這個行程能讀寫哪些檔案、執行哪些操作」。就算你用一般會員登入，後端程式也可能以固定的服務帳號執行。所以一次命令執行，並不表示取得了管理整台主機的權限。

2.5.2 資料進入命令語法

假設應用程式收到日期與會場後，把它們接到固定的程式名稱後面，再把整串交給 shell。設計者只想讓使用者決定報表內容，shell 收到的卻是一整段可以解讀的命令文字。若可控資料能引入額外命令結構，應用程式就把超出原本用途的控制權交了出去。這稱為作業系統命令注入（OS command injection）；這裡只談透過 shell 解讀字串的情況。

以上面的正常命令為例，shell 依語法辨認文字單位與運算符；沒有引號等其他結構時，空白把程式名稱、日期與會場分成三個單位。但 shell 除了照空白切字，還會辨認引號與特殊結構、完成必要的展開，再決定要執行什麼、傳哪些參數，以及輸入輸出接到哪裡。所以應用程式認為是一個欄位的文字，進入 shell 後不一定仍是一個資料參數。

常見的特殊語法可依作用分成幾類，實際符號與規則依 shell 而異：

  • 引號與跳脫：把部分文字保留在同一個參數中，或限制某些字元的特殊意義；不同引號保護的範圍不完全相同。
  • 分隔與串接：界定一條命令何時結束，或依前一條命令是否成功決定是否執行下一條。有些結構也能讓工作在背景執行。
  • 管線：把一個程式的輸出接到另一個程式的輸入，改變資料流向。
  • 命令替換：先執行一段內嵌命令，再把它的輸出放回外層命令的某個位置。
  • 重新導向：改變程式讀取輸入或寫出結果的通道，例如把輸出寫進檔案，而不是留在原本的輸出通道。

字串的組法如下，方括號代表被換掉的那段輸入。

正常：固定程式名稱 + 日期資料 + 會場資料
解讀：啟動報表程式，傳入兩個資料參數

被操縱：固定程式名稱 + 日期資料 + [能改變命令結構的輸入]
解讀：原本的報表操作 + [攻擊者附加的命令]

網站有沒有登入、表單是不是只有一個選單，都不影響這件事。瀏覽器介面只是送資料的一種方式，伺服器得自己驗證收到的值；請求格式完全合法，值也可能超出這個功能允許的範圍。

以管線（pipeline）為例，它把左側程式的標準輸出接到右側程式的標準輸入。標準輸出是程式送出一般結果的通道，標準輸入則是接收資料的通道。有些程式會讀這份輸入，有些不會。命令結構若被改成管線，應用程式最後取得的就可能是另一個程式的輸出。下圖畫的是管線。如果是多條命令依序執行，而應用程式擷取的是共用的輸出通道，報表與額外命令的輸出可能同時出現，原回應不一定被完全取代。

2.5.3 從表單到回應

沿用活動報表的例子。請求只節錄需要的部分，省略了會話與訊息長度等欄位。這裡假設應用程式會擷取報表程式的文字輸出，放入回應本文。

正常的請求

POST /demo/attendance HTTP/1.1
Host: example.com
Content-Type: application/x-www-form-urlencoded

reportDate=2026-10-01&venue=hall-a
  1. 表單表示：在這種表單格式中，& 分隔欄位，= 左右是名稱和值。同一個符號在 shell 語法中另有意義，所以要分清目前是哪個元件在解析。
  2. 應用程式取值：依 Content-Type 解析後，得到日期 2026-10-01 與會場 hall-a。Content-Type 是用來指明內容格式的標頭。
  3. 建立命令：應用程式組成 demo-attendance 2026-10-01 hall-a，交給 shell。這裡假設值沒有改變命令結構。
  4. 啟動程式：shell 啟動報表程式，傳入日期與會場；報表程式取得兩個資料值後，產生文字 demo-count: 18。
  5. 回到網站：應用程式讀取這份輸出，將它放進 HTTP 回應。瀏覽器只收到傳回的文字，報表命令是在伺服器上執行的。

編碼只改變傳送時的表示。例如在表單中，無害名稱 hall a 可以表示為 hall%20a，也常寫成 hall+a；在這種表單格式中解析後，兩者都是含空白的值。先編碼不會讓值變安全，交給 shell 的是應用程式解析、組合之後的內容。

哪一步越過邊界

現在只把會場資料換成 [能改變命令結構的輸入]。HTTP 解析依然可能成功，但在第三步，應用程式把這個值接成命令字串；第四步 shell 若把其中一部分當成命令結構，就可能啟動 [額外行程]。如果其輸出又被應用程式放進回應，第五步便可能出現報表不會產生的內容。問題出在第三、四步的交接。

條件回應本文判讀
原本的日期與會場demo-count: 18建立正常功能的比較基準。
只替換會場值的形狀[額外行程的輸出]排除反射與假資料之後，才能支持輸出來自非預期執行。
恢復原本的會場demo-count: 18確認差異隨這個輸入出現與消失；結論還要對照資料流。

回應若只是把收到的字串印出來，那是反射輸入，證明不了程式執行。回應裡出現一個帳號名稱，也可能只是網頁上原有的文字。輸入、處理路徑和一個能獨立辨認的效果連得起來，才支持「命令執行」這個結論。

2.5.4 什麼情況下成立

  • 必須有通往命令執行的路徑。參數叫作 command 或出現在報表功能，都只是線索；應用程式若完全以內部函式計算，就沒有這裡假設的 shell 交接。
  • 輸入必須能改變解讀結果。固定程式接收受限制的資料參數，與不可信字串被解讀為命令，是兩回事。
  • 語法取決於環境。這裡以 Unix-like 系統常見的 shell 與文字輸出為模型。換成別的 shell、Windows 的執行方式或不同的字串組合方式，同一個形狀就未必適用。
  • 執行仍受權限限制。非預期程式通常沿用啟動它的執行環境與權限。一次看得到的輸出，推不出能讀所有檔案、寫入任何位置或取得最高權限。
  • 執行與可見是兩個問題。應用程式可能丟棄輸出、只回傳工作編號，或讓工作稍後執行，所以看不到文字不表示沒有風險。

看不到輸出時

若命令注入發生，但 HTTP 回應沒有直接帶回命令輸出，常稱為盲目命令注入（blind command injection）。這和上一節的 blind 推論相似：看不到直接結果，仍可能看到處理造成的其他效果。差別在於這裡執行工作的是伺服器上的行程。

  • 時間差：若 [額外行程] 需要等待，而網站又等它完成才回應，等待可能反映在請求耗時上。網站若立即回傳工作編號、在背景執行，請求耗時就看不出等待。
  • 輸出重新導向：若輸出被寫入 [之後可取回的位置]，原請求雖沒有結果，之後取回的資料仍可能提供線索。前提是行程有寫入權限，網站或另一個已授權管道也讀得到同一份內容；寫得進檔案，不代表能從網址取回。
  • 帶外通道（out-of-band）：若 [額外行程] 使伺服器向 [授權觀察端] 發出網路連線，就可能在原 HTTP 回應以外看到紀錄。這取決於可用功能、名稱解析與出站網路限制；看不到連線不能直接排除執行。

這三種管道描述的是機制，不是某個網站已驗證的行為。看到訊號後，要和正常基準對照、重複觀察，並排除其他原因：單次變慢可能來自網路或負載，檔案可能是舊內容，對外連線也可能來自別的元件。單一訊號支持的是假說，證明不了執行位置、命令內容或權限範圍。

2.5.5 辨認可疑的交接

先問正常功能如何完成。檔案轉換、報表產生、系統診斷等功能可能呼叫外部程式，也可能使用安全的函式庫，光看功能名稱不是漏洞證據。有程式碼或設計資料時，可以追蹤使用者欄位是否被拼接到命令字串，以及呼叫是否經過 shell。閱讀呼叫位置時，先分辨它接收的是「交給命令解讀器的一整串文字」，還是「固定程式加上分開的參數清單」，再核對該介面的實際行為，不要只看函式名稱。

只有回應可看時，要分開「已知」和「推測」。已知的可能是某個欄位改變後回應不同，推測的可能是後端呼叫了外部程式。錯誤文字是線索，不能直接當成伺服器內部架構的事實。閱讀經授權的實驗資料時，至少記下正常功能、唯一改動的欄位、回應差異，以及其他可能原因。

在自己電腦的終端機顯示帳號，只說明本機行程的身分；在瀏覽器看到文字，也不表示那段文字是在瀏覽器執行。要判斷執行位置，就沿請求與回應的箭頭追蹤。

2.5.6 靠不住的防禦

做法為什麼不夠
只讓畫面提供固定選單使用者仍能自行建立請求；伺服器必須重新驗證實際收到的值。
刪除少數看似危險的字元命令語言有多種結構與解析位置，黑名單未必涵蓋所有解讀方式；檢查前後的解碼也可能不同。
把輸入做 URL 編碼這是傳輸表示法，應用程式通常會先解碼，shell 解讀這個步驟並沒有被移除。
自己替字串加引號引號的作用取決於 shell 與所在位置，拼接或多次解讀容易破壞預期邊界。應優先避免整段命令字串，不要自己發明跳脫規則。
隱藏輸出或錯誤改變可見性不會阻止非預期程式被啟動，已發生的操作仍可能有影響。

2.5.7 怎麼修補

優先使用內部功能

如果報表可以直接查詢資料並在程式內產生，就不必為此啟動 shell。函式庫（library）提供可直接呼叫的既有功能；應用程式介面（application programming interface，API）則規定如何呼叫功能及傳入資料。選用合適的函式庫 API，就省掉了把使用者資料再當命令語言解析的那一步。日期、會場與存取權限仍要照功能規則驗證。

需要外部程式時

另一種方式是使用作業系統提供的行程啟動介面（讓應用程式要求系統啟動程式並傳入參數的功能）。透過這種介面指定固定執行檔，把各個參數分開傳入，不先組成 shell 命令字串。下面只列出呼叫時要傳的資料，不是可以執行的程式：

執行檔：/opt/demo/bin/demo-attendance
參數一：2026-10-01
參數二：hall-a
呼叫方式：直接啟動該執行檔，不透過 shell

這樣每個參數都保有資料的身分，不會因為長相特殊就變成另一條 shell 命令。被呼叫的程式仍會解讀自己的參數，某個值可能被當成選項、檔案路徑或另一種程式語言，所以拿掉 shell 之後，還要限制可接受的值。

在報表的例子裡，日期須符合既定格式且為有效日期，會場只接受伺服器允許清單（allow-list，列出業務明確接受的值，其餘拒絕）中的項目。需要讓使用者挑選不同功能時，也由伺服器把有限選項對應到固定功能，不接受使用者任意指定執行檔位置。

程式庫的「不經 shell」選項實際怎麼運作，要看平台與目標檔案種類。例如在 Windows 上啟動批次檔，即使呼叫端選了「不經 shell」，系統也可能交給命令解讀器處理。另外，不要先啟動一個 shell，再把不可信字串當成它的參數。用 Python 的話，可參考官方 subprocess 文件，其中參數序列與 shell 呼叫是不同的介面。檢查程式有沒有正常結束，並不算檢查了輸入。

額外限制影響範圍

以最小權限（least privilege）執行工作，只授予必要檔案與資源的權限；限制執行時間及輸出大小，避免耗盡資源；對外只給適當的錯誤，詳細診斷留在受保護的紀錄。這些是額外防線，輸入驗證與正確的呼叫方式仍不可少。

2.5.8 小結

  • 命令注入發生在交接處：使用者資料被接進命令字串，shell 解讀時，資料取得了改變命令結構的能力。
  • 回應裡的文字要追到來源。反射輸入證明不了執行；看不到輸出，也不表示沒有執行。
  • 非預期程式沿用執行帳號的權限，一次命令執行推不出整台主機的控制權。
  • 刪字元、URL 編碼、自己加引號都沒有拿掉 shell 解讀這一步；隱藏輸出只改變看不看得到。
  • 修補優先改用內部功能、移除 shell；必須呼叫外部程式時，固定執行檔、分開傳參數，再用格式檢查與允許清單驗證每個值。

  • OS command injection, simple case：分開記下送入的資料、伺服器執行的操作與回應裡的證據，判斷證據指向哪台機器執行。
