本節模型：shop.example.com 的後台出貨量查詢功能

上一節的輸入進了查詢字串，資料庫把其中一段讀成 SQL 語法。這一節的輸入交給 shell：後台的出貨量查詢要呼叫一支外部報表程式，網站把日期與倉庫接成一條命令，由作業系統的 shell 解讀。問題是 shell 讀到這兩個值時，把它們當成什麼。

2.5.1 應用程式如何呼叫外部命令

先看正常的情況。店員在報表頁選好日期 2026-10-01 與倉庫 warehouse-a，按下「查詢出貨量」。瀏覽器把兩個值放在 POST 請求的本體送出，伺服器回傳出貨量摘要：

Request
POST /demo/shipping HTTP/1.1Host: shop.example.comContent-Type: application/x-www-form-urlencodedreportDate=2026-10-01&warehouse=warehouse-a
Response
HTTP/1.1 200 OKContent-Type: text/htmldemo-count: 18

請求與回應之間，伺服器內部的動作從外面看不到。出貨量由一支獨立的命令列程式 demo-shipping 計算，後端只負責啟動它，再把結果交還給店員。啟動外部程式需要一條命令字串，所以後端用字串相加，把兩個值接在程式名稱後面，交給 shell 執行。

兩個值是 demo-shipping 的參數（argument，交給程式的輸入值）。後端的程式碼如下：

date = request.form["reportDate"]
warehouse = request.form["warehouse"]
cmd = "demo-shipping " + date + " " + warehouse   # 把兩個值接在程式名稱後面
out = subprocess.run(cmd, shell=True, capture_output=True, text=True).stdout
return out

shell=True 把 cmd 這整段文字交給 shell，這段文字怎麼讀，由 shell 決定。程式跑完，它印出的文字被收集起來，原樣成為上面那份回應的本體，店員在頁面上看到的就是出貨量摘要。

後端組出的字串是 demo-shipping 2026-10-01 warehouse-a，shell 如何拆開它，決定了倉庫值能影響多少事。

2.5.2 Shell 如何拆解命令字串

shell 拿到字串後，依空白和它認得的語法符號拆開：第一段是要啟動的程式，其餘每一段是交給程式的參數。倉庫值是 warehouse-a 時，字串拆成三段：

除了空白，shell 還認得其他符號，有些會把一行文字切成多條命令。把倉庫值換成 warehouse-a 加上 [命令分隔符號][附加的命令]，組出的字串會拆成這樣：

shell 讀到 [命令分隔符號]，就在這裡結束前一條命令，開始下一條。

倉庫值本來只是第二個參數，一筆資料。它被接進字串之後，shell 把它當成命令結構的一部分。你可能會問 shell 為什麼不分辨哪些字來自使用者：它拿到的只有文字，沒有這種標記。使用者輸入被 shell 讀成命令結構的漏洞，稱為作業系統命令注入（OS command injection）。

2.5.3 成立條件

這種拆法的前提是後端把組好的字串交給 shell 執行，例如上面的 shell=True。本節用的是 Linux 上 /bin/sh 的規則；後端用的 shell 不同，語法符號也跟著不同，例如 Windows 的 cmd 與 PowerShell 另有自己的一套。

影響範圍：附加的命令以執行網站的作業系統帳號執行，例如 demo-worker。這個帳號能讀的檔案、能寫的目錄、能啟動的程式，附加的命令都做得到，跟店員登入後台的身分無關。

2.5.4 判斷命令是否被執行

你看不到後端組出的字串，只能從回應推斷 shell 有沒有多跑一條命令。做法是把同一個請求送兩次，只改倉庫值，先用正常的倉庫值留下基準。

再把倉庫值換成帶 [命令分隔符號][附加的命令] 的版本，回應多出一行：

正常的倉庫值
Request
POST /demo/shipping HTTP/1.1Host: shop.example.comContent-Type: application/x-www-form-urlencodedreportDate=2026-10-01&warehouse=warehouse-a
Response
HTTP/1.1 200 OKContent-Type: text/htmldemo-count: 18
附加命令的倉庫值
Request
POST /demo/shipping HTTP/1.1Host: shop.example.comContent-Type: application/x-www-form-urlencodedreportDate=2026-10-01&warehouse=warehouse-a[命令分隔符號][附加的命令]
Response
HTTP/1.1 200 OKContent-Type: text/htmldemo-count: 18[額外命令的輸出]

回應多出一行，先別下結論。核對兩件事：

  • 第一，把倉庫值換回 warehouse-a 再送一次。回應裡那一行消失，表示它由倉庫值觸發。
  • 第二，看回應裡那一行的內容。後端若只是把輸入印回來，回應裡的字會和送出的字完全相同；這一行的內容卻無法從送出的文字推得，例如伺服器上某個檔案的內容或當下的系統資訊。

兩項核對都成立，表示 shell 啟動了第二條命令。

Blind command injection

後端若丟棄命令輸出，或只回傳固定的「完成」，回應裡就看不到 [額外命令的輸出]。看不到輸出的命令注入稱為盲目命令注入（blind command injection）：命令照樣執行，只是要換個管道觀察結果：

  • 時間差：後端同步等命令結束才回應，命令跑多久，回應就晚多久。若正常請求約零點幾秒回來，倉庫值帶上讓程式等待十秒的 [附加的命令] 時，回應會晚約十秒才回來。重送幾次都慢十秒；網路抖動造不出這麼固定的延遲。
  • 寫入檔案再取回：[附加的命令] 把輸出寫進 [可取回的位置]，也就是網站公開給瀏覽器下載檔案的目錄，例如放圖片的目錄。再用一般請求去取那個檔案，讀到 [額外命令的輸出]，就證明命令跑過。這個做法需要執行網站的帳號對該目錄有寫入權。
  • 對外連線（out-of-band）：[附加的命令] 讓伺服器連向 [觀察端]，也就是你控制的主機。你把一個只用於這次請求的識別值放進 [觀察端] 的位址。觀察端的紀錄若出現帶這個識別值的查詢或連線，時間又和你送出請求的時間吻合，就表示伺服器執行了命令。這個做法需要伺服器能連到外部網路。

2.5.5 小結

  • 判斷輸入進了哪裡，先看這個值最後被哪個元件當成語法處理。命令字串由 shell 處理，所以要檢查的是後端程式碼裡組命令字串的那一行，而不是輸入欄位本身。
  • 確認命令有沒有執行靠對照：同一個請求只改一個值，回應的差異穩定出現，換回原值就消失。輸出看不到時，改看時間、檔案或對外連線。
  • shell 收到的只有文字，沒有哪一段來自使用者的標記，所以值裡的符號會被當成命令結構的一部分。

PortSwigger Academy 的對應練習（主題頁 OS command injection）：

  • OS command injection, simple case：回應直接顯示命令輸出。
  • Blind OS command injection with time delays：看不到輸出，只能從回應時間判斷。
  • Blind OS command injection with output redirection：命令輸出先寫進檔案，再從網站取回來看。
