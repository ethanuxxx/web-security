本節模型：shop.example.com 的商品說明書下載功能

你在茶壺的商品頁按下「下載說明書」，瀏覽器請求 /download?file=manual-102.pdf，網站把這個檔名接在說明書所在的目錄（基底目錄）後面，請檔案系統讀出 manual-102.pdf，再把 PDF 送回瀏覽器。這種寫法很常見：伺服器依檔名取檔。問題出在 file 是使用者送來的文字（任何能改網址的人都能改），伺服器卻拿它決定讀哪一個檔案：把 manual-102.pdf 換成別的字串，伺服器就去讀別的檔案，能讀到多遠，要看程式有沒有設限。同一棵目錄樹裡，說明書旁邊還有訂單、設定這些不該被下載的檔案。

2.1.1 檔案系統是一棵樹

作業系統用檔案系統（file system）管理檔案。在 Linux、macOS 這類 Unix-like 系統裡，所有檔案都掛在同一棵樹上，樹的最上層叫根目錄（root directory），寫成 /。目錄（directory，俗稱資料夾）裡可以放檔案，也可以放更多目錄。

絕對路徑與相對路徑

描述一個檔案在樹上的位置，就是它的路徑（path）。從根目錄 / 一路寫下來的叫絕對路徑（absolute path），例如 /srv/shop/files/manuals/manual-102.pdf：不管程式當下在哪裡，它都指向同一個檔案。只寫「從目前所在目錄算起」的叫相對路徑（relative path），例如 manual-102.pdf。它指哪個檔案，要看「目前目錄」在哪裡。

路徑裡有兩個特殊的名字：. 代表「目前這個目錄」，.. 代表「上一層目錄」。所以在 /srv/shop/files/manuals/ 這個目錄裡，../ 指向 /srv/shop/files/，../../ 指向 /srv/shop/，依此類推，如上圖所示。

路徑正規化

暫時假設路徑經過的目錄都存在、可以通行，而且途中沒有符號連結。在這個假設下，可以把路徑裡的 . 與 .. 依文字規則化簡成最短的等價形式，這叫字面正規化（normalization）：

表 2.1.1-1
化簡前化簡後
/srv/shop/files/manuals/..//srv/shop/files/
/srv/shop/files/manuals/../..//srv/shop/
/srv/shop/files/manuals/../../[範圍外的檔案]/srv/shop/[範圍外的檔案]

最後一列寫起來以 /srv/shop/files/manuals/ 開頭，化簡後卻落在基底目錄之外。

字面正規化只動文字。系統實際去找檔案時，會沿著檔案系統一層層解析，途中解開符號連結，得到最終位置，這叫 canonicalization。路徑上沒有符號連結時，兩種做法的結果相同；有符號連結時，文字化簡可能改變路徑原本的意思。修補時要用的是 canonicalization。

根目錄沒有上一層：在 Unix-like 系統裡，對 / 再做 .. 仍然停在 /，所以多寫幾個 ../ 也只會停在根目錄。這是路徑計算的規則，實際讀檔能不能成功是另一回事。

2.1.2 應用程式與檔案系統之間

這裡有兩種路徑。瀏覽器網址列裡的 /download 是 URL 路徑，只告訴網站要用哪個功能，伺服器上不一定有叫 download 的資料夾。檔案路徑出現在下一層：應用程式（Application，即網站背後處理請求的程式）收到 file 之後，自己組出主機上的檔案路徑，再請作業系統的檔案系統去讀。

這種功能可能這樣寫：

# 不安全的做法
base_directory = "/srv/shop/files/manuals/"
file = request.args["file"]              # 使用者送來的文字
target = base_directory + file          # 直接接在後面
return read_file(target)

設計者想讓它只讀說明書目錄裡的檔案，程式卻只把兩段字串接起來，沒有檢查最後會走到哪裡。檔案系統照路徑的語意去走，遇到 .. 就往上爬。使用者可控制的文字被當成路徑交給檔案系統，途中沒有任何一步確認最後的位置仍在允許範圍內，這類問題稱為 Path Traversal（路徑穿越，也叫 directory traversal）。

兩筆 request 只差在 file，功能、Cookie、請求方法都一樣，所以回應的差異來自這個輸入。

回應的 Content-Type 標頭可能仍寫著 PDF 類型，因為程式不會因為內容改變而改標頭，瀏覽器的 PDF 檢視器於是報告「無法開啟檔案」。要知道讀到了什麼，得看 body 的文字。

片段裡需要幾個 ../，取決於基底目錄和目標檔案的相對位置：從 manuals/ 到 shop/ 要往上兩層；基底若是 /srv/shop/manuals/，往上一層就到了。自己數層數即可，不必背固定的數字。

2.1.4 成立條件與平台差異

  • 網站有用使用者輸入決定檔案路徑的功能，例如說明書下載、圖片、模板選擇、語言檔這類以名稱取檔案的功能。網站沒有拿輸入去讀檔，就沒有這個問題。
  • 能讀到的範圍受執行程式的帳號權限限制。網站程式通常以權限有限的帳號執行；那個帳號本來就讀不到的檔案，穿越也讀不到。
  • 上面的例子只涉及讀取。能不能寫檔、改檔，要看另外的功能與權限。
  • Windows 的路徑用反斜線 \ 分隔，並有磁碟機代號（例如 C:\）。一般的 Windows 路徑處理通常兩種斜線都接受（細節依 API 與路徑種類而定），所以 ..\ 與 ../ 都可能有效。範圍外的檔案在 Windows 上也要換成該系統上確實存在的檔案。

名字裡有 password 的檔案不一定存著明文密碼。讀到 [範圍外的檔案] 只證明目錄限制被越過；裡面有什麼，要看那個檔案本身的內容與權限，不能從檔名推斷。

2.1.5 Information disclosure

Information disclosure（資訊揭露）指網站在不該給的時候，把資訊交給了不該拿到的人。比較正常與錯誤的回應、從中辨認多出來的資訊，這套觀察方法在 Seeing the Web Through the Browser 一節的「錯誤訊息與資訊揭露」介紹過。

穿越可能洩漏什麼

能讀到範圍外的檔案，就可能看到原本不公開的內容：帳號清單、應用程式的設定檔、原始碼，以及放在檔案中的金鑰或連線資訊。哪些檔案存在、是否可讀，要看權限與部署方式。密碼若以明文放在網站程式讀得到的檔案裡，讀到檔案就等於拿到密碼。

錯誤訊息也會洩漏路徑

即使沒有穿越，錯誤頁也會透露資訊。例如以 file=manual-999.pdf 請求一個不存在的檔名，回應可能是：

FileNotFoundError: /srv/shop/files/manuals/manual-999.pdf
(framework DemoFramework 1.2.3)

這一行告訴對方基底目錄、使用的框架與版本。基底目錄讓人可以算出需要幾個 ../；版本則可能對應到已公開的弱點。

2.1.6 防禦手法

有效的防禦

最好不讓使用者決定路徑

最穩的方式是讓輸入根本不是路徑。例如說明書用編號：使用者只能送 id=102，伺服器自己從資料庫或設定查出「編號 102 對應 /srv/shop/files/manuals/manual-102.pdf」。這叫 id 到檔案的對應（mapping）。若檔案數量有限，也可以用允許清單（allow-list）：輸入必須恰好等於清單中的某個名字，否則拒絕。這樣 ../ 之類的字串連進入檔案系統的機會都沒有。

必須用檔名時，先解析再檢查

如果一定要用使用者給的檔名，處理順序是：依所用的傳輸格式取得解碼後的值；組合路徑；讓系統解析出實際的最終位置，同時解開符號連結（symbolic link，一種指向別處的捷徑檔案）；驗證這個位置在允許的基底目錄之內；通過才開檔讀取。解析要用實際沿檔案系統走的函式（realpath 一類），只做文字化簡的函式（normpath 一類）看不到符號連結。檢查與開檔之間的時間差，見下面「其他限制」。

# 較安全的做法（偽碼，採 Unix-like 路徑；
# real_path 代表沿實際檔案系統解析並解開連結的函式）
base = real_path("/srv/shop/files/manuals")     # 基底目錄的最終位置
target = real_path(join(base, file))            # 組合後解析成實際的最終位置

# 比較時要含結尾的分隔符，避免 /srv/shop/files/manuals-old 誤判
if not target.startswith(base + "/"):
    return error("not allowed")                 # 回一般錯誤，不洩漏細節
return read_file(target)

這樣受檢查的就是實際要讀的位置。輸入裡的 .. 或多餘斜線怎麼變化，都在解析之後才比較。百分比編碼要在更前面依傳輸格式解碼一次，一般的檔案路徑函式不處理 URL 編碼。

其他限制

  • 檢查與使用之間若檔案被替換（例如符號連結被改指向別處），就會出現時間差（競態）問題；正式系統要用能原子化處理的檔案開啟方式，或限制誰能改動該目錄。
  • 以最小權限（least privilege）執行網站程式，讓它只讀得到必要檔案。這能縮小出事時的損害，但不能取代路徑檢查。

部署與錯誤處理

  • 錯誤時對外只回一般性的訊息（例如「找不到這份說明書」），路徑、框架與版本等細節寫進有存取控制的內部紀錄。
  • 備份檔、暫存檔與設定檔不放在網站的公開範圍；部署前清掉編輯器留下的 .bak、~ 之類的檔案。
  • 關閉目錄列表（directory listing），讓不存在預設首頁的目錄回傳錯誤，而不是檔案清單。
  • robots.txt 只是給爬蟲的建議，任何人都讀得到；不想公開的路徑要靠存取控制，不要列在裡面。
  • 密碼、金鑰與連線資訊不以明文放在網站程式讀得到的檔案；放進環境變數或專門的機密管理服務，密碼本身只存加 salt 的慢速雜湊。

無效的防禦

很多開發者的第一反應是把 ../ 擋掉。這類做法檢查的是輸入字串長什麼樣子，看不到檔案系統最後走到哪裡：

表 2.1.6-1
做法為什麼不夠
把輸入裡的 ../ 刪掉（只刪一次）刪除之後的結果可能又拼出新的 ../：被刪掉的片段前後各留下幾個字元，湊在一起又成了 ../。一次性的刪除不會重複檢查結果。
檢查字串是否以 /srv/shop/files/manuals/ 開頭字面上以 /srv/shop/files/manuals/ 開頭、後面接著若干 ../ 的路徑就是以它開頭，但解析成最終位置後在目錄外。如果前綴少了結尾的斜線（/srv/shop/files/manuals），連 /srv/shop/files/manuals-old/ 也會被誤判為通過。
要求副檔名是 .pdf副檔名只限制檔名結尾，不限制所在目錄，目錄外同樣是 .pdf 的檔案照樣讀得到。有些舊環境還會在空字元（null byte）處把字串提早截斷，讓結尾檢查被繞過。
在檢查前後沒有一致地解碼URL 中的百分比編碼（percent-encoding，前一章的「資料放在請求的哪裡」已說明）解碼後可以還原成 ../。如果檢查在解碼之前做，而讀檔在解碼之後做（或被重複解碼），檢查看到的和實際用到的就成了兩個字串。
只擋 ../，卻接受完整的絕對路徑有些組合路徑的函式在遇到以 / 開頭的輸入時，會直接丟掉前面的基底目錄，輸入一個完整的絕對路徑，它就成了最終路徑。

受檢查的字串和最後拿去開檔的路徑對不上，這幾種做法都敗在這裡。靠列舉壞的寫法來防守，每出現一種新變形就得再補一條規則。

2.1.7 小結

  • .. 代表上一層。文字化簡和沿檔案系統解析的結果可以不同，讀檔時用的是後者。
  • Path Traversal 的成因：應用程式把使用者可控的文字當成檔案路徑，沒確認解析後的最終位置仍在允許目錄內。
  • 能讀到範圍外的檔案，不代表能寫入或執行；檔名叫什麼，也不代表裡面有什麼。
  • 修補：用 id 對應或允許清單，不讓使用者決定路徑；必要時先解析實際位置再驗證，並配合最小權限、一般性的錯誤訊息，以及不把備份檔與機密放進公開範圍。
  • 刪 ../、檢查前綴或副檔名都只看字面，檢查的和實際使用的對不上。

PortSwigger Academy 的對應練習（主題頁 File path traversal、Information disclosure），只在 Lab 或其他獲明確授權的系統上測試：

  • File path traversal, simple case：只改檔名參數，把回應 body 的變化和本節的路徑展開對照。
  • 同一主題頁下的其他 Lab：分別對應無效的防禦所列的情況，例如刪去 ../、檢查前綴或副檔名、解碼。

Path Traversal 裡解讀輸入的是檔案系統，它把 .. 當成往上一層。下一節 File Upload Vulnerabilities 從讀檔轉到存檔：使用者送來的是整個檔案，它被存進哪個目錄、取回時交給哪個處理器，決定它被當成資料送出還是被當成程式執行。
