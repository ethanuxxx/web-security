本節模型：shop.example.com 的帳號頭像上傳功能

你在 shop.example.com 的帳號頁選好圖片、按下上傳，瀏覽器把圖片放在請求的本體送出，上傳處理器（網站裡接收上傳的那段程式）驗證後選一個位置存起來，頁面換成新照片。

看起來只有一個動作，網站卻至少做了兩件事：先接收並儲存檔案，再讓瀏覽器用另一筆請求把圖片取回。送來的若是一份程式，網站會把它當資料保存還是拿去執行，要看整條處理流程。

上一節 Path Traversal 追蹤的是一段檔名怎麼決定伺服器讀哪個檔案，這裡的輸入是整個檔案，要問的是它存到哪裡、之後由誰接手處理。網站接受了上傳、檔案能被取回、檔案內容被當成程式執行，三者各需要不同的證據。

2.2.1 檔名、類型標籤與內容

檔案的內容是一串位元組（bytes），即電腦實際儲存的資料。圖片有圖片格式規定的內容；純文字檔則保存文字。檔名是用來稱呼檔案的名字，最後的 .jpg 或 .php 叫副檔名（extension）。把文字檔改名成 demo.jpg，裡面的文字不會因此變成 JPEG 圖片。

上傳時還會有一個內容類型標籤，例如 image/jpeg。這種描述內容種類的標籤稱為 MIME 類型（Multipurpose Internet Mail Extensions）。在請求裡，Content-Type 標頭用它描述內容。不過檔案 part 中的標籤只是用戶端送來的聲明，伺服器並沒有因此檢驗過內容。

用戶端（client）就是發出請求的一方，平常是瀏覽器，也可能是能自行組出 HTTP 請求的工具。正常的檔案選擇視窗即使只讓你挑圖片，對方仍可能送出別的請求，所以「介面只讓選圖片」不能代替伺服器端的檢查。

2.2.2 上傳請求的結構

回顧 HTTP 的 header（標頭）與 body（本體）：上傳檔案通常把檔案放在 body。當同一個表單還有文字欄位時，常用 multipart/form-data，意思是把 body 分成多個部分（part），每個部分代表一個欄位。boundary 是分隔這些部分的字串；外層標頭宣告字串，body 則用它標出每個部分的開始與整份內容的結束。

例如一個表單有暱稱 display_name 與頭像 avatar 兩個欄位。圖片位元組用說明文字代替，長度等標頭也沒有列出，但 multipart 的各部分、空行與結束分隔線都有展開。HTTP/1.1 的標頭行與分隔線以 CRLF（回車加換行）結尾，畫面上的換行只用來表達結構。

Request
POST /demo/profile/avatar HTTP/1.1Host: shop.example.comCookie: demo_session=demo-onlyContent-Type: multipart/form-data; boundary=DemoUploadBoundary--DemoUploadBoundaryContent-Disposition: form-data; name="display_name"demo-reader--DemoUploadBoundaryContent-Disposition: form-data; name="avatar"; filename="demo-portrait.jpg"Content-Type: image/jpeg[此處省略有效的 JPEG 圖片位元組]--DemoUploadBoundary--
  • 最上面的 Content-Type: multipart/form-data 描述整個 body 的包裝方式，整個請求並不是一張圖片。boundary=DemoUploadBoundary 宣告分隔字串；body 裡每條分隔線在它前面加 --，最後一條再在末端加 --。
  • Content-Disposition: form-data 說明這部分是一個表單欄位；name="avatar" 是欄位名，讓接收程式知道它是哪一格。filename="demo-portrait.jpg" 是用戶端提供的原檔名，兩者用途不同。
  • 檔案部分自己的 Content-Type: image/jpeg 只描述那一部分的宣稱類型。它與外層的 Content-Type 位於不同層。
  • 每組標頭後面的空行把標頭與內容分開；圖片的實際內容在檔案 part 的空行後面，不在檔名裡。

分隔字串不能與內容中的分隔線衝突，一般由瀏覽器或工具替你產生。表單欄位名、檔名、類型標籤與內容全都來自用戶端，伺服器應檢查預期欄位、拒絕不合規的內容，不能把這些值當成可信的保證。完整格式可參考 RFC 7578。

2.2.3 取回時由誰解讀

接收上傳的程式先驗證輸入，再選一個儲存位置，把檔案寫入。之後，瀏覽器可能用另一筆 GET 請求取回檔案。負責處理這筆請求的元件叫處理器（handler）：有的只把檔案當靜態資料送出，有的把檔案交給程式語言執行，再把執行產生的內容送出。哪一種處理器接手，要看網站的路由、伺服器設定與執行環境。

以 PHP 為例，它是一種常用於伺服器的程式語言。在設定了相應 PHP 處理器的路徑中，請求某份 PHP 檔案可能使它被執行；在沒有這種設定的儲存服務中，同樣的檔案可能只會被下載，或遭拒絕。所以 .php 檔不會在任何網站上都自動執行。

常見的對應方式，是依請求的 URL 路徑、對應的檔案位置或副檔名選擇處理器，不一定先查看檔案內容。Apache 的處理器說明就區分依副檔名與依位置設定的方式。所以同一份內容放在不同目錄，可能得到不同處理。要確認的是上傳目錄有沒有沿用應用程式的執行設定，或另有禁止執行的設定。

有些伺服器還支援目錄層級的設定檔，例如 Apache 的 .htaccess，可在管理者允許的範圍內改變該目錄及子目錄的行為。它是否生效取決於主設定，並非每台伺服器都會讀取；詳見 Apache 目錄設定說明。所以上傳功能也必須避免讓使用者提供的檔案成為有效的伺服器設定。

檔名如何比對還受平台影響：Windows 的常見檔案存取環境預設不區分大小寫，許多 Unix 環境則會區分；Windows 對名稱末端空白與句點的處理也有介面限制。具體行為取決於檔案系統、呼叫介面與設定，某個平台上的結果不能直接套到另一個平台。Microsoft 的檔案命名規則說明了這些限制。驗證檔名的程式與最後選處理器的元件若採不同規則，只擋少數名稱就可能漏掉實際被當成程式處理的檔案。

檔案上傳漏洞（file upload vulnerability）發生在網站對可接受內容、儲存位置或後續用途的控制不足時。其中一條危險路徑是：原本只應接受頭像的功能，讓使用者提供的程式進入可執行區域，後續請求又把它交給執行器。這時資料跨過了「儲存內容」與「伺服器程式」的界線。

Path Traversal 區分過 URL 路徑與磁碟路徑，上傳也一樣。公開網址 /demo/media/demo-image.jpg 可能對應到磁碟的 /srv/demo-upload/demo-image.jpg，也可能由程式從別的儲存服務取回。光看網址推不出磁碟位置，也不能假定伺服器保留了上傳時的檔名。

2.2.4 追蹤一次頭像上傳

假設一個練習用的網站以 PHP 處理部分 URL，頭像功能又錯把未驗證的檔案存進 PHP 處理器可執行的區域。

原檔與執行輸出

PHP 是伺服器端語言，程式檔可以包含要求處理器完成的動作。它的 echo 負責把文字放進輸出，文字值稱為字串。處理器若執行一份「輸出固定標示文字」的程式，回應可能只有這段文字；處理器若只是提供靜態檔案，回應就會包含原本那份程式的內容。PHP 官方 echo 說明可用來核對輸出的意義。

分開讀兩個回應

沿用正常圖片的例子，上傳回應的 201 或「上傳成功」訊息，只表示網站聲稱已接受並儲存檔案；網站也可能用 200 表示成功。這些回應都不能證明檔案被執行。要判斷後續用途，得讀取回請求的原始回應本體（raw response body），拿它和原檔及網站的處理方式對照。

瀏覽器畫面不能當唯一的證據，因為瀏覽器會依回應類型解析內容，HTML 標籤本身可能不會顯示出來。HTTP 檢視工具中的原始 body，才能分清「檔案本身的文字」和「處理後產生的文字」。那段固定標示文字若原本就寫在檔案裡，畫面上看到它並不夠，還要排除靜態回傳或文字轉換。

2.2.5 從取回結果下結論

執行路徑的前提

「上傳後，取回請求觸發伺服器執行」這條路徑要成立，下列條件要分開確認：

  • 接收與儲存：功能確實接受並保留了使用者提供的內容，而不是在驗證時拒絕或轉換成其他內容。
  • 取回位置：有可對應到已存內容的請求入口；判讀者須知道實際 URL，不能只根據原檔名猜測。
  • 處理方式：該位置的有效設定會交給程式執行器，且內容符合執行器能處理的語言或格式。只有副檔名相似並不足夠。
  • 執行權限：處理器能存取該檔案；後續能讀寫的資源仍受執行帳號、隔離及環境設定限制。

辨識時，把正常上傳紀錄、實際取回位置、原始回應本體與可取得的伺服器設定相互對照。缺少某項證據，就保留那項不確定性。背景處理或瀏覽器解析是另外的路徑，這張清單排除不了。

對一份含程式內容的檔案，取回處理器可能產生下圖的三種結果，光憑狀態碼 200 不能判斷執行成功。body 是整份 PHP 原始碼時，這筆請求把檔案當資料送出；若那是網站自己的敏感原始碼，直接送出也可能造成資訊揭露。body 只有固定標示文字時，還要排除其他功能只是抽取或轉換文字，而且一段文字推不出所有路徑都有相同行為。403、404 或其他拒絕回應可能來自權限限制、網址錯誤、名稱改變或檔案不存在。

執行之後能做什麼

若伺服器真的執行了外部提供的程式，就可能形成遠端程式碼執行（Remote Code Execution，RCE）：從網路送來的內容獲得在伺服器執行的機會。這不一定要經過 shell（作業系統上負責解讀並執行命令的程式）：PHP 本身就能執行某些檔案操作。但能做什麼仍受網站執行帳號、環境設定與隔離措施限制，不能推論已取得整台主機的最高權限。

PHP 也有讀取檔案的功能，例如 file_get_contents。函式呼叫就是請一項功能根據提供的資料完成工作：程式給它一個本機檔案位置，它嘗試取得伺服器上那份檔案的內容，再交回程式。讀到資料與把資料放進 HTTP 回應是不同動作，後者可以由輸出功能完成。讀取是否成功，要看檔案是否存在、帳號權限與環境設定；PHP 官方函式說明記載其回傳與失敗行為。

處理流程即使確實讀到一份檔案，也只支持「在這個環境能讀這個位置」，不支持「整個磁碟都可讀」。Web shell 是透過網頁請求操作伺服器的程式，它能做的事同樣受執行帳號與環境的限制。

2.2.6 防禦手法

有效的防禦

接收時只收需要的格式

頭像功能可以採用允許清單（allow-list），只接受業務需要的少數圖片格式。伺服器應檢查實際內容，用維護中的圖片解碼器嘗試讀取；適合時把像素重新編碼成受控的輸出格式，不要原封不動保存所有上傳位元組。重新編碼時由伺服器產生新的圖片內容，不需要的附帶資料就比較不會留下來。這仍不是絕對的保證，解碼器本身也要更新並限制資源。

同時限制檔案大小、圖片尺寸與處理資源，避免小檔案在解碼後耗掉過多記憶體。尚未驗證的原始內容應放在外界無法取回或執行的暫存區，通過才發布。不要先把不可信內容放到公開可執行路徑，再指望後續檢查能及時移除。

內容若先能被取回，檢查卻還沒完成，另一筆請求就可能在這段時間內使用未驗證的內容。安全與否取決於兩項操作的先後，這是競態條件（race condition）的例子。先隔離暫存、驗證後才發布，就是為了消除這個時間窗。第 6 章的 Race Conditions 會建立並行與時間順序的模型。

由伺服器決定名稱與位置

用伺服器產生的新名稱或識別碼保存檔案，原始檔名若有顯示需要，只當作資料保存。這樣用戶端就不能透過名稱選擇路徑或覆寫既有檔案；最終儲存位置也要確認在允許範圍內，這是 Path Traversal 那一節的位置邊界。依實際部署，把上傳資料放在不會被當成應用程式執行的區域或獨立儲存服務，並確認相關路由沒有腳本執行處理器。

「禁止執行」必須在實際執行鏈上成立。只移除檔案系統的可執行權限，不一定能阻止 PHP 這類解譯器讀取並執行檔案。網站、伺服器與儲存服務的配置要共同確保上傳內容只被當成資料提供。

取回時檢查授權與類型

下載處理器應依檔案的公開或私人性質檢查授權（這位使用者是否有權取得這個檔案）。登入只回答「你是誰」，並不表示你可以拿任何人的上傳內容。Authentication 與 Access Control 會在第 4 章展開。

還要考慮瀏覽器這個解讀者。HTML 是描述網頁結構的文字格式，SVG（Scalable Vector Graphics，可縮放向量圖形）則以文字描述圖形；上傳內容若以 HTML 頁面或 SVG 文件提供，瀏覽器會依文件規則解析，內容中的腳本可能在允許執行的環境中運作。不過並非每張 SVG 圖片都會執行腳本：以圖片元素載入 SVG 時，瀏覽器通常會停用其中的 JavaScript，直接作為文件開啟則是另一種處理情境。MDN 的 SVG 圖片限制說明了這項區別。實際影響還取決於回應類型、嵌入方式與瀏覽器安全政策，第 3 章會接著追蹤這條邊界。

伺服器應依驗證後的內容決定回應類型；不需要在頁面內呈現的檔案，可以作為附件下載提供，並配合避免瀏覽器自行猜測類型的回應設定。這些措施控制的是瀏覽器如何使用內容，伺服器端的內容驗證與禁止執行仍不可少。最後，以最小權限執行網站與檔案處理工作，讓它們只能讀寫必要位置，降低某一層失守後的影響。

無效的防禦

檔案從接收到取回，可能由不同元件解讀。只有一個元件檢查了名字，其他元件仍可能依不同規則處理內容。下表的做法各有用處，單獨使用都保證不了整條流程的安全。

表 2.2.6-1
做法為什麼不夠
前端只允許選圖片限制的是正常介面的操作，擋不住用戶端直接送出其他內容。
相信 part 的 Content-Type這個值是用戶端的聲明；改成 image/jpeg 不會改變檔案位元組。

通過圖片驗證，也不代表檔案不會被執行。有些檔案能同時被不同格式的解析器接受，稱為 polyglot（多格式檔案）。問題不只在檔頭像圖片：某些圖片格式有放置描述資訊的區域，圖片解析器把其中內容當成附帶資料，另一個程式解析器卻可能依自己的規則，把同一份位元組中的某個區段當成程式。

例如 PHP 支援程式區段與非程式內容共存，程式區段以外的內容不會被當成 PHP 語法解析，詳見 PHP 的混合內容說明。這是 PHP 的行為，其他解譯器不一定也會略過不認得的內容。兩個解析器都接受這份檔案，也還要有前面說的處理器對應才會執行。

2.2.7 小結

  • 一次上傳至少有兩筆請求：POST 接收並儲存檔案，之後的 GET 由某個處理器取回。
  • 檔名、part 的 Content-Type 與內容位元組都由用戶端提供，要分開檢查；改名或改標籤都不會改變位元組。
  • 上傳成功、能夠取回、內容被執行各需要不同的證據，判斷時讀取回請求的原始回應本體。
  • 處理器常依路徑、位置或副檔名選定；上傳目錄若沿用了執行設定，存進去的資料就可能被當成程式。
  • 修補要一路控制到取回階段：允許清單加內容驗證、伺服器決定名稱與位置、儲存區不執行程式，取回時檢查授權與回應類型。只檢查副檔名不夠。

PortSwigger Academy 的對應練習（主題頁 File upload vulnerabilities）：

  • Remote code execution via web shell upload：找出上傳入口與實際取回位置，判斷每項證據支持的是「已上傳」「可取回」還是「已執行」。
