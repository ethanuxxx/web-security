6.1.1 語法照常解讀的請求

第 2、3 章的注入類漏洞有一個共同的樣子：使用者送來的資料被接進查詢、指令或頁面，改變了它們的語法解讀。在 SQL Injection 裡，資料庫把一部分資料當成 SQL 語法執行；在 XSS 裡，瀏覽器把一部分資料當成標記或腳本。

業務邏輯漏洞（business logic vulnerability，也叫 logic flaw）不必改變任何語法。數量欄位收到一個整數，優惠碼欄位收到一個存在的優惠碼，確認頁收到一筆普通的 GET，解析器照常解讀每一個值，被違反的是業務規則。問題出在網站對使用者行為的假設：假設價格欄位會原封不動送回來、假設數量是正數、假設有人走到確認頁之前一定已經付了錢。使用者不照這些假設做，網站就把合法的功能組合成設計者沒想過的結果。

這類問題和特定的程式語言、框架無關，掃描器也很難找到。掃描器能認出一段跑進 SQL 語法的輸入，卻不知道這家商店規定「優惠券每筆訂單只能用一次」。要判斷一筆請求有沒有問題，得先知道這個網站的業務規則。

狀態（state）
伺服器記錄「事情進行到哪裡」的資料，例如一張訂單目前是待付款、已付款或已出貨，帳戶餘額剩多少，哪張優惠券已經用過。
不變條件（invariant）
每一次操作之後都必須成立的業務規則，例如「餘額不能是負數」「訂單總額等於各商品單價乘數量再扣掉折扣」。

6.1.2 一家商店的購物流程

例子都發生在同一家商店 shop.example.com。每位顧客有一筆商店餘額，wiener 目前有 100 元；商品有咖啡豆（80 元）、帆布袋（20 元）、旅行背包（1,250 元）。從瀏覽器看，購物分成幾個畫面；從伺服器看，是幾筆各自獨立的請求：

  1. 加入購物車：POST /cart，送出商品編號與數量。
  2. 套用優惠碼：POST /cart/coupon。
  3. 結帳：POST /cart/checkout，伺服器核對總額與餘額，扣款並建立訂單。
  4. 確認頁：瀏覽器被導向 GET /cart/order-confirmation，顯示「訂單已成立」。

一張訂單在這個流程裡依序經過幾個狀態，每一次轉換都有進入條件：

把這家商店的規則寫成不變條件：

  • 每項商品的單價取自商店的商品資料，總額等於單價乘數量的總和，再扣掉折扣。
  • 數量是 1 到 99 之間的整數；總額不小於 0。
  • 結帳後餘額不小於 0。
  • 同一張優惠券在同一張訂單只能用一次。
  • 訂單只能沿上圖的實線前進。

後面每個例子，都是某一條不變條件在某一筆請求裡沒有被檢查。

6.1.3 前端送來的價格

商品頁的「加入購物車」按鈕是一張表單。為了讓購物車頁面不必再查一次商品資料，開發者把價格放進隱藏欄位，一起送出：

# 把一個旅行背包加入購物車
POST /cart HTTP/1.1
Host: shop.example.com
Cookie: session=DEMO123
Content-Type: application/x-www-form-urlencoded

productId=7&quantity=1&price=125000

price 以「分」為單位，125000 就是 1,250 元。伺服器把這三個值存進購物車，結帳時用購物車裡的 price 計算總額。

隱藏欄位不顯示在畫面上，但它和其他欄位一樣是請求本體的一部分。在 1.2 用過的 Burp 裡攔下這筆請求，把 price 換成 [改小的價格] 再送出（方括號代表被換掉的那段輸入），伺服器收到的就是新的值。購物車顯示背包只要幾元，結帳時的總額不超過 100 元，餘額檢查通過，訂單成立。

前端的各種限制都屬於同一類：數量欄位的 max="99"、JavaScript 檢查「數量必須大於 0」、灰掉的「套用」按鈕。這些限制只約束在瀏覽器裡操作畫面的人。請求一旦離開瀏覽器，就能在 Burp 裡改寫或重新送出，伺服器只看得到請求本身。Access Control 的「由使用者送來的角色」是同一個錯誤用在權限上，這裡用在價格上。

6.1.4 伺服器沒想到的數值

修掉價格欄位之後，伺服器改從商品資料取單價，只收商品編號與數量。數量仍然由使用者決定，而開發者可能只想過「使用者會填 1、2、3」。

負的數量

假設伺服器只檢查數量是整數，沒有檢查範圍。wiener 的購物車裡已經有一個背包，他再送一筆 POST /cart，商品是帆布袋，數量是 [負的數量]。伺服器照單全收：

品項單價數量小計
旅行背包1,25011,250
帆布袋20[負的數量]負數
總額1,250 減去帆布袋那一行抵掉的金額

負的那一行抵銷了一部分背包的價格。抵掉之後的總額若不超過餘額，結帳就通過；若伺服器另外檢查「總額不能是負數」，只要總額仍是正的，這張購物車也過得了關。背包出貨了，負數個帆布袋當然寄不出去。被違反的是「數量是 1 到 99 的整數」這一條，而總額的檢查看不出來。

大到繞回來的總額

這次伺服器檢查了每次加入的數量必須在 1 到 99 之間，但沒有限制購物車裡同一商品累積的總數，而且以「分」為單位，把總額存在 32 位元有號整數裡。32 位元有號整數能表示的範圍是 −2,147,483,648 到 2,147,483,647。計算結果超過上限時會發生整數溢位（integer overflow），接下來怎樣取決於語言的運算規則。Java 的 int 運算不報錯，結果直接回繞（wrap around）：從最小值那一端繼續往上算，像里程表跑過最大值後歸零。Rust 在開啟溢位檢查時會中止程式；資料庫欄位與型別轉換各有自己的錯誤處理。這裡的商店程式採用前一種規則，溢位後回繞：

數學上的結果存進 32 位元有號整數後
2,147,483,6472,147,483,647
2,147,483,648−2,147,483,648
3,000,000,000−1,294,967,296
4,294,967,2960

每一列的規則相同：結果超出範圍時，加上或減去 232（4,294,967,296），直到落回範圍內。

購物車裡的背包累積到 [讓總價回繞的數量] 時，系統存下的總額可能是一個很大的負數，也可能是一個看起來普通的正數，和這些背包的實際價格已經沒有關係。金額一旦失真，餘額檢查和「總額不小於 0」的檢查比較的都是錯的數字，結帳的判斷也就不再可靠。每一筆請求的數量都在 1 到 99 之間，單看任何一筆都合法；出錯的是累積起來的結果。Python 的整數沒有固定寬度，不會溢位，但資料庫欄位、其他語言寫的服務或轉成固定寬度的地方仍可能會。

檢查之後才被轉換的字串

同樣的落差也發生在字串上。註冊功能要求使用者名稱不可重複，流程大致是三步：用原樣的名稱查資料庫有沒有同名帳號，沒有就通過；把名稱轉成小寫，方便日後登入時不分大小寫比對；把轉換後的名稱寫入新帳號。

步驟名稱結果
輸入Alice使用者填的原樣名稱
查重複（區分大小寫）Alice資料庫裡已有別人以 alice 註冊，沒有 Alice，檢查通過
轉小寫alice與既有帳號的名稱相同
寫入alice兩個帳號共用同一個名稱：登入或重設密碼時分不出是誰，也可能覆蓋既有資料

檢查驗證的是 Alice，之後使用的是 alice。每一步單看都合理，錯在檢查和使用拿到的不是同一個值。

其他會在驗證後改變字串的處理，同樣值得檢查：欄位長度超過上限時的截斷、Unicode 正規化、去除前後空白。凡是儲存前後兩個值可能不相等的地方，都要把驗證放在轉換之後。

6.1.5 不照順序走的使用者

流程的每一步是一筆獨立的請求，瀏覽器照畫面順序送，請求本身卻沒有順序。Access Control 的多步驟流程和 Authentication 的第二個因素都看過跳過中間步驟的情況；購物流程裡有更多種變化。

跳過結帳

正常結帳時，POST /cart/checkout 核對總額與餘額，成功就扣款、建立訂單，再把瀏覽器導向確認頁：

# 結帳成功後，瀏覽器被導向這裡
GET /cart/order-confirmation?order-confirmed=true HTTP/1.1
Host: shop.example.com
Cookie: session=DEMO123

如果確認頁的處理程式看到 order-confirmed=true，就把目前購物車裡的商品當成已售出、安排出貨，那麼真正完成訂單的是確認頁。結帳時的總額與餘額檢查仍然存在，確認頁卻沒有回頭確認它們發生過：這個處理程式少了「這張訂單在伺服器上有成功付款的紀錄」這項檢查。只測正常購買與餘額不足的情況，網站看起來一切正常。確認頁能被打開，不表示付款發生過；付款有沒有成功，要由伺服器保存的紀錄回答。

重複同一步

同一筆請求送兩次，網站該怎麼反應，取決於這筆請求代表什麼。使用者網路斷線後重送同一筆付款，應該只扣一次款、只出一次貨；這叫冪等性（idempotency）：同一個業務操作執行一次和執行多次，結果相同。

常見做法是讓每個業務操作帶一個識別值（idempotency key），重送時沿用同一個值：伺服器把識別值和這次操作的參數綁在一起記錄，同一個識別值再出現時，回傳第一次的結果，不再執行一次。兩筆帶同一識別值的請求同時抵達時，伺服器要以原子方式先保留這個識別值，只讓其中一筆真正執行。識別值可以由伺服器發給頁面，也可以由客戶端產生。冪等的對象是「同一個操作」：顧客隔天再買一次同樣的商品是一筆新交易，不該被當成重送而擋掉，也不該和昨天那筆共用付款紀錄。

確認頁也有這個問題：每次載入都出一次貨的話，使用者重新整理頁面就會多收到一份。

換順序與在步驟之間改內容

另一種情況是步驟都做了，但順序或中間的資料變了。wiener 把一個咖啡豆放進購物車並結帳，伺服器扣款 80 元，訂單變成已付款；接著他在出貨前送出 POST /cart，把數量改成 10。若出貨步驟讀的是購物車目前的內容，沒有在付款當下鎖定訂單內容，付 80 元就會收到 10 包。訂單狀態圖上方那條虛線就是這種轉換。

還有一種是缺了某一步或某個欄位。登入後要先選擇角色（例如「顧客」或「內容編輯」）的網站，如果使用者把選角色那筆請求丟掉，直接打開首頁，程式可能套用某個預設角色；預設值若是權限最高的那個，跳過一步就等於升級。同樣地，把某個必填參數整個從請求裡拿掉（不是留空），程式可能走進另一條沒有檢查的分支。

6.1.6 商店自己的規則

有些規則只屬於這家商店的業務，例如折扣怎麼算、優惠券能不能並用。這些規則每家店都不同，漏洞也只有懂這門生意的人看得出來。

折扣的適用條件變了，還要重算

商店有一張優惠碼 BOOK15，只適用於「書籍」分類的商品，折扣金額為符合條件商品小計的 15%。折扣的適用條件是購物車的內容，而購物車在套用優惠碼之後仍然可以改。假設程式在套用的那一刻，檢查購物車裡至少有一本書，就把折扣率 cart.discount = 0.15 記在購物車上，之後計算總額一律從原價扣掉小計的這個比例。

wiener 先放一本書，套用成功，再把書移除，加進一台咖啡機。購物車記著折扣比例，咖啡機也被扣掉 15%。申請折扣時的條件成立，結帳時條件已經不成立，程式卻沒有重新判斷。

這類規則可以用一個問題來檢查：折扣依賴哪些輸入（商品分類、會員身分、訂單金額、日期），這些輸入一變，折扣是否重算。把折扣存成固定比例，輸入一變就失效；存成「套用了哪張優惠碼」，每次計算總額時再依當下的內容判斷，就不會出現這種落差。重算時還要只對符合條件的商品計算：只因購物車裡有一本書，就替整車打折，即使每次都重算，也不符合「僅限書籍」的規則。

輪流使用兩張優惠券

商店發了兩張優惠券，每張折 10%，規則是同一張券在同一張訂單只能用一次。程式的檢查寫成「這次送來的券是不是和上一次套用的那張相同」：

# 不安全的做法：只和上一張比較
if code == cart.last_coupon:
    return error("優惠券已使用")
cart.apply_discount(code)
cart.last_coupon = code

連續套用 A 兩次會被擋下；先 A、再 B、再 A，第三次比較的是 A 和 B，不相同，於是放行。A 和 B 輪流送，折扣就一直累加。規則說的是「用過的券」，程式只記住了「最後一張」。

可以兌現的折扣

當商店賣的東西本身就是錢，折扣就變成一台印鈔機。假設商店販售 100 元面額的禮物卡，而優惠券適用於所有商品：用九折買一張禮物卡付 90 元，兌換後餘額增加 100 元，每輪淨賺 10 元。每一步（買禮物卡、套用優惠券、兌換）都完全符合規則，只是規則的組合沒有人想過。這種問題只能從業務面修：例如禮物卡不適用折扣。

6.1.7 讓使用者端決定的狀態

有些網站把流程進行到哪裡交給使用者保管：隱藏欄位裡的 step=3、Cookie 裡的 discount_applied=true、付款服務導回網站時網址上的 paid=true。之後的請求帶著這些值，伺服器讀到「已付款」就當作已付款。

這和前面的價格欄位是同一個錯誤，只是被交出去的換成了狀態。paid=true 是請求裡的一段文字，任何人都能自己寫上。付款是否成功，要由伺服器向付款服務查證，或接收付款服務直接送到伺服器、可以驗證來源的通知，再寫進伺服器自己的訂單紀錄；瀏覽器帶回來的值只能用來決定要顯示哪一頁。來源可信的通知仍要逐項比對：這筆付款對應的是哪張訂單、金額與幣別是否等於應付金額、付款狀態是不是成功。同一筆付款的通知重複送達時，只入帳、出貨一次。

6.1.8 怎麼找出來

邏輯漏洞沒有固定的特徵字串，找它要從規則出發：

  1. 用正常帳號完整走一遍功能，在 HTTP history 列出每一步的請求，標出每一步改變了哪些狀態（購物車、訂單、餘額、優惠券）。
  2. 寫下這個功能應該維持的不變條件。
  3. 對每一筆請求問：拿掉某個參數會怎樣？數值換成 0、負數、極大值、很長的字串呢？跳過這一步、重送這一步、換到別的步驟之前或之後送呢？在兩步之間修改購物車或帳號資料呢？
  4. 每次測試後，回頭查狀態本身：重新載入帳戶頁看餘額、看訂單列表與訂單狀態。「訂單已成立」的字樣不夠，餘額沒扣、訂單卻存在，才是不變條件被打破的證據。

每次測試前記下起始的餘額與購物車內容。購物車裡留著上一次的商品，或餘額已經變了，就無法判斷差異來自哪一步。

6.1.9 防禦手法

伺服器端重新計算

凡是影響金額、權限或狀態的值，都由伺服器從自己的資料算出，請求只提供「使用者想要什麼」：

def add_to_cart(cart, product_id, quantity):
    product = db.get_product(product_id)        # 單價取自商品資料
    if product is None:
        return error("商品不存在")
    if not isinstance(quantity, int) or not 1 <= quantity <= 99:
        return error("數量必須是 1 到 99")
    if cart.quantity_of(product_id) + quantity > 99:
        return error("同一商品最多 99 件")
    cart.add(product.id, quantity)              # 不存使用者送來的價格

def cart_total(cart):
    # 每次需要總額時重算；金額用不會溢位的整數或十進位型別
    subtotal = sum(db.get_product(i.product_id).price_cents * i.quantity
                   for i in cart.items)
    return apply_discounts(cart, subtotal)      # 折扣也在這裡依目前內容重新判斷

累積的數量也有上限，金額使用不會溢位的型別，資料庫欄位也要容得下最大的合法總額。折扣在每次計算總額時依當下的內容重新判斷適用條件，購物車內容一變，條件不符的折扣自然消失。優惠券的檢查改成查「這張訂單用過的券的集合」。

把流程寫成明確的狀態機

訂單的狀態存在伺服器，所有轉換都經過同一個函式，由它檢查目前狀態與進入條件：

ALLOWED = {
    "cart":    {"pending"},
    "pending": {"paid", "cancelled"},
    "paid":    {"shipped", "refunded"},
}

def transition(order, new_state):
    if new_state not in ALLOWED.get(order.state, set()):
        raise InvalidTransition(order.state, new_state)
    if new_state == "paid" and not payments.confirmed(order.id):
        raise InvalidTransition(order.state, new_state)
    order.state = new_state
    order.save()

payments.confirmed 查的是伺服器自己保存的付款紀錄：要有一筆付款服務回報為成功的付款，屬於這張訂單，金額與幣別等於訂單的應付金額。訂單已經是 paid 時，ALLOWED 不允許再轉成 paid，重複的付款通知因此不會讓同一張訂單入帳兩次。

確認頁只讀取訂單目前的狀態並顯示出來，不負責把訂單變成已付款或安排出貨。結帳成立時，把商品、數量與金額複製成訂單內容並鎖定；之後修改購物車，只影響下一張訂單。每個會改變狀態的請求都檢查訂單屬於目前登入的使用者，這是 4.2 的授權檢查，和狀態檢查一起做。

不變條件寫成測試

前面列的不變條件可以直接變成自動化測試。除了測正常流程，也測每一種不該發生的轉換與數值：

def test_confirmation_does_not_complete_unpaid_order():
    cart = make_cart(user="wiener", balance=20, items=[("backpack", 1)])
    get("/cart/order-confirmation", user="wiener")
    assert balance("wiener") == 20
    assert orders_of("wiener") == []

def test_quantity_out_of_range_is_rejected():
    for q in (0, -1, 100):
        assert post_cart("wiener", "tote", q).status == 400

def test_same_coupon_twice_in_one_order():
    cart = make_cart(user="wiener", items=[("backpack", 1)])
    for code in ("A", "B", "A"):
        apply_coupon(cart, code)
    assert cart.discount_percent == 20

正式環境也可以在寫入資料庫前再檢查一次關鍵條件（例如餘額不小於 0），違反就中止這筆交易並留下紀錄。這不能取代前面的修補，但能讓漏掉的情況在造成損失前被擋下來。

檢查和使用同一個值

檢查之後才轉換字串的問題，要讓檢查的值和最後保存、使用的值一致：需要正規化（例如轉小寫、Unicode 正規化）的值，先正規化再檢查，存的也是檢查過的那一份；輸入超過欄位長度就拒絕，不要默默截斷。

把假設寫下來

多數邏輯漏洞來自沒說出口的假設：「數量一定是正的」「到得了確認頁就是付過錢」「券只會一張一張輪流用」。設計流程時，把每一步依賴的前提寫進文件，再推演使用者不照這個前提做時，伺服器會發生什麼事。PortSwigger 的 Business logic vulnerabilities 主題頁也把「了解業務領域」和「記錄每一步的假設」列為主要的預防方式。

6.1.10 小結

  • 注入類漏洞改變語法的解讀，業務邏輯漏洞違反業務規則，錯在網站對使用者行為的假設；找它要先寫出業務規則與不變條件。
  • 價格、數量、狀態旗標若由請求決定，使用者就能改寫；前端的隱藏欄位、輸入限制與灰掉的按鈕不約束直接送出的請求。
  • 負數、累積到溢位的數量、檢查後才被轉換的字串，讓單筆看似合法的值累積或轉換成違反規則的結果。
  • 流程的每一步都可能被跳過、重送、換順序；折扣與優惠券的條件要在結帳時依當下內容重新判斷。
  • 修補：金額與狀態在伺服器端計算與保存，用明確的狀態機控制轉換，把不變條件寫成測試，檢查與使用同一個值。

PortSwigger Academy 的對應練習（主題頁 Business logic vulnerabilities），只在 Lab 或其他獲明確授權的系統上測試：

  • Excessive trust in client-side controls：找出由請求決定的價格。
  • High-level logic vulnerability：數量欄位沒有範圍檢查時，總額會怎麼變。
  • Low-level logic flaw：累積的數量讓總額超出整數範圍。
  • Inconsistent handling of exceptional input：檢查時與保存後的電子郵件地址不一致。
  • Insufficient workflow validation：確認頁是否依賴可信的結帳結果。
  • Authentication bypass via flawed state machine：少走一步時程式套用了什麼預設狀態。
  • Flawed enforcement of business rules：優惠券的「只能用一次」實際檢查的是什麼。
  • Infinite money logic flaw：幾個各自合理的規則組合成可以重複獲利的循環。

這一節的每個檢查都假設請求一筆接一筆抵達：先查餘額、再扣款，先看優惠券有沒有用過、再記下已使用。下一節 Race Conditions 讓同一筆請求在同一瞬間送出很多次。每一筆都在別筆還沒寫回之前讀到「餘額足夠」「券還沒用過」，於是單獨看都正確的檢查一起放行，不變條件在檢查與寫入之間的空檔被打破。
