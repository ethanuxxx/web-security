本節模型：shop.example.com 的優惠碼套用

你在購物車頁輸入優惠碼 SAVE10 按下「套用」，網站依序做三件事：查這個購物車有沒有用過、沒用過就加上折扣、記下已使用。購物車頁隨後顯示折扣與新的合計。

shop.example.com 規定同一張優惠碼在同一個購物車只能用一次。你再輸入一次，網站回「這張優惠碼已經用過」。照畫面一筆一筆操作，規則看起來沒有漏洞。Business Logic Vulnerabilities 看的是請求的內容與順序，這一節多加一個變數：時間。如果兩筆套用優惠碼的請求幾乎同時抵達，伺服器會各自處理它們，兩邊的處理過程可能在時間上交錯。

6.2.1 檢查與更新之間

套用優惠碼的程式通常分三步：查這個購物車有沒有用過這張優惠碼；沒用過就把折扣加上去；最後記下「已使用」。三步之間各隔幾毫秒，用來查資料庫、計算金額、寫入資料。

網站伺服器同時處理許多請求，每筆請求由各自的執行緒或行程負責。兩筆請求讀寫同一份資料（這裡是同一個購物車的優惠碼紀錄），這份資料就是它們的共享狀態（shared state）。兩筆請求一前一後處理，第二筆看到的是第一筆寫完的結果；兩筆同時處理，第二筆可能在第一筆寫入之前就做了讀取。

右邊兩筆請求各自的步驟都沒有錯：讀到未使用，所以套用折扣，最後標記。錯在交錯之後的組合。最後資料庫裡的「已使用」紀錄只寫了一份（或寫了兩份相同的），折扣卻加了兩次。

這類問題稱為競態條件（race condition）：結果取決於多筆處理之間的時間先後，而程式沒有控制這個先後。上面的例子屬於最常見的一種，叫 TOCTOU（time-of-check to time-of-use，檢查時與使用時不一致）：做決定時讀到的狀態，到了動手時已經不是那樣。從檢查到寫入之間、允許另一筆請求插進來的那段時間，稱為 race window。它常常只有幾毫秒，甚至更短，但只要第二筆請求的讀取落在其中，就會讀到舊的狀態。

判斷要看業務規則有沒有被打破，不能只看回應。兩筆請求都回「已套用」，折扣不一定真的加了兩次；回應都正常，也不表示沒事。要回頭看購物車的折扣與總額。

6.2.2 超過次數與額度的限制

優惠碼重複使用屬於 limit overrun（超過上限）：網站規定某件事最多做幾次、最多用多少額度，平行送出的請求讓實際次數超過規定。下面這段處理程式就有這個問題：

# 先查、再寫：查詢與寫入之間沒有任何保護
def apply_coupon(cart_id, code):
    used = db.fetch_one(
        "SELECT 1 FROM cart_coupons WHERE cart_id = %s AND code = %s",
        (cart_id, code))
    if used:
        return "這張優惠碼已經用過"
    discount = lookup_discount(code)
    db.execute("UPDATE carts SET discount = discount + %s WHERE id = %s",
               (discount, cart_id))
    db.execute("INSERT INTO cart_coupons (cart_id, code) VALUES (%s, %s)",
               (cart_id, code))
    return "已套用"

第一個 SELECT 是檢查，最後的 INSERT 才讓檢查生效。兩筆請求都在對方 INSERT 之前執行 SELECT，就都會走到加折扣那一行。

餘額超用

帳戶或禮物卡餘額是同樣的結構，只是限制換成金額。假設帳戶有 100 元，扣款的程式先讀出餘額、在程式裡算出新餘額，再寫回：

balance = db.fetch_value("SELECT balance FROM accounts WHERE id = %s", (account_id,))
if balance < amount:
    return "餘額不足"
db.execute("UPDATE accounts SET balance = %s WHERE id = %s",
           (balance - amount, account_id))
pay_out(amount)

兩筆 80 元的提領同時進來：

帳戶付出 160 元，餘額卻顯示 20 元，B 的寫入蓋掉了 A 的結果。這種現象叫 lost update（更新遺失）。如果程式改成在資料庫裡做減法（balance = balance - 80），但檢查仍在前面單獨做，最後餘額會變成 −60：兩次扣款都記到了，卻都通過了「餘額夠不夠」的檢查。兩種寫法的帳面結果不同，錯在同一個地方：檢查和寫入是兩個分開的動作。

其他有次數限制的功能

同樣的結構出現在很多地方：每人只能評分一次的商品、只能兌換一次的禮物卡、驗證一次就失效的 CAPTCHA 答案。Authentication 的「猜密碼與嘗試次數」談過登入失敗次數的限制，計數若是「讀出次數、比對密碼、再把次數加一」，平行送出的一批猜測會在計數增加之前全部通過檢查，實際嘗試次數就超過上限。

6.2.3 為什麼難以重現

Race window 很短，兩筆請求要在伺服器上剛好交錯，抵達的時間差要比它更小。請求從你的電腦到伺服器要經過許多網路設備，每一筆的延遲都不一樣，這種延遲的隨機變動稱為網路抖動（network jitter）。即使兩筆請求在同一毫秒從你的電腦送出，抵達伺服器的時間仍可能差上數毫秒，足以錯過整個 race window。伺服器內部也有自己的抖動：排程、快取、資料庫連線池，都讓同樣的請求每次花費的時間不同。

所以同一個漏洞，有時十次才碰到一次，有時一次就成功；一輪沒有重現，不能據此判斷沒有競態。

讓請求同時湊齊

伺服器可以在請求還沒收完時就開始解析，但許多應用程式要等整筆請求到齊，才進入讀資料庫、檢查狀態這些會碰到 race window 的處理。在這個前提下，可以把每筆請求的大部分先送過去，只留下最後一小段，等所有請求的前段都到了，再把各自的最後一段一起送出。這樣一來，前段在網路上花了多少時間都不影響結果，影響「何時湊齊」的只剩觸發處理的最後一段。

在 HTTP/1.1，Burp 為每筆請求各開一條連線，先送前段，最後一段再在各條連線上同時送出，稱為 last-byte synchronization（最後位元組同步）。各條連線上的最後一段仍各自經歷網路抖動。

HTTP/2 允許多筆請求共用同一條 TCP 連線：每筆請求被切成許多 frame（訊框），交錯在同一條連線上傳送，稱為多工（multiplexing）。因此可以在一條連線上先送出每筆請求的前段，再把多筆請求的最後一個 frame 塞進同一個 TCP 封包；PortSwigger 的研究一次約放 20 到 30 筆。一個封包要嘛整個到達，要嘛整個沒到，這些請求就在同一刻湊齊，網路抖動對它們之間的時間差不再有影響。PortSwigger 的研究稱這種做法為 single-packet attack（單封包攻擊），Burp Suite 的 Repeater 以「平行送出一組分頁」的功能實作了它。

Single-packet attack 消除的是網路造成的時間差。伺服器內部的抖動仍在，所以一次送出多筆請求會比只送兩筆容易碰到 race window：即使利用漏洞只需要兩筆，探測時多送一些，交錯的機會就大一些。

以 Session 為單位的鎖

有些框架會讓同一個 Session 的請求排隊處理。PHP 預設的檔案式 Session 處理器在請求開啟 Session 時取得一把鎖，直到請求結束或明確關閉 Session 才釋放，同一個 Session 的請求因此一次只跑一筆。帶著同一個 Session Cookie 平行送出的請求，在伺服器上被排成了一列，看起來就像沒有競態。這把鎖只保護同一個 Session 內的請求；換成兩個不同的 Session 各送一筆，就不會互相等待。所以測試時若所有請求都被依序處理，可以改用不同的 Session 再比較一次。

反過來，有些情況必須用同一個 Session：優惠碼的例子裡，購物車是依 Session 找到的，兩筆請求要作用在同一個購物車，就得帶同一個 Session Cookie。用哪種 Session 組合，取決於要測的共享狀態屬於誰。

6.2.4 先依序，再平行

PortSwigger 把找競態的過程分成三步：預測（predict）、探測（probe）、證明（prove）。

  1. 預測：找出和安全有關、而且有多筆請求會讀寫同一筆資料的功能，例如有次數或金額限制的操作、會改變帳號狀態的流程。也要確認測試的請求真的作用在同一筆資料上：兩筆請求各用一個購物車，就沒有共享狀態可以競爭。
  2. 探測：先把同一組請求依序送出，記下正常的回應與最後狀態，作為基準。把狀態還原到同樣的起點，再平行送出同一組請求，比較兩次結果。任何差異都值得記下：回應內容不同、多出一封郵件、額度變化與預期不符。
  3. 證明：把請求刪減到能重現差異的最少組合，重複確認，再判斷影響。影響以業務狀態為準：最後的折扣、訂單、餘額，或帳號的實際權限。

依序送出的基準很重要。沒有它，就無法分辨某個回應是競態造成的，還是這個功能本來就會這樣回應。

6.2.5 跨端點的競態

前面的例子是同一個端點的多份請求。競態也可能發生在兩個不同的端點之間。想像結帳流程：POST /cart/checkout 先檢查購物車總額不超過可用額度，扣款，再把購物車裡的商品轉成訂單。這三件事在同一筆請求裡依序完成，中間有一小段時間差。若此時另一筆 POST /cart 把一件新商品加進同一個購物車，而它落在「檢查總額」之後、「轉成訂單」之前，訂單裡就會多出一件沒有算進金額的商品。

兩個端點平行送出，比同一個端點更難對齊。原因有兩類：

  • 網路架構：網站前面常有反向代理或負載平衡器。如果它要先和後端建立連線，第一筆請求就會比後面的慢。這種延遲對所有請求大致相同，可以先送一筆無害的請求（例如讀取首頁）讓連線先建立起來，再送真正要比較的請求。這稱為 connection warming（連線暖機）。
  • 端點各自的處理時間：結帳要查額度、算金額，加入商品只寫一筆資料，兩者花的時間本來就不同。暖機改變不了這種差異。這時要估計兩邊的處理時間差，讓 race window 與另一筆請求的處理時點重疊。

6.2.6 同一個端點、不同的值

同一個端點也可能在帶著不同參數的請求之間發生競態。這類問題常出在把一組相關的欄位分開寫進 Session 的處理程式。以結帳前的運費試算為例，假設 POST /cart/shipping 的處理程式這樣寫，而且兩個欄位各自寫進其他請求立刻看得到的共享 Session 儲存，沒有把這段流程串行化的鎖：

  1. 把請求裡的寄送目的地寫進 Session：session["ship_to"] = destination。
  2. 向物流公司的報價服務查詢這個目的地的運費，這一步要透過網路，花的時間比其他步驟長。
  3. 把查到的運費寫進 Session：session["ship_fee"] = fee。

這個漏洞只在兩個欄位分別寫入、而且寫入立刻被其他請求看到時才成立。同一個 Session 的鎖若涵蓋整段流程（見上文「以 Session 為單位的鎖」），兩筆請求會排隊，不會交錯；框架若在請求內只改本地副本、結束時整份 Session 一次寫回，結果就是最後寫回的那一份，不會出現 B 的目的地配 A 的運費。

結帳頁之後直接讀 Session：收貨地址用 ship_to，運費用 ship_fee。依序處理時，兩個欄位一定成對。攻擊者用同一個 Session 同時送出兩筆試算請求，一筆選國內（運費 60 元），一筆選海外（運費 480 元）：

只有在交錯剛好是這個順序時，才會留下錯配的結果：A 先開始、卻因為報價較慢而最後寫入。所以要像「先依序，再平行」那樣，平行送出多組請求來探測，並在結帳頁確認實際讀到的兩個值。最後攻擊者以 60 元付款，貨品寄往海外。

處理過程中要呼叫外部服務、等待佇列或背景工作的操作，間隔本來就長，race window 也跟著變寬，特別值得檢查。

6.2.7 請求內部的暫時狀態

一筆請求在伺服器裡可能經過好幾個中間狀態，只是它們存在的時間很短，平常觀察不到。Authentication 的「第二個因素」談過，第一步通過後 Session 應該標成「還差第二因素」。如果處理程式先把 Session 設成已登入，下一行才補上「還需要第二因素」的標記，這兩行之間就有一段時間 Session 是完整登入的狀態。和登入請求平行送出一筆讀取帳號頁的請求，就可能落在這段時間裡。

部分構造的物件

物件分好幾步建立時，中間會有欄位還沒填好的時刻，這稱為 partial construction（部分構造）。例如註冊時，程式先在資料庫新增使用者那一列，下一個步驟才產生並寫入這個帳號的 API 金鑰。兩步之間，這一列的 api_key 欄位是空值（NULL）。

如果某個端點驗證 API 金鑰的方式是「請求帶來的值和資料庫裡的值相等就放行」，而請求可以送出 [會被框架解析成空值的參數寫法]，那麼在這段時間裡，空值就會和資料庫裡的空值相符。方括號代表被換掉的那段輸入。很多框架在解析參數時，會把某些寫法轉成空陣列或空值，攻擊者只要讓自己送出的值在比較時等於「尚未設定」就夠了。

以時間產生的 token

有些 token 只依據高解析度的時間戳記產生，沒有其他隨機來源。兩筆請求若在同一刻被處理，會拿到相同的 token。平行送出一筆替自己帳號、一筆替別人帳號的重設請求，自己信箱收到的 token 就可能和別人的一樣。這是 token 產生方式的問題，平行請求只是讓它被利用的手段；修補是改用密碼學安全的隨機數產生 token。

6.2.8 防禦手法

有效的防禦

修補的目標是讓「檢查狀態」和「依結果寫入」成為一個原子操作（atomic operation）：在其他請求看來，它要嘛整個還沒發生，要嘛整個已經完成，中間沒有可以插進來的時刻。這件事交給資料庫做，因為共享狀態本來就在資料庫裡，資料庫也有現成的機制。

把條件寫進更新語句

最直接的做法是把檢查放進同一條更新語句的條件裡，讓資料庫一次完成：

-- 餘額足夠才扣款；檢查與扣款是同一條語句
UPDATE accounts
SET balance = balance - 80
WHERE id = 7 AND balance >= 80;
-- 受影響的列數為 0：餘額不足，拒絕這筆提領

資料庫更新一列時會先鎖住它。在 PostgreSQL 預設的 Read Committed 下，第二筆 UPDATE 要等第一筆所屬的交易結束；第一筆提交後，它對更新後的餘額 20 重新判斷 WHERE 條件，條件不成立，受影響的列數是 0。應用程式依受影響的列數決定是否付款，就不會再有兩次 80 元的提領。

唯一性約束

「同一個購物車同一張優惠碼只能出現一次」可以直接寫成資料表的規則：

ALTER TABLE cart_coupons
  ADD CONSTRAINT one_use_per_cart UNIQUE (cart_id, code);

套用優惠碼時先寫入使用紀錄，寫入成功才加折扣，兩件事放在同一個交易裡：

def apply_coupon(cart_id, code):
    try:
        with db.transaction():
            # 同一購物車、同一優惠碼只能有一列；第二筆會在這裡失敗
            db.execute("INSERT INTO cart_coupons (cart_id, code) VALUES (%s, %s)",
                       (cart_id, code))
            db.execute("UPDATE carts SET discount = discount + %s WHERE id = %s",
                       (lookup_discount(code), cart_id))
    except UniqueViolation:
        return "這張優惠碼已經用過"
    return "已套用"

兩筆請求同時寫入同一組 (cart_id, code) 時，後到的那筆會等前一筆的交易結束。前一筆提交了，後到的這筆收到違反唯一性的錯誤；前一筆撤銷了，這筆就能成功寫入。收到錯誤時，交易必須整筆撤銷，折扣與使用紀錄才會一起不生效。上面的 db.transaction() 在例外離開 with 區塊時撤銷整筆交易。

MySQL InnoDB 的重複鍵錯誤本身通常只撤銷出錯的那條語句，程式若攔下錯誤後照樣提交，同一交易裡先前已執行的語句會留下來。唯一性約束也適合當作縱深防禦：即使應用程式其他地方的檢查寫錯了，資料庫仍然不會存進第二份。

交易與隔離等級

交易（transaction）把幾個資料庫操作綁成一組，要嘛全部生效，要嘛全部撤銷。交易同時執行時彼此能看到多少，由隔離等級（isolation level）決定。常見的預設值並不會讓一般的讀取互相等待：PostgreSQL 預設是 Read Committed，MySQL 的 InnoDB 預設是 Repeatable Read，在這兩種設定下，兩個交易各自執行一般的 SELECT，都能讀到「還沒用過」，交錯照樣發生。所以只把開頭那段先查後寫的程式包進交易，問題還在。

要讓第二筆請求等待，可以在讀取時明確上鎖。SELECT ... FOR UPDATE 會鎖住讀到的列，其他交易要讀取並鎖定或修改同一列時，必須等這個交易提交（commit）或撤銷。以優惠碼為例，要檢查的是「使用紀錄還不存在」，還沒有現存的紀錄列可以鎖；這時鎖住購物車那一列，讓同一個購物車的操作排隊。下圖以 PostgreSQL 的 Read Committed 為例：

B 取得鎖之後，下一條普通 SELECT 在 Read Committed 下會讀到 A 已提交的使用紀錄。MySQL InnoDB 預設的 Repeatable Read 不同：交易裡第一次普通讀取就建立快照，之後的普通 SELECT 都讀這份快照。如果 B 在上鎖之前已經讀過資料，就算等到了鎖，仍會讀到舊快照裡「沒有使用紀錄」。要讓這個做法在 InnoDB 上有效，鎖購物車列必須是交易裡的第一個讀取，或者查使用紀錄時也改用 FOR UPDATE、FOR SHARE 這類讀取最新版本的鎖定讀取。

這個做法還要求每一條會檢查或改寫這個購物車優惠碼的程式路徑都先鎖同一列；只要有一條路徑沒鎖，它就不會排隊。前面的唯一性約束仍保留，當作最後一道防線。

另一種做法是把隔離等級提高到 Serializable：資料庫保證結果等同於把交易一個接一個執行，偵測到無法這樣排列的交錯時，會讓其中一個交易失敗。應用程式要準備好處理這種失敗，通常是重試或回報錯誤。

Session 裡的狀態

運費試算的例子錯在目的地與運費分兩次寫進 Session，中間還夾著一段外部查詢。修補方式：

  • 不把推導出來的值存下來，也不在流程中途重讀會變動的目的地。結帳時只讀一次 ship_to，形成訂單快照，之後用同一份快照向報價服務取得運費（快取鍵也要包含目的地與計價條件）、計價並建單。若允許途中變更目的地，就比對版本，不符則拒絕或重新報價；重新報價也必須針對同一份目的地，否則仍可能配出海外目的地加國內運費。
  • 不得不放在 Session 的相關欄位，一次一起更新，例如先在區域變數算出目的地與運費，再用一次寫入同時存入。有些框架或 ORM（Object-Relational Mapping，把資料表對應成程式物件的函式庫）會把多次欄位修改分開寫出，要確認它們是一起生效的，並且是原子保存。
  • 以 Session 為單位的鎖能讓同一個 Session 的請求排隊，保護只屬於這個 Session 的狀態，而且只約束遵守同一把鎖的路徑。資料庫裡的共享資料，例如餘額、庫存、優惠碼的使用次數，要用資料庫本身的原子操作保護。

部分構造的問題也是同樣的思路：物件要一次建立完整，或在完成之前不讓其他請求看到它；比對金鑰或 token 時，空值與未設定一律視為不相符。

6.2.9 小結

  • 競態發生在多筆請求讀寫同一份共享狀態、而檢查與寫入是兩個分開的動作時；從檢查到寫入的那段時間就是 race window。
  • Limit overrun 讓優惠碼、禮物卡、餘額、嘗試次數超過限制；判斷影響要看最後的業務狀態，不看回應數量。
  • 網路抖動讓請求抵達時間散開，所以競態難以重現；single-packet attack 把多筆請求的最後一段放進同一個封包，讓它們同時湊齊。
  • 競態可以跨端點、可以在同一端點帶不同的值，也可以藏在一筆請求內部的暫時狀態裡，例如部分構造的物件。
  • 修補是讓資料庫負責檢查與寫入的原子性：條件更新、唯一性約束、上鎖或足夠的隔離等級；Session 鎖只保護同一個 Session 的狀態。

PortSwigger Academy 的對應練習（主題頁 Race conditions）：

  • Limit overrun race conditions：比較依序與平行送出同一筆套用優惠碼的請求，並從購物車總額判斷結果。
  • Bypassing rate limits via race conditions：登入失敗次數的計數在平行請求下失效。
  • Multi-endpoint race conditions：讓兩個不同端點的處理時點重疊。
  • Single-endpoint race conditions：同一端點帶不同的值，觀察待確認的電子郵件地址與確認信內容之間的競態。
  • Partial construction race conditions：在物件尚未建立完整的時間裡通過檢查。
  • Exploiting time-sensitive vulnerabilities：辨認只依時間產生的 token。

到這裡為止，出問題的都是同一個應用程式與它自己的資料：請求的順序、內容與時間。第二部分把範圍擴大到網站背後的其他元件。網站常常替使用者去做別的事：抓取一個網址的內容、解析上傳的 XML、把資料交給範本引擎。下一章從 Server-Side Request Forgery 開始：伺服器依使用者提供的網址替他連線時，連得到的地方往往比使用者自己連得到的多，包括只對內部開放的服務。
