本節模型：shop.example.com 的商品搜尋頁

你在商店的搜尋框輸入「teapot」按下搜尋，瀏覽器把關鍵字放在網址的 q 參數裡送出請求。伺服器不讀檔、也不呼叫外部程式，只是把關鍵字放回 HTML，組成結果頁上方的「你搜尋的是：teapot」，連同商品數量一起回傳。

第 2 章到 OS Command Injection 為止，解讀輸入的都是伺服器上的元件：檔案系統、檔案處理器、資料庫、shell。回應送到瀏覽器之後，還有一個解讀者：瀏覽器的 HTML 解析器（把 HTML 文字讀成頁面結構的元件）。伺服器放進回應的文字，在瀏覽器裡可能變成新的頁面結構，甚至變成會執行的程式。

3.1.1 瀏覽器怎麼讀回應

在 Seeing the Web Through the Browser 看過：回應是一段 HTML 文字，瀏覽器讀完後建出 DOM（Document Object Model，文件物件模型）這棵節點樹，畫面依 DOM 畫出。把文字讀成節點的那個元件稱為 HTML 解析器（HTML parser）。例如搜尋結果頁的這一段：

<!-- 搜尋結果頁的一段 -->
<h1>搜尋結果</h1>
<p>你搜尋的是：teapot</p>
<p>找到 2 件商品。</p>
<script src="/static/search.js"></script>

解析器逐字讀這段文字。看到 < 加上標籤名稱，它就知道一個元素開始了；直到對應的結束標籤，中間的字是元素的內容。你搜尋的是：teapot 因此成為段落元素底下的一個文字節點（text node），畫面上只會顯示成字。

最後一行的 script 元素不顯示在畫面上。它告訴瀏覽器去載入 /static/search.js 這個檔案，並把內容當成 JavaScript 執行。JavaScript 是瀏覽器內建能執行的程式語言，網站用它在頁面載入後改變內容、回應點擊、向伺服器發出請求。一段 JavaScript 常由函式呼叫（function call）組成，例如 showResults(2) 表示「執行名為 showResults 的功能，並交給它數字 2」。你不必會寫 JavaScript，只要知道 HTML 裡有些結構會讓瀏覽器執行程式，script 元素是最直接的一種。

如果使用者想在畫面上看到 < 這個字元本身，伺服器要寫成字元參照（character reference）&lt;。解析器看到 &lt; 會產生字元 <，放進文字節點，不會把它當成標籤的開頭。同樣地，&gt; 代表 >，&amp; 代表 &，&quot; 代表雙引號。

沒有攻擊者也會出錯

商店的衣物有尺寸標示，有人會搜尋「T 恤 <XL>」。伺服器若把搜尋字直接接進 HTML，回應會是：

<!-- 未經處理就接入的搜尋字 -->
<p>你搜尋的是：T 恤 <XL></p>

解析器讀到 <XL>，把它當成標籤的開頭，建出一個名為 xl 的元素；瀏覽器不認得這個名稱，也照規則建立。畫面上只顯示「你搜尋的是：T 恤」，使用者打的 <XL> 從畫面上消失了。正確的回應應該是：

<!-- 搜尋字以字元參照寫入 -->
<p>你搜尋的是：T 恤 &lt;XL&gt;</p>

這次解析器只建出一個段落，裡面的文字節點是「你搜尋的是：T 恤 <XL>」，和使用者輸入的一模一樣。兩份回應只差在伺服器寫入時有沒有轉換那幾個字元，解析器建出的 DOM 卻不同：前者讓使用者的資料參與了頁面結構。

3.1.2 資料變成程式

同一個缺陷落在攻擊者手上，結果就不只是排版錯亂。資料若能決定頁面上出現哪些元素，就能讓解析器建出一個會執行程式的元素。這類漏洞稱為跨站腳本（Cross-Site Scripting，縮寫 XSS；用 X 是為了不和樣式表 CSS 混淆）：網站把不可信的輸入放進回應，瀏覽器把其中一部分當成網站自己的程式執行。名稱來自早期的案例，指攻擊者讓別人的網站替他送出腳本。

下圖並排三種回應。方括號代表被換掉的那段輸入，[攻擊者插入的 HTML 片段] 指一段描述新元素的文字，那個元素被解析後會執行程式。

中間那一列，伺服器的程式碼和正常時完全相同，只是拿到的輸入不同。解析器無從分辨哪些標籤是開發者寫的、哪些是從搜尋欄位來的，它看到的只是一整段 HTML 文字。第三列用字元參照寫入同樣的片段，解析器只產生文字，畫面上會顯示那串字的原樣，沒有任何東西被執行。

和 OS Command Injection 比較：命令注入是資料在伺服器的 shell 裡變成命令，XSS 則是資料在使用者的瀏覽器裡變成程式。兩者都發生在「把資料接進另一種語言的文字」這一步，執行的地點不同。

3.1.3 以網站的身分執行

瀏覽器同時開著許多網站，卻不讓一個網站的程式讀另一個網站的頁面。區分的單位是來源（origin）：網址的協定、主機名稱與連接埠三者合起來。https://shop.example.com 和 https://blog.example.com 是不同的來源。瀏覽器依同源政策（same-origin policy，SOP）限制：一個來源的程式，通常不能讀取另一個來源的頁面內容或回應。跨站的細節與例外在第 5 章 CSRF, CORS, and Cross-Site Trust 討論，這裡只需要這條基本規則。

XSS 正是利用這條規則。被插入的程式出現在 https://shop.example.com 送來的回應裡，瀏覽器就把它當成這個來源的程式，給它和網站自己的 search.js 一樣的權限。這段程式可以：

  • 讀取並修改目前頁面的 DOM，包括只有登入者才看得到的內容，例如帳號資料或表單裡的隱藏欄位。
  • 向同一個網站發出請求。瀏覽器會照常附上這個網站的 Cookie（見 HTTP Requests and Sessions），所以伺服器會把這些請求當成使用者本人的操作；同源的回應內容，程式也讀得到。
  • 讀取沒有設定 HttpOnly 屬性的 Cookie。
  • 改寫頁面的外觀，例如在網站原本的網址下顯示一個假的登入框。

被攻擊的是開啟頁面的那位使用者。攻擊者不需要知道他的密碼，只要讓他的瀏覽器在這個網站的頁面裡執行一段程式，這段程式就能以他的登入狀態行事。

3.1.4 兩條送達路徑

依不可信的輸入怎麼進到受害者收到的回應，XSS 常分成兩類。

反射型 XSS（reflected XSS）：輸入在同一次請求的回應中出現。搜尋頁就是典型例子：搜尋字寫在網址的查詢參數中，伺服器把它放回當次的結果頁。每觸發一次，受害者的瀏覽器就要送出一次帶有該輸入的請求。最常見的方式是誘使他點開準備好的連結；自動送出的表單或頁面導向，也能讓他的瀏覽器送出同樣的請求。輸入沒有被保存，只有送出這個請求的瀏覽器會收到那份回應。

儲存型 XSS（stored XSS）：輸入先被伺服器保存，之後在別的回應中顯示。商品頁的評論就是例子：攻擊者送出一則評論，網站把它存進資料庫；之後任何人打開那個商品頁，伺服器都會把評論放進頁面。受害者只要正常瀏覽就會受影響，不需要點任何特別的連結。

這兩個名稱描述資料怎麼抵達瀏覽器，不代表嚴重程度的排序。儲存型常被認為較嚴重，因為受害者不必做任何特別的事，而且一則評論可能被大量使用者看到；但反射型若出現在管理介面，受害者是管理員，影響同樣可觀。常見的第三個名稱 DOM 型 XSS（DOM-based XSS）換了分類的角度，看的是不安全的處理發生在哪裡：頁面上的 JavaScript 自己讀取網址等來源，在前端以不安全的方式寫進 DOM。所以它可以和前兩類重疊，伺服器反射或保存的資料，也可能再被前端程式這樣寫進 DOM。

3.1.5 從請求到 DOM

用商店的搜尋頁逐步走一次，請求與回應都省略了大部分標頭。

正常的搜尋

GET /search?q=teapot HTTP/1.1
Host: shop.example.com
  1. 取值：伺服器解析網址的查詢字串，得到參數 q 的值 teapot。
  2. 組回應：伺服器的程式把這個值接進結果頁的模板，產生 <p>你搜尋的是：teapot</p>，連同頁面其他部分一起回傳。
  3. 解析：瀏覽器的 HTML 解析器讀這份回應，建出段落元素與裡面的文字節點。
  4. 執行網站自己的程式：解析到 script 元素時，瀏覽器載入並執行 /static/search.js。這是開發者寫的程式。
  5. 畫面：使用者看到「你搜尋的是：teapot」。

參數被換掉時

攻擊者準備一個連結，把 q 的值換成 [攻擊者插入的 HTML 片段]，再設法讓已登入的使用者點開。網址裡的特殊字元會經過 URL 編碼，伺服器取值時先解碼，拿到的就是那段片段的原文。

  1. 取值：和正常時一樣，伺服器得到一個字串，只是內容不同。
  2. 組回應：程式照樣把字串接進 HTML。如果沒有把特殊字元轉成字元參照，回應裡就出現 <p>你搜尋的是：[攻擊者插入的 HTML 片段]</p>。
  3. 解析：邊界在這一步被越過。解析器把片段讀成標籤，建出一個新的元素，如上方三種回應的對照圖中間那一列。
  4. 執行：那個元素讓瀏覽器執行 [會被當成程式執行的片段]。它出現在 shop.example.com 的頁面裡，所以和 search.js 擁有相同的來源。
  5. 畫面：使用者可能什麼都沒察覺，頁面看起來和平常一樣。

整個過程中，伺服器沒有執行攻擊者的任何東西，HTTP 請求的格式也完全合法。問題出在第二步把資料接進 HTML 的方式，後果則在第三、四步的瀏覽器裡發生。

3.1.6 影響與界限

判斷一個 XSS 能造成什麼，要回到「程式在誰的瀏覽器、哪個來源、以誰的身分執行」：

  • 執行地點在瀏覽器。注入的程式不能直接讀伺服器的檔案或資料庫，這點和命令注入不同。它能碰到的伺服器資料，是受害者本來就能透過網站取得的那些。
  • 能力等於受害者在這個網站的權限。一般會員打開頁面，程式能以會員身分操作；管理員打開同一頁，程式就能使用管理功能。儲存型 XSS 若出現在管理員會檢視的頁面，例如待審核的評論，影響會大得多。
  • 範圍限在這個來源。依同源政策，程式通常讀不到其他網站的頁面。其他網站若特意開放跨來源存取，情況會不同，那是第 5 章的主題。
  • HttpOnly 只擋住讀取 Cookie 的值。Cookie 設了 HttpOnly，頁面中的 JavaScript 就讀不到它，Session 識別字比較不容易被帶走。但程式從頁面發出的同源請求仍會自動附上這個 Cookie，所以在頁面開著的期間，它還是能以使用者的身分讀資料、送出操作。
  • 需要有人開啟頁面。反射型要受害者送出那個請求，儲存型要有人瀏覽含有資料的頁面。沒有人開啟，程式就不會執行。

練習環境常以「讓瀏覽器跳出一個對話框」作為完成條件。對話框出現，表示程式在這個頁面執行了，但從它看不出程式讀不讀得到 Cookie、能不能完成某項操作。評估影響時，要另外確認 Cookie 屬性、受害者的權限，以及頁面上有哪些功能可以被呼叫。

3.1.7 辨認反射位置

辨認 XSS 先要找到輸入在回應裡出現的位置，再判斷它在那裡被當成什麼。

  1. 送一個獨特的標記。在欄位裡輸入一個不會和頁面原有文字撞在一起的普通字串，例如 demo7731。它只有字母和數字，用來定位，不會改變頁面結構。
  2. 在原始回應中搜尋。到 DevTools 的 Network 面板或 Burp Suite 看回應原文，找出標記出現的每一處。不要只看 Elements：那裡顯示的是解析後的 DOM，已經看不出原文寫的是字元參照還是原字元。
  3. 看它落在哪裡。標記可能在元素的文字中、某個屬性的值裡，或一段 JavaScript 裡。不同位置由不同的規則解讀；搜尋頁的例子都落在元素的文字裡。
  4. 看特殊字元有沒有被轉換。在標記旁邊加上 HTML 會特別解讀的字元，觀察回應裡它們是原樣出現，還是變成 &lt; 這類字元參照。
  5. 儲存型要看別的頁面。輸入可能在送出時沒有顯示，之後才出現在商品頁、個人資料頁或管理介面。記下輸入的地方和顯示的地方，兩者常不是同一頁。

回應裡出現了輸入，只說明這裡有反射。搜尋頁的值落在元素的文字中；若特殊字元都已轉成字元參照，而且這個值之後沒有再被前端程式當成 HTML 寫入，這一處就不構成 XSS。落在屬性或 JavaScript 裡的值，要依那個位置的規則另外判斷。另外，Burp Suite 的 Repeater 只顯示回應文字，不會執行頁面上的 JavaScript；要確認程式真的執行，必須讓瀏覽器開啟那個回應。

3.1.8 防禦手法

有效的防禦

輸出時依位置編碼

修補的位置在資料寫進回應的那一刻。輸出編碼（output encoding，也常稱 escaping）是指依資料將要放進的位置，把會被解讀成語法的字元轉成安全的表示法。資料放在 HTML 元素的文字中時，至少把 &、<、> 轉成 &amp;、&lt;、&gt;。如果引號也一併轉換，同一個函式也能用在加了引號、名稱固定的一般文字屬性（例如 title）。轉換後，解析器只會產生文字節點，畫面顯示的仍是使用者原本輸入的字。

這條規則只適用於 HTML 元素的文字和上述的一般文字屬性。事件處理屬性的值會先還原字元參照，再交給 JavaScript 執行；網址屬性的值還要經過 URL parser；JavaScript 程式碼裡的字串也有自己的規則。這些位置需要不同的處理，有些位置任何編碼都不夠安全，不應放入不可信資料。各位置的比較見 Output Contexts and DOM-Based XSS。

交給模板引擎

多數網站用模板引擎（template engine）產生 HTML：開發者先寫好固定的頁面骨架，再標出要填入資料的空位。現代模板引擎多半預設會對填入的資料做 HTML 編碼，開發者不必手動轉換每個字元。常見的錯誤來自繞過這個預設：

  • 使用模板的「原樣輸出」功能，把資料標記成「已經安全、不需編碼」。
  • 不用模板，而是在程式裡用字串相接的方式組出 HTML。
  • 在前端用 JavaScript 把資料當成 HTML 寫進頁面，而不是當成文字。這屬於 DOM 型 XSS。

檢查程式碼時，留意每一個把資料當成 HTML 輸出的地方，確認那份資料不來自使用者，或已經過 HTML 清理器（見下一小段）處理。

需要保留格式時

有些功能本來就要讓使用者寫一部分 HTML，例如可以加粗體、連結的評論編輯器。這時編碼會把格式也一起變成文字，不合用。做法是使用維護中的 HTML 清理器（HTML sanitizer）函式庫：它解析使用者送來的 HTML，只保留允許清單中的元素與屬性，其餘移除。不要自己用字串替換寫一個；HTML 的解析規則很多，自製的過濾器幾乎一定會漏。

驗證有固定格式的輸入

商品編號、日期、排序方式這類欄位有明確的格式，伺服器應該拒絕不符合的值。這能縮小攻擊面，但搜尋字、評論這種自由文字無法靠驗證排除所有特殊字元，仍然要靠輸出編碼。

縱深防禦

內容安全政策（Content Security Policy，CSP）是網站以回應標頭告訴瀏覽器的一組限制，例如「只執行來自這些位置的程式，頁面內嵌的程式不要執行」。設定嚴格時，即使有片段被注入，瀏覽器也可能拒絕執行。把 Session Cookie 設成 HttpOnly，則減少了 Cookie 值被讀走的機會。這兩項都只是在輸出處理出錯時降低損害，不能代替正確的編碼。

3.1.9 小結

  • 伺服器送出的回應由瀏覽器的 HTML 解析器讀成 DOM；未經轉換的使用者資料可能變成新的元素，其中有些會讓瀏覽器執行程式。
  • 注入的程式出現在網站自己的回應裡，因此擁有網站的來源，能讀寫頁面、以受害者的登入狀態向網站發出請求。
  • 反射型的輸入在當次回應中出現，每次都要受害者的瀏覽器送出帶有該輸入的請求；儲存型先被保存，之後每位閱覽者都會收到。
  • 影響受限於受害者的權限與這個來源；HttpOnly 讓程式讀不到 Cookie 的值，但擋不住它在頁面中代替使用者操作。
  • 修補在輸出端：依位置編碼，交給預設會編碼的模板，避免原樣輸出 HTML；需要格式時用清理器。CSP 與 HttpOnly 是縱深防禦。

  • Reflected XSS into HTML context with nothing encoded：在回應原文找到搜尋詞，再對照解析後的 DOM，看特殊字元有沒有被轉換。
  • Stored XSS into HTML context with nothing encoded：說明輸入在哪一步被保存、在哪一份回應中重新出現。

搜尋頁的例子都把輸入放在 HTML 元素的文字裡，所以轉換角括號就足以守住邊界。下一節 Output Contexts and DOM-Based XSS 比較其他位置：同一個搜尋字放進屬性的引號中、一段 JavaScript 字串裡，或由前端程式從網址讀出再寫進頁面時，邊界由不同的字元決定。
