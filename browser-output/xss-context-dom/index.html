點地圖：到首頁地圖看這一章

本節模型：shop.example.com 的商品搜尋頁

同樣輸入「teapot」按下搜尋，這次要看網站把關鍵字放進回應的哪些地方：結果標題裡、搜尋框裡（方便你修改後再搜一次），以及頁面上一小段統計用的 JavaScript 裡。開發者對三個位置做的是同一種處理，結果在標題裡沒事，在搜尋框或腳本裡卻可能讓字串改變頁面結構。

Cross-Site Scripting Basics 談的是輸入落在 HTML 標籤之間、被 HTML parser 當成標記解讀的情況。輸入也可能落在標籤的屬性值（例如搜尋框的 value="…"）、網址、JavaScript 與 CSS 裡。資料流也可以不經過伺服器的回應：頁面上的 JavaScript 自己讀取一個值，再寫進頁面。

3.2.1 同一個值，不同的解讀者

瀏覽器拿到一份 HTML 回應後，先由 HTML parser（把 HTML 文字解析成元素與屬性的程式）從頭讀起。讀到 <script> 元素的內容，會交給 JavaScript 引擎；讀到 href 這類屬性的值，之後由 URL parser 解讀；讀到 style 的內容，則交給 CSS parser。每一種 parser 都有自己的語法，也就有自己的「特殊字元」：在某處只是普通文字的符號，換個地方可能表示「資料到此結束、後面是語法」。

輸入在回應裡所處的語法位置，稱為輸出上下文（output context）。要判斷一個值會不會改變頁面結構，得知道此刻是哪個 parser 在讀它，以及在這個 parser 眼中，什麼字元會結束資料的範圍。

3.2.2 五種常見位置的邊界

表中每一列都是正常輸出：搜尋關鍵字 teapot 放在不同位置時回應的樣子。第三欄是在該位置的語法中，會讓 parser 認為資料已經結束或改變意義的字元。

表 3.2.2-1
位置正常輸出結束資料範圍或改變意義的字元合適的處理
HTML 文字（標籤之間）<p>結果：teapot</p>小於號開始一個新標籤；& 開始字元參照（character reference，例如用 &lt; 表示小於號）。HTML 編碼：把這些字元換成字元參照，讓它們顯示成文字。
屬性值（有引號）<input value="teapot">和包住值相同的那種引號結束屬性值，後面的文字會被當成下一個屬性。若屬性值沒有加引號，空白就能結束它。屬性編碼，連同兩種引號；屬性一律加引號；屬性名稱由程式固定。
網址屬性（href、src）<a href="/s?q=teapot">屬性邊界同上一列。值完整取得之後，還要由 URL parser 解讀：開頭的 scheme（例如 https:）決定瀏覽器點擊或載入時做什麼；在查詢參數裡，& 與 = 分隔參數。只放查詢參數的值時用百分比編碼（percent-encoding）；接受整個網址時，檢查 scheme 是否在允許清單內，再做屬性編碼。
JavaScript 字串<script>let t = 'teapot';</script>和開頭相同的引號結束字串；反斜線改變下一個字元的意義；換行在一般字串裡不合法。更早一步，HTML parser 只要看到 script 元素的結束標記，就結束整個腳本，不管 JavaScript 字串是否已結束。避免把值拼進腳本。改由模板把值放進 data- 屬性（經屬性編碼），腳本再讀出來當資料。
CSS 屬性值<p style="color: blue">分號結束一條宣告；在 <style> 元素裡，右大括號結束規則區塊。屬性形式時，引號邊界同第二列。只讓值出現在屬性值的位置，並限制為允許清單（例如幾個固定顏色）。

沒有一種跳脫函式能同時滿足這五列。HTML 編碼把小於號變成字元參照，這在標籤之間有效；但第四列的字串由單引號包住，HTML 編碼不一定處理單引號，也不處理反斜線。第三列的危險可能完全不涉及特殊字元：一個以不安全 scheme 開頭的網址，每個字元都可以是普通字母。

位置還會疊加。屬性裡的網址先經過 HTML parser，再經過 URL parser；事件處理屬性（event handler attribute，在點擊、載入等事件發生時執行其中 JavaScript 的屬性）的值先由 HTML parser 解讀並還原字元參照，再交給 JavaScript。疊加的位置要依解讀順序分別處理，所以動態資料不要放進事件處理屬性或 <script> 的程式碼裡。

3.2.3 屬性值裡的搜尋詞

沿用開頭的搜尋功能，省略了不相關的標頭。網站對關鍵字做了一種處理：把小於號與大於號換成字元參照，其他字元原樣輸出。

正常的請求

GET /search?q=teapot HTTP/1.1
Host: shop.example.com
<!-- 回應節錄 -->
<h1>搜尋結果：teapot</h1>
<input name="q" value="teapot">
  1. 伺服器取值：從查詢字串取得 q 的值 teapot。
  2. 輸出：同一個值放進標題文字和 value 屬性，各自經過相同的角括號替換。
  3. 瀏覽器解析：HTML parser 建立一個 h1 元素，文字是「搜尋結果：teapot」；再建立一個 input 元素，有 name 與 value 兩個屬性。

只對角括號編碼時

現在只把關鍵字換成 [跳出屬性值的片段]。方括號代表被換掉的那段輸入：它不含角括號，但含有和包住 value 相同的那種引號，後面接著一段看起來像屬性的文字。

  1. 標題那一處：值落在標籤之間。引號在這裡只是普通文字，沒有角括號就開不了新標籤，所以標題只會顯示一串看起來奇怪的字。
  2. 搜尋框那一處：值落在雙引號包住的屬性值裡。角括號替換沒有碰到引號，HTML parser 讀到那個引號時，判定 value 已經結束。
  3. 解析結果：引號後面的文字不再是 value 的一部分，而被當成同一個 input 元素上的新屬性。

如果新屬性是事件處理屬性，瀏覽器會在該事件發生時（例如滑鼠移到搜尋框上）執行其中的 JavaScript。這需要事件真的發生；有些屬性要使用者操作才觸發，有些在載入時就觸發。網站對標題和搜尋框做的處理相同，結果一處無害、一處有害，差別在兩處的 parser 怎麼解讀引號。

判斷時看瀏覽器解析後的結構，別只看回應原文。開發者工具的元素面板顯示的是 DOM（Document Object Model，瀏覽器依 HTML 建立的元素樹），可以直接看到 input 有幾個屬性、各是什麼。

3.2.4 source 與 sink

上面的例子裡，輸入由伺服器放進回應。現代網頁還有另一條路：頁面上的 JavaScript 載入後，自己從網址或其他地方讀出一個值，再寫進 DOM。輸入若在這條前端資料流中被當成 HTML 或程式碼解讀，稱為 DOM-based XSS。反射型與儲存型說的是資料怎麼送達，DOM-based 說的是不安全的處理發生在前端，所以兩者可以重疊：伺服器反射或先前儲存的資料，也可能被前端程式讀出、再交給危險的寫入點。

追蹤這條資料流要找兩端。source 是 JavaScript 讀到「可能由別人控制的值」的地方；sink 是把值交給會解析或執行它的 API 的地方。

表 3.2.4-1

sink 決定風險的種類。textContent 也是一種寫入，但它只建立文字節點，不經過 HTML parser；location 的問題多半是導向哪裡，不一定是 XSS。所以同一個 source 接到不同 sink，需要的處理也不同。

3.2.5 從網址片段到歡迎詞

一個歡迎頁會依網址顯示名字：開啟 https://shop.example.com/welcome#name=demo 時，頁面顯示「歡迎，demo」。# 之後的部分稱為片段（fragment）。伺服器對每個人都回傳同一份固定的 HTML 與 JavaScript，名字由下面這段前端程式加上：

// 從網址片段讀出名字並顯示
const params = new URLSearchParams(location.hash.slice(1)); // source
const name = params.get('name');
document.getElementById('greeting').innerHTML = '歡迎，' + name; // sink
  1. 取得頁面：瀏覽器向伺服器請求 /welcome，片段不隨請求送出。伺服器回傳固定的 HTML 與這段程式。
  2. 讀 source：location.hash 是 #name=demo，去掉開頭的 # 後解析成參數，name 得到 demo。
  3. 寫入 sink：程式把「歡迎，demo」指定給 innerHTML，HTML parser 解析這段字串，結果只有文字，畫面顯示歡迎詞。

把片段換成 #name=[來自網址的片段]，前兩步完全一樣，伺服器看到的請求也一樣。差別出在第三步：若片段裡的文字含有標記，HTML parser 會依它建立新元素。如果那個元素帶有事件處理屬性，瀏覽器就可能執行其中的程式碼，這段程式碼以 shop.example.com 的身分執行。攻擊者只需要讓別人點開一條帶著這個片段的連結。

把最後一行改成 textContent，被操縱的片段就只會顯示成一串文字：

// 同一個值，改用只建立文字的 sink
document.getElementById('greeting').textContent = '歡迎，' + name;

MDN 的 innerHTML 說明指出，經由 innerHTML 插入的 <script> 元素不會執行，但 HTML 還有其他方式讓解析出的元素執行程式。「這個 API 不會執行 script」因此不能當成安全的理由。

3.2.6 伺服器端為什麼看不到

在上面的例子裡，片段依 URL 的規則不隨 HTTP 請求送出，而是由瀏覽器在取得頁面後自行處理（見 MDN 的 URI fragment）。伺服器的存取紀錄只有 GET /welcome；檢查請求內容的伺服器端過濾或防火牆，也沒有機會看到那個值。

source 是查詢字串（location.search）時，值會出現在請求和紀錄裡。伺服器若沒有把它放進回應、只由前端程式讀取，在回應原文中就搜尋不到；伺服器若也反射了它，同一個值會同時出現在回應與前端資料流裡，兩處要分別判斷。postMessage 的訊息則在兩個瀏覽器視窗之間傳遞，從不經過這個網站的伺服器。

所以檢查 DOM-based XSS 時，回應原文與 DOM 要分開看。當次回應的原文在開發者工具的 Network 面板裡看；元素面板顯示解析與 JavaScript 執行後的 DOM。兩者不同只是追查的線索：HTML parser 本身也會讓 DOM 和原文不同，例如自動結束段落、補上省略的元素、把字元參照還原成字元。先排除這類解析造成的差異，再在寫入 sink 的那一行設中斷點，確認是哪段腳本、在什麼時候、寫入了什麼值。

3.2.7 DOM-based XSS 成立的條件

  • 值要能被別人影響。寫死在程式裡的字串、只由伺服器產生且不含使用者資料的值，沒有可控的 source。
  • 要有一條從 source 到 sink 的路徑。中間若有檢查或轉換，要看它是否符合 sink 的語法：轉成數字後才寫入，與原樣拼接，是兩回事。
  • sink 要會解析或執行。寫進 textContent，或用 setAttribute 設定名稱固定、本身沒有執行語意的一般屬性（例如 title），值只會是文字。有些屬性會解讀自己的值：事件處理屬性把值當 JavaScript，srcdoc 把值當成一份 HTML 文件，網址屬性的值還要經過 URL parser。這些屬性即使名稱寫死在程式裡，仍然是 sink。
  • 上下文決定需要哪些字元。屬性值的例子需要引號，HTML 文字需要角括號；某位置做了正確編碼，換一個位置就要重新判斷。
  • 執行與觸發是兩個條件。新屬性若要等使用者的某個操作才觸發，這個前提就屬於影響評估的一部分。
  • 影響範圍同 XSS。程式碼以該網站的身分在受害者瀏覽器中執行，能做的事和 Cross-Site Scripting Basics 所說的一樣，受同源政策與該頁面的權限限制。

前端資料流還有一種較間接的形式：輸入改動了 JavaScript 物件之間共用的屬性，之後其他程式讀到這個值。它需要更多物件模型的背景，在 Prototype Pollution 一節展開。

3.2.8 辨認輸出位置與資料流

伺服器放進回應的值

在經授權的測試環境中，先送一個不會引起任何解讀的獨特字串，例如 demo4821，再在回應原文中搜尋它出現的每個位置。對每一處判斷：它在標籤之間、在哪個屬性裡、該屬性用哪種引號、是不是在 <script> 或 style 裡。一個值出現在多處很常見，每一處都要分別看。

接著比對同一處在 DOM 中的樣子。回應裡看到的字元參照，在 DOM 中已經被還原；回應裡的值若被前端程式再處理過，DOM 也會不同。看到某個字元被編碼了，只能說明這個位置處理了這個字元，推不出其他位置或其他字元也被處理。

前端程式自己讀的值

有原始碼或可讀的前端程式時，先搜尋常見的 sink 名稱，再往回追它的值從哪裡來；或從 source 出發往下追。程式經過壓縮或分成很多檔案時，瀏覽器開發者工具的搜尋與中斷點能幫你停在寫入 sink 的那一行，看當下的值。中間經過的函式要逐一確認：它是把值當資料處理，還是又拼成 HTML 或程式碼。

接收 postMessage 的程式要看兩件事：收到訊息時有沒有檢查 event.origin（傳送者的來源），以及 event.data 被交給哪個 sink。

3.2.9 防禦手法

有效的防禦

由模板引擎依位置編碼

伺服器端產生 HTML 時，用模板引擎的自動跳脫（auto-escaping），不要自己拼字串。許多引擎的預設跳脫是為標籤之間和加引號的屬性設計的；有些會依位置自動選擇編碼方式，例如 Go 的 html/template。用前查清楚你的引擎在每種位置做什麼，並避免使用「原樣輸出、不跳脫」的語法，除非內容是可信的 HTML。

依位置的做法（參考 OWASP XSS Prevention Cheat Sheet）：

  • 標籤之間與屬性值：用引擎的 HTML 與屬性編碼；屬性永遠加引號，屬性名稱由程式決定。
  • JavaScript 需要的資料：不把值拼進 <script>。讓模板把值放進一般的 data- 屬性（經屬性編碼），腳本用 dataset 讀出，它就只是一個字串。
  • 網址的一部分：只放查詢參數的值時，用百分比編碼該值；接受整個網址時，見下方的 scheme 檢查。
  • CSS：只讓值出現在屬性值的位置，並限制在允許清單裡。
<!-- 模板把搜尋詞放進 data- 屬性，腳本只把它當資料讀 -->
<div id="search-config" data-term="teapot"></div>
<script>
  const term = document.getElementById('search-config').dataset.term;
</script>

前端改用不解析 HTML 的 API

要顯示文字，就用 textContent。要建立元素，用 createElement() 建立程式固定的元素種類（例如段落），再用 textContent 放文字、用 setAttribute() 設定名稱固定、沒有執行語意的屬性。這些 API 不會把值交給 HTML parser，但有些元素和屬性會自己解讀值：script、iframe 這類元素，以及事件處理屬性、srcdoc 與網址屬性，用這些 API 設定的值照樣會被當成程式、HTML 或網址。不可信的值不要放進這類元素、事件處理屬性或 srcdoc；網址屬性要先做下方的 scheme 檢查。確定需要插入一段 HTML 時（例如使用者撰寫的格式化內容），先用維護中的 HTML 清理器（sanitizer，移除不安全元素與屬性的函式庫）處理，例如 MDN innerHTML 說明的範例中使用的 DOMPurify。

避免把可控字串交給 eval()、Function() 或以字串為參數的 setTimeout()。這些 API 的用途就是執行程式碼，編碼救不了它們；改成傳入函式，把值當參數。

網址要檢查 scheme

setAttribute('href', 值) 不會解析 HTML，但瀏覽器仍會依網址的 scheme 決定點擊時做什麼，而有些 scheme 會讓網址其餘部分被當成 JavaScript 執行。所以從不可信來源取得的完整網址，要先解析，再用允許清單檢查 scheme，必要時也限制目的地：

// 只接受同站的 https 網址，其餘一律不設定
const raw = new URLSearchParams(location.search).get('next');
const url = new URL(raw ?? '/', location.origin);
if (url.protocol === 'https:' && url.origin === location.origin) {
  link.setAttribute('href', url.href);
}

第一行從查詢字串取出 next 參數；沒有這個參數時，第二行的 ?? 讓它改用 /。link 是頁面上要設定目的地的那個連結元素。if 那一行的 === 表示兩邊完全相同，&& 表示「而且」：兩個條件都成立，才執行大括號裡設定連結的那一行，否則什麼都不做，連結維持原樣。例如 next 是 /products/42 時，解析結果是同站的 https 網址，連結會被設定；next 指向另一個網域，或使用 https 以外的 scheme，連結就不會被設定。

new URL() 以瀏覽器的規則解析網址，protocol 屬性是解析後的 scheme（含冒號）。用解析結果比對，比在原字串上找子字串可靠。檢查目的地也能防止網站被當成跳板，把使用者導到別的網站。

跨視窗訊息先驗來源再驗格式

MDN 的 postMessage 說明建議：不需要接收其他網站的訊息，就不要註冊 message 監聽器；需要時，先確認 event.origin 是預期的來源，再檢查資料的結構，最後交給安全的 sink。

// 只接受特定來源、且 count 是數字的訊息
window.addEventListener('message', (event) => {
  if (event.origin !== 'https://widget.example.com') return;
  if (typeof event.data?.count !== 'number') return;
  badge.textContent = String(event.data.count);
});

addEventListener 註冊一個函式，每收到一則訊息就執行一次，event 代表這則訊息。return 表示到此為止、不再執行下面的行，所以兩個檢查任一不符，訊息就被丟棄：!== 表示「不相同」，?. 讓 event.data 沒有值時也不會出錯。兩項都通過，才把 count 轉成文字，寫進 badge（頁面上顯示數量的小標籤）。來自 https://widget.example.com、count 為 3 的訊息會讓標籤顯示 3；同樣的內容來自其他網站，或 count 是一段文字，都會被丟棄。

Trusted Types 與 CSP 作為後備

Trusted Types 讓瀏覽器拒絕把一般字串交給 innerHTML、eval() 等注入 sink。網站在 CSP（Content Security Policy，以回應標頭告訴瀏覽器哪些腳本與資源可以載入、執行的政策）中加上 require-trusted-types-for 'script' 後，程式只能傳入由網站自己定義的政策（policy）物件產生的值，沒有設定預設政策時，傳字串會拋出錯誤。Trusted Types 本身不清理內容，政策裡的轉換函式要自己呼叫清理器；它的作用是把所有危險寫入集中到少數幾個可以審查的政策。MDN 將它標為 2026 年起在主流瀏覽器的新版本都能使用（Baseline 2026），舊版瀏覽器不會強制（見 MDN Trusted Types API 與 W3C Trusted Types 規格草案）。

CSP 也能限制哪些腳本可以執行。MDN 建議以 nonce（每個回應各不相同、無法預測的隨機值）或雜湊值核准腳本，稱為 strict CSP；這樣的政策會擋下未經核准的內嵌腳本與事件處理屬性。MDN 與 OWASP 都把 CSP 定位為後備：輸出處理失誤時，它還有機會阻止瀏覽器執行注入的程式碼，但不能取代編碼與安全的 API（見 MDN Content Security Policy）。

3.2.10 小結

  • 輸出上下文決定由哪個 parser 解讀輸入，也決定哪些字元會結束資料範圍；HTML 文字、屬性值、網址、JavaScript 字串與 CSS 各不相同。
  • 一種跳脫函式無法涵蓋所有位置。只編碼角括號的屬性值仍可被引號結束；網址的危險可能完全在 scheme。
  • DOM-based XSS 指不安全的處理發生在瀏覽器內：前端程式從 source 讀值，交給會解析或執行的 sink。值可能先由伺服器反射或儲存，也可能完全不經過伺服器；片段與跨視窗訊息不會出現在伺服器紀錄裡。
  • 修補依位置選擇：模板引擎的自動跳脫；用 textContent 寫文字，用 setAttribute() 設定固定且沒有執行語意的屬性；網址的 scheme 允許清單；訊息的來源檢查。
  • Trusted Types 與 CSP 是縱深防禦，用來攔下遺漏的危險寫入與執行，不取代上述處理。

  • Reflected XSS into attribute with angle brackets HTML-encoded：找出搜尋詞落在哪個屬性、用哪種引號，以及哪些字元被編碼。
  • DOM XSS in document.write sink using source location.search：在前端程式中找出 source 與 sink，判斷值在 sink 處落在什麼位置。
  • DOM XSS in innerHTML sink using source location.search：和上一題比較，換成 innerHTML 後哪些元素會被建立、哪些不會執行。
  • DOM-based open redirection：sink 是導向網址時，風險在導向的目的地，修補也換成目的地檢查。
