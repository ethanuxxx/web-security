第 4 章的伺服器把每筆請求都拆成兩個問題：帶著這個 Session Cookie 的是誰，他有沒有權限做這件事。兩個都答對了，還有一個問題沒有問：這筆請求是不是他自己要送的。你登入 shop.example.com 之後，在另一個分頁打開一個無關的網站，那個網站的頁面也能讓你的瀏覽器向商店送出請求，而瀏覽器照樣會附上商店的 Cookie。伺服器看到的是 wiener 的 Session、wiener 有權限的動作，看起來和 wiener 親手按下按鈕沒有差別。

5.1.1 瀏覽器替誰帶 Cookie

HTTP Requests and Sessions 說過，瀏覽器保存 Cookie 後，只要請求符合傳送條件，就自動用 Cookie 標頭帶回去。這個判斷看的是請求要送到哪裡，例如目標的主機名稱、路徑、是否走 HTTPS，以及 Cookie 是否過期。請求是怎麼產生的，傳統的 Cookie 規則並不在乎：使用者在商店頁面上按的按鈕、網址列直接輸入的網址、別的網站頁面裡的表單或圖片，只要目標是 shop.example.com，都可能帶上同一個 Session Cookie。

這種不必由頁面程式主動提供、瀏覽器自己附上的憑證，常稱為環境憑證（ambient credentials）。Cookie 是最常見的一種，瀏覽器記住的 HTTP Basic 驗證帳密也是。它讓網站使用起來很方便：你點開商店的任何一個連結，都不必重新登入。代價是伺服器看到 Cookie，只能確定「這是 wiener 的瀏覽器送來的」，不能確定「wiener 想送這筆請求」。

HttpOnly 屬性改變不了這件事。它禁止頁面中的 JavaScript 讀取 Cookie 的值，瀏覽器送請求時仍然照常附上。後來加入的 SameSite 屬性才開始讓瀏覽器考慮請求從哪裡發起，這要先分清楚 origin 與 site 兩個單位。

5.1.2 Origin 與 site

Cross-Site Scripting Basics 定義過來源（origin）：協定、主機名稱、連接埠三者都相同，才是同一個 origin。https://shop.example.com 和 https://blog.example.com 主機名稱不同，是不同的 origin。

Site 是比較寬的單位。它看協定，加上可註冊網域：公共後綴（public suffix，例如 .com、.co.uk 這類任何人都能在其下註冊網域的後綴，也稱 eTLD，effective top-level domain）再往左多一層，例如 example.com。shop.example.com 和 blog.example.com 都屬於 example.com，兩者是 same-site、cross-origin。早期的 site 定義不看協定，現在的瀏覽器多採「含協定」的判定（schemeful same-site），所以 http:// 與 https:// 下的同一個網域算不同的 site。

發起請求的頁面目標same-originsame-site
https://shop.example.com/carthttps://shop.example.com/my-account是是
https://shop.example.comhttps://shop.example.com:8443否，連接埠不同是
https://blog.example.comhttps://shop.example.com否，主機名稱不同是，都在 example.com 下
http://shop.example.comhttps://shop.example.com否，協定不同否（含協定的判定）
https://attacker.example.nethttps://shop.example.com否否，可註冊網域不同

兩個單位各管不同的規則。同源政策以 origin 為單位，決定一個頁面的程式能讀哪些回應；SameSite 以 site 為單位，決定跨站請求帶不帶 Cookie。把兩者混為一談，就會誤以為「不同子網域之間一定隔開了」：對 SameSite 來說，同一個網域下的所有子網域都是自己人。

5.1.3 送出、執行、讀取

一個網站的頁面讓瀏覽器向另一個網站送請求時，結果由三個各自獨立的決定組成：

同源政策（same-origin policy，SOP）管的是第三個決定。它限制一個 origin 的程式讀取另一個 origin 的回應，不禁止送出請求。跨 origin 的表單送出、連結導覽、載入圖片與 script，向來都是允許的，網頁本來就靠這些互相連結。攻擊者的頁面讀不到商店的回應，但請求已經送到商店，伺服器也可能已經照做。

所以兩類問題要分開看：

  • 跨站請求偽造（cross-site request forgery，CSRF）只需要第一、二個決定對攻擊者有利：Cookie 被帶上、伺服器執行了動作。攻擊者不必看到結果。
  • CORS 設定錯誤出在第三個決定：伺服器自己宣告「這個來源可以讀我的回應」，讓攻擊者的頁面讀到只有登入者才看得到的資料。

5.1.4 CSRF 成立的三個條件

CSRF 是讓受害者的瀏覽器，在他不知情的情況下，帶著他的登入狀態向目標網站送出一筆會改變狀態的請求。判斷一個動作會不會被這樣利用，最直接的方式是站在伺服器的位置，比較它在兩筆請求上能觀察到什麼。第一筆是 wiener 在商店帳號頁修改預設收貨地址；第二筆是他在另一個網站的頁面上，被自動送出的表單觸發的同一個動作。

伺服器能觀察到的項目wiener 自己送出攻擊者的頁面觸發
Cookiesession=DEMO123相同，由瀏覽器附上
路徑與參數名稱POST /my-account/default-address，欄位 recipient、address相同
參數的值wiener 在表單裡輸入的地址攻擊者事先寫在自己的頁面裡的地址；伺服器看得到值不同，卻無法只憑地址判斷是誰的意思
Originhttps://shop.example.comhttps://attacker.example.net
Sec-Fetch-Sitesame-origincross-site

這張表是沒有任何防護的版本：表單不帶 CSRF token，後端也不檢查來源。伺服器認人靠 Cookie 裡的 Session，路徑和參數名稱只是合法的欄位，單憑這些判斷不出這筆操作是不是 wiener 的本意。兩筆請求只有 Origin 與 Sec-Fetch-Site 不同，後端本來可以拿這兩個標頭來拒絕，這種處理程式卻沒有看它們。攻擊要成立，需要同時滿足三項，每一項對應上表的一個位置：

  1. 有一個值得觸發的動作：改預設收貨地址、改密碼、轉帳、新增管理員之類會改變伺服器狀態的操作。只讀取資料的請求，攻擊者讀不到回應，觸發了也沒有用。
  2. 伺服器只靠瀏覽器自動附上的憑證認人（第一列）：以本節的 Cookie Session 為例，Session 只由 Cookie 識別，沒有其他需要頁面主動提供的憑證。瀏覽器記住的 HTTP Basic 帳密也屬於這一類。
  3. 攻擊者能寫出整筆請求（第二、三列）：每個參數都能事先知道或猜到，也沒有一個只有 wiener 的頁面才拿得到的值。若動作要求輸入目前的密碼或帶 token，而且伺服器確實驗證，攻擊者寫不出有效的請求。

第二項還隱含一個條件：受害者送出請求時，瀏覽器真的會附上 Cookie。這取決於 Cookie 的 SameSite 屬性與請求的種類，後面會細看。

5.1.5 一次跨站修改收貨地址

商店有「一鍵購買」：按下去直接用帳號的預設收貨地址下單。wiener 在帳號頁修改預設地址時，瀏覽器送出：

POST /my-account/default-address HTTP/1.1
Host: shop.example.com
Origin: https://shop.example.com
Content-Type: application/x-www-form-urlencoded
Cookie: session=DEMO123

recipient=Peter+Wiener&address=12+Demo+Street

這個動作會改變之後每一張一鍵購買訂單的出貨地點；身分只由 Cookie 決定；body 只有 recipient 和 address，值由送出者決定，沒有 token，也不需要輸入密碼。前面說的三個條件在這裡都成立。

攻擊者在自己的網站放一個頁面，裡面有一個隱藏表單：action 指向 https://shop.example.com/my-account/default-address，方法是 POST，recipient 與 address 填 [攻擊者控制的收件資料]，頁面一載入就自動送出。方括號代表攻擊者換進去的值。接著他想辦法讓 wiener 打開這個頁面，例如在論壇留言或社群貼文中放上連結。

步驟 ④ 的請求和 wiener 自己送的那筆相比，欄位名稱沒有變，recipient 與 address 的值換成攻擊者的，Origin 標頭變成 https://attacker.example.net。瀏覽器附上的 Referer、Sec-Fetch-Site 等標頭也會跟著發起的頁面改變，後面的防禦會用到。如果伺服器不檢查請求來源，也沒有其他防禦，它就照常寫入新地址。wiener 之後按下一鍵購買，貨品寄到攻擊者指定的地方。

整個過程中攻擊者沒有碰到 wiener 的 Cookie，也沒有讀到任何回應。表單是一般的跨站導覽，不需要商店允許 CORS；同源政策在這裡沒有出場的機會。

5.1.6 什麼情況下成立

  • 受害者必須在攻擊發生時處於登入狀態，而且瀏覽器會為這種請求附上 Cookie。Session Cookie 設為 SameSite=Strict 或 Lax 時，上面這種跨站 POST 不會帶 Cookie，伺服器看到的是未登入的請求。
  • HTML 表單只能送出三種 Content-Type：application/x-www-form-urlencoded、multipart/form-data、text/plain，也不能加自訂標頭。端點若只接受 application/json 並嚴格檢查，表單就送不出被接受的請求；改用跨站的 JavaScript 送 JSON，瀏覽器會先發一個預檢請求（preflight，見後面的 CORS），伺服器沒有允許就不會送出正式請求。伺服器若不檢查 Content-Type，照樣解析表單送來的 body，這道限制就不存在。
  • 攻擊者拿不到回應，所以只有「做了就有效果」的動作有意義。需要先讀一個值再送下一步的多步驟流程，攻擊者無法完成。
  • 動作需要使用者重新輸入密碼、第二因素或其他攻擊者不知道的值時，第三個條件不成立。

5.1.7 CSRF token

最直接的防禦是讓第三個條件不成立：每個會改變狀態的請求都要帶一個攻擊者無法得知的值。伺服器在產生表單時放進一個隨機值，稱為 CSRF token，並在 Session 中記下它；收到請求時比對 token 是否等於這個 Session 記下的值。

<form method="POST" action="/my-account/default-address">
  <input type="hidden" name="csrf" value="（伺服器產生的隨機值）">
  <input name="recipient">
  <input name="address">
</form>

攻擊者的頁面可以讓瀏覽器送出請求，卻讀不到商店的頁面（這時同源政策發揮作用），所以拿不到表單裡的 token。CSRF token 防的是「攻擊者能寫出整筆請求」這一項，與 Cookie 帶不帶上無關。

token 只有在伺服器每次都正確驗證時才有效。驗證要滿足三項契約，缺任何一項，攻擊者就有路可走：

契約檢查程式這樣寫時攻擊者因此能做的事
token 必須存在程式寫成「請求有 csrf 參數才比對」，參數缺席時直接往下執行。把參數整個拿掉，請求不經比對就通過。
token 必須屬於這個 Session伺服器只確認 token 是它發出過的值，沒有查發給了哪個 Session。用自己的帳號取得一個有效 token，放進要讓受害者送出的請求。
token 對應的是 Session 以外的另一個 Cookie。若能在受害者的瀏覽器設定 Cookie，就把自己的一組 Cookie 與 token 放進去。
伺服器不記錄 token，只比對請求參數是否等於某個 Cookie 的值，這種做法稱為 naive double-submit。若能設定那個 Cookie，就讓 Cookie 與參數都等於自己選的值。
每個改變狀態的入口都要驗證驗證只掛在 POST 的處理流程上，同一個動作也能用 GET 觸發。改用 GET 送出同樣的參數，繞過檢查。

Session 歸屬的後兩種情況，都需要攻擊者能在受害者的瀏覽器上設定 Cookie。同一個網域下任何一個子網域的漏洞都可能提供這個能力，因為子網域可以設定作用於上層網域的 Cookie。

5.1.8 SameSite Cookie

SameSite 是 Cookie 的屬性，讓瀏覽器在跨站請求時決定要不要附上這個 Cookie，處理的是第一個決定：

值跨站請求時
Strict一律不附上。從別的網站點連結進來，第一個頁面也看不到登入狀態。
Lax只在頂層導覽（top-level navigation，網址列的頁面整個換掉）且使用安全方法（safe method，只讀取、不改變狀態的方法，常見的是 GET）時附上，例如點連結進入。跨站的 POST 表單、iframe、圖片與 script 發出的請求都不附。
None照傳統規則附上；必須同時設定 Secure，否則瀏覽器拒收。

Cookie 沒有寫 SameSite 時，Chrome 自 2020 年起分批改成預設當作 Lax，Edge 從 86 版跟進，Safari 18 也改成同樣的處理。各瀏覽器採用的時間與平台不同，網站要明確寫出這個屬性，不要依賴預設值。Chrome 對沒寫屬性的 Cookie 另有一個相容例外：Cookie 剛設定後約兩分鐘內，跨站的頂層 POST 仍會附上它，好讓部分單一登入流程繼續運作。明確寫了 SameSite=Lax 的 Cookie 沒有這個例外。

SameSite 從瀏覽器端擋掉「Cookie 被帶上」這個條件，不需要改動表單。它的效力有幾個邊界：

  • Lax 與頂層 GET：Lax 允許跨站的頂層 GET 導覽帶 Cookie。伺服器若讓 GET 也能執行修改，攻擊者只要讓受害者的瀏覽器整頁導覽到那個網址，Cookie 就會附上。有些框架允許用一個參數覆寫請求方法（例如表單送的是 GET，參數聲稱自己是 POST），效果相同。
  • 同一個 site 不受限制：SameSite 只管跨 site 的請求。blog.example.com 若有 XSS，從那裡發出的請求對 shop.example.com 是 same-site，Strict 也照樣附上 Cookie。
  • Cookie 被設成 None：有些網站為了避免 Lax 預設破壞既有功能，把所有 Cookie 一律設成 None，連 Session Cookie 也一起放寬。

所以 SameSite 適合當第二道防線，和 CSRF token 一起用。token 不受 site 範圍影響，SameSite 則在 token 驗證有缺陷時仍能擋掉大部分跨站請求。

5.1.9 依 Referer 判斷來源

有些網站檢查 Referer 標頭（瀏覽器附上的「從哪個頁面來」，拼字照 HTTP 規範的歷史寫法），只接受來自自己網域的請求。Access Control 的「依請求附帶資訊做的檢查」已經看過，拿它做授權靠不住；拿它防 CSRF 也有類似的弱點：

  • 標頭不一定存在。使用者的瀏覽器設定、隱私外掛或頁面的 Referrer-Policy 都可能讓它消失。網站為了不擋到正常使用者，常寫成「沒有 Referer 就放行」，而攻擊者的頁面可以用自己的 referrer policy 讓瀏覽器不送這個標頭。
  • 比對寫得太寬。只檢查 Referer 是否「包含」或「以」商店網域開頭，攻擊者可以把商店網域放進自己網址的子網域名稱或查詢字串裡，讓檢查通過。

同樣標示來源的 Origin 標頭比較可靠：瀏覽器在跨 origin 的 POST 等請求上會附上它，網頁無法偽造，內容只有協定、主機與連接埠。它也有缺席的時候：同 origin 的 GET 或 HEAD 請求可以不帶，跨 origin 但不經 CORS 的 GET 或 HEAD（例如載入圖片）也可以不帶。請求若來自不透明來源（opaque origin，瀏覽器不給它任何真實 origin 的文件，例如從 file: 開啟的本機檔案），或經過某些跨 origin 的轉址，值則是字串 null。缺席和 null 都表示無法確認來源，對會改變狀態的請求不能因此放行：要嘛拒絕，要嘛交由有效的 CSRF token 決定。所以 Origin 檢查適合放在 token 之外，當額外的一道。

5.1.10 誰能讀取回應

回到第三個決定。商店的帳號頁有一支 API，GET /api/account，回傳登入者的 email 與 API 金鑰。攻擊者的頁面可以用 JavaScript 對它發出請求。跨 origin 的 fetch 預設不帶 Cookie，程式要明確要求帶上憑證（fetch 的 credentials 選項，或 XMLHttpRequest 的 withCredentials 屬性），而且 Cookie 的 SameSite 與瀏覽器的第三方 Cookie 政策也允許，請求才會附上 Cookie。即使附上了，回應回來後，瀏覽器不會把內容交給 attacker.example.net 的程式。這是同源政策的預設。

有時網站需要開放跨 origin 讀取，例如 app.example.com 的前端要呼叫 api.example.com。跨來源資源共用（cross-origin resource sharing，CORS）讓伺服器用回應標頭宣告「哪些 origin 可以讀這份回應」，瀏覽器據此放寬同源政策。下面的請求由 app.example.com 的程式發出，程式要求帶上憑證；兩者同屬 example.com 這個 site，SameSite 不擋這個 Cookie：

# 瀏覽器自動加上發起頁面的 origin；Cookie 因程式要求帶上憑證才附上
GET /api/account HTTP/1.1
Host: api.example.com
Origin: https://app.example.com
Cookie: session=DEMO123

# 伺服器宣告這個 origin 可以讀，且可以是帶 Cookie 的請求
HTTP/1.1 200 OK
Access-Control-Allow-Origin: https://app.example.com
Access-Control-Allow-Credentials: true
Vary: Origin
Content-Type: application/json
  • Access-Control-Allow-Origin（常縮寫 ACAO）：允許讀取的 origin。可以是一個完整的 origin，或 * 代表任何 origin。
  • Access-Control-Allow-Credentials: true（ACAC）：允許「帶著 Cookie 的請求」的回應也被讀取。程式要求帶上憑證時，回應少了這個標頭，瀏覽器就不交出內容。它只管回應交不交出，不會讓瀏覽器多附任何 Cookie。* 不能和它一起用：瀏覽器遇到 Access-Control-Allow-Origin: * 配上帶 Cookie 的請求，會拒絕交出回應。
  • Vary: Origin：告訴快取這份回應依 Origin 而不同，避免把給某個 origin 的版本交給另一個 origin。

程式發出的跨 origin 請求，若方法不是 GET、HEAD、POST，或手動設定了不在 CORS 允許清單（CORS-safelisted request headers）上的標頭，或標頭的值超出清單的限制，瀏覽器會先送一個 OPTIONS 方法的預檢請求，詢問伺服器是否允許；伺服器回應允許後才送出正式請求。最常碰到的值限制是 Content-Type：只有 application/x-www-form-urlencoded、multipart/form-data、text/plain 三種不需要預檢，application/json 就需要。完整條件見 MDN 的說明；瀏覽器若已快取了相符的預檢結果，也會省略這次 OPTIONS。不需要預檢的請求直接送出，只在讀取回應時檢查 ACAO。

普通的 HTML 表單送出不是這類程式請求，本來就不需要預檢或 CORS 許可才能送出。所以 CORS 防不了 CSRF：CSRF 用的表單照樣把請求送到伺服器。

CORS 只會放寬同源政策，不會收緊。沒有 CORS 標頭時，跨 origin 讀取本來就被擋；加上標頭，等於伺服器自己開了一扇門，設定錯誤就是把門開給了不該進來的人。

5.1.11 CORS 設定錯誤

商店的 API 要讓自家的前端、合作夥伴的前端讀取，而 ACAO 一次只能寫一個值，所以伺服器通常讀取請求的 Origin，判斷是否可信，再把它填進 ACAO。這個判斷只該放行確實列在清單上的完整 origin。常見的錯誤有兩類：Origin 根本沒說明請求來自誰，或是授權範圍比預期的寬。

反射任意 Origin 並允許 credentials

最常見的錯誤是不做判斷，直接把收到的 Origin 原樣填回 ACAO，同時送出 Access-Control-Allow-Credentials: true。瀏覽器看到 ACAO 正好等於發起頁面的 origin，又允許 credentials，就把帶著使用者 Cookie 取得的回應交給那個頁面。結果和直接寫 * 一樣寬，卻繞過了瀏覽器對 * 加 credentials 的限制。

這要求請求真的帶著 Cookie：攻擊者頁面的程式要求帶上憑證，而這個跨站請求能附上 Session Cookie，也就是 Cookie 設為 SameSite=None，瀏覽器也沒有封鎖第三方 Cookie。條件成立時，受害者只要在登入狀態下打開攻擊者的頁面，頁面中的程式就能向 /api/account 發出帶 Cookie 的請求、讀到回應，再把 email 與 API 金鑰送回攻擊者的伺服器。和 CSRF 不同，這次攻擊者拿到了資料。

沒有說出身分的 null

Origin 的值可能是字串 null：例如被 sandbox 限制為不透明來源的文件發出的請求、從 file: 開啟的本機檔案，以及某些跨 origin 的轉址之後。這個值不屬於任何一個網站，許多互不相干的頁面都能產生它。整合外部前端時，若有人為了讓某個發出 null 的測試頁通過，把 null 加進允許清單，就等於信任了所有能產生 null 的頁面：攻擊者只要讓自己的程式在一份不透明來源的文件中執行，就符合清單。缺席的 Origin 同樣說明不了身分，要看端點的性質決定是拒絕，還是改用其他方式驗證。

授權範圍比預期的寬

假設合作夥伴的前端在 https://partner.example.org，允許清單用字串規則辨識它：

  • 用「包含」判斷：只要 Origin 內有 partner.example.org 這段字串就放行。攻擊者的網域只要把這段字串放在自己的主機名稱裡任何位置（例如當成某個子網域名），就通過，實際主機屬於攻擊者。
  • 用正規表示式判斷但沒有跳脫 .，它會比對任何字元；沒有錨定整個字串的頭尾，則前後可以多出別的內容。
  • 只比對主機名稱、不看協定與連接埠，http:// 版本或別的連接埠上的服務也被一起信任。

清單想表達的是一個完整的 origin，字串規則卻放行了一整類字串。

信任所有子網域

「example.com 底下的任何子網域都可信」看起來合理，但只要其中一個子網域有 XSS，攻擊者的程式就能以那個子網域的 origin 發出請求、讀取回應。允許清單若連 http:// 的子網域也信任，能竄改未加密流量的攻擊者（例如同一個公共 Wi-Fi 上的人）就能冒充那個 origin。

5.1.12 Clickjacking

跨站的頁面還有另一種能力：把別的網站整頁嵌進自己的頁面。攻擊者的頁面用 iframe 載入 shop.example.com 的帳號頁，把 iframe 設成透明，疊在一個誘餌按鈕上，例如「領取優惠」。使用者以為點的是誘餌，點擊落在透明 iframe 裡商店頁面的「刪除帳號」上。這稱為 clickjacking（點擊劫持）。

CSRF token 擋不住它。iframe 裡是商店自己的頁面，表單裡有商店自己產生的有效 token，送出的請求和使用者在商店上親手操作完全相同。差別只在使用者看到的畫面被蓋住了。

成立的條件是商店頁面允許被別的網站嵌入，而且 iframe 中的操作帶著使用者的登入狀態。後一項不一定成立：攻擊者的頁面和商店是不同 site，iframe 又不是頂層導覽，Session Cookie 若為 Lax 或 Strict，瀏覽器不會在這個 iframe 裡附上它，商店頁面處於未登入狀態，「刪除帳號」做不成。

這只限於跨 site：same-site 但不同 origin 的頁面，例如 blog.example.com，嵌入商店時 Cookie 照樣附上。瀏覽器封鎖第三方 Cookie 的設定也不能當成保證：嵌入的頁面可能經由 Storage Access API（讓 iframe 中的頁面在使用者同意後取用自己 Cookie 的瀏覽器介面）取得許可。這項許可解除的是第三方 Cookie 封鎖，SameSite 仍照自己的規則判斷。防禦要由伺服器宣告「誰可以嵌入我」：

Content-Security-Policy: frame-ancestors 'self'
X-Frame-Options: SAMEORIGIN

frame-ancestors 是內容安全政策（Content Security Policy，CSP）的指令，列出可以把這個頁面放進 iframe 的 origin；'self' 只允許同 origin，'none' 則完全禁止。X-Frame-Options 是較舊的標頭，給不支援 frame-ancestors 的瀏覽器用。用 JavaScript 偵測自己是否被嵌入再跳出的寫法（frame busting）可以被 sandbox iframe 停用，不能取代這兩個標頭。

5.1.13 防禦手法

CSRF

依 OWASP Cross-Site Request Forgery Prevention Cheat Sheet，主要防禦與縱深防禦分開來看：

  • 使用框架內建的 CSRF 防護，不要自己寫。token 由密碼學安全的亂數產生、綁定 Session、在伺服器端比對；缺少或不符一律拒絕。
  • 驗證套用到每一個會改變狀態的請求，不論方法。GET 只用來讀取，不讓任何修改經由 GET 完成，也不接受用參數覆寫方法。
  • Session Cookie 明確設定 SameSite，一般網站用 Lax，不需要從外站連入時保持登入的網站可用 Strict：Set-Cookie: session=...; Secure; HttpOnly; SameSite=Lax。
  • 額外檢查請求的來源：比對 Origin 是否為自己的 origin，或檢查瀏覽器附上的 Sec-Fetch-Site 標頭，拒絕標示為 cross-site 的狀態變更請求。
  • 修改密碼、email、付款資訊這類高風險動作，要求重新輸入密碼或第二因素。攻擊者不知道這些值，第三個條件自然不成立。

CORS

依 PortSwigger 的 CORS 說明與 MDN 的 CORS 指南：

  • 不需要跨 origin 讀取的端點，不要送任何 CORS 標頭。
  • 需要時，維護一份完整 origin（協定、主機、連接埠）的允許清單，以整個字串相等比對；不用開頭、結尾或未錨定的正規表示式。
  • 不把 null 放進允許清單，只允許 https:// 的 origin。
  • Access-Control-Allow-Credentials: true 只給確實需要帶 Cookie 的端點；回應依 Origin 變化時，在 Vary 裡加上 Origin。回應可能已經有 Vary: Accept-Encoding 之類的值，要附加而不是覆蓋；多數框架有現成的合併函式，例如 Django 的 patch_vary_headers。
  • CORS 是瀏覽器端的讀取規則，不是存取控制。伺服器仍要對每個請求做身分驗證與授權。
# 允許清單以完整 origin 逐字比對
ALLOWED_ORIGINS = {"https://app.example.com", "https://admin.example.com"}

def add_vary(response, field):
    # 保留既有的 Vary 欄位；已有 * 或已有同名欄位時不重複加
    current = response.headers.get("Vary", "")
    fields = [f.strip() for f in current.split(",") if f.strip()]
    if "*" in fields or field.lower() in (f.lower() for f in fields):
        return
    response.headers["Vary"] = ", ".join(fields + [field])

def add_cors_headers(request, response):
    origin = request.headers.get("Origin")
    add_vary(response, "Origin")
    if origin in ALLOWED_ORIGINS:
        response.headers["Access-Control-Allow-Origin"] = origin
        response.headers["Access-Control-Allow-Credentials"] = "true"
    # 不在清單上：不送 CORS 標頭，瀏覽器維持同源政策

Clickjacking

所有頁面預設送出 Content-Security-Policy: frame-ancestors 'self'（或 'none'），需要被特定網站嵌入的頁面才明列那些 origin；同時送出 X-Frame-Options 照顧舊瀏覽器。Session Cookie 使用 Lax 或 Strict，也讓跨 site 的 iframe 拿不到登入狀態，但擋不住 same-site 的嵌入者。

5.1.14 小結

  • Cookie 由瀏覽器依目標及請求情境自動附上，頁面不必知道它的值；HttpOnly 只擋 JavaScript 讀取，不擋附帶。
  • Origin 比對協定、主機與連接埠，site 比對協定與可註冊網域；同一網域下的子網域是 same-site、cross-origin。同源政策以 origin 為單位限制讀取回應，SameSite 以 site 為單位限制附帶 Cookie。
  • CSRF 需要三個條件同時成立：有值得觸發的動作、只靠瀏覽器自動附上的憑證（常見的是 Cookie）認人、所有參數都能預先寫出。CSRF token 讓參數不可預測，SameSite 讓 Cookie 不被帶上；token 要綁定 Session 並在所有方法上驗證，Lax 仍放行頂層 GET，同一個 site 的子網域不受 SameSite 限制。
  • CORS 只會放寬同源政策。反射任意 Origin 並允許 credentials、信任 null、用字串片段或未錨定的規則比對允許清單，在請求帶得到 Cookie 時，都讓攻擊者的頁面讀到使用者的資料；正確做法是完整 origin 的逐字比對。
  • Clickjacking 讓使用者在真頁面上點擊，token 擋不住；由伺服器用 frame-ancestors 與 X-Frame-Options 限制誰能嵌入。

PortSwigger Academy 的對應練習（主題頁 CSRF、CORS、Clickjacking），只在 Lab 或其他獲明確授權的系統上測試：

  • CSRF vulnerability with no defenses：對照三個條件，確認修改帳號設定的請求裡沒有攻擊者無法預測的值。
  • CSRF where token validation depends on request method：同一個動作換一種方法時，token 還有沒有被檢查。
  • CSRF where token validation depends on token being present：token 欄位整個不見時伺服器怎麼處理。
  • CSRF where token is not tied to user session：用兩個帳號判斷 token 是否綁定 Session。
  • SameSite Lax bypass via method override：Lax 放行的頂層 GET 與方法覆寫如何組合。
  • CSRF where Referer validation depends on header being present：Referer 缺席時的處理方式。
  • CORS vulnerability with basic origin reflection：比較不同 Origin 得到的 ACAO 與 ACAC。
  • CORS vulnerability with trusted null origin：允許清單裡的 null 會讓哪些頁面通過。
  • Basic clickjacking with CSRF token protection：頁面能否被嵌入，以及為什麼 token 在這裡沒有作用。

到這裡，伺服器對一筆請求問過三件事：送出的人是誰，他有沒有權限，這是不是他的意思。三項都通過的請求仍可能不該執行：優惠券在已經套用過之後又套用一次，訂單在付款前就被標成已出貨，數量欄位填了負數。下一章的 Business Logic Vulnerabilities 看的是另一種檢查：在目前的業務狀態下，這個動作是否被允許，每一步都合法的請求組合起來是否仍然合理。
