回應是 302 而不是直接顯示頁面：Location 把瀏覽器帶去帳號頁，Set-Cookie 發下的 session 是之後的通行證。之後每個請求都帶著它，伺服器靠它認出你是 alice，見 Cookie 與 Session。

3.1.1 身分驗證與授權的分別

身分驗證（authentication）是網站確認送來請求的人確實是某個帳號的持有人；授權（authorization）是知道帳號之後，網站再決定這個帳號能不能讀這筆資料、做這個動作。兩件事依序發生，各自會出問題；授權在下一節 Access Control。

網站驗證身分的依據可分為三類：所知之事（Something you know）、所持之物（Something you have）、所具之形（Something you are）。下圖左側各配一個例子，右側是一個請求依序經過的兩道檢查：

所知之事還包括安全問題的答案，所持之物包括驗證器 App 與實體金鑰，所具之形是指紋、臉部等生物特徵。

登入漏洞有兩個來源。一是機制本身弱：密碼可以被一直猜、猜的時候又得到線索。二是實作有邏輯缺陷：流程設計出一條不必通過驗證的路。帳號一旦被攻破，後果取決於那個帳號：一般會員的帳號讓你看到他的訂單與個人資料；管理員的帳號則連同後台功能一起交出去，也讓你站進內部才看得到的攻擊面。

用第三方帳號登入的流程在 OAuth。

3.1.2 暴力猜測帳號與密碼

暴力猜測（brute force）是用程式一個個試帳號或密碼，直到登入成功。從所有字元組合窮舉太慢，實際有效的做法是猜得準：先推出帳號的格式，再照人的習慣猜密碼。被猜的對象是 tickets.example.com 的一般會員，例如 bob 或 carol。

逐一送出候選值通常交給程式自動做。送得越多就越慢，也越容易被網站擋下，所以候選清單越準越好。命中的回應和其他不同，狀態碼與長度都可以拿來比。

帳號有固定格式

網站的帳號常依同一種規則產生：英文名字加生日（例如 alice0315），或 email 的前綴；管理帳號幾乎一定有，名字叫 admin 之類。要推格式，先看網站公開的資料：個人檔頁、留言者名稱，以及 HTTP 回應裡出現的 email。在 tickets.example.com，bob 的公開個人檔頁列出 bob@tickets.example.com，@ 之前就是帳號。公開個人檔頁顯示的名稱也可能就是登入名稱，留言者名稱、個人檔頁列出的名字都能直接當候選帳號。

密碼靠習慣猜

密碼政策（至少 8 字元、要有大小寫與數字）逼使用者符合規則，他們會用最省力的方式：常見的詞開頭大寫、結尾加個數字。定期更換密碼更糟：使用者只改一個字元，Password1 變 Password2。知道一個舊密碼，下一個就很好猜。

用公開資料推出格式，照這個格式產生候選帳號，再搭配一份常見密碼清單，範圍就從所有字元組合縮成一份短得多的清單。

3.1.3 從登入回應判斷帳號是否存在

猜密碼前，先確認帳號存在，工作量差很多。使用者名稱列舉（username enumeration）就是從登入頁的回應差異，判斷哪些帳號真的存在。差異有三種來源：狀態碼、錯誤訊息（連一個字元的差別都算）、回應時間（存在的帳號要多做一次密碼比對）。

先看第一種和第二種。如果登入頁對不存在的帳號回 200 加「找不到此使用者」，對存在但密碼錯的 bob 回 401 加「密碼錯誤」，兩種回應就不一樣：

不存在的帳號
Request
POST /login HTTP/1.1Host: tickets.example.comContent-Type: application/x-www-form-urlencodedusername=[不存在的帳號]&password=[密碼]
Response
HTTP/1.1 200 OKContent-Type: text/html找不到此使用者
存在的帳號，密碼錯誤
Request
POST /login HTTP/1.1Host: tickets.example.comContent-Type: application/x-www-form-urlencodedusername=bob&password=[錯誤的密碼]
Response
HTTP/1.1 401 UnauthorizedContent-Type: text/html密碼錯誤

比對方法與 資訊揭露「怎麼有系統地找出洩漏」那一節一樣：以一個對照組的回應為基準，其他請求只改帳號，逐項比狀態碼、長度與時間。

差異可以很細。如果登入頁對兩種情況都顯示「帳號或密碼錯誤」，只有密碼錯的那種句末多一個句號，肉眼很容易漏看，但用程式比對回應本體裡的字串，就抓得到這種差異。

回應時間是第三種。如果登入頁的回應文字完全相同，但只有存在的帳號才會做密碼比對，存在的帳號耗時就較長。時間差很小時，送很長的密碼把比對的耗時放大，差距才看得出來。瀏覽器 DevTools 的 Network 分頁（或 Burp 的 HTTP history）會列出每個請求的耗時：

註冊頁也是同一類洩漏。對已存在的帳號回「使用者名稱已被使用」，你不用登入就能逐個問網站這個帳號有沒有人用。

PortSwigger Academy 的對應練習（主題頁 Authentication）：

  • Username enumeration via different responses：對應上面錯誤訊息不同的例子：不存在的帳號與存在的 bob，回應不一樣。要觀察狀態碼與錯誤訊息，哪些帳號的回應與對照組不同，那些就是存在的帳號。
  • Username enumeration via subtly different responses：對應上面只差一個句號的例子：兩種情況的訊息只差句末一個句號。要觀察回應本體，畫面上不容易看出差異，要靠 Grep 條件（在回應本體裡找出或擷取指定字串）抓出字串的不同。

這些 Lab 用 Burp Suite 的 Intruder 扮演「逐一送出候選值」的角色，工具本身在資訊揭露那一節介紹過；Community 版 Intruder 有速度限制。Lab 用的候選帳號清單與候選密碼清單可在 Academy 取得。

3.1.4 帳號鎖定的漏洞

常見的防護是帳號鎖定：同一個帳號連續失敗幾次，就暫時不讓它登入。如果登入頁的規則是連續失敗 3 次就鎖定 1 分鐘（之後自動解除），要注意這個做法只保護被鎖的那個帳號，所以有兩種猜法不碰門檻：

  • password spraying（密碼噴灑）：少數幾個常見密碼，配許多帳號。每個帳號只失敗一兩次，計數器不到門檻。
  • credential stuffing（憑證填充）：拿其他網站外洩的帳號與密碼組合，每組只在這裡試一次。使用者在多個網站重複使用密碼，就有機會命中。

鎖定本身也是線索。被鎖的帳號一定存在，所以鎖定訊息成了另一種列舉：對一批候選帳號各送幾次錯誤密碼，哪個帳號出現鎖定訊息，哪個就存在。

鎖定期間還有一個差異：對錯誤密碼與對正確密碼，伺服器的回應不同。

鎖定期間，錯誤密碼
Request
POST /login HTTP/1.1Host: tickets.example.comContent-Type: application/x-www-form-urlencodedusername=bob&password=[錯誤的密碼]
Response
HTTP/1.1 200 OKContent-Type: text/html帳號已鎖定，請 1 分鐘後再試
鎖定期間，正確密碼
Request
POST /login HTTP/1.1Host: tickets.example.comContent-Type: application/x-www-form-urlencodedusername=bob&password=[正確的密碼]
Response
HTTP/1.1 200 OKContent-Type: text/html登入暫時無法使用

兩種訊息不同，所以就算帳號鎖著，你仍能從回應判斷剛才送的密碼是不是對的。

封鎖解除的方式有三種：等一段時間、管理員手動解除、通過 CAPTCHA（要求辨認圖片或勾選方塊的人機驗證）。各有取捨：等時間最省事，卻讓猜測繼續；手動解除成本高；CAPTCHA 會打斷正常使用者。比起依帳號鎖定，依來源 IP 封鎖較不容易被拿來列舉帳號，也不會讓攻擊者靠故意輸錯就把別人的帳號鎖死。

PortSwigger Academy 的對應練習（主題頁 Authentication）：

  • Username enumeration via account lock：對應上面鎖定訊息的例子：被鎖的帳號一定存在。要觀察對一批候選帳號各送幾次錯誤密碼後，哪個帳號的回應出現鎖定訊息。

Lab 用的候選帳號清單與候選密碼清單同樣可在 Academy 取得。

3.1.5 繞過登入限速

限速是依來源 IP 計算失敗次數，不管帳號，一個 IP 連續失敗太多次就擋下來。這個做法的弱點在於「來源 IP」怎麼判定。如果登入頁依 X-Forwarded-For 這個請求 header 的值當作來源 IP，連續失敗 3 次封鎖 1 分鐘，但 header 的值是請求自己宣告的，可以隨意填。

伺服器相信 header 裡填的來源，資訊揭露一節的 X-Internal-Client-IP 也是同一種信任問題；那裡是 proxy 加的內部 header，這裡是轉送用的 X-Forwarded-For，名稱不同，道理一樣。

計數器也可能被特定動作重置。如果同一個來源成功登入 alice 之後，這個來源的計數器就歸零，而你手上有 alice 的密碼，那麼每失敗兩次就成功登入一次，一來一回把失敗次數攔在門檻之前，別人的密碼想試幾次就試幾次：

第三種弱點在計數的單位。如果限速計的是請求數，而不是密碼嘗試次數，一個請求裡塞進多組候選密碼，計數器只加 1，就可能繞過限制：

PortSwigger Academy 的對應練習（主題頁 Authentication）：

  • Broken brute-force protection, IP block：對應上面計數器被登入自己帳號重置的例子：連續失敗 3 次就封鎖，但登入自己的帳號會讓失敗次數歸零。Lab 的 carlos 相當於正文的 bob。要觀察登入自己的帳號之後，封鎖有沒有解除、失敗次數有沒有重新累計。
  • Username enumeration via response timing：對應 X-Forwarded-For 偽造來源 IP 的例子，再接回應時間差的例子。要觀察換掉 header 的值之後封鎖是否消失，以及存在與不存在的帳號在耗時上的差距，送很長的密碼時差距會不會放大。

Lab 用的候選帳號清單與候選密碼清單同樣可在 Academy 取得。

3.1.6 HTTP Basic 認證

HTTP Basic 認證（basic authentication）是另一種登入方式：網站沒有自己的登入頁，帳號密碼由瀏覽器內建的對話框取得，之後再請求受保護的頁面，都用 Authorization header 帶著送。tickets.example.com 的內部管理頁用的就是這種方式，帳號是 admin。

使用者第一次開 /internal 時，請求還沒有帳密。伺服器回 401 Unauthorized，並用 WWW-Authenticate: Basic header 表示這個頁面要用 Basic 認證。realm="internal" 的 realm 是伺服器替這塊受保護區域取的名稱，用來區分同一個網站裡不同的受保護區域：

Request
GET /internal HTTP/1.1Host: tickets.example.com
Response
HTTP/1.1 401 UnauthorizedWWW-Authenticate: Basic realm="internal"

瀏覽器收到後，跳出自己內建的帳號密碼對話框（不是網站做的 HTML 頁面）。使用者輸入後，瀏覽器把「帳號:密碼」編碼成 Base64（一種可逆的編碼，不是加密），放進 Authorization header 重送請求；之後再請求這個 Basic 認證保護的頁面，瀏覽器都自動帶上這個 header，不靠 Cookie：

重送的請求與伺服器的回應長這樣：

Request
GET /internal HTTP/1.1Host: tickets.example.comAuthorization: Basic [Base64 字串]
Response
HTTP/1.1 200 OKContent-Type: text/html[內部頁內容]

Basic 後面那段就是 Base64：把任意字節轉成可印字元的編碼方式，沒有金鑰，任何人都能解碼回原文。拆開來就是帳號與密碼，中間用一個冒號分隔：

攔到這個字串，解碼就得到帳號與密碼。Basic 認證常見的問題有四個：

  • 每個請求都重複送出帳密，一旦被看到就直接拿到完整登入憑證。
  • 很少附帶暴力猜測防護。
  • 同一組憑證可能在其他服務重複使用。
  • 頁面看起來不重要，也可能是進一步攻擊的入口。

傳輸風險取決於有沒有 HSTS（HTTP Strict Transport Security：網站用 Strict-Transport-Security header 叫瀏覽器之後一律走 HTTPS）。使用者輸入的網址沒寫 https，或點到 http:// 連結時，瀏覽器會先送 http 請求；網站正常會回轉址（例如 301），叫瀏覽器改走 https。沒有 HSTS 時，中間人能攔下這個改走 https 的轉址（頁面裡的 https 連結也一樣），自己和網站走 https，對瀏覽器卻維持 http。瀏覽器一直停在 http，Authorization 裡的帳密以明文經過中間人，每一次都是如此。有 HSTS 時，瀏覽器記住規則之後直接走 https，不會送出那個 http 請求，也就沒有轉址可攔；瀏覽器尚未記住、網站也不在預載清單的首次造訪，仍有這個空窗。Basic 認證把帳密放進每個請求，這個弱點因此格外重要。

瀏覽器通過 Basic 認證後，會把憑證附在之後對這個網站的請求上，不靠 Cookie，也沒有額外的防護；CSRF 這類借用瀏覽器自動帶憑證的攻擊同樣打得中。

3.1.7 雙因素驗證的漏洞

雙因素驗證（two-factor authentication，2FA）要求三類驗證因素中的兩類都通過才算登入：通常是密碼（所知之事）加上另一類因素。同一類因素驗兩次不算雙因素：寄到信箱的驗證碼仍然是所知之事（能登入信箱就拿到），沒有引入第二類因素。第二類因素是專用硬體或驗證器 App（在裝置上產生碼，離開密碼本身），或是手機收到的 SMS 驗證碼（所持之物），但 SMS 有 SIM swapping（把受害者的電話號碼轉移到攻擊者手機的手法）這個弱點，不如硬體或 App 可靠。雙因素驗證比單一密碼安全：同時取得另一個管道的因素（偷到手機、換到 SIM 卡）比只偷密碼難得多。

tickets.example.com 的登入是上圖第一種：帳密通過後進到驗證碼頁，再輸入寄到信箱的碼。嚴格說這是同一類因素驗兩次。

三種弱點各自獨立，位置見上圖標號：

  • 第一步後就當成已登入：伺服器在帳密通過時就發下能存取受保護頁的 session，驗證碼頁只是畫面上的一道關卡，直接把網址改成受保護頁就進去了，不需要真的輸入驗證碼。
  • 驗證碼請求只靠可改的 Cookie 認人：送出驗證碼的請求（見下方）用 Cookie account=<名稱> 判斷現在驗證的是哪個帳號，把值改成別人的名字（例如 account=bob），網站就會替 bob 產生一組新的驗證碼寄到他的信箱；你不知道這組碼，但可以靠下一條的弱點三去猜。
  • 驗證碼無限速：4 位數碼只有一萬種組合，若沒有錯誤次數限制，可以用程式自動逐一試完。有些網站試圖用「猜錯幾次就登出」擋下這招，但這個防護擋不住：攻擊者把登入與猜碼兩步做成巨集自動重複，每次被登出就自動重新登入，繼續猜下一個候選碼。
送出驗證碼（弱點二的請求）
Request
POST /login/verify HTTP/1.1Host: tickets.example.comCookie: account=bobContent-Type: application/x-www-form-urlencodedcode=[4 位數碼]
Response
HTTP/1.1 200 OKContent-Type: text/html[驗證結果頁]

這三種弱點都出在流程，和第二步用哪一類因素無關，換成驗證器 App 或簡訊收碼同樣成立。

PortSwigger Academy 的對應練習（主題頁 Authentication）：

  • 2FA simple bypass：對應弱點一：帳密通過後伺服器就發下 session。要觀察不輸入驗證碼、直接把網址改成受保護頁，回應是不是正常的頁面。
  • 2FA broken logic：對應弱點二加弱點三：驗證碼請求只靠 Cookie 認人，驗證碼又無限速。要觀察把 account 改成別人的名字後，網站替誰產生了驗證碼，以及連續猜錯時有沒有被擋下。

4 位數碼沒有可縮小的範圍，一萬種都要試，逐一送完要花不少時間。

3.1.8 「保持登入」Cookie

登入頁常有一個「保持登入」的勾選框。勾選後，網站除了一般的 session Cookie，還會發下一個 persistent Cookie（效期很長的 Cookie，關掉瀏覽器也還在），範例網站取名 stay-logged-in。之後只要瀏覽器帶著它，網站就直接認定你已登入，不必再輸入密碼，等於跳過登入這一步。

要注意的是這個 Cookie 的內容怎麼來。Cookie 與 Session 的 session Cookie 是伺服器隨機產生、沒有規律的值；stay-logged-in 卻是用帳號資料算出來的：把使用者名稱、冒號、密碼的 MD5 雜湊接在一起，再做 Base64 編碼。雜湊（hash）是一種單向的計算：同一個輸入永遠得到同一串固定長度的結果，但沒辦法從結果直接倒推回原文。Base64 只是把資料換成另一種寫法，誰都能還原，沒有保護作用，和上一小節 Basic 認證用的一樣。拆開之後長這樣：

既然是算出來的，只要知道算法與某人的密碼，任何人都能自己做出一模一樣的 Cookie。網站收到後只是照同一個算法驗證、符合就放行，它分不出這個 Cookie 是自己發的，還是別人算的。這就是問題所在，接下來兩種攻擊都從這裡來。

怎麼知道 Cookie 的組成方式

攻擊者要先知道公式，有兩條路。

第一條，查原始碼。很多網站不是從零開始寫，而是用現成的框架（framework）：別人寫好、可重複使用的網站程式骨架，登入、Cookie 這類每個網站都需要的功能已經做好，開發者只補自己的部分。框架若是開源（open source，原始碼公開，任何人都能閱讀），它怎麼產生 stay-logged-in 這類 Cookie，程式碼和文件上都看得到，攻擊者不必自己摸索。

第二條，沒有原始碼也行，用自己的帳號 alice 反推。登入 alice 並勾選「保持登入」，把自己拿到的 Cookie 解碼，得到 alice 和一段雜湊；再把自己知道的 alice 密碼算 MD5，和解碼出來的雜湊比對。兩個一樣，就確認公式是「使用者名稱:MD5(密碼)」，這個 Cookie 的產生方式因此被完整掌握：

線上猜 bob 的密碼（攻擊一）

公式有了，卻還缺 bob 的密碼，所以對一份候選密碼清單逐一試：把候選密碼算 MD5、接在 bob: 後面、做 Base64 編碼、放進 stay-logged-in Cookie，送給網站。候選密碼不對時，網站驗證不過，視為沒登入，回應把你導回登入頁；候選密碼剛好是 bob 的密碼時，網站驗證通過，回應就是 bob 的帳號頁。兩種回應差別明顯，看回應就知道猜中沒有：

猜錯
Request
GET /account HTTP/1.1Host: tickets.example.comCookie: stay-logged-in=[Base64 字串]
Response
HTTP/1.1 302 FoundLocation: /login
猜中
Request
GET /account HTTP/1.1Host: tickets.example.comCookie: stay-logged-in=[Base64 字串]
Response
HTTP/1.1 200 OKContent-Type: text/html（bob 的帳號頁）

這種猜法不受帳號鎖定限制。網站只在登入頁計算失敗次數，Cookie 驗證走的是另一條路，猜錯也不會被計入，所以猜得再多也不會被鎖，只剩候選清單夠不夠好的問題。這是它比一般暴力猜密碼更危險的地方。

離線破解（攻擊二）

第二種攻擊的前提是已經拿到別人的 Cookie。常見的來源是網站有 XSS 漏洞：攻擊者放進網站的程式碼會在受害者的瀏覽器裡執行，因此能讀出瀏覽器裡的 Cookie 送給攻擊者，怎麼做見 XSS，這裡不重講。

拿到 bob 的 Cookie 後解碼，就得到 bob 和一段雜湊。雜湊不能直接倒推，但這裡的雜湊沒有加 salt（在雜湊前混進一段隨機值，讓同一個密碼在不同帳號算出不同的雜湊）：同一個密碼永遠得到同一個 MD5 值。所以常見密碼的 MD5 值早就被算好，整理成密碼與雜湊的對照表公開在網路上，把雜湊貼進搜尋引擎，常常一查就看到對應的密碼。查不到的話，也能拿一份密碼清單，自己逐一算 MD5 去比對，相同的那一個就是密碼。

這種攻擊稱為離線破解，因為所有計算都在攻擊者自己的電腦上做，不必再對網站送任何請求：網站看不到，也沒有失敗次數可以計算或鎖定，想擋也擋不了。

PortSwigger Academy 的對應練習（主題頁 Authentication）：

  • Brute-forcing a stay-logged-in cookie：對應攻擊一。要觀察自己帳號的 Cookie 解碼後的使用者名稱與雜湊兩部分，以及依同一公式算出的值有沒有與 Cookie 相符；之後猜目標帳號的密碼時，猜錯與猜中的回應差在哪裡。
  • Offline password cracking：對應攻擊二。這個 Lab 用 stored XSS 把受害者的 Cookie 送到 exploit server（Academy 提供、用來接收資料的外部伺服器），偷 Cookie 的做法見 XSS。要觀察的是解碼別人的 Cookie 後拿到的雜湊，與查表或密碼清單算出的 MD5 哪一個相符。

3.1.9 密碼重設與更改流程

忘記密碼的流程不能靠密碼驗證身分，使用者正是因為不記得密碼才會走這條路。tickets.example.com 的忘記密碼頁改用信箱：輸入帳號，伺服器寄一封含重設連結的信到這個帳號的信箱，點開連結設定新密碼。

這個流程有幾個環節可能出錯：

  • 寄出密碼本身：有些做法直接把密碼寄出，而不是寄連結。email 是持久且會同步到多個裝置的儲存空間，密碼留在信箱裡的時間，遠超過一個重設流程該有的生命週期；要安全，密碼得很快失效，或使用者立刻登入改掉。
  • 連結用可猜的參數（標號 1）：如果重設連結是靠帳號名稱或序號之類容易猜的值組成，不需要真的收到信也能構造出別人的連結。tickets.example.com 在資訊揭露一節的帳號頁，網址用 user=<名稱> 指定要看誰，就是這種直接用名稱當參數的做法；重設請求若也這樣設計，改掉參數就能指定別人的帳號。
  • token 沒設期限或用後沒作廢（標號 2）：重設密碼連結裡的 token 是 32 位十六進位亂數，正常設計是 15 分鐘後失效、用過一次就作廢；少了任何一條，舊的重設連結就能重複使用。
  • 沒有重新驗證 token 對應哪個帳號（標號 3）：連結裡的 token 應該和發出它的那個帳號綁定。重設密碼頁的缺陷是提交新密碼時只確認 token 本身存在，沒再確認它對應的帳號；帳號另外用表單裡的隱藏欄位 username 指定。改掉這個隱藏欄位，就能用自己收到的 token 改掉別人的密碼。

重設連結如果是用 Host header 動態組出網域部分，還有另一種攻擊方式：password reset poisoning（重設連結指向偽造網域），改 Host header 讓連結指到你控制的網域。這個手法需要先懂 Host header 的機制，留到 Host Header 一節。

更改密碼頁是另一個入口。更改密碼頁要求輸入目前密碼與新密碼兩次，用的也是表單裡的隱藏欄位 username 指定要改誰的密碼；這個頁面不需要登入就能用。於是它變成了另一個暴力猜測入口：拿目前密碼的猜測結果去試，對了或錯了，回應不同。

目前密碼錯誤
Request
POST /account/change-password HTTP/1.1Host: tickets.example.comContent-Type: application/x-www-form-urlencodedusername=bob&current-password=[猜測的密碼]&new-password-1=[新密碼]&new-password-2=[新密碼]
Response
HTTP/1.1 200 OKContent-Type: text/html目前密碼錯誤
目前密碼正確，新密碼兩次不一致
Request
POST /account/change-password HTTP/1.1Host: tickets.example.comContent-Type: application/x-www-form-urlencodedusername=bob&current-password=[正確的密碼]&new-password-1=[新密碼甲]&new-password-2=[新密碼乙]
Response
HTTP/1.1 200 OKContent-Type: text/html新密碼不一致

兩種回應不同：「目前密碼錯誤」表示猜測落空，「新密碼不一致」表示目前密碼猜對了，只是故意讓兩次新密碼不同，不會真的改掉密碼。這和帳號列舉一節的回應差異是同一種判斷，只是搬到了更改密碼頁上。

PortSwigger Academy 的對應練習（主題頁 Authentication）：

  • Password reset broken logic：對應上面重設密碼頁的隱藏欄位缺陷：帳號由表單裡的 username 指定。要觀察把這個欄位改成別人的帳號後，提交新密碼的回應是否仍然成功；Lab 裡 token 完全沒被檢查。
  • Password brute-force via password change：對應上面更改密碼頁的例子：回應會隨目前密碼猜對或猜錯而不同。要觀察「目前密碼錯誤」與「新密碼不一致」兩種訊息，後者表示猜對了。

網站確認了帳號之後，還要決定這個帳號能做什麼。下一節 Access Control 處理這一步：alice 通過登入之後，網站用什麼方式決定她能看誰的資料、能做哪些動作，又在哪些環節把這個判斷弄錯。
