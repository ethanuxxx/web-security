本節模型：shop.example.com 的登入頁

你在表單填入帳號與密碼，瀏覽器用 POST 把它們送到 /login；伺服器把送來的密碼做單向運算，與資料庫裡存的雜湊（hash，一種無法倒推回原密碼的轉換結果）比對，相符就建立 Session，回傳 Session Cookie，把你帶到登入後的頁面。

在 HTTP Requests and Sessions 那一節，登入只是一筆 POST /login：送出帳號密碼，拿回一個 Session Cookie，之後每筆請求都靠它代表你。實際的網站在這一筆前後還有很多步驟：輸錯密碼時顯示的訊息、連續輸錯後的限制、手機上的驗證碼、「忘記密碼」寄來的連結、讓你下次免輸入的「記住我」。每一步都在回答同一個問題：送出這筆請求的人，是不是他自稱的那個帳號的主人。任何一步答錯，別人就能以你的身分操作。

4.1.1 登入的每一步

身分驗證（authentication）是確認「你是誰」的過程。確認之後網站還要決定「你能做什麼」，那叫授權（authorization），屬於下一節 Access Control 的範圍。這一節只看前者。

網站拿來確認身分的證據稱為因素（factor），通常分成三類：

  • 知道的東西：密碼、PIN 碼。
  • 擁有的東西：手機上的驗證器 App、實體安全金鑰，或能收到簡訊的手機。
  • 本身的特徵：指紋、臉部等生物特徵，通常在你的裝置上比對，不直接送給網站。

只用密碼登入是單一因素。多因素驗證（multi-factor authentication，MFA）要求來自不同類別的因素；只有兩個因素時常稱為 2FA（two-factor authentication）。同一類的兩樣東西，例如密碼加上一個安全提問，仍然都是「知道的東西」，不算兩個因素。寄到信箱的驗證碼也不能直接算成第二個因素：信箱往往只靠另一組密碼保護，打得開信箱不代表持有另一個裝置。

把整段登入看成狀態的轉換，比較容易看出每一步該檢查什麼：

每個箭頭都是伺服器端的一道檢查，狀態也由伺服器保存在 Session 裡。瀏覽器手上只有 Session 識別字，看不到也不該能改「目前在哪個狀態」。

  • ①：伺服器比對帳號與密碼。沒有啟用第二因素的帳號，這一步通過就直接進入「已登入」。
  • ②：伺服器比對第二因素，比對的必須是剛才通過第一步的那個帳號。
  • ③：登出或閒置過久時，伺服器讓這個 Session 失效。只刪掉瀏覽器上的 Cookie 不夠，伺服器端的紀錄也要作廢。
  • ④ 與 ⑤：重設密碼與「記住我」都能讓人取得帳號的控制權，卻完全不經過密碼比對。它們的檢查要和正門一樣嚴格。

攻擊者要冒用一個帳號，只需要找到其中檢查最弱的一個箭頭。

4.1.2 失敗訊息透露帳號是否存在

登入失敗時，網站可能回「帳號不存在」，也可能回「密碼錯誤」。對使用者來說這很貼心，對攻擊者則多回答了一個問題：這個帳號存在嗎。從回應的差異判斷哪些帳號存在，稱為帳號列舉（username enumeration）。

逐筆比較三個請求

以 shop.example.com 的登入表單為例。先用一個確定不存在的帳號和一個隨便的錯密碼送出，作為基準：

請求 A：不存在的帳號
Request
POST /login HTTP/1.1Host: shop.example.comContent-Type: application/x-www-form-urlencodedusername=demo-missing&password=wrong-pass
Response
HTTP/1.1 200 OK（其他標頭略）… <p class="error">Invalid username</p> …

接著密碼保持不變，只把帳號換成另一個值：

請求 B：只換帳號
Request
POST /login HTTP/1.1Host: shop.example.comContent-Type: application/x-www-form-urlencodedusername=demo-member&password=wrong-pass
Response
HTTP/1.1 200 OK（其他標頭略）… <p class="error">Incorrect password</p> …

兩筆請求只差在 username，所以訊息的差異來自帳號。「Incorrect password」等於告訴你：這個帳號存在，只是密碼不對。把請求 B 原樣再送一次（請求 C），訊息相同，表示這個差異至少能重現。這還不夠下結論：帳號鎖定、限速或表單隱藏欄位裡的一次性值，都可能讓回應在一段時間內停在同一種樣子，A 和 B 也可能剛好落在某個狀態改變的前後。要確定差異只來自帳號，用已知的帳號，每次都從相同的狀態出發（重新取得表單的一次性值，失敗次數也還沒累積），把 A、B 交錯送出幾次，結果穩定分成兩組才算數。

測試者若要找出未知的帳號，會固定密碼，把帳號依序換成 [候選帳號]，看哪一個的回應落在 B 那一組。方括號代表被換掉的那段輸入。找到存在的帳號之後，下一步才是反過來固定帳號、換密碼。

列舉的結果只是一個帳號名稱。它縮小了之後要猜的範圍，但還沒有證明任何密碼，也還沒登入任何帳號。要判斷是否真的登入成功，看的是之後的帳號頁顯示誰的資料，單看 302 不夠（見 HTTP Requests and Sessions）。

訊息相同時的其他差異

把兩種訊息統一成同一句話，只封住了最明顯的一個差異。回應還有很多地方會因帳號存在與否而不同：

  • 狀態碼：文字相同，但不存在的帳號回 200，錯密碼回 403。
  • 長度與細節：兩句話看起來一樣，其中一句卻多一個句點或空白，或頁面某處多了一個欄位。比較時要看回應原文，不能只看畫面。
  • 時間：處理不存在的帳號比處理存在的帳號快。
  • 其他頁面：註冊頁回「這個帳號已被使用」，重設密碼頁回「找不到這個 email」，同樣回答了帳號是否存在。

時間差異的成因可以從伺服器的處理流程看出來：

密碼雜湊（下面「密碼在伺服器上怎麼存」會說明）刻意設計成計算很慢，所以「有沒有算雜湊」會在回應時間上留下痕跡。時間會受網路與伺服器負載影響，一次量測不算數；判讀方式和 UNION, Blind, and NoSQL Injection 的時間訊號相同，要重複量測，並和已知不存在的帳號比較。

4.1.3 猜密碼與嘗試次數

反覆嘗試不同的帳號密碼組合，直到猜中為止，稱為暴力破解（brute-force attack）。這類嘗試通常由程式自動送出，猜的也不是隨機字串，而是常見密碼，或從其他網站外洩的帳號密碼組合。許多人在不同網站重複使用密碼，所以把外洩組合拿到另一個網站逐一試，常常有效，這種做法稱為撞庫（credential stuffing）。

網站無法阻止別人送出登入請求，能控制的是每個帳號、每個來源在一段時間內可以失敗幾次。常見的做法各有代價：

帳號鎖定（account lockout）：同一帳號連續失敗若干次就暫停登入針對單一帳號的大量猜測任何人都能故意輸錯，把別人的帳號鎖住，變成阻斷服務。攻擊者也可以對很多帳號各試一兩個常見密碼，每個帳號都沒達到鎖定門檻。

失敗計數在某些事件後歸零（本意是讓正常使用者登入後不受舊的失敗次數影響）如果攻擊者用自己的帳號成功登入一次就能讓計數歸零，他就可以穿插著登入自己的帳號，繞過次數限制。

NIST（美國國家標準與技術研究院）的數位身分指引 SP 800-63B-4 要求驗證端限制失敗次數，並且分開計算帳號上的每一個驗證器（authenticator），例如這個帳號的密碼，或綁定的某一支驗證器 App。同一個驗證器連續失敗最多 100 次，網站可以訂得更低；達到上限就停用這個驗證器，使用者要重新綁定或重設後才能再用。100 是在猜中機率與帳號復原的麻煩之間取捨：NIST 在說明這條規定時，以六位數的十進位一次性驗證碼為例。以六位數驗證碼來算，100 次猜中的機率是 100／1,000,000＝萬分之一。密碼的情況不同，前 100 個常見密碼就可能猜中，所以這個上限要搭配下一小節的密碼規則，先排除常見與外洩過的密碼才有意義。計數跟著驗證器走，換一個新的 Session、要求重發驗證碼或重新開始登入，都不該讓它歸零。還沒到上限時，網站也可以逐步拉長等待時間、要求額外驗證，或通知帳號主人。

4.1.4 密碼在伺服器上怎麼存

伺服器要比對密碼，卻不該保存密碼本身。資料庫一旦外洩，明文密碼會讓所有帳號立刻失守，還會連累使用者在其他網站的同一組密碼。

雜湊與 salt

雜湊（hash）是一種單向的計算：同樣的輸入永遠得到同樣的輸出，但從輸出推不回輸入。網站註冊時只保存密碼的雜湊值；登入時把收到的密碼用同樣方法計算一次，比較結果是否相同。

只做雜湊還不夠。兩個使用者用了同一個密碼，雜湊值就相同；攻擊者還能事先為常見密碼算好一張對照表。所以每個密碼計算前要先混入一段隨機、每個帳號各不相同的值，稱為 salt，和雜湊值一起保存。SP 800-63B-4 要求 salt 至少 32 位元。

為什麼要慢

拿到外洩雜湊值的攻擊者，可以在自己的電腦上不停猜測、計算、比對，網站的嘗試限制完全管不到，這稱為離線猜測。SHA-256 之類一般用途的雜湊函式設計得很快，一般電腦每秒就能算大量次數，對離線猜測幾乎沒有阻力。

密碼專用的雜湊演算法刻意讓每次計算花費可調整的時間與記憶體。正常登入只算一次，多花一點時間無感；攻擊者要算上億次，成本就成倍增加。OWASP（Open Worldwide Application Security Project，維護 Web 安全指引的非營利社群）的 Password Storage Cheat Sheet 依優先順序建議：

  • Argon2id：最低設定為 19 MiB 記憶體、2 次迭代、平行度 1。
  • 無法使用 Argon2id 時用 scrypt：CPU／記憶體成本參數至少 217，區塊大小 8，平行度 1。
  • 只能用 bcrypt 的舊系統：工作因子（work factor）至少 10。多數 bcrypt 實作只處理密碼的前 72 個位元組（byte），之後的部分直接忽略。位元組和字元要分開算：英文字母一個佔 1 個位元組，中文字在常用的 UTF-8 編碼下佔 3 個，24 個中文字就用完了，還不到下面「至少允許 64 個字元」的一半。這類系統要明確處理過長的密碼，不能默默截斷，並規劃遷移到上面的演算法。
  • 需要符合 FIPS-140 規範時用 PBKDF2：以 HMAC-SHA-256 為內部函式，迭代至少 600,000 次。

這些數字是下限，會隨硬體進步調高。SP 800-63B-4 也建議在驗證端效能負擔得起的範圍內把成本盡量拉高；實際的值要在自己的伺服器上依登入負載量測後決定。salt 以外，還可以加一把與資料庫分開保管的金鑰（OWASP 稱為 pepper），讓只偷到資料庫的人無法單獨驗證猜測。

密碼規則

SP 800-63B-4 對密碼本身的要求和許多網站的習慣不同：

  • 密碼作為唯一因素時至少 15 個字元；作為多因素中的一個時至少 8 個字元。應允許至少 64 個字元。
  • 不得強制「大小寫、數字、符號都要有」這類組合規則，也不得要求定期更換；有證據顯示密碼外洩時才強制更換。
  • 設定或更換密碼時，要和一份常見、可預期或已外洩的密碼清單比對，命中就要求另選，並說明原因。

4.1.5 第二個因素

常見的第二因素是一組短的一次性驗證碼，由手機上的驗證器 App 產生，或由網站以簡訊寄送。驗證器 App 多半採用 TOTP（Time-based One-Time Password，RFC 6238）：綁定時網站和 App 共享一把祕密金鑰，之後雙方各自用這把金鑰和目前的時間區段（常見每 30 秒一段）算出同樣的數字，所以不用連線也能對上。位數由設定決定，常見是 6 位。不論驗證碼從哪裡來，伺服器都要像上面的狀態圖那樣，在第一步通過後記住「哪個帳號、還差第二因素」，等第二步通過才進入已登入。

流程裡多了第二步，伺服器上的每條路卻未必都經過它。下圖是一個正確的設計和兩種常見的缺陷：

第一步就給了已登入的 Session

有些網站在密碼正確時就把 Session 標成已登入，再把瀏覽器導向輸入驗證碼的頁面。驗證碼頁只是畫面上的下一步，伺服器的其他頁面並沒有檢查它是否完成。知道密碼的人直接請求帳號頁，就跳過了第二因素。這時多因素只存在於使用者看到的流程，伺服器上的狀態並沒有「還差一步」這回事。

第二步由請求決定帳號

另一種缺陷是第二步從請求中的欄位或 Cookie 讀取「要驗證哪個帳號」，例如一個存放帳號名稱的 Cookie。攻擊者先用自己的帳號通過第一步，再把這個值改成 [被換掉的帳號識別值]，第二步就變成在驗證別人的帳號。若網站還會為該帳號產生新的驗證碼，而驗證碼只有 6 位數（共 100 萬種組合），又沒有限制嘗試次數，猜中只是時間問題。這時攻擊者連對方的密碼都不需要。

兩種缺陷的共同點是第二步與第一步沒有綁在一起：伺服器沒有在 Session 中記下「這個 Session 已經用哪個帳號通過第一步」，並以此為唯一依據。

4.1.6 重設密碼的流程

忘記密碼時，網站要在不知道舊密碼的情況下，確認提出要求的人是帳號主人。常見的做法是寄一封含連結的郵件：能打開那個信箱的人，就被當成帳號主人。連結中帶著一個 token，也就是伺服器產生、只交給信箱主人的一次性憑證。

這條流程繞過了密碼，所以 token 就等於帳號的鑰匙。常見的缺陷都出在 token 或它與帳號的對應：

  • token 可以預測：由帳號名稱、時間戳記或遞增編號算出來，攻擊者不必收信就能自己算出別人的 token。
  • 最後一步沒有檢查 token：⑤ 送出時，伺服器只在 ④ 開啟頁面時檢查過 token，收到新密碼時卻沒有再查，甚至在 token 欄位空白時照樣接受。
  • 帳號由請求決定：⑤ 的表單帶著一個隱藏欄位寫明「要改哪個帳號」，伺服器照著改。攻擊者用自己帳號拿到的有效 token，搭配 [被換掉的帳號識別值]，就能改掉別人的密碼。
  • token 不會失效：沒有到期時間，或用過一次還能再用，舊郵件、瀏覽紀錄中留下的連結就一直有效。
  • 連結被送到別處：網站依請求中的 Host 標頭組出連結的網域，請求被竄改時，信中的連結就指向別人的伺服器，使用者一點，token 就送到那裡。這和主機名稱的信任有關，Host Headers and Web Caches 那一節會再看到。

重設頁面本身也會洩漏帳號是否存在：「已寄出重設信」和「找不到這個帳號」兩種回應，與登入時的列舉相同。

4.1.7 登入之後的 Session

所有檢查都通過後，網站要把「這個人已經登入」交給一個 Session 保存。這一步本身也會出錯。

登入時換發新的識別字

很多網站在你第一次造訪時就建立 Session，登入時再把身分寫進去（HTTP Requests and Sessions 提過這種設計）。如果登入前後沿用同一個 Session 識別字，而攻擊者有辦法讓受害者使用一個攻擊者事先知道的識別字，受害者登入之後，攻擊者手上的那個識別字也就成了已登入的 Session。這稱為 Session fixation（Session 固定）。修補方式是登入成功（以及權限提升）時產生新的識別字，並讓舊的失效。

登出要讓伺服器端失效

登出時若只叫瀏覽器刪掉 Cookie，伺服器的 Session 表裡那筆紀錄仍然有效。之前被複製到別處的識別字，例如留在代理紀錄或共用電腦上的，仍然能用來請求帳號頁。登出、閒置逾時與修改密碼時，都要在伺服器端作廢 Session。

「記住我」

「記住我」讓瀏覽器保存一個有效期很長的 token，Session 過期後網站憑它直接讓你登入。這個 token 的效力等於密碼，所以它必須是伺服器產生的隨機值，伺服器端記錄它屬於哪個帳號、何時到期，並能單獨撤銷。若 token 是由帳號名稱、時間或密碼的快速雜湊直接算出來的，任何知道算法的人都能替別的帳號算出一個，或從偷來的 token 反推、離線猜出密碼。

修改密碼的頁面

修改密碼的功能通常要求輸入目前的密碼。這個比對和登入一樣是一道密碼檢查，同樣需要統一的錯誤訊息與次數限制；若頁面還從請求欄位讀取「要改哪個帳號」，就和重設流程的缺陷相同。

4.1.8 成立的前提

  • 帳號列舉需要可重現的差異。只出現一次的不同，可能來自表單一次性值過期、限速或伺服器負載；網站啟用帳號鎖定後，回應也可能隨嘗試次數改變。
  • 列舉之後能不能猜中密碼，取決於密碼強度與嘗試限制；網站若只能用 email 登入，而 email 本來就公開，列舉帶來的新資訊就很少。
  • 第一種 MFA 缺陷（第一步就給了已登入的 Session）需要先知道帳號的密碼；第二種缺陷則需要攻擊者有自己的帳號，能走完第一步。
  • 重設流程的缺陷，多半需要攻擊者能先合法拿到自己帳號的 token，或能讓網站替受害者發出重設信。
  • Session fixation 需要攻擊者能讓受害者使用他事先知道的識別字；網站若在登入時換發新的識別字，這條路就不存在。

4.1.9 Information disclosure

從回應的差異讀出多餘的資訊，這套觀察方法在 Seeing the Web Through the Browser 的「錯誤訊息與資訊揭露」介紹過。帳號列舉就是登入功能上的資訊揭露：網站多回答了「這個帳號存在」。登入相關功能附近還有其他常見的洩漏：

  • 公開的個人頁面、留言作者、文章署名直接顯示登入用的帳號名稱。
  • 回應或 HTML 註解中出現管理員、客服人員的 email。
  • 登入請求格式不對時，回應帶出程式的錯誤細節，例如資料表名稱、驗證元件與版本。
  • 登入失敗的詳細原因被寫進對外可讀的紀錄或除錯頁面。

一個帳號名稱、一個 email，或錯誤頁上的版本號，本身都沒有讓任何人登入，只是縮小了後續猜測的範圍。評估影響時，把多知道的資訊和已經證明能做到的事分開寫。

4.1.10 防禦手法

統一的失敗回應

登入、註冊、重設密碼的失敗回應，不論帳號是否存在、是否被鎖定，對外都用同一段文字、同一個狀態碼與同樣的頁面結構。例如登入失敗一律回「帳號或密碼錯誤」，重設頁一律回「如果這個 email 已註冊，你會收到一封重設信」。處理時間也要一致：帳號不存在時，也拿收到的密碼和一組預先準備的假雜湊值（含 salt 與相同的參數）跑一次同樣的驗證計算，讓回應時間一致。詳細原因寫進伺服器端有存取控制的紀錄，紀錄裡不要寫入使用者送來的密碼。這些做法與 OWASP Authentication Cheat Sheet 的建議一致。

不在對外可見處洩漏資訊

  • 公開頁面（個人頁、留言作者、文章署名）顯示暱稱或另設的顯示名稱，不顯示登入用的帳號名稱。
  • 管理員與客服的 email 不寫在公開頁面或 HTML 註解裡；需要聯絡窗口時用專用的共用信箱或表單。
  • 請求格式不對時，對外回一般性的錯誤頁，不帶出資料表名稱、驗證元件與框架版本；關閉正式環境的除錯模式。
  • 登入失敗的詳細原因只寫進有存取控制的內部紀錄，不放進對外可讀的紀錄檔或除錯頁面。

限制嘗試

同時依帳號與來源計算失敗次數，失敗計數不因登入其他帳號而歸零。逐步拉長等待時間，比永久鎖定更不容易被拿來鎖別人；被鎖定的使用者仍能走重設密碼流程取回帳號。驗證碼與重設 token 的檢查也要限制次數。來源位址只取自可信的網路設定，不讀使用者能改的標頭。

安全地保存密碼

依前面「密碼在伺服器上怎麼存」：每個密碼各自加 salt，用 Argon2id、scrypt、bcrypt 或 PBKDF2 這類刻意放慢的演算法，參數不低於 OWASP 的建議值，並隨硬體進步調高。新密碼要和常見與外洩密碼清單比對。

把第二因素綁在同一個 Session 上

第一步通過後，伺服器在 Session 裡記下帳號與「待第二因素」的狀態；所有需要登入的頁面只接受「已登入」狀態。第二步要驗證的帳號只從 Session 取得，不讀請求中的任何帳號欄位。驗證碼有效期短、用過即作廢。錯誤次數算在帳號的這個驗證器上，達到上限就停用它（見猜密碼與嘗試次數）。也可以另外讓這次登入從頭來過，但重新登入或重發驗證碼都不能讓計數歸零。

重設 token 的條件

OWASP Forgot Password Cheat Sheet 列出的條件包括：

  • 用密碼學安全的亂數產生器產生，長度足以抵抗猜測。
  • 伺服器端記錄它綁定的帳號，最後一步只依 token 找出帳號。
  • 設定到期時間，只能使用一次，用過或重設完成後立即作廢；伺服器端可以只存 token 的雜湊值，資料庫外洩時 token 不會跟著外洩。
  • 連結的網域寫在設定中，不由請求的 Host 標頭決定；重設頁面設定 Referrer-Policy: no-referrer，避免 token 隨 Referer 標頭送到第三方網站。
  • 重設完成後，讓該帳號既有的 Session 失效（或讓使用者選擇）。

Session 的換發與失效

登入與權限提升時換發新的 Session 識別字；登出、逾時、修改或重設密碼時，在伺服器端作廢 Session 與「記住我」token。Session 識別字與「記住我」token 都用隨機值，Cookie 加上 Secure（只經 HTTPS 傳送）與 HttpOnly。SameSite 屬性與跨站請求有關，留到 CSRF, CORS, and Cross-Site Trust 那一節討論。

多因素驗證

密碼終究可能被猜中或外洩，正確實作的多因素驗證讓光有密碼不足以登入。一次性驗證碼是使用者看得到、能轉述的數字，假網站騙到之後可以立刻拿去真網站輸入。安全金鑰與 passkey 使用的 WebAuthn（Web Authentication，瀏覽器提供的公開金鑰登入標準）不同，每個憑證綁定一個網域（稱為 RP ID，relying party identifier），瀏覽器只讓相符的網站使用它，伺服器還會檢查簽章資料裡記錄的 origin。假網站的網域對不上，就拿不到可轉用的登入證明，所以這類因素稱為抗釣魚（phishing-resistant）。

4.1.11 小結

  • 身分驗證是一段由伺服器保存狀態的流程：帳號密碼、第二因素、換發 Session、失效；重設密碼與「記住我」是另外兩個入口，檢查要和正門一樣嚴格。
  • 失敗回應在文字、狀態碼、長度、時間或其他頁面上的任何可重現差異，都可能洩漏帳號是否存在；列舉只得到帳號名稱，還沒有登入任何帳號。
  • 嘗試限制要同時考慮帳號與來源，並防止鎖定被拿來鎖住別人；密碼以加 salt 的慢速雜湊保存，讓外洩的資料庫難以離線猜測。
  • MFA 與重設流程的常見缺陷，是最後一步沒有綁定前一步：第二因素要只驗證 Session 裡的帳號，重設要只修改 token 綁定的帳號。
  • 登入時換發新的 Session 識別字，登出與改密碼時在伺服器端作廢 Session。

PortSwigger Academy 的 Authentication 主題有對應的 Lab：

  • Username enumeration via different responses：從失敗訊息的差異找出存在的帳號。
  • Username enumeration via response timing：訊息相同時，用回應時間區分帳號。
  • Broken brute-force protection, IP block：找出失敗計數在什麼情況下歸零。
  • 2FA simple bypass：第一步之後的 Session 是否已被當成登入。
  • 2FA broken logic：第二步從哪裡決定要驗證的帳號。
  • Password reset broken logic：重設的最後一步檢查了什麼、依什麼決定帳號。
  • Brute-forcing a stay-logged-in cookie：「記住我」token 是怎麼算出來的。

到這裡，網站已經知道每筆請求代表哪個帳號。知道是誰之後，還要決定這個人能讀哪些資料、能做哪些動作。HTTP Requests and Sessions 的「身分與目標」已經看過，一筆請求同時帶著目前身分與想操作的目標，伺服器若只確認了前者，就可能把別人的資料交出去。下一節 Access Control 從這個區分出發，看角色、物件與多步驟操作上的授權檢查。
