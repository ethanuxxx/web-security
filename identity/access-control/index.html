在 HTTP Requests and Sessions 的「身分與目標」，同一個 Cookie 搭配不同的 id，伺服器就可能交出另一個帳號的資料。當時的問題只有一種：讀取別人的帳號頁。實際網站裡要判斷的事情多得多：一般會員能不能打開後台、能不能替自己加上管理員角色、能不能取消別人的訂單。上一節 Authentication 讓伺服器知道請求來自誰；這些問題都發生在知道是誰之後。

4.2.1 知道是誰之後

網站處理一筆登入後的請求，依序靠三種機制：

Authentication（身分驗證）
登入時確認「你是 wiener」，例如核對密碼與第二因素。
Session management（Session 管理）
登入之後，讓伺服器從每一筆請求的 Session 識別字認出「這還是 wiener」。
Authorization（授權）
對這一筆請求判斷「wiener 可以做這件事嗎」。

網站用來落實授權的整套規則與程式，稱為存取控制（access control）。前兩種機制都正確，第三種仍可能出錯：伺服器很清楚發出請求的是 wiener，只是沒有問 wiener 能不能做。

授權判斷需要三項輸入，1.2 看過的是前兩項（目前身分、目標資源）：

  • 執行者：發出請求的人。伺服器從 Session 表查出，連同他的角色，例如「wiener，顧客」。
  • 目標：被操作的資料或物件，例如「訂單 1042」，以及它屬於誰。
  • 動作：要做的事，例如讀取、修改、刪除、變更角色。同一張訂單，顧客能讀自己的，不一定能改金額。

執行者只能來自伺服器自己查到的資料。目標與動作則寫在請求裡，使用者可以任意改寫；伺服器拿它們當「對方想做什麼」的描述，再用執行者去比對規則。

4.2.2 水平與垂直越權

使用者做到了規則不允許的事，稱為越權（privilege escalation）。依照越過的方向分成兩類：

水平越權（horizontal privilege escalation）
同一層級的使用者存取彼此的資料。wiener 讀到 carlos 的訂單、改掉 carlos 的收件地址，都屬於這一類。1.2 的 IDOR 例子就是水平越權。
垂直越權（vertical privilege escalation）
使用者用到更高角色才能用的功能。一般會員打開管理後台、刪除其他帳號、替別人變更角色，都屬於這一類。

兩類問題也會串在一起。水平越權讀到的若是管理員的帳號頁，頁面上剛好又顯示了管理員的密碼欄位或 API key（程式呼叫服務時用的存取憑證），拿到這些資料的人就能以管理員身分登入或呼叫 API，水平越權於是變成垂直越權。

有些規則還取決於流程走到哪裡，例如付款之後就不能再改購物車內容。這類依狀態而定的限制在第 6 章談業務邏輯時處理；這一節只問執行者有沒有權限做這個動作。

4.2.3 IDOR 的各種識別值

1.2 的 IDOR 用帳號名稱當識別值。只要請求裡有一段文字指出「要哪一筆資料」，伺服器又直接拿它去查，就可能出現同樣的問題。常見的識別值有：

  • 資料庫的流水號：訂單 1042、發票 88017。數字連續，換一個就可能是別人的。
  • 使用者名稱或電子郵件：1.2 的 id=wiener。
  • 檔名：例如客服對話紀錄存成 /download/transcript/12.txt。若檔案放在網站直接提供的位置，連應用程式的程式碼都沒經過，更不會檢查擁有者。
  • 長識別值，例如 UUID（Universally Unique Identifier，一種 128 位元的識別值）。UUID 有好幾個版本，由時間或名稱算出的版本不見得難猜；用安全亂數產生的 UUIDv4 很難猜，但網站常在別處把它顯示出來：留言作者的連結、公開個人頁的網址、API 回應中的欄位。

難猜只會延後對方拿到識別值的時間。伺服器沒有比對擁有者，任何拿到識別值的人照樣能用。

一筆發票請求的推演

wiener 在 shop.example.com 下載自己的發票：

# wiener 下載自己的發票
GET /orders/1041/invoice HTTP/1.1
Host: shop.example.com
Cookie: session=DEMO123

處理這個請求的程式可能這樣寫：

# 不安全的做法：只確認已登入
user = current_user(request)      # 用 Session 識別字查表：wiener
if user is None:
    return redirect("/login")

order = db.query("SELECT * FROM orders WHERE id = ?", order_id)
return render_invoice(order)

查詢用了參數化的 ?，不會有 SQL Injection；問題在查詢條件只有訂單編號。逐步看兩種請求：

正常
  請求路徑：    /orders/1041/invoice
  執行者：      wiener（查表得知）
  查詢條件：    id = 1041
  查到的訂單：  1041，擁有者 wiener
  回應：        wiener 的發票

被操縱
  請求路徑：    /orders/[別人的訂單編號]/invoice
  執行者：      wiener（Cookie 沒變）
  查詢條件：    id = [別人的訂單編號]
  查到的訂單：  擁有者 carlos
  回應：        carlos 的發票

方括號代表被換掉的那段輸入。兩次請求的執行者都是 wiener，程式也都確認了他已登入；第二次請求中，執行者與目標擁有者不同，程式卻從頭到尾沒有比較這兩項。

寫入與刪除也一樣

讀取只是其中一種動作。POST /orders/[別人的訂單編號]/cancel 若同樣只檢查已登入，wiener 就能取消 carlos 的訂單；修改收件地址、刪除留言、變更通知設定也是同一個模式。寫入類的 IDOR 不一定在回應裡留下明顯痕跡，要回頭看資料有沒有被改變。

拒絕了，資料卻已送出

有些程式發現使用者無權存取時，回傳 302 把瀏覽器導回首頁，卻在同一份回應的本體裡已經放了目標帳號的頁面內容。瀏覽器照 Location 跳走，畫面上什麼都看不到；在 Burp 的 HTTP history 點開那一筆 302，本體裡就有資料。程式先產生了內容，最後才決定導向，資料在拒絕之前就已經寫進回應。

4.2.4 只藏起來的管理功能

垂直越權最直接的形式，是管理功能根本沒有檢查。管理員首頁有一個「管理後台」連結，一般會員的首頁沒有；設計者以為沒有連結就沒人進得去，伺服器處理 /admin 時卻沒有確認執行者的角色。

沒有連結的網址仍然找得到：

  • robots.txt 是寫給搜尋引擎爬蟲的規則檔，任何人都能讀。把後台路徑列進去「請爬蟲別收錄」，等於公開了它的位置。
  • 前端程式決定要不要顯示管理選單時，程式碼本身會送到每一位使用者的瀏覽器：
// 這段程式送給每一位使用者，不分角色
if (currentUser.isAdmin) {
  addMenuLink("管理後台", "/admin-console-7f3a");
}

判斷是否顯示的條件在瀏覽器執行，網址字串則原原本本躺在程式碼裡。把後台改成難猜的網址，換來的只是「不容易被猜到」；網址出現在任何一份送給使用者的檔案裡，就失去作用。

同樣的道理適用於所有只在前端做的檢查：灰掉的按鈕、隱藏的表單欄位、JavaScript 裡的 if (isAdmin)。這些都只決定畫面長什麼樣子。在 1.2 用過的 Repeater 裡，請求可以不經過任何畫面直接送出，伺服器收到的只有請求本身。

4.2.5 由使用者送來的角色

有些網站在登入時查出使用者的角色，接著把結果放到使用者手上：一個 Cookie、一個隱藏的表單欄位、網址的查詢參數。之後每次請求，伺服器讀這個值，沒有驗證它是否被改過就直接採信，決定要不要放行。

# 登入後，伺服器在 Cookie 裡記下角色
GET /admin HTTP/1.1
Host: shop.example.com
Cookie: session=DEMO123; role=customer

Session 識別字指向伺服器端的資料，role 卻是一個由瀏覽器保管的值。在 Repeater 把它換成 role=[被換掉的角色值]，伺服器讀到的就是新的值（1.2 提過，Cookie 的值使用者看得到也改得動）。問題在伺服器直接相信這個值，和它放在 Cookie 裡無關：伺服器若在值後面附上只有自己算得出的簽章，收到時先驗證，被改過的值就會被認出來。更簡單的做法是不把角色交給瀏覽器，只從伺服器端的 Session 資料查（見怎麼修補）。

多送一個欄位

另一種情況發生在更新個人資料。前端表單只送出電子郵件：

# 正常的更新請求
POST /my-account/update HTTP/1.1
Host: shop.example.com
Cookie: session=DEMO123
Content-Type: application/json

{"email": "wiener@example.com"}

若伺服器把收到的 JSON 欄位全部寫回使用者資料，請求本體多加上 [額外加入的角色欄位]，角色也會一起被寫入。這叫 mass assignment（大量指派）：程式本意只讓使用者改幾個欄位，卻照單全收。回應若把整筆使用者資料傳回來，往往連角色欄位的名稱都會出現在裡面。

4.2.6 多步驟流程

敏感操作常拆成幾個畫面。以管理員替使用者變更角色為例：

  1. 開啟管理頁：GET /admin，列出所有使用者。
  2. 選擇對象與新角色，送出：POST /admin/roles，伺服器回傳一個「確定要變更嗎？」的頁面。
  3. 按下確認：POST /admin/roles/confirm，伺服器把新角色寫進資料庫。

對瀏覽器來說，這是使用者依序點擊三個畫面。對伺服器來說，這是三個獨立的請求，各由一段處理程式（handler）負責。瀏覽器照畫面順序走，不代表請求只能照這個順序來：知道第 3 步請求格式的人，可以跳過前兩步直接送出它。

設計者在第 1 步確認了管理員身分，便假設能抵達第 3 步的人都通過了第 1 步。實際上第 3 步的請求只帶著 Cookie 和要變更的內容，裡面沒有任何東西證明前面的檢查做過。

第 3 步的請求裡，Cookie 和 username 指的是不同的人：

# 第 3 步：管理員確認把 carlos 改成編輯者
POST /admin/roles/confirm HTTP/1.1
Host: shop.example.com
Cookie: session=[管理員的 Session 識別字]
Content-Type: application/x-www-form-urlencoded

username=carlos&role=editor&confirm=yes

Cookie 決定執行者，username 決定被變更的對象。管理員送出這筆請求是合法的管理操作。同樣格式的請求若由一般使用者送出，Cookie、username、role 三個值都換掉，就是一般使用者替自己升級：

# 一般使用者跳過前兩步，直接送出第 3 步
POST /admin/roles/confirm HTTP/1.1
Host: shop.example.com
Cookie: session=[一般使用者的 Session 識別字]
Content-Type: application/x-www-form-urlencoded

username=[被變更的帳號]&role=[想取得的角色]&confirm=yes

若第 3 步不檢查執行者，這筆請求和管理員那筆走的是同一段程式。三種情況放在一起比較：

執行者請求應有的結果只有第 1 步檢查時
administrator開啟管理頁允許允許
wiener開啟管理頁拒絕拒絕
wiener直接送出第 3 步拒絕角色被改成管理員

只測前兩列，網站看起來沒有問題。第三列的請求寫入的是角色，一旦成功，wiener 之後的每一筆請求都帶著管理員權限。

4.2.7 依請求附帶資訊做的檢查

還有一類檢查只看請求「從哪裡來」或「怎麼送」，沒有看執行者是誰。

依 Referer 判斷

Referer 標頭記錄使用者是從哪個頁面點過來的，瀏覽器通常會自動帶上，但可能依 Referrer Policy（控制要不要送、送多少的政策）省略，或縮短成只剩 origin（協定、網域與埠號）。有些網站對 /admin 本身做了角色檢查，對它底下的子功能卻只看 Referer：從 /admin 頁面點過來的，就當作是管理員。Referer 和 Cookie 一樣是請求裡的一個標頭，在 Repeater 裡可以寫成任何內容，伺服器無從分辨它是瀏覽器自動填的還是手動改的。

依方法或網址字面判斷

有些網站把存取規則放在應用程式前面的一層（例如反向代理或框架的路由設定），寫成「非管理員不得對 /admin/roles 送 POST」。規則本身沒錯，但後面的應用程式若也接受用 GET 加查詢參數完成同一個動作，那筆 GET 請求就不在規則範圍內。網址的比對也有同樣的落差：前面那層把 /admin/roles 和大小寫不同或結尾多一個斜線的寫法看成不同的路徑，應用程式卻把它們當成同一個功能。檢查規則和實際處理請求的程式各自解讀請求，兩邊對不上，就留下規則沒涵蓋到的請求。

4.2.8 用兩個帳號比對

找存取控制問題，靠的是比對：同一筆請求，換不同的執行者送出，看結果是否符合規則。準備方式：

  • 兩個角色不同的帳號，例如一個管理員、一個一般使用者；查水平越權則準備兩個同角色的帳號。
  • 兩個互不干擾的瀏覽器工作階段，例如一個普通視窗、一個無痕視窗，各自登入，並記下各自的 Cookie 屬於誰。

先用權限高的帳號走一遍正常流程，在 HTTP history 找出每一步的請求；再把這些請求的 Cookie 換成權限低的帳號，或乾脆拿掉 Cookie，逐一重送。把結果填進表格：每一列是一筆請求，每一欄是一種執行者，格子裡寫實際結果，再和應有的結果比較。

判讀結果時常犯的錯：

  • 200 只表示伺服器回了內容，要看內容是否屬於目標、資料是否真的被改了。寫入類的請求，換回權限低的帳號重新載入頁面，確認角色或資料的實際狀態。
  • 重送時誤留了管理員的 Cookie，成功只代表管理員能做管理員的事。每次送出前確認 Cookie 屬於哪個帳號。
  • 首頁或第一步拒絕了，不代表後面的步驟也會拒絕；每一筆請求都要單獨測。

4.2.9 靠不住的防禦

做法為什麼不夠
只在畫面上隱藏連結或按鈕請求不經畫面也能送出，伺服器處理請求時沒有檢查
把後台放在難猜的網址網址可能出現在前端程式、robots.txt 或其他回應中；拿到網址的人照樣能用
用 UUID 取代流水號識別值變難猜，但可能在其他頁面公開；伺服器仍沒有比對擁有者
把角色放在 Cookie 或隱藏欄位，不驗證是否被改過這些值由使用者保管，伺服器沒有驗證完整性就直接採信，被改過也分辨不出來
只在流程第一步檢查後續步驟的請求可以直接送出，不必先經過第一步
依 Referer 判斷來源頁面Referer 是請求者自己填的標頭
只在前面一層限制特定方法與網址應用程式若接受其他方法或其他寫法的網址，就有規則沒涵蓋的請求

這些做法都在依賴請求裡由使用者決定的東西，或依賴使用者「應該」照什麼順序操作。

4.2.10 怎麼修補

每筆請求都在伺服器端判斷

授權判斷放在伺服器，對每一筆請求重新做，用的是伺服器用 Session 識別字查出來的執行者與角色。請求裡的角色欄位、Referer、「前一步已通過」之類的資訊都不拿來做決定。多步驟流程的每一步都要檢查，最後真正寫入資料的那一步尤其不能省。

預設拒絕

規則採預設拒絕（deny by default）：沒有明確規則允許的請求一律拒絕。新增一個功能卻忘了寫規則時，結果是誰都用不了，而不是誰都能用；前者在測試時馬上會被發現。

集中在一處檢查

讓每個 handler 各寫各的 if，總會有一個漏掉。較好的做法是把授權寫成全站共用的一個機制，每個功能宣告它需要什麼權限，由共用的程式在 handler 執行前檢查：

# 每個功能宣告需要的權限；require 在 handler 執行前
# 用 Session 查出的執行者檢查，沒有宣告權限的功能一律拒絕
@require("users:change-role")
def confirm_role_change(request):
    actor = current_user(request)                 # 來自 Session
    target = find_user(request.form["username"])
    new_role = request.form["role"]

    if new_role not in assignable_roles(actor):   # 這個管理員能指派哪些角色
        return forbidden()
    if not manages(actor, target):                # 目標在不在他的管理範圍
        return forbidden()
    set_role(target, new_role)

角色變更比讀取資料多兩項檢查：執行者能指派哪些角色（一般管理員不一定能指派最高權限），以及目標帳號是否在他的管理範圍內。

把擁有者寫進查詢

針對特定資料的請求，讓查詢同時比對編號與擁有者，擁有者取自 Session：

order = db.query(
    "SELECT * FROM orders WHERE id = ? AND owner_id = ?",
    order_id, user.id)        # user.id 來自 Session，不來自請求
if order is None:
    return not_found()

不是 wiener 的訂單，查詢就查不到，後面的程式根本拿不到別人的資料。查不到時回 404，對方也無法從回應分辨「訂單不存在」和「訂單存在但不是你的」。「我的帳號」「我的訂單列表」這類只看自己資料的功能，乾脆不從請求讀使用者識別值，直接用 Session 查出的身分。

單一擁有者只是最簡單的規則。共享文件、團隊帳號、客服人員代查訂單這類情況，需要明確寫出「誰和這筆資料是什麼關係、因此能做什麼」，同樣採預設拒絕。

只接受允許的欄位

更新資料時，程式列出這個功能允許修改的欄位（例如只有 email），其他欄位一律忽略。角色只能經由專門的、有權限檢查的管理功能變更。

把規則寫成測試

上一小節的比對表格可以直接變成自動化測試：每個功能、每種執行者（未登入、擁有者、同角色的其他使用者、管理員）各一個案例，寫明應有的結果。每次修改程式都跑一遍，新增的功能沒有對應的規則與測試，就不該上線。

難猜的識別值、隱藏的連結仍然可以保留，它們讓資訊少外流一點，但都不能取代上面的檢查。OWASP 的 Authorization Cheat Sheet 整理了這些原則。

4.2.11 小結

  • 授權判斷需要執行者、目標、動作三項輸入；執行者只能取自伺服器用 Session 查到的身分，目標與動作來自請求，可以被改寫。
  • 水平越權跨到同層級的其他使用者，垂直越權跨到更高的角色；讀到管理員的憑證時，兩者會串在一起。
  • IDOR 的識別值可以是流水號、名稱、檔名或 UUID；難猜不能代替擁有者比對，寫入與刪除同樣要檢查。
  • 隱藏的網址、前端檢查、使用者保管的角色值、只檢查第一步、依 Referer 或方法判斷，都依賴使用者可控制的東西。
  • 修補：每筆請求在伺服器端、以預設拒絕集中檢查；查詢帶上擁有者條件；更新只收允許的欄位；用每種執行者的測試把規則固定下來。

PortSwigger Academy 的 Access control 主題有對應的 Lab，只在 Lab 或其他獲明確授權的系統上測試：

  • Unprotected admin functionality：找出沒有連結也沒有檢查的管理頁。
  • User role controlled by request parameter：辨認角色被放在使用者手上的哪個位置。
  • User ID controlled by request parameter with data leakage in redirect：在導向回應的本體裡找出已送出的資料。
  • Insecure direct object references：以檔名當識別值的 IDOR。
  • Multi-step process with no access control on one step：用兩個帳號比對多步驟流程的每一步。
  • Referer-based access control：只依 Referer 放行的子功能。

這一節的伺服器都假設：帶著 wiener 的 Cookie 送來的請求，就是 wiener 想做的事。1.2 提過，瀏覽器只要請求符合條件就會自動附上 Cookie，不管這筆請求是 wiener 自己按的，還是別的網站的頁面讓他的瀏覽器送出的。下一章的 CSRF, CORS, and Cross-Site Trust 從這裡出發，看執行者與權限都檢查無誤時，伺服器還要怎麼確認操作出於使用者本人的意思，以及瀏覽器在什麼條件下會在其他網站發起的請求中帶上登入狀態、讓其他網站讀到回應。
