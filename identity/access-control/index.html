3.2.1 什麼是存取控制

存取控制（access control）接在身分驗證與 session 後面：前者確認請求來自哪個帳號，後者讓之後每個請求都認得是同一個人，存取控制則對每個請求判斷一次，這個人能不能對這項資源做這件事。身分驗證與 session 都正確，但網站沒有判斷這個人能不能做這件事，alice 仍能做到她不該做的事。

存取控制可分為三類：

  • 垂直（vertical）：依使用者類型限制功能。一般會員不能進管理頁，只有管理員能刪除使用者。
  • 水平（horizontal）：限制使用者只能碰自己的那一部分資源。alice 只能看自己的帳號頁與訂單，看不到 bob 的。
  • 依狀態或流程（context-dependent）：依應用程式目前的狀態，或使用者走到流程的哪一步來限制。訂單付款之後，就不能再改票數。

下圖把 alice、bob、admin 和三種資源連起來。每個人存取自己的資源是正常連線；alice 越過角色的界線去碰管理頁，是垂直越權（vertical privilege escalation）；越過資料的界線去碰 bob 的帳號頁，是水平越權（horizontal privilege escalation）。

登入只發生一次，授權檢查卻發生在每個請求。下圖標出檢查擋在請求與資源之間的位置，三類存取控制各有自己的一道：

這三道檢查都要網站自己去做。規則得落在每個頁面、每個 API（供程式呼叫的介面）與每個步驟上，漏掉任何一處，那一處就能被繞過。存取控制設錯或漏掉，稱為 broken access control。OWASP（Open Worldwide Application Security Project，整理常見 Web 風險清單的開放社群）的 Top 10（2021）把 Broken Access Control 列在第一項。

上圖的三道檢查不通過時，伺服器回的狀態碼通常是 403。401 與 403 容易記混：

  • 401 Unauthorized：請求沒帶或帶錯身分憑證，伺服器不知道是誰。HTTP 規格（RFC 9110）要求這種回應附上 WWW-Authenticate header，告訴用戶端該用哪種方式驗證，HTTP Basic 認證那一節有完整的 401 回應。名稱雖然是 Unauthorized，意思是還沒通過身分驗證。
  • 403 Forbidden：伺服器已經知道是誰，但這個帳號沒有權限。存取控制擋下請求，回的是這一種。

實際的網站不一定照規格：有些網站擋下請求時回 404，讓人看不出資源是否存在，有些轉址到登入頁。

設計規則時有兩個原則：

  • 職責分離（separation of duties）：敏感操作不由單一角色獨攬。例如退款要由客服提出、管理員核准，兩個角色都同意才會執行。
  • 最小權限原則（least privilege）：只給完成工作所需的權限。一般會員只碰自己的訂單，客服只看訂單狀態，不需要管理頁。

這些規則怎麼定，是設計決定：哪個角色能做什麼、哪些資料算誰的，都得由人來決定。自動化掃描工具能看出某個頁面沒有檢查，卻看不出這個頁面該不該有人擋，因為它不知道網站打算讓誰使用。要判斷什麼算越權，得先知道網站原本的權限設計，例如一般會員預期不能進管理頁。

3.2.2 權限規則的存放與判斷

「誰能對什麼做什麼」的規則，可以由作業系統、資料庫或網站程式執行，常見的做法歸納成幾種安全模型（security model）。這些模型說明網站的權限規則怎麼設計，也用來對照前面的垂直與水平越權各靠哪一種檢查擋下。區分模型有兩個角度：規則存放在哪裡、怎麼查；權限怎麼分配，也就是誰能授權、權限掛在誰身上。

規則的存放方式，常見的是程式內的權限矩陣（programmatic access control）：把一張記錄權限的表存在資料庫，內容是使用者、群組或角色對各動作的許可，程式處理每個請求時去查。售票平台把兩個角色能做的動作列成下表，程式每次都查這張表。alice、bob 屬於會員，admin 帳號屬於管理員：

表 3.2.2-1 售票平台的權限矩陣
動作會員管理員
看自己的訂單✓ 可✓ 可
看他人的訂單✗ 不可✓ 可
進管理頁✗ 不可✓ 可

權限的分配有三種模型：

  • DAC（discretionary access control，自主存取控制）：權限依使用者或群組授予，資源的擁有者可以自行把權限授予別人。雲端文件的共用設定就是這樣：文件的擁有者想分享給誰就分享給誰，系統照擁有者的設定放行。
  • MAC（mandatory access control，強制存取控制）：由一個中央管理者統一規定，資源的擁有者和使用者都不能自行授權或修改。軍方的機密文件是典型例子：每個人有許可等級，每份資料有機密標籤，由系統比對兩者，文件的作者也不能把它交給許可等級不夠的人。
  • RBAC（role-based access control，角色型存取控制）：權限授予角色，由管理者把使用者指派到一個或多個角色，使用者就有該角色的權限。售票平台的某位會員要改當活動主辦方，只要換他的角色；要新增客服這類身分，就多開一個角色，都不必逐項改權限。

規則的存放方式與權限的分配模型彼此獨立，所以可以並用。售票平台的規則存放在程式內的權限矩陣，矩陣以角色為欄位，代表權限掛在角色上，這就是 RBAC：會員與管理員是兩個角色，每個使用者歸屬其中一個。RBAC 的角色數量要適中：角色太少，分不出不同的權限；角色太多，規則又難以管理。

垂直越權擋的是角色：一般會員不能進管理頁，由 RBAC 的角色檢查負責。

水平越權只靠角色擋不住：alice 和 bob 都是會員，角色檢查對兩人的請求都放行，所以還要檢查這筆資料屬於誰。這個擁有者檢查不是 DAC：alice 不能把自己的訂單授權給 bob 看。它和 MAC 一樣由網站統一規定、擁有者不能自行授權，但它不比對許可等級與標籤，而是比對資料的擁有者是不是登入的人，所以也不是典型的 MAC。

不論用哪個模型，判斷都得在伺服器端做，依據是伺服器自己記的資料：用 session 認出使用者，再查出這個使用者的角色。請求進來後，網站依下圖的順序判斷：

上圖中，請求自己帶的角色旗標與角色欄位都在使用者手上，改成別的值就是另一個角色。這些值由使用者決定，不能拿來當權限依據；依據是伺服器端存的身分：session 對應到哪個使用者，資料庫裡這個使用者是什麼角色。

3.2.3 未受保護的管理功能

垂直越權最直接的一種：管理功能沒有任何檢查（unprotected functionality）。管理頁有網址，網站卻沒有在這個網址上確認來訪者是不是管理員，知道網址的人都進得去。

管理頁的網址可能從 robots.txt、網站載入的 JavaScript 洩漏，也可能被一份常見管理頁網址的清單猜中：清單裡的某個網址有回應，就表示該網址存在。

第一個例子，網址就列在 robots.txt。資訊揭露一節看過 tickets.example.com 的 robots.txt 把管理頁（網址 /admin-panel）列為不讓搜尋引擎收錄的路徑。alice 是一般會員，她直接把這個網址輸入瀏覽器。下圖比較兩種結果，差別只在伺服器有沒有做這道檢查：

沒有檢查時，alice 打開 /admin-panel 看到的畫面：使用者清單，每個會員旁邊都有刪除按鈕。

第二個例子，路徑不在 robots.txt：管理頁的網址是一串難猜的字（/admin-x7k2q9），看起來猜不到。但網站載入的 JavaScript 檔（/static/app.js）在程式碼裡寫了這個網址，瀏覽器載入這個檔案時就拿到了：

瀏覽器端的程式碼人人讀得到：網址沒有連結出來，仍然可以存取；網址既然寫在瀏覽器載入的 JavaScript 檔裡，任何人用 DevTools 的 Sources 分頁，在檔案裡搜尋 admin 之類的字就找得到。難猜的網址只是 security by obscurity，安全建立在沒人知道這件事上，不是存取控制，被讀出來之後就沒有任何東西擋著。

PortSwigger Academy 的對應練習（主題頁 Access control vulnerabilities and privilege escalation）：

  • Unprotected admin functionality：管理頁的位置寫在 robots.txt，沒有任何檢查，對應上面 robots.txt 列出管理頁網址的例子。Lab 的 carlos 相當於正文的 bob，要用管理頁上的刪除使用者功能刪掉他。
  • Unprotected admin functionality with unpredictable URL：管理頁的網址難猜，卻出現在首頁的 JavaScript 裡，對應上面網址只出現在前端 JavaScript 的例子。要觀察網址在哪段程式碼出現。

3.2.4 由使用者控制的角色

網站得記得「這個人是不是管理員」。有些網站把答案放在請求裡，讓瀏覽器每次帶回來：Cookie、query string 裡的 ?admin=true 之類的參數，或隱藏的表單欄位（網頁表單上有、畫面不顯示的欄位，送出時值照樣隨請求送出）。這種做法稱為 parameter-based access control。放在請求裡的值，使用者自己改了，就能提升自己的權限。

先看 Cookie。tickets.example.com 的帳號頁依 Cookie 裡的 admin 旗標決定要不要多顯示管理功能的入口。Cookie 存在瀏覽器裡，使用者自己就改得到。下面兩個請求的 session 相同，只差在 admin 的值，回應就不一樣：

alice 的原始 Cookie
Request
GET /account HTTP/1.1Host: tickets.example.comCookie: session=a1b2…; admin=false
Response
HTTP/1.1 200 OKContent-Type: text/html[alice 的帳號頁]
admin 旗標被改成 true
Request
GET /account HTTP/1.1Host: tickets.example.comCookie: session=a1b2…; admin=true
Response
HTTP/1.1 200 OKContent-Type: text/html[多出管理功能入口的帳號頁]

session 與其他欄位都沒動，回應就多出管理功能。網站沒有查「alice 是不是管理員」，它只讀了請求自己帶的值。下面是這兩個回應畫出來的帳號頁：

第二種是個人資料更新。帳號頁的表單上沒有角色欄位，送出時另外帶著記錄帳號編號的隱藏欄位 id；伺服器則把請求裡所有欄位都收下，不論欄位是否出現在表單上。如果你在請求本體多送一個 roleid，伺服器也把它寫進資料庫，角色就被改了：

一般的個人資料更新
Request
POST /account/update HTTP/1.1Host: tickets.example.comCookie: session=a1b2…Content-Type: application/x-www-form-urlencodedemail=alice%40tickets.example.com&id=7
Response
HTTP/1.1 200 OKContent-Type: text/html[個人資料已更新，頁面列出帳號欄位：id=7、email=alice@tickets.example.com、roleid=member]
多送一個 roleid 欄位
Request
POST /account/update HTTP/1.1Host: tickets.example.comCookie: session=a1b2…Content-Type: application/x-www-form-urlencodedemail=alice%40tickets.example.com&id=7&roleid=[管理員角色]
Response
HTTP/1.1 200 OKContent-Type: text/html[頁面列出的帳號欄位中，roleid 變成管理員角色]

表單上沒有這個欄位，但使用者能從第一個請求的回應得知它的名字：更新成功後，回應列出帳號的所有欄位，因此 roleid 這個欄位名稱對使用者是可見的。伺服器收下請求中的所有欄位，多帶 roleid 就會被寫入，這就是第二個請求。隱藏的表單欄位是同一類：欄位只是不顯示在畫面上，值照樣隨請求送出，使用者一樣能改。

這兩種情況的原因相同：網站把角色放在請求裡，沒有改查伺服器端記的角色（見權限規則的存放與判斷）。

PortSwigger Academy 的對應練習（主題頁 Access control vulnerabilities and privilege escalation）：

  • User role controlled by request parameter：角色旗標放在 Cookie，對應 admin=false 改成 admin=true 的例子。要觀察改值之後，頁面多了什麼功能。
  • User role can be modified in user profile：個人資料更新的請求可以多帶一個角色欄位，對應 roleid 的例子；Lab 的更新請求是 JSON，多送的欄位一樣是 roleid。要觀察更新請求的回應裡，有沒有出現角色欄位。

3.2.5 以編號指向的資料

帳號頁用網址上的編號指向資料庫的一筆記錄：alice 的帳號頁網址帶著 id=7。編號是整數，一個帳號一個編號，換成別的數字（例如 3），該編號存在時就指向另一個帳號。伺服器如果只照編號查、不確認這筆記錄屬於誰，就把 bob 的資料回給 alice：

Request
GET /account?id=3 HTTP/1.1Host: tickets.example.comCookie: session=a1b2…
Response
HTTP/1.1 200 OKContent-Type: text/html[bob 的帳號頁：名稱、email、角色]

這是水平越權，也是 IDOR（insecure direct object reference，不安全的直接物件參照）的典型：使用者送來的編號，直接被拿去取得資料庫裡的一筆記錄，名稱裡的「物件」就是這筆記錄。這類問題因 OWASP 2007 年的 Top Ten 而廣為人知。

資訊揭露一節也看過以使用者名稱查詢帳號頁時，回傳他人的 email、電話與 API key。那一節看的是頁面洩漏了哪些欄位；這裡看的是授權：網站有沒有確認發出請求的人能看這筆記錄。

更新請求也有同樣的問題。帳號頁的更新請求用 id 指定要改哪個帳號。這個 id 與 ?id=7 一樣由使用者送來，伺服器沒核對所有權，IDOR 在寫入上同樣成立：

alice 用 id=3 改 bob 的資料
Request
POST /account/update HTTP/1.1Host: tickets.example.comCookie: session=a1b2…Content-Type: application/x-www-form-urlencodedemail=[新的 email]&id=3
Response
HTTP/1.1 200 OKContent-Type: text/html[bob 的個人資料已更新]

IDOR 多數是水平越權，也可能造成垂直越權：如果換成較高權限的使用者編號，例如管理員的 id=1，記錄裡若含登入用的資料，就能以管理員身分登入，見下一小節。

PortSwigger Academy 的對應練習（主題頁 Access control vulnerabilities and privilege escalation）：

  • User ID controlled by request parameter：帳號頁以網址上的 id 指定使用者，對應上面把網址上的編號 7 改成 3 的例子。要在別人的帳號頁找出什麼資料可以讀。

3.2.6 隱藏與存取控制的區別

有些網站的維護者以為把資料藏起來就夠了，卻沒有確保沒有權限的請求拿不到資料：把數字編號換成 GUID（一長串隨機的識別碼）讓人猜不到、把沒有權限的請求轉走、把密碼在畫面上遮成圓點。這些做法只是讓資料不容易被看到，並不會擋下回應裡的資料。三種做法各用一個頁面示範資料怎麼漏出：

  • GUID 出現在別處：活動討論區的每則留言，都有指向留言者帳號頁的連結。連結帶著留言者的 GUID，所以 bob 留言的連結公開了 bob 的 GUID，把它換進帳號頁網址就能查到 bob 的資料。GUID 只讓編號難猜，編號從別的頁面拿得到，就沒有保護作用。
  • 被擋下的回應仍帶資料：網站有檢查，偵測到你不能看這個帳號頁，回 302（要瀏覽器改去另一個網址的回應）把瀏覽器導向登入頁。瀏覽器收到 302 會直接跳轉，不顯示 body（回應裡帶的頁面內容）；但 body 裡仍夾帶該帳號的資料。body 仍在原始 HTTP 回應裡，Burp 的 HTTP history 這類記錄原始往來的工具看得到；瀏覽器的 DevTools 通常不顯示轉址回應的 body。但 302 只決定瀏覽器接下來顯示什麼，回應裡的資料沒有被擋下。
  • 畫面上只顯示圓點：帳號頁預填一個密碼欄位，畫面上是一排圓點，原始碼的 value 卻是明文，所以檢視原始碼或回應內容就看得到。圓點只遮住畫面，回應裡的密碼仍是明文。
帳號頁回應裡的密碼欄位
Request
GET /account?id=[GUID] HTTP/1.1Host: tickets.example.comCookie: session=a1b2…
Response
HTTP/1.1 200 OKContent-Type: text/html[…]<input type="password" name="password" value="[明文密碼]">[…]

三種做法共同的問題，是網站沒有真正擋下沒有權限的請求。圓點遮蔽和編號的形式無關：編號是數字或 GUID，回應裡的密碼都是明文。

資料洩漏也可能造成垂直越權：透過 IDOR 讀到管理員的帳號頁與密碼，就能用管理員的身分登入，使用管理員才有的功能。下圖用三個請求走一遍：

PortSwigger Academy 的對應練習（主題頁 Access control vulnerabilities and privilege escalation）：

  • User ID controlled by request parameter, with unpredictable user IDs：使用者以 GUID 識別，對應活動討論區留言者連結的例子。要找出 GUID 在別的頁面出現的位置。
  • User ID controlled by request parameter with data leakage in redirect：請求被導向別處，被導向的回應 body 卻帶著資料，對應 302 回應的例子。要觀察原始回應，瀏覽器畫面看不到這些。
  • User ID controlled by request parameter with password disclosure：帳號頁預填遮罩的密碼欄位，對應原始碼裡 value 的例子。要觀察密碼欄位的 value；拿到管理員密碼登入之後，就能進管理頁，是垂直越權；Academy 主題頁把這種情況稱為 horizontal to vertical privilege escalation。

3.2.7 以檔名存取的檔案

IDOR 的另一種，指向靜態檔案（內容固定、由伺服器直接送出的檔案）。售票平台把客服對話紀錄存成遞增檔名的文字檔，放在 /static/chat/ 底下，帳號頁的「客服對話紀錄」連結指向登入者自己的那一份：/static/chat/123.txt。檔名是遞增的編號，換成 122.txt 就取得別人的紀錄，內容可能含帳號與密碼：

自己的客服紀錄
Request
GET /static/chat/123.txt HTTP/1.1Host: tickets.example.comCookie: session=a1b2…
Response
HTTP/1.1 200 OKContent-Type: text/plain[alice 的客服對話紀錄]
檔名改成前一號
Request
GET /static/chat/122.txt HTTP/1.1Host: tickets.example.comCookie: session=a1b2…
Response
HTTP/1.1 200 OKContent-Type: text/plain[別人的客服對話紀錄，含帳號與密碼]

PortSwigger Academy 的對應練習（主題頁 Access control vulnerabilities and privilege escalation）：

  • Insecure direct object references：客服對話紀錄存成遞增編號的文字檔，對應上面把客服紀錄檔名 123.txt 改成 122.txt 的例子。要觀察檔名的規律，以及紀錄裡有什麼可用的資料。

3.2.8 proxy 與網站程式的檢查

有些網站把存取控制放在 reverse proxy（接在網站程式前面，先收請求、再轉給網站程式的伺服器，以下簡稱 proxy）：proxy 依網址或 method 擋掉某些請求，例如內部管理頁（網址 /console）一律不讓外部連。網站程式自己沒有檢查，它假設到得了這裡的請求都是 proxy 放行過的。兩層對同一個請求的判斷不一樣時，就會出問題。兩層的判斷可能在三個地方不一樣：header、網址與 method。header 與 method 屬平台設定問題（platform misconfiguration），網站程式接受了 proxy 沒預期的 header 或 method；網址屬網址比對差異（URL-matching discrepancies），兩層對同一個網址的解讀不同。

第一種差異來自 header。有些網站程式用的框架（別人寫好、可重複使用的網站程式骨架，見身分驗證）接受 X-Original-URL（或 X-Rewrite-URL）這類 header，用它指定的路徑取代請求行（GET / HTTP/1.1 那一行）裡的網址。X-Original-URL 來自 IIS（Microsoft 的網站伺服器）的網址改寫功能：改寫網址時，把改寫前的原始網址記在這個 header，讓後面的程式知道使用者原本要的網址；有些框架（例如 2018 年修正前的 Symfony）因此照它的路徑處理。Original 指的是改寫前的網址，不是請求從哪裡來。框架分不出這個 header 是改寫功能加的，還是使用者自己帶的，所以使用者自己填也照收。proxy 看請求行：/ 沒有規則擋；網站程式卻改用 header 的 /console：

直接要 /console
Request
GET /console HTTP/1.1Host: tickets.example.comCookie: session=a1b2…
Response
HTTP/1.1 403 Forbidden
請求行是 /，header 指定 /console
Request
GET / HTTP/1.1Host: tickets.example.comCookie: session=a1b2…X-Original-URL: /console
Response
HTTP/1.1 200 OKContent-Type: text/html[管理頁]

第二種差異來自網址比對。規則寫的是 /console，proxy 逐字比對；網站程式卻對大小寫、結尾多一個斜線（/console/）或副檔名後綴（/console.anything）寬鬆，把不同寫法當成同一個網址。proxy 與網站程式對同一個網址的解讀不同，proxy 就擋不到：

第三種差異來自 method。規則寫成「某角色不得對某路徑用某 method」，例如不准 member 用 POST 呼叫升級使用者的功能（/console/promote）。規則只擋 POST，換成 GET 送同一個路徑，網站程式卻照樣處理：

以 POST 升級使用者
Request
POST /console/promote HTTP/1.1Host: tickets.example.comCookie: session=a1b2…Content-Type: application/x-www-form-urlencodedusername=alice&action=upgrade
Response
HTTP/1.1 403 Forbidden
改用 GET 送同一個路徑
Request
GET /console/promote?username=alice&action=upgrade HTTP/1.1Host: tickets.example.comCookie: session=a1b2…
Response
HTTP/1.1 200 OKContent-Type: text/html[alice 已升級為管理員]

proxy 與網站程式對同一個請求的判斷不一致時，只差一處（header、網址寫法或 method）的兩個請求，proxy 會擋下一個、放行另一個，到了網站程式卻是同一個功能：被擋下的回應是 403，放行的回應是 200。換 method 這一種要成立，得先知道升級功能的請求格式（路徑與參數）。這些格式可能從網站的 JavaScript 得知，或在持有管理員帳號時，從管理員送出的請求看到。而網站程式不檢查角色，所以 alice 用自己的 session 送出同樣內容的 GET 請求，也會被執行。

PortSwigger Academy 的對應練習（主題頁 Access control vulnerabilities and privilege escalation）：

  • URL-based access control can be circumvented：proxy 擋掉管理頁，網站程式卻接受 X-Original-URL，對應請求行與 header 路徑不同的例子。要觀察被擋與放行的兩個回應差在哪裡。用 X-Original-URL 改寫時，header 只放路徑，要帶的參數仍放在請求行的 query string。
  • Method-based access control can be circumvented：存取控制依 method 判斷，對應 POST 被擋、換 method 通過的例子。要觀察同一個路徑在不同 method 下的回應差別。

3.2.9 多步驟流程、來源與地點檢查

依狀態或流程的存取控制，例子是多步驟流程：管理員升級使用者要走三步：載入表單、送出要升級的使用者、確認。網站在前兩步檢查是不是管理員，確認那一步沒檢查。前兩步不必走，確認的請求可以直接送出。下圖標出三步的請求，與 alice 跳過前兩步的做法：

第三步請求的路徑與欄位並不是秘密：可能從網站的 JavaScript 得知，或在持有管理員帳號時，從管理員走完三步送出的請求看到。網站對第三步只看請求內容、不查角色，所以 alice 帶著自己的 session 送出同樣的請求，也會被執行。請求帶著要升級的使用者與確認的旗標：

直接送出確認那一步
Request
POST /ops/upgrade/confirm HTTP/1.1Host: tickets.example.comCookie: session=a1b2…Content-Type: application/x-www-form-urlencodedusername=alice&confirmed=true
Response
HTTP/1.1 200 OKContent-Type: text/html[alice 已升級為管理員]

每一步都是獨立的請求。伺服器若沒有記錄你走到哪一步，每個請求就只能各自判斷，確認那一步沒檢查，誰都送得出去。業務邏輯上的流程順序問題留到 業務邏輯一節。

另一種是 Referer-based：伺服器看 Referer header 判斷請求從哪裡來。Referer 是瀏覽器自動帶的 header，記錄你是從哪個頁面送出這個請求。匯出資料的管理功能只檢查 Referer 是不是來自管理頁。但這個 header 由發出請求的人決定，所以自己填一個管理頁的網址就通過了：

沒有帶管理頁的 Referer
Request
POST /ops/export HTTP/1.1Host: tickets.example.comCookie: session=a1b2…
Response
HTTP/1.1 403 Forbidden
Referer 被改成管理頁網址
Request
POST /ops/export HTTP/1.1Host: tickets.example.comCookie: session=a1b2…Referer: https://tickets.example.com/ops
Response
HTTP/1.1 200 OKContent-Type: text/csv[匯出的資料]

再一種是 location-based：依地理位置限制，例如只開放某些地區。判斷依據是請求的來源位置，而使用者能改變它：經過代理伺服器或 VPN（virtual private network，虛擬私人網路；都是使用者自己用來轉送連線、改變來源 IP 的服務），伺服器看到的來源就是出口的位置；網站若依用戶端回報的定位判斷，使用者可以自行回報別的位置。

PortSwigger Academy 的對應練習（主題頁 Access control vulnerabilities and privilege escalation）：

  • Multi-step process with no access control on one step：多步驟的升級流程，只有部分步驟檢查，對應上面三步升級流程的例子。要觀察哪一個請求沒有權限檢查。這個 Lab 需要管理員帳號送出的確認請求作為樣本，換成一般帳號的 session 重送後觀察回應。
  • Referer-based access control：網站以 Referer 判斷請求來自管理頁，對應上面匯出資料功能的例子。要觀察移除或改寫 Referer 時回應的變化。這個 Lab 需要管理員帳號送出、帶管理頁 Referer 的請求作為樣本，換成一般帳號的 session 重送後觀察回應。

本章的身分驗證與存取控制都靠 session 識別使用者。下一章談別的網站怎麼借用這個 session，第一節 Cross-Site Request Forgery (CSRF) 看別的網站怎麼讓你的瀏覽器在不知情下，帶著 session 送出請求。
