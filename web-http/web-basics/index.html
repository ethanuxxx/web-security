本節模型：shop.example.com 的商品頁

上圖從左到右是一次正常的瀏覽：你在商品列表點一個商品，瀏覽器把商品編號放進請求的網址，送給 shop.example.com 的伺服器；伺服器依編號向資料庫取出商品資料，組成商品頁送回來。畫面出現之前，瀏覽器和遠端的電腦之間來回交換了好幾次訊息，每一次都是一段文字送出去、一段文字送回來。Web 安全的問題大多出在這些文字裡，尤其是虛線框標出的、由你控制的部分。

1.1.1 瀏覽器、伺服器與一次往返

Web 是一套讓人透過網址取得資源的系統：資源可以是網頁、圖片、影片，也可以是某個功能的結果。其中有兩個角色：

  • 瀏覽器（browser，更精確地說是 client，客戶端）是提出要求的一方，例如 Chrome、Firefox、Safari。
  • 伺服器（server）是另一台電腦上，負責接收要求並回傳內容的程式。它背後的網站程式（稱為 application，應用程式）可能會去讀檔案、查詢資料庫，或呼叫別的服務，再決定回傳什麼。

兩者之間講的「語言」叫 HTTP（HyperText Transfer Protocol，超文字傳輸協定）。規則是瀏覽器送出一個請求（request），伺服器回一個回應（response）。一來一往，稱為一次往返。

一個畫面通常要經過很多次往返。瀏覽器先要「主文件」，主文件是一段 HTML（HyperText Markup Language）文字，描述頁面的內容與結構。瀏覽器讀懂 HTML 之後，發現裡面提到圖片、樣式表（CSS，描述外觀）、程式（JavaScript，讓頁面能動態改變），才針對每一項再發出新的請求。

一頁有十張圖，請求數也未必是十一個：有些資源已經在瀏覽器的快取（cache，暫存的副本）裡，不必重新要；頁面也還會引用樣式表、程式等其他資源。

伺服器看不到你的螢幕，只收到瀏覽器送出的那串文字。這串文字由瀏覽器替你組好，你也可以用工具看見並改動它。

1.1.2 拆開一個 URL

瀏覽器要去哪裡拿資源，由 URL（Uniform Resource Locator，統一資源定位器，即平常說的網址）決定。商品頁的網址可以拆成這幾段：

https://shop.example.com/product?productId=1
表 1.1.2-1
部分在這個例子中的意義
httpsscheme（協定）：用 HTTP 溝通，並且加上加密（HTTPS 的 S）。
shop.example.comhost（主機名稱）：要連到哪一台伺服器。
/productpath（路徑）：要求伺服器的哪一個功能或資源。
?分隔符號，後面是查詢參數。
productId=1查詢參數（query parameter）：名稱是 productId，值是 1。多個參數用 & 相接。

URL 還可能有埠號（port）、# 後面的片段（fragment）等部分。

參數的意義由網站自己決定。伺服器看到 productId=1，由它的程式決定拿這個值做什麼；在這個網站裡，是挑選要顯示哪個商品。別的網站未必用同樣的名稱或格式。

路徑也不必對應伺服器上的檔案位置。/product 只是告訴網站「我要商品這個功能」，磁碟上不一定有叫 product 的資料夾，網站可以用任何方式決定怎麼回應。第 2 章講檔案讀取時會再用到這個區別。

只改參數的值

動手前先猜一猜：點開另一個商品時，網址會改變哪個部分。然後找一個有商品列表的購物網站，或你可以合法操作的練習環境（見小結裡的 Academy 練習），自己試試：

  1. 開啟兩個不同商品，各在一個分頁。
  2. 比較兩個網址的 host、path、參數名稱、參數值，找出哪些相同、哪些不同。
  3. 在其中一個分頁，只把參數的值換成另一個商品的編號，按 Enter，看看顯示的商品是否跟著變。

以這個網站為例，兩個網址只差在值：

表 1.1.2-2
網址顯示的商品
https://shop.example.com/product?productId=1帆布袋
https://shop.example.com/product?productId=2保溫杯

這樣做只是向伺服器要另一個商品的內容，伺服器上的商品資料沒有被改動。把一個正常的網址留著，後面看錯誤訊息時要拿它當對照。

1.1.3 request 與 response

網址只告訴瀏覽器去哪裡，實際送出去的是一段有固定格式的文字。商品頁那次往返簡化後如下，用 HTTP/1.1 的可讀形式寫出起始行與標頭。實際訊息還有更多欄位；現代瀏覽器也常改用 HTTP/2，它用二進位的訊息框架傳送，工具會把它轉成類似的可讀顯示。本體可以是文字，也可以是圖片之類的位元組。

# 瀏覽器送出的 request（簡化）
GET /product?productId=1 HTTP/1.1
Host: shop.example.com
# 伺服器回傳的 response（簡化）
HTTP/1.1 200 OK
Content-Type: text/html

<h1>帆布袋</h1>
  • GET 是 method（方法），表示「我想取得這個資源」。瀏覽器網址列輸入網址，通常就是送 GET 請求。方法還有其他種類，下一節介紹。
  • /product?productId=1 是路徑加查詢參數。Host 那一行說明要找哪台主機。
  • 回應的第一行有狀態碼（status code）：200 表示成功，404 表示找不到，500 表示伺服器處理時發生內部錯誤。狀態碼只反映這次請求的處理結果：200 不保證內容正確或安全，500 也不證明有可利用的漏洞。
  • Content-Type 是一個標頭（header），宣告回應內容的格式：HTML 常是 text/html，JPEG 圖片是 image/jpeg。瀏覽器依此決定怎麼處理內容。
  • 空白行之後是 body（主體），放內容本身。

Content-Type 只是伺服器的宣告，和 body 可能對不上：一個回應可以在標頭說自己是圖片，body 卻是一段文字。實際收到了什麼，要看 body。

1.1.4 在 Network 面板看實際的往返

現代瀏覽器內建開發者工具（DevTools），其中的 Network（網路）面板把每一次往返列成一列：同一列可以看到 request 的 URL 與 method，以及 response 的 status、Content-Type 與 body。在網頁上按右鍵選「檢查（Inspect）」就能開啟 DevTools。這裡用 Chrome 的英文介面名稱，其他瀏覽器的名稱相近，中文介面的譯名會有出入。

找出 HTML 與圖片各是哪一列

先猜猜打開一個商品頁會送出幾筆請求，然後：

  1. 開啟任一商品頁，開啟 DevTools，切到 Network。
  2. 確認正在記錄，清掉文字篩選，選 All，然後重新整理頁面（記錄是從開啟面板之後才開始，所以需要重新載入一次）。
  3. 找出 Type 為 document 的那一列（也可以點 Doc 篩選）。點開它，在 Headers 看 URL、method、status，在 Response 看 HTML 文字。
  4. 改選 Img 篩選，點一張商品圖片的那一列。看它的 URL 與 Content-Type；內容可在 Preview 直接看圖，不必讀它的位元組。
  5. 把這張圖片的網址複製到新分頁，看看它是否能單獨顯示。

做完後，你應該能指出哪一列取得了這一頁的 HTML、哪一列取得了圖片。兩列各有自己的網址、回應格式與內容，對應往返圖裡的兩次往返。

在這個網站，兩列大概是這樣：

表 1.1.4-1
資源Request URL 的路徑與參數Method回應格式
商品頁/product?productId=1GETtext/html
商品圖片/image?filename=42.jpgGETimage/jpeg

Network 只告訴你：瀏覽器向這個網址要東西，拿到了這份內容。圖片在伺服器上怎麼保存，從這裡看不出來，它可能是磁碟上的檔案，也可能來自資料庫或另一個儲存服務。

1.1.5 HTML、DOM 與畫面

主文件是 HTML 文字，用標籤（tag）標記內容的意義。例如商品頁主文件裡的這一小段：

<!-- 商品頁主文件的一小段 -->
<h1>帆布袋</h1>
<img src="/image?filename=42.jpg">
<p>NT$ 300</p>
  • <h1>帆布袋</h1>：<h1> 與 </h1> 是一對標籤，表示中間的「帆布袋」是第一層標題。
  • <img src="...">：img 標籤表示這裡要放一張圖；src 是它的屬性（attribute），值是圖片的網址。瀏覽器看到這行，才會去發第二次請求，對應往返圖中的第 ③ 步。
  • <p>NT$ 300</p>：一段文字。

瀏覽器讀完這段文字後，會在記憶體中建立一棵由節點（node）組成的樹，稱為 DOM（Document Object Model，文件物件模型）：標題是一個節點、圖片是一個節點、段落是一個節點。畫面就是依這棵樹畫出來的。DevTools 的 Elements 面板顯示的是這棵樹目前的樣子。

於是同一頁在你面前有三份東西：

  1. Response：伺服器送來的 HTML 文字。Network 保存的是收到當下的原文，之後不會再變。
  2. DOM：瀏覽器依 HTML 建出的樹，可以被程式或你手動修改。
  3. 畫面：依 DOM 畫出的結果。

在 Elements 改商品名稱

先猜一猜：在 Elements 改掉商品名稱，Network 裡那份 HTML 會不會跟著改，重新整理之後又會怎樣。

  1. 在商品名稱上按右鍵選「檢查」，Elements 會定位到對應的元素。
  2. 雙擊標籤之間的文字，改成「我改的名稱」，按 Enter。只改文字，不碰表單或按鈕。
  3. 看畫面是否改變；再到 Network 看剛才載入的主文件 Response，找原本的商品名稱。
  4. 重新整理頁面，看名稱是否恢復，以及 Network 是否多了一次新的往返。

一般的結果如上圖：畫面改了，原本那筆 Response 沒變，重新整理後名稱恢復。重新整理是向伺服器要一份新的 HTML，再用它重建 DOM；你改的只是自己瀏覽器裡的副本，沒有寫回伺服器。

上面說的是手動編輯純文字的情況。如果網站用 JavaScript 動態更新頁面，或把資料存在瀏覽器裡，結果會不一樣；DevTools 的 Local Overrides 之類的功能也會讓瀏覽器自己保存修改。結果和預期不同時，先確認你改的是哪一份東西。

1.1.6 錯誤訊息與資訊揭露

網站上幾乎每個功能都帶著使用者給的值，例如活動公告列表用 page 指定要看第幾頁。正常的頁碼得到公告列表，但網站遲早會收到預期外的值：該是數字的地方送來文字，或頁碼大得離譜。常見的失誤是出錯時把只有開發者需要的訊息，一起交給了任何來訪的人。

三組輸入

同一個網站的活動公告頁，伺服器端程式拿到 page 之後，先把它轉成整數，再計算要從第幾筆公告開始取。比較三組輸入：

表 1.1.6-1
輸入請求回應節錄
A（正常）GET /news?page=1<h1>活動公告（第 1 頁）</h1>
B（另一頁）GET /news?page=2<h1>活動公告（第 2 頁）</h1>
C（值的型別不符）GET /news?page=latestCannot parse page number: "latest"
at NewsListView.paginate (DemoFramework version 1.2.3)

A 與 B 是正常功能：值不同，內容不同。C 與 A、B 的差別只有 page 的值，路徑、方法都沒變，所以多出來的那段文字來自這個值引起的處理差異。

C 的回應裡有三樣東西：

  • Cannot parse page number: "latest"：說明哪裡出錯。這句對使用者也有一點幫助。
  • NewsListView.paginate：伺服器內部的程式名稱。使用者不需要，開發者除錯時才需要。
  • DemoFramework version 1.2.3：網站使用的框架（framework，網站程式所依賴的現成程式元件）名稱與版本（該元件的版本編號）。

資訊揭露

資訊揭露（information disclosure，也稱 information leakage）指網站在不該給的時候，把資訊交給了不該拿到的人。上面的例子是這樣發生的：

  1. 輸入的型別不符（該是整數，收到文字）；
  2. 處理過程發生例外；
  3. 錯誤處理沒有分辨「對外」與「對內」，把詳細診斷整段放進公開的回應；
  4. 任何人都能讀到內部名稱、框架與版本。

框架與版本告訴外人這個網站用了哪種元件。該版本若有公開已知的弱點，對方就知道從哪裡下手；內部路徑和程式名稱則透露程式的結構。這些資訊本身通常構不成入侵，但能縮小對方猜測的範圍。

有版本號，不代表有漏洞

這次觀察看得到的是：只改了 page 的值，回應就多出框架名稱與版本。由此可以合理推論，這個網站的錯誤處理把診斷資訊交給了一般使用者。版本號本身只是一個字串，它有沒有可利用的弱點、網站是否真的受影響，需要另外的證據。一個錯誤頁也只呈現一個入口的一條錯誤路徑，看不出整個後端。

修補與預防

  • 驗證輸入：伺服器應檢查 page 是否為合理範圍內的整數，不符就拒絕。
  • 對外回簡單的訊息，對內留詳細紀錄：對使用者顯示「找不到這一頁」之類的一般性訊息；詳細診斷寫進有存取控制的內部事件紀錄（log，記錄系統發生了什麼事的檔案或服務），由維運人員查看。圖中實線與虛線的差別就在這裡。
  • 正式環境關閉除錯模式：許多框架在開發時會自動顯示詳細錯誤，上線後應改成一般錯誤頁。

隱藏版本號修補不了框架本身的漏洞，只是不讓人輕易看到；把這個參數限制成數字，其他入口照樣可能洩漏資訊。資訊揭露常見於錯誤頁、HTML 裡留下的註解、備份檔、目錄列表等地方。第 2 章的 Path Traversal 會看到它與檔案讀取的關係，之後的章節也會再遇到。

1.1.7 常見誤解

表 1.1.7-1
你看到的東西表示什麼不一定的事
網址列瀏覽器將要請求的位置。伺服器會照預期處理你的輸入。網址的每個部分，使用者都能自己改。
Network 裡的 Response伺服器對這次請求實際回傳的文字或位元組。內容正確、安全；也看不出伺服器內部怎麼產生它。
狀態碼伺服器對這次處理結果的訊號。200 的內容是對的；500 代表有漏洞。
Elements 中的 DOM瀏覽器此刻記憶體中的結構。和伺服器送來的原始 HTML 相同。它可能已被頁面上的程式或你自己改過。
畫面上看不到的東西沒有畫出來。網站沒有送出。隱藏的內容仍可能在 Response 裡。

瀏覽器端的一切都在使用者手上。網站可以在畫面上隱藏按鈕、限制輸入框只能填數字，這些只方便一般使用者，擋不住有心的人：任何人都能直接改網址、改 DOM，或用工具送出自己寫的請求。所以檢查必須在伺服器端做，後面幾乎每一章都會用到這條原則。

1.1.8 小結

  • 一次往返是一個 request 加一個 response；打開一頁通常要好幾次往返，先拿 HTML，再拿圖片等資源。
  • URL 由 host、path、查詢參數等組成；參數的意義由網站決定，path 也不必對應磁碟上的檔案。
  • Response 是已收到的紀錄，DOM 是瀏覽器裡可改的副本，畫面依 DOM 畫出；改 DOM 動不到伺服器。
  • 錯誤頁把框架、版本等診斷交給使用者，就是資訊揭露；修補是驗證輸入、對外回一般訊息、細節寫進內部 log。
  • 瀏覽器端的一切都能被使用者改動，檢查要放在伺服器端。
