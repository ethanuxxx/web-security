本節模型：shop.example.com 的「我的帳號」頁

登入後按下「我的帳號」，瀏覽器送出的請求網址帶著 id=wiener，並自動附上 Cookie；伺服器依 Cookie 裡的識別字查出這個 Session（伺服器替這次登入保存的記錄）屬於 wiener，取回他的訂單，畫成帳號頁。

上一節 Seeing the Web Through the Browser 看的是網址與一次次的往返。網址只說明要看哪個帳號的頁面，並沒有證明你是誰，伺服器卻能顯示你的訂單，不會拿出別人的。它靠的是網址以外的東西：請求的其他欄位、瀏覽器自動帶上的 Cookie，以及伺服器怎麼把這些對應到你這個人。

1.2.1 HTTP 訊息的四個區塊

HTTP（HyperText Transfer Protocol）是瀏覽器與伺服器約定好的對話格式。一次對話由兩份訊息組成：瀏覽器送出請求（request），伺服器回傳回應（response）。兩份訊息的結構很像，都依序分成四個區塊：

  1. 起始行：請求寫的是「要做什麼、對哪個目標」；回應寫的是「結果如何」。
  2. 標頭（headers）：每行一組「名稱: 值」，是關於這次交換的附加資訊。
  3. 空行：在 HTTP/1.1 的可讀形式中，標頭到此結束。沒有這個空行，接收方不知道本體從哪裡開始。
  4. 本體（body）：要傳的內容本身，可以是空的。

把請求的起始行拆開，會得到三個部分：

方法（method）
例如 GET、POST。它表達「想對目標做什麼」：GET 慣例上用來取得內容，POST 慣例上用來送出資料讓伺服器處理（登入、下單）。方法只是請求者宣告的意圖，伺服器是否照慣例處理，要看它怎麼寫。
目標（path 與 query）
/my-account?id=wiener 中，? 之前的 /my-account 是路徑，? 之後的 id=wiener 是查詢字串（query string），由「名稱=值」組成，多組之間用 & 隔開。
版本
HTTP/1.1 是這份訊息使用的協定版本。這裡的例子都用最好讀的 HTTP/1.1 可讀形式；HTTP/2 改用二進位的訊息框架，工具通常會把它轉成類似的可讀顯示。本體可以是文字，也可以是圖片之類的位元組。

回應的起始行則有狀態碼（status code），三位數字加一段說明，告訴你伺服器怎麼處理這次請求。常見的有：

表 1.2.1-1
狀態碼意思要注意的地方
200 OK請求成功，本體是要求的內容「成功」是指伺服器照做了，不保證內容是你該看到的
302 Found內容在別處，請照 Location 標頭再發一次請求瀏覽器會自動跟隨，跟隨時另發一筆新請求
403 Forbidden伺服器明白你要什麼，但拒絕常用來表示「已知身分但沒有權限」
404 Not Found找不到目標有些網站為了不洩漏資源是否存在，也用它拒絕

完整的狀態碼清單可看 MDN 的 HTTP 狀態碼，訊息格式的正式說明可看 MDN 的 HTTP Messages。狀態碼只是第一個線索，要知道發生了什麼事，還得看標頭與本體。

1.2.2 登入，再看帳號頁

以購物網站 shop.example.com 為例，登入後看自己的帳號頁，會依序產生四份訊息。瀏覽器通常會附帶的其他標頭都省略，標成 （其他標頭略）。

瀏覽器送出登入表單

# 登入請求
POST /login HTTP/1.1
Host: shop.example.com
Content-Type: application/x-www-form-urlencoded
Content-Length: 30
（其他標頭略）

username=wiener&password=peter

空行之後的 username=wiener&password=peter 是本體，剛好 30 個字元（15 + 1 + 14），所以 Content-Length（本體的位元組數）是 30。Content-Type 告訴伺服器「本體要用表單格式（名稱=值，以 & 分隔）解讀」，伺服器才知道怎麼切出 username 與 password。

伺服器要瀏覽器記住一個值

# 登入回應
HTTP/1.1 302 Found
Location: /my-account
Set-Cookie: session=DEMO123; HttpOnly
（其他標頭略）

（本體為空）

Set-Cookie 是伺服器對瀏覽器說：「請把名稱 session、值 DEMO123 記起來。」302 加上 Location，則要瀏覽器接著去 /my-account。302 本身只是導向，不代表登入成功：沒登入的人也常被 302 導回登入頁，要看 Location 指向哪裡。

瀏覽器帶著 Cookie 再發一次請求

# 登入後的帳號頁請求
GET /my-account HTTP/1.1
Host: shop.example.com
Cookie: session=DEMO123
（其他標頭略）

這一筆是瀏覽器因為上一步的 302 而另外發出的新請求；你沒有按任何按鈕，它自己跟過去了。只要這個 Cookie 還有效，且請求符合它的適用範圍與傳送設定，瀏覽器送請求給 shop.example.com 時就會自動附上 Cookie: session=DEMO123。

伺服器靠 Cookie 認出你

# 帳號頁回應
HTTP/1.1 200 OK
Content-Type: text/html
（其他標頭略）

<html> … 你好，wiener … </html>

這個請求的網址裡沒有 wiener，伺服器是靠 Cookie 知道該顯示誰的帳號頁。

Cookie 也會在登入之前出現。許多網站在你第一次造訪時就建立 Session，登入時再把身分填進去，有些網站登入時也不換新的 Cookie。所以看到 Set-Cookie 不能當成登入成功的證據；要判斷是否已登入，得看整體行為。

1.2.3 資料放在請求的哪裡

使用者填的資料可以放在網址的查詢字串，也可以放在本體；上面的登入表單用的是本體。

表 1.2.3-1
位置常配合的方法特點
查詢字串GET在網址中，會出現在瀏覽器網址列、書籤與伺服器紀錄；適合單純取得內容
本體POST不在網址中；適合送出資料、讓伺服器改變狀態

這個差別出於慣例與方便，與安全性無關。POST 並不加密：本體裡的帳號密碼仍是明文，路上會不會被偷看，要看連線有沒有使用 HTTPS（HTTP 加上由 TLS 提供的傳輸加密；TLS 是保護網路傳輸的協定，讓路上的人看不到也改不了內容）。HTTPS 只保護傳輸過程。送進伺服器的內容是否可信、伺服器會不會檢查你的權限，它都管不到。

特殊字元必須編碼

表單格式用 = 與 & 當分隔符。資料本身若含有空白或 & 這類有特殊作用的字元，原樣放進去會改變分隔的意思，所以送出前要依所用的格式做編碼（URL encoding，也稱 percent-encoding），收到後再依同一種格式解碼。做法是把這些字元換成 % 加兩位十六進位數字（十六進位用 0–9 與 A–F 表示數值，例如 26 是十進位的 38）；空白在表單中常寫成 +，也可以是 %20。瀏覽器和工具通常會自動處理；在工具的參數編輯器裡改值時，也讓工具替你編碼。

這套規則屬於表單格式。網址本身的語法、瀏覽器把表單轉成文字的方式、應用程式解析參數的方式，各有各的規則；表單格式要求編碼的字元，網址語法不一定禁止。

表 1.2.3-2
使用者輸入的原文實際傳送的樣子伺服器解碼後
red shoesq=red+shoesq = red shoes
salt & pepperq=salt+%26+pepperq = salt & pepper

第二列的 %26 是 & 的編碼。因為編過碼，伺服器把它當成資料的一部分，不會當成下一組參數的開頭。同一個值傳送時和解碼後長得不一樣，之後講各種注入時，常要追問是誰在哪一步解碼；正常情況下只該解碼一次。

1.2.4 伺服器怎麼記得你

HTTP 本身是無狀態（stateless）的：每一份請求都獨立，伺服器不會自動記得「這是剛才那個人」。網站要記得登入狀態，得自己想辦法。最常見的設計裡有三樣東西：

  • Cookie 是瀏覽器保存的一組「名稱與值」。伺服器用 Set-Cookie 要求瀏覽器存起來，之後只要請求符合該 Cookie 的傳送條件（例如尚未過期，且目標位置與連線方式在它的適用範圍內），瀏覽器就用 Cookie 標頭自動帶回；同一個主機名稱並不是唯一的條件（詳見 MDN 的 Using HTTP cookies）。兩個標頭方向相反：Set-Cookie 在回應中，由伺服器發給瀏覽器；Cookie 在請求中，由瀏覽器交給伺服器。
  • Session（會話）是伺服器自己保存的狀態，例如「這個會話屬於 wiener、已登入」。它存在伺服器端（記憶體或資料庫），不在瀏覽器裡。
  • Session 識別字（session identifier，常縮寫 Session ID）是連接兩者的鑰匙：一串難以猜到的隨機值，瀏覽器放在 Cookie 裡，伺服器用它去查自己的 Session 表。

瀏覽器手上只有 DEMO123 這一串字，沒有你的姓名、權限或密碼，像一張寄物櫃的號碼牌。身分資料（誰、已登入、有什麼權限）都留在伺服器端。Cookie 的值使用者看得到，也改得動，所以伺服器每次都要自己查表，不能直接相信它。

誰拿著這個號碼牌，伺服器就把誰當成那個使用者，所以識別字必須難以猜測，也不能隨手貼到公開的地方；在 Burp 裡看到它時，要當成密碼對待。

Cookie 還有一些屬性，例如上面出現過的 HttpOnly（頁面中的 JavaScript 讀不到這個 Cookie）。這些屬性是 Cookie 的保護設定，也影響跨網站請求時 Cookie 會不會被帶上，談跨站信任的那一章會再討論。另有一種設計把身分直接放進 Cookie 的值、不查表，談 JWT 的那一節會看到；這裡用的是最常見的識別字加查表。

1.2.5 用 Burp Suite 觀察並重送請求

瀏覽器的開發者工具（DevTools）能看到請求，但想改動其中一個欄位再送一次，就需要另一種工具。Burp Suite 是資安測試常用的工具，它擺在瀏覽器與網站之間，記錄經過的請求與回應，並讓你修改後重送。免費的 Community Edition 就夠用：這裡用到的 Proxy、HTTP history、Repeater 都不需要付費版。

Burp 在這裡用來觀察：它把瀏覽器原本隱藏的細節（標頭、Cookie、完整本體）攤開，讓你比較改了什麼、結果有什麼不同。它不會替你找出漏洞；伺服器不允許的事，經過 Burp 也不會變成允許。

安裝與基本設定請看官方文件；選單位置與名稱會隨版本調整，畫面和這裡的說明對不上時，以官方文件為準：

  • 下載 Burp Suite Community Edition
  • 官方入門：攔截 HTTP 流量
  • 官方入門：重送 HTTP 請求

Proxy、HTTP history 與 Repeater

Proxy（代理）
Burp 的核心。瀏覽器的請求先到 Burp，由 Burp 轉給網站；回應也經過它再回到瀏覽器。Burp 內附一個已設定好的瀏覽器（Proxy → Intercept → Open Browser），用它瀏覽網站，流量就會自動經過 Burp，不必自己改瀏覽器的代理設定。
HTTP history（HTTP 歷史）
Proxy 分頁下的清單，依時間順序列出每一筆經過的請求。點選一列，下方會顯示完整的請求與回應，格式就是上面那四個區塊。
Repeater（重送器）
一個可以編輯請求並按 Send 重新送出的工作區。把歷史裡的某筆請求「送到 Repeater」，就得到一份可以反覆修改與重送的副本，每次送出都會看到伺服器的新回應。

Proxy 還有一個 Intercept（攔截）功能，開著時請求會停在 Burp 等你放行。平常瀏覽請把它關掉，否則頁面會一直轉圈，看起來像網站壞了。這裡的流程只用到歷史紀錄，不需要攔截。

在 Repeater 每次只改一個欄位

  1. 開啟 Burp，建立暫時專案（Community 版只提供暫時專案）。在 Proxy 分頁確認 Intercept 是關閉的。
  2. 在 Proxy → Intercept 分頁點 Open Browser，在這個瀏覽器中開啟要練習的網站並登入。以上面的購物網站為例：登入後點「我的帳號」。
  3. 回到 Burp 的 Proxy → HTTP history，找到路徑是 /my-account 的那一列並點選。下方可以看到完整的請求（其中有 Cookie 標頭）和回應中的帳號頁內容。若看到一個 302 的列，點它看 Location，再往後找它導向的那一列：那就是前面「瀏覽器帶著 Cookie 再發一次請求」的實際樣子。
  4. 在該列按右鍵，選 Send to Repeater，然後切到 Repeater 分頁。
  5. 先什麼都不改，按 Send。回應應該和瀏覽器看到的相同：同樣是你的帳號頁。這一步建立基準：原樣的請求可用，之後出現差異，就能確定是你的修改造成的。
  6. 每次只改一個欄位，例如把 id=wiener 的值換成別的字串，再按 Send。比較回應與基準的狀態碼、標頭、本體，看哪裡不一樣。
  7. 要回到基準時，把欄位改回原值再送一次。想同時保留兩份請求，就在 Repeater 的請求編輯區按右鍵，選 Send to Repeater，建立另一份副本；也可以回到 HTTP history，對同一筆請求再送一次到 Repeater。一份留作基準，一份用來實驗。

「相同的回應」不必每個位元組都一樣：時間戳記、頁面內的隨機碼等動態欄位每次都會變，要比的是身分與內容。另外，Repeater 的重送是 Burp 直接送給網站，瀏覽器並不知道，所以在 Repeater 做的修改不會改變瀏覽器目前的畫面。

HTTP history 與 Repeater 中的請求含有你真正登入的 Session Cookie。不要把整份請求、截圖或「Copy as cURL」的輸出貼到公開平台或聊天群；需要分享時，把 Cookie 的值遮掉，道理和分享密碼一樣。

1.2.6 身分與目標

這兩筆請求帶著同一個 Cookie，只有 id 不同：

# 兩筆請求使用同一個 Cookie
GET /my-account?id=wiener HTTP/1.1
Cookie: session=DEMO123

GET /my-account?id=[其他帳號的識別值] HTTP/1.1
Cookie: session=DEMO123

每一筆請求都同時帶著兩份資訊：

  • 目前身分：由 Cookie 決定。伺服器查 DEMO123，得知發出請求的人是 wiener。
  • 目標資源：由 id 參數決定。它指明「要看哪一個帳號的資料」。

這兩個欄位互相獨立。第二筆請求只改了目標，沒有改身分：發出請求的人仍是 wiener，他要求看另一個帳號的帳號頁，該帳號由 [其他帳號的識別值] 指定（方括號代表被換掉的那段輸入）。伺服器要判斷的是 wiener 有沒有權限看那個帳號的資料。

如果伺服器只確認「這個人已登入」（Cookie 有效），就直接用 id 查資料並回傳，等於把任何登入的人都當成能讀任何帳號的人。這類問題叫 IDOR（Insecure Direct Object Reference，不安全的直接物件參考）：請求裡直接使用物件的識別（這裡是帳號名稱），伺服器卻沒有檢查請求者對那個物件有沒有權限。

沒有身分和越權是兩種問題。設計正確的網站會這樣分別處理：

表 1.2.6-1
Cookie目標正確系統應有的反應
wiener 的 Sessionid=wiener顯示 wiener 的帳號頁
wiener 的 Sessionid=[其他帳號的識別值]拒絕（例如 403）：身分已知，但沒有權限
沒有 Cookieid=wiener導向登入頁：身分未知，連自己的資料都不能看

看到其他帳號的資料，是因為伺服器沒有檢查你對目標的權限，你並沒有變成另一個使用者。反過來，一次重送得到回應，也只說明那一筆請求得到了那樣的結果；要判斷是不是漏洞，得比較身分與目標，並知道系統預期怎麼拒絕。

只在畫面上隱藏連結也擋不住這種請求。網站可能只顯示通往自己帳號的連結，但請求可以由任何人自行構造或用工具修改。

修補要在伺服器端做：同時用目前身分與目標資源判斷這個請求是否允許。更穩妥的做法是不讓請求自己宣稱要看哪個使用者，直接用 Session 查出的身分決定顯示誰的資料。

上面區分的是認證（你是誰）與授權（你可以做什麼）。授權有許多形式，例如角色、物件所有權、多步驟流程，完整的分類與修補在 Access Control 一節；登入機制本身的弱點則在 Authentication 一節。

1.2.7 伺服器只依賴自己查到的身分

Cookie 的值和 id 參數都是使用者送來的，在 Repeater 裡隨手就能改。伺服器能依賴的只有一樣：它拿 Session 識別字到自己的 Session 表查出的身分。要不要讓這個身分讀取目標資源，也由伺服器用這個身分判斷。

1.2.8 小結

  • HTTP 訊息由起始行、標頭與本體組成，HTTP/1.1 以空行隔開標頭與本體；請求起始行有方法、目標與版本，回應起始行有狀態碼。
  • 資料放在查詢字串或本體，特殊字元要編碼。POST 沒有加密，HTTPS 只保護傳輸。
  • 伺服器用 Set-Cookie 發出 Session 識別字，瀏覽器之後用 Cookie 帶回，伺服器拿它查 Session 表。識別字要像密碼一樣保密。
  • 在 Burp 裡先原樣重送一次當基準，再每次只改一個欄位。
  • 請求同時帶著目前身分與目標資源；只檢查有沒有登入、不檢查對目標的權限，就會出現 IDOR。

PortSwigger Academy 的對應練習（主題頁 Authentication、Access control），只在 Lab 或其他獲明確授權的系統上測試：

  • User ID controlled by request parameter：在 Repeater 只改識別使用者的參數，比較回應裡的帳號，再用身分與目標的區分解釋結果。

IDOR 例子裡的 id 被伺服器拿來決定要查哪個帳號。下一節 Path Traversal 進入第 2 章「伺服器如何處理使用者輸入」，把目標參數換成檔名，看伺服器拿請求中的 filename 決定讀哪個檔案時，檔案系統怎麼解讀那段文字；HTTP history 與 Repeater 的流程在那裡直接用得上。
